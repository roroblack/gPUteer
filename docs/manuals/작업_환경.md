## 왜 여기로 옮겼나

2026-09-06 까지 이 내용은 `CLAUDE.md` 안에 48줄로 들어가 있었다. 그런데
그 파일은 스스로 이렇게 적어 뒀다.

> 이 문서는 매 세션 자동으로 읽힌다. 그래서 규칙이 아닌 것을 여기 두지
> 않는다.

"x600 에 RTX 4070 SUPER 가 있다" 는 **사실**이지 규칙이 아니다. 그리고
`docs/manuals/` 는 "환경 구축 절차" 를 담기로 해 놓고 **`.gitkeep` 만
있는 빈 폴더**였다 — `docs/README.md` 와 `RULE.md` 는 내용이 있는 것처럼
가리키고 있었다. 둘을 한 번에 정리했다.

★ **규칙에 해당하는 것은 `CLAUDE.md` 에 남겼다.** 특히 "x600 의 C: 에서는
  작업하지 않는다" 는 사용자 지시라 규칙이다.

## 쓸 수 있는 기계 (2026-09-07 실측)

| 이름 | OS | GPU | 쓰임 |
|---|---|---|---|
| (개발 기계) | Windows 11 | 없음 (Intel Iris Xe) | 기본 작업. **NVML 실패 경로**를 재는 데는 오히려 유용하다 |
| `x600` | Windows 11 | RTX 4070 SUPER 12GB | GPU 실측. 작업은 **`E:\gputeer-work` 아래에서만** |
| `x600` 의 WSL2 | Ubuntu (WSL2) | **같은 4070 SUPER 가 보인다** | ★ 2026-09-08 추가. **리눅스 + GPU 를 반복 가능하게 쓸 수 있는 유일한 곳.** CUDA 로 VRAM 실제 할당 확인. **MPS·MIG·compute mode 는 불가** |

| `pocof7t`/`pocof7u` | Android (POCO F7) | Adreno | **NVML 대상이 아니다.** 이 계층으로는 잴 것이 없다 |
| `runpod-gpu` | — | — | 2026-09-07 연결 거부(pod 정지 추정) |

### ★ MIG 는 가진 하드웨어로 못 잰다

```text
x600      RTX 4070 SUPER   mig.mode.current = [N/A]
remote5090  RTX 5090         mig.mode.current = [N/A]
```

MIG 는 데이터센터 카드(A100·H100 계열) 기능이고 **GeForce 는 지원하지
않는다.** MIG 거부 판정은 합성 테스트로만 남는다 — 그 사실을 결론에
적어야 한다(`CLAUDE.md` §0.4, 강제할 수 없는 것을 보장으로 선언하지 않는다).

### ★ x600 에서 `bash` 를 쓰지 마라

`ssh x600 "bash ..."` 는 **WSL 의 bash** 를 부른다(`C:\Windows\System32ash.exe`).
WSL 작업은 사용자가 명령하기 전까지 하지 않으므로, x600 원격 실행은
**`cmd` 배치(`.cmd`)로만** 한다.

## 장기 안정성 시험은 x600 에서 (2026-09-07 사용자 지시)

오래 도는 것, 반복해서 돌려야 아는 것은 **x600 에서** 돌린다.

```cmd
cargo build --release -p gputeer-cli
scripts\soak_selftest.cmd 300
```

★ **왜 반복하나** — 이 저장소의 교착 버그(`DoD-22`·`DoD-23`·`DoD-27`)는
  전부 특정 시나리오 조합에서만 드러났고, 셋 다 "기존 시나리오들이 그
  조합을 우연히 피해가 안 드러났었다" 로 기록돼 있다. **한 번 통과하는
  것과 늘 통과하는 것은 다르다.**

★★ **2026-09-07 첫 소크가 실제로 무언가를 잡았다** — 200회 중 2회 실패
  (1회차와 **151회차**). 151 은 중간이라 "첫 실행 특유" 로 설명되지
  않는다. 약 1% 다. **원인은 아직 모른다.**
  `docs/evidence/_raw/selftest_소크_x600.txt`

★ **소크가 도는 동안 같은 디렉터리에서 다른 실행을 겹치지 마라.**
  포트·파일이 부딪혀 실패가 나면 제품 결함인지 구분이 안 된다.
  (첫 소크에서 실제로 겹쳤고, 그래서 실패 2건 중 하나가 그 영향일
  가능성을 배제하지 못했다.)

## ★ 개발 기계에서 워크스페이스 테스트가 `core` 를 못 찾으면 (2026-09-10 관측)

`cargo test --workspace` 가 컴파일 단계에서 이렇게 실패한 적이 있다(두 번 연속):

```text
error: only metadata stub found for `rlib` dependency `core`(또는 `alloc`) ...
error[E0463]: can't find crate for `std`
```

툴체인은 멀쩡했다 — 최소 크레이트는 기본 설정으로 빌드됐고 sysroot 의 rlib·rmeta 크기도
정상이었다. 그때 커밋 메모리 여유가 **1.7GB / 23.7GB**, C: 여유가 9.7GB 였고,
`-j 2` 로 돌리니 **1081 passed · 0 failed** 로 통과했다.

```text
cargo test --workspace -j 2
```

★ 메모리 부족이 **원인이라고 확정하지 않았다.** 관측한 것은 "기본 병렬도(8)에서 실패 ·
2 에서 통과 · 그때 커밋 여유가 작았다" 까지다. 병렬도 8 을 메모리가 넉넉한 상태에서 다시
돌려 보지 않았다.
