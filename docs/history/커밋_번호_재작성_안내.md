# 2026-09-18 이전 문서의 커밋 번호는 **옛 이력**의 것이다

> **성격** 안내(사실 기록) · **관련 결함** 207 ·
> **근거** `docs/reports/debugs/2026-09-22_1619_이력_재작성으로_증거의_커밋_번호가_전부_끊겼다.md`

## 무슨 일이 있었나

2026-09-18, 공개 원격 저장소에 올라간 민감한 값(공인 IP · 계정 · 호스트 · 도메인)을 지우려고
`git filter-repo` 로 **전 이력을 다시 썼다.** 그 결과 **모든 커밋 번호가 바뀌었다.**

그래서 그 이전에 쓴 문서가 적어 둔 커밋 번호는 **지금 저장소에서 찾을 수 없다.**

## 어디를 고쳤고 어디를 안 고쳤나

```text
고쳤다      docs/evidence/*.md 의 frontmatter `commit:` 과 본문 인용 (75개 파일 · 104곳)
            -> 이유: `verify_evidence.py` 가 실제로 존재를 검사한다. 재현 가능성이 증거의 요건이다(ADR-029)
안 고쳤다   docs/history/HISTORY.md · docs/plans/ · docs/reports/ · docs/runbooks/ (옛 번호 약 249곳)
            -> 이유 ① HISTORY 는 **추가 전용**이다. 과거 기록을 고치면 그 규칙이 깨진다
            -> 이유 ② 나머지도 **그때의 기록**이다. 사후에 번호만 갈아 끼우면 "그때 그렇게 적었다" 가 사라진다
```

## 옛 번호를 만나면 어떻게 하나

옛 번호 -> 새 번호 대응표가 있다. **저장소에 넣지 않는다.**

```text
위치   <개발 기계>/gputeer/.git/filter-repo/commit-map   (459줄 · 옛 hash <공백> 새 hash)
사본   개발 기계의 세션 백업 폴더에 한 부 더 둔다
```

★ **왜 저장소에 안 넣나** — 옛 번호는 **민감한 값이 그대로 들어 있는 옛 커밋**을 가리킨다.
지운 커밋이 원격 캐시에 남아 있을 수 있어, 번호 목록을 공개하면 그 커밋을 찾는 길을 같이 주는 셈이다.
표 자체에는 hash 밖에 없지만, **쓰임이 그렇다.**

★ 그래서 이 대응표가 사라지면 **옛 번호는 영영 해석할 수 없다.** 그 사실을 여기 적어 둔다.

## 다시 이력을 쓰게 되면

커밋 번호를 적는 곳은 증거만이 아니다. 재작성 **직후에** 이 순서로 확인한다:

```text
1  docs/evidence/*.md 의 commit: 을 새 번호로 바꾼다
2  **새로 복제한 사본**에서 verify_evidence.py 를 돌린다
   ★ 작업 트리에서 통과하는 것은 증거가 못 된다 — filter-repo 가 남긴 옛 객체를 git 이 아직 찾아낸다
3  대응표를 저장소 밖 안전한 곳에 복사한다
4  이 문서에 날짜와 범위를 덧붙인다
```
