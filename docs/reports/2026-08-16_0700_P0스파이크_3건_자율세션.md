## 3. 결과

| 스파이크 | 판정 | 핵심 |
|---|---|---|
| **P0-01** | **PASS** | Restricted Token 에서 CUDA 완전 동작. Job Object 종료 시 VRAM 반환 |
| **P0-07** | **PASS** | σ = 0.021 (DoD 0.20). warmup 을 10→300 으로 올리면 오차 9.3%→1.2% |
| **P0-06** | **FAIL-SCOPE** | §10.3 의 "Job Object 는 VRAM 무관" 이 **틀렸다**. ADR-027 신설 |

### P0-01 — ADR-005 유지

```text
b0_alive    exit=0  ALIVE
b1_import   exit=0  TORCH 2.13.0+cu126
b2_avail    exit=0  CUDA_AVAIL True
b3_compute  exit=0  matmul_ok True
```

`CreateRestrictedToken(DISABLE_MAX_PRIVILEGE)` 로 특권을 전부 제거한 토큰에서
CUDA 초기화와 실제 연산이 모두 됐다. **Windows S1 경로를 로드맵에서 제거하지 않는다.**

Job Object 종료 시 VRAM 이 `168 → 489 → 168 MiB` 로 정확히 반환됐다.

### P0-07 — ADR-007 유지 + §12.3 개선점 도출

워크로드 5종 × 3회 = 15 시행에서 **σ = 0.021**. 기준선 가정(0.15)보다 7배 좋다.

다만 **총 3초짜리 실행의 값**이라 지속시간 스케일링을 추가로 쟀다.

```text
warmup=10   40,000 step 에서 오차 -9.3%  (step drift -10.2%)
warmup=300  40,000 step 에서 오차 +0.4%  (step drift -0.4%)
```

오차와 drift 가 거의 일치하므로 원인은 **드리프트 누적이 아니라 calibration 구간 편향**이다.
warmup 10 step 후의 50 step 이 아직 정상 상태가 아니었다.

→ **§12.3 에 `warmup >= 300 step` 추가 요청.** 현재 문서에는 warmup 규정이 없다.

### P0-06 — §10.3 이 틀렸다

기준선 §10.3 은 "Job Object 는 시스템 RAM 만 제한하고 VRAM 과 무관" 이라고 단언한다.
**Windows WDDM 에서 틀렸다.**

```text
RAM=무제한   1024:OK  2048:OK  3072:OK  4096:OK  6144:OK
RAM=8192    1024:OK  2048:OK  3072:OK  4096:OK  6144:OK
RAM=6144    1024:OK  2048:OK  3072:OK  4096:OK  6144:FAIL
RAM=4096    1024:OK  2048:OK  3072:FAIL 4096:FAIL 6144:FAIL
RAM=3072    1024:OK  2048:FAIL 3072:FAIL 4096:FAIL 6144:FAIL

VRAM 최대 ≈ Job Object RAM 제한 − 약 2000 MiB
```

**워크로드 협조가 필요 없는 유일한 수단**이라는 점에서 PyTorch fraction 과 성격이 다르다.

그럼에도 **ADR-015(Exclusive 기본값)는 유지**했다 — 상한이 코스하고(±2GB),
Windows 전용이며(v0.1 주 타깃은 Linux), VRAM quota 가 아니라 총 커밋 상한이기 때문이다.

부수 발견: `nvidia-smi --query-compute-apps` 의 `used_memory` 가 WDDM GeForce 에서 `[N/A]` 다.
**프로세스별 VRAM 직접 조회가 불가능**하므로 §10.5 의 `external_process_vram` 은
"전체 − 자신의 할당" 으로 간접 산출해야 한다.

## 4. ★ 이번 세션에서 틀렸다가 정정한 것 — 5건

`RULE.md` §1.2 에 따라 전부 기록한다. **이 중 셋은 잡지 못했으면 아키텍처를 잘못 뒤집었을 것이다.**

| # | 오판 | 실제 | 잡은 방법 |
|---|---|---|---|
| 1 | `OpenProcessToken` err=6 → "토큰 조작 불가" | `ctypes` restype 미지정으로 64비트 핸들 truncate. **프로브 버그** | Win32 API 문서 대조 |
| 2 | 빈 출력 → "CUDA 실패, FAIL-ARCHITECTURE" | 작업 디렉터리 문제. 실제로는 **전 단계 통과** | 단계 사다리(b0~b3) 도입 |
| 3 | P0-06 B `INCONCLUSIVE` 로 종료할 뻔 | Job Object 가 **실제로 VRAM 을 막고 있었다** | 대조 실험(Job Object 없이 동일 할당) |
| 4 | P0-06 C `PASS` (프로세스별 조회 가능) | `used_memory` 가 `[N/A]`. **PID 만 보인다** | 출력 문자열을 실제로 읽음 |
| 5 | P0-07 σ=0.021 을 최종값으로 쓸 뻔 | 3초 실행의 값. 긴 구간에서는 9.3% | 지속시간 스케일링 추가 측정 |

**#2 가 가장 위험했다.** 그대로 뒀으면 ADR-005 를 뒤집고 Windows S1 을 로드맵에서
통째로 제거했을 것이다. **"출력이 없다" 는 "실패했다" 가 아니다.**

**#3 은 반대 방향의 위험이었다.** `INCONCLUSIVE` 로 넘겼으면 §10.3 의 오류가
그대로 남아 Windows 노드의 실제 강제 수단을 놓쳤을 것이다.
