설치기는 이름으로 부르지만 상승 창을 거부하므로 같은 사용자 권한을 넘지 않는다.

## 결함 — 상승 창에서 돌면 같은 사용자가 쓴 값이 관리자 권한으로 실행된다

여섯 스크립트는 환경 파일(`gputeer.env` · `agent-<노드>.env`)의 `GPUTEER_BIN` 을 그대로 부른다. 그 파일은 사용자 폴더에 있고 **같은 사용자가 고칠 수 있다.**
스크립트가 상승된 관리자 창에서 돌면 그 값이 관리자 권한으로 실행된다. 작업 스케줄러 등록 예시는 전부 `/RL LIMITED`(상승 없음)이지만, 사람이 관리자 창에서
직접 돌리는 것은 막지 않는다.

```text
운영자 PC 에서 같은 계정으로 S0(호스트 실행) 작업을 한 번 받음 → 작업이 운영자 gputeer.env 의 GPUTEER_BIN 을 자기 실행 파일로 바꿈
→ 운영자가 관리자 창에서 admit-node.ps1 을 돌림 → 그 실행 파일이 관리자 권한으로 돈다(UAC 경계를 넘는다)

또는  agent.ps1 을 관리자 창에서 돌림 → agent-loop 이 관리자 권한 → 호스트에서 도는 작업(S0 · RESTRICTED)이 관리자 토큰을 물려받는다
      (Job Object 는 권한을 낮추지 않는다 — CLAUDE.md §0.4 "S1 은 호스트를 지키지 못한다" 보다 더 나쁜 상태)
```

## 위험도

**중간.** 사람이 관리자 창을 여는 조건이 필요하지만, `agent.ps1` 쪽은 한 번 그렇게 띄우면 그 뒤의 **모든 호스트 작업**이 관리자 권한으로 돈다.
UAC 를 Microsoft 가 엄밀한 보안 경계로 보지 않는다는 점은 있으나, 이 저장소는 설치기에서 같은 이유로 이미 막았다(465) — 나머지가 비어 있는 것이 불일치다.

## 고칠 방향 (수정 전에 적는다)

설치기(465)와 같은 검사를 여섯 스크립트 머리에 넣는다 — `WindowsPrincipal.IsInRole(Administrator)` 이면 `*_ELEVATED` 로 멈춘다(아무것도 읽거나 쓰기 전).
관리자 권한이 필요한 스크립트가 없다(전부 사용자 폴더 · 사용자 작업 스케줄러 · `/RL LIMITED`). 런북의 설치기 문단에 "운영자 · 실행 스크립트도 같다" 를 더한다.

## 안 해본 것 (이 결론으로 문을 닫지 않는다)

- ~~**Agent 실행 파일 자체**의 상승 검사~~ → **2026-09-29 11:04 넣었다**(아래 조치 표 마지막 줄). 리눅스는 K1 때문에 root Agent 가 정상 경로라 같은 규칙을 쓰지 않는다
- PowerShell 사용자 모듈이 cmdlet 이름을 가리는지(모듈 자동 로드 순서) — 재지 않았다. 상승 창을 거부하면 같은 사용자 권한 안의 일이 된다
- 사용자 프로필(`$PROFILE`) — 예시 명령과 작업 등록이 전부 `-NoProfile` 이다. 사람이 이미 연 창은 프로필을 읽은 뒤다(554 셸 쪽과 같은 한계 — 런북에 적혀 있다)
