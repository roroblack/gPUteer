## 556 — 설치기가 메모리 상한을 Agent 에 넘기지 않는다 → 신뢰망 노드의 모든 작업이 256MiB 로 묶인다

### 위치

```text
crates/agent/src/lib.rs:4494~4496     --workload-commit-limit-bytes 가 없으면 256MiB("실행 자체를 증명하기 위한 최소값이고 정책이 아니다")
deploy/trusted-party/install/install-node.sh:364 · install-node.ps1:351
                                      --ram-gib / -RamGiB 는 가입 파일의 available_ram_bytes 로만 간다
deploy/ 전체                          --workload-commit-limit-bytes 를 넘기는 곳이 없다
                                      (확인: `grep -rn "commit-limit\|CommitLimit\|WorkloadCommit" deploy` — 자르지 않은 검색, 0건)
crates/agent/src/exec.rs:516          컨테이너 --memory = --memory-swap = 그 값(policy.commit_limit_bytes)
```

런북 설치 절(`docs/runbooks/신뢰망_설치_운영.md:143`)은 이 인자를 선택(`[--workload-commit-limit-bytes <바이트>]`)으로 적고, 자원 절(`:479`)은
"RamGiB 와는 별개 값" 이라고만 적는다 — 설치기를 쓰면 이 값이 **항상 기본 256MiB** 라는 것은 어디에도 없다.

### 반례

```text
소유자  install-node.sh --ram-gib 16 …                     가입 파일 available_ram_bytes = 16GiB
제출자  resources.ram_bytes = 8GiB 인 학습 작업             스케줄러: 16GiB >= 8GiB — 이 노드에 배치
Agent   컨테이너 --memory=268435456 --memory-swap=268435456  작업이 256MiB 를 넘는 순간 OOM 으로 죽는다
```

배치는 "16GiB 를 줄 수 있다" 고 믿고 보내는데, 실행은 256MiB 로 죽인다. 작업 입장에서는 원인이 보이지 않는 실패다(보고에는 `OOM_KILLED` 가 메모리 관측 칸에
남는다 — `exec.rs` 의 컨테이너 결과).

### 위험도

**높음(가용성) · 경계 넘음 아님.** 신뢰망 노드에서 256MiB 를 넘는 작업은 전부 실패한다 — 실제 GPU 학습은 거의 다 넘는다. 남의 PC 를 망가뜨리지는
않는다(더 좁게 묶는 쪽의 오류다).

### 정정 — 이 결함 때문에 틀렸던 서술

- 결함 510 · 511 문서의 "실제로 작업마다 거는 상한은 메모리(`--workload-commit-limit-bytes`)" 는 맞지만, **설치기를 쓴 노드에서 그 값이 무엇인지**(항상 256MiB)를
  적지 않았다 — 운영자가 이 인자를 따로 넣지 않는 한 RamGiB 와 무관하게 256MiB 다.

## 557 — 상한을 걸었는지 확인하지 않는다(가설 — 실측 전)

### 위치

`crates/agent/src/container.rs` 의 `create_args` 가 `--memory` · `--memory-swap` · `--pids-limit` 을 넣고, create 가 성공하면 그대로 start 한다. create 뒤
런타임이 **그 값을 실제로 적용했는지**(`inspect` 의 `HostConfig.Memory` · `MemorySwap` · `PidsLimit`) 보지 않는다.
확인 범위: `container.rs` 에서 `HostConfig` 를 grep — 0건. 놓칠 수 있는 것: 다른 이름으로 상한을 확인하는 경로(찾지 못했다).

### 가설 — 왜 문제일 수 있나 (★ 실측하지 않았다)

- docker 는 커널 · cgroup 이 지원하지 않는 자원 옵션을 **경고만 내고 버리는** 경우가 있다고 알려져 있다(예: 스왑 상한 — "Memory limited without swap").
  그러면 create 는 성공하고, `--memory = --memory-swap`(스왑으로 새지 않게 — `container.rs` 머리말)이 조용히 깨진다.
- rootless podman 은 cgroup v2 컨트롤러가 사용자에게 **위임되지 않으면** 그 상한을 걸 수 없다(기본 위임은 배포판마다 다르다 — 확인하지 않았다).
  실패가 create 에서 나는지, start(OCI 런타임이 cgroup 을 만들 때)에서 나는지 **확인하지 않았다** — start 에서 나면 이 브랜치의 보수 규칙대로
  "시작했는지 모른다"(결함 490) 경로로 간다.

### 위험도

**중간(가설).** 성립하면 `CLAUDE.md` §0.4 위반이다 — 걸지 못한 상한을 건 것처럼 보고한다(`WORKLOAD_EXITED … commit_limit_bytes=…`).

### 실측 계획

x600 WSL2(docker — 2026-09-25 사용자 허가 범위, E: 만)와 가능하면 rootless podman 에서: 상한을 준 create → `inspect` 로 `HostConfig` 대조 → 경고 문구 채집.
cgroup 컨트롤러를 뺀 환경을 흉내 낼 수 있는지부터 본다(못 하면 `ENVIRONMENT-BLOCKED` 로 적는다 — PASS 로 세지 않는다).
