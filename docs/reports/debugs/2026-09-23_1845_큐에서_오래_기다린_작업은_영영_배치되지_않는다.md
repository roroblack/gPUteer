# 큐에서 오래 기다린 작업은 영영 배치되지 않는다

> **발견** 2026-09-23 18:45(신뢰망 남은 일 K — 무인 운영 설계 중 코드 대조) · **상태** 원인 확인 · **결함 번호** 211

## 1. 위치

```text
crates/cli/src/scheduler_tick.rs   Lease 시각 유도 — issued = queued_at, expires = queued_at + TTL
```

## 2. 재현(코드 대조)

```text
노드 하나 · 작업 둘. A 가 노드를 잡고 TTL 보다 오래 돈다. B 는 그동안 큐 맨 앞에서 기다린다.
A 가 끝나 노드가 풀린다 -> tick 이 B 를 본다
  expires_at = B.queued_at + TTL <= now   ->   TICK_REFUSED: QUEUE_TOO_OLD
그 뒤로 매 tick 이 같은 거부를 낸다. B 는 QUEUED 로 영원히 남고, FIFO 맨 앞이라 C · D 도 인질이 된다
```

★ 시험으로는 아직 재현하지 않았다 — 코드 경로를 읽고 확정했다. 고친 뒤 시험으로 고정한다.

## 3. 실측 — 무엇을 확인했고 무엇을 안 했나

- 확인: `scheduler_tick.rs` 가 발급 시각을 `queued_at` 으로 두고 `expires_at <= now` 면 거부한다(주석이 "시계를 안 읽는다" 를 이유로 적었다)
- 확인: `scheduler-loop` 는 `TICK_REFUSED` 를 세고 **계속 돈다** — 같은 맨 앞 작업을 계속 만난다
- 안 했다: 실제로 몇 분 기다리는 시험은 돌리지 않았다

## 4. 위험도

- [x] 가용성 — 작업 수가 GPU 수보다 많으면(신뢰망의 **보통** 상황이다) 기다린 작업이 전부 멈춘다

## 5. ★ 정정

`scheduler_tick.rs` 는 발급 시각을 저장된 사실에서 유도한 이유로 "재시도가 같은 요청을 만든다" 를 들었다.
그 이득은 **같은 tick 이 두 번 도는 경우**에만 있는데, 그 경우는 Job 이 이미 STAGING 이라 큐에서 빠져 있어
두 번째 tick 이 그 Job 을 다시 보지 않는다. 대가(기다린 작업의 영구 정지)가 이득보다 컸다 — 따져 보지 않았다.
