## 3. 실측 — 최신 자료로 확인한 것

```text
rename_noreplace   아직 제안 단계 (rust-lang/libs-team#131)

macOS              renameatx_np(RENAME_EXCL)

```
표준만으로 그 성질을 얻는 방법이 **hard_link** 다 — `link()` 는
EEXIST 로, `CreateHardLinkW` 는 실패로 끝난다. **확인과 확정이 한
연산**이 된다.

## 4. 위험도
- [x] 사용자 데이터 손실 가능 — ①·③ 은 창이 좁지만 실재한다

★ **"고쳤다" 는 보고가 성급했다.** 1차 수정을 커밋 메시지와 리포트에
"닫았다" 로 적었는데 재검수가 셋을 더 찾았다. 다음부터 **재검수 전에는
"고쳤다" 대신 "고쳤고 아직 검수 안 받았다"** 로 쓴다.

# 결함 ㊱ — out_file 경쟁 테스트가 Windows 에서 간헐적으로 "액세스 거부" 로 실패한다

★ 검수가 아니라 결함 ㉞ 의 워크스페이스 실행이 밟았다. ㉞ 는 인자 파서만 바꿨고 `out_file.rs` 는
  건드리지 않았다 — 이 실패는 ㉞ 가 만든 것이 아니다.

## 1. 위치
```text
crates/cli/src/out_file.rs  create_exclusive_temp — `<대상>.tmp.<pid>.<n>` 을 create_new 로 만든다.
                            AlreadyExists 만 다음 번호로 넘기고, 그 밖의 오류는 곧바로 실패로 반환한다
crates/cli/src/out_file.rs  tests::concurrent_writers_without_overwrite_leave_exactly_one_winner
                            — 한 프로세스의 스레드 16개 × 20라운드. 스레드끼리 pid 가 같다
```

## 2. 재현
개발 기계(Windows)에서 그 테스트만 **10회 반복 — 3회 실패**. 셋 다
`T: X 임시 파일을 만들지 못했다(...race.pb.tmp.<pid>.<n>): 액세스가 거부되었습니다. (os error 5)`,
실패 라운드는 3 · 6 · 15 로 매번 달랐다. 그 직후 워크스페이스 전체 실행에서는 통과했다.

## 3. 실측 · 가설
실패 빈도(10회 중 3회)와 메시지는 잰 것이다. **원인은 확인하지 않았다.** 가설: 다른 스레드가 방금
지운 같은 이름이 Windows 에서 삭제 대기(delete-pending) 상태로 남아 있을 때 create_new 가
AlreadyExists 가 아니라 PermissionDenied 를 돌려주고, 위 반복문은 그것을 다음 번호로 넘기지 않는다.
★ 실제 CLI 는 호출마다 별도 프로세스라 pid 가 다르다 — 제품 경로에서도 나는지는 **확인하지 않았다**
★ 20:46 가설의 한 형태를 쟀다 — 스크래치패드에서 독립 Rust 프로그램(cargo 밖)을 3회 실행했다.
  같은 프로세스가 핸들을 연 채 `remove_file` 한 뒤 같은 이름을 `create_new` 로 다시 만들면 **성공했다**
  (3회 모두). 즉 "같은 프로세스의 열린 핸들 때문에 이름이 삭제 대기로 남는다" 는 형태는 **이 시험이
  재현하지 못했다.** 가설이 죽은 것은 아니다 — 재지 않은 것: 다른 프로세스(예: 백신)가 공유 삭제 없이
  연 핸들 · 스레드 16개가 동시에 부딪히는 타이밍. ★ 그 실험의 3단계(핸들을 닫은 뒤 다시 만들기)가 낸
  AlreadyExists 는 2단계가 만든 파일을 안 지운 **실험 설계 결함**이라 아무것도 말하지 않는다

## 4. 위험도
- [x] 검증 신뢰도 저하 — 간헐 실패는 다른 회귀를 가린다

## 6. 조치
- [x] 고치기 전에 쓴다
- [ ] 가설을 먼저 잰다(실패 순간 그 이름의 상태). 확인되면 PermissionDenied 도 다음 번호로 넘길지,
  이름에 스레드 구분자를 더할지 — 둘 다 **다른 쓰기의 파일을 건드리지 않는다**는 기존 규칙과 같이 본다
