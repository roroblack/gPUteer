# 재검수 129 가 찾은 결함 2건 (510 · 511) — 소유자가 "내놓는 양" 은 배치용 숫자이고 강제되지 않는다

재검수 129 가 반례를 찾지 못한 것 — 509(root 진입 명령의 절대 경로 · 셸 설정 가로채기 서술) · 506~508 · 501 · 502 · 503 · 504 · 505 · 다른 설치 · 반입 ·
refresh 셸과 PowerShell 의 상승 경로.

| # | 심각도 | 결함 | 반례 요지 |
|---|---|---|---|
| 510 | 높음(검수 판정) | `--workspace-gib`(`-WorkspaceGiB`)는 가입 파일의 `available_workspace_bytes` 로만 가고 작업의 디스크 사용에 상한이 없다 — 체크포인트 폴더는 읽기/쓰기 bind mount 이고 생성 인자에 저장공간 제한이 없다(docker 는 이미지 `VOLUME` 도 별도 쓰기 경로). 런북 · 설치기의 "소유자가 내놓는 양" 이 코드보다 강하다 | `--workspace-gib 10` 으로 등록 → 작업이 `/gputeer/checkpoints/fill` 에 계속 씀 → 체크포인트 루트가 있는 파일시스템 전체가 참 → Agent 가 다시 뜰 때 사건 폴더 쓰기 시험이 `ENOSPC` 로 실패 → 남은 컨테이너 정리보다 먼저라 기동 거부 → 사람이 호스트에서 치울 때까지 노드가 묶임 |
| 511 | 중간 | `--cpu-cores`(`-CpuCores`)도 가입 파일에만 가고 컨테이너 생성 인자에 `--cpus` 등이 없다 | 32코어 PC 에서 2코어를 내놓음 → 2코어 작업이 배치됨 → 작업이 논리 CPU 수만큼 스레드를 돌림 → 32코어 전체를 씀 |

★ 코드 대조로 더 확인한 것 — `--ram-gib`(`-RamGiB`)도 같다. 가입 파일(`available_ram_bytes`)에만 가고, 작업의 메모리 상한은 Agent 설정
`--workload-commit-limit-bytes`(기본 256MiB · 컨테이너는 `--memory`)라는 **별개 값**이다. 셋 다 스케줄러의 배치 기준 숫자다.

★ 판정 — 이번 브랜치의 위협 모델(같은 계정의 프로그램이 그 계정 권한을 **넘는** 일을 막는다)에서 이것은 경계를 넘는 결함이 아니라 **소유자 PC 의 가용성**
문제이고, 문서가 강제되는 것처럼 적은 **과장**이다. 이 브랜치에서는 과장을 바로잡고, CPU · 디스크 강제는 별도 과제로 뗀다(rootless podman 의 cgroup 위임 ·
docker `--storage-opt` 의 파일시스템 조건 등 설계가 필요하다).
