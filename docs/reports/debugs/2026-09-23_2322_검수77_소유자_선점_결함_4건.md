## 2. 재현(코드 대조)

### 229 체크포인트 루트가 링크면 되찾음 표시를 못 본다

```text
--checkpoint-root C:\pool\alias\cp (junction -> D:\data\cp)
실행 중 settle 이 루트를 D:\data\cp 로 바꾼다 -> 선점 표시는 D:\data\cp.owner-reclaimed 에 생긴다
다음 agent-loop 회차는 입력값으로 C:\pool\alias\cp.owner-reclaimed 를 본다 -> 없다 -> 풀에 붙는다
-> 소유자가 되찾은 GPU 에 새 작업(방금 PAUSED 된 그 Job 까지)이 온다
```

### 230 표시를 보고보다 먼저 만들어, 못 보낸 선점 보고를 다시 보낼 길이 막힌다 — 그리고 보고 연결이 되찾음을 푼다

```text
1. 소유자가 멈춘다 -> 표시 생성 -> 보고를 outbox 에 남긴다 -> REPORT 전송이 실패한다(또는 그 사이 프로세스가 죽는다)
2. 다음 기동은 run() 머리에서 OWNER_RECLAIMED 로 곧바로 끝난다 -> outbox 재전송(flush_report_outbox)에 영영 닿지 않는다
3. Coordinator 는 선점을 모른 채 Lease 만료를 기다리고, 체크포인트가 없으면 FAILED 로 끝낸다 — 재배치될 Job 을 잃는다
```

★ 고치다가 **함께 드러난 것**(검수 밖, 내가 찾음): Coordinator 는 FRESH · RENEW · REPORT 어느 Hello 든 생존 관측으로 적고, 되찾음 접기는
  "되찾은 **뒤에** 온 Hello" 가 있으면 노드를 다시 후보로 본다. 그래서 되찾은 노드가 **보고를 다시 보내기만 해도** 되찾음이 풀린다.
  2 를 고쳐 outbox 를 보내게 하면 바로 그 경로를 밟는다.

### 231 = 결함 215 (INTERRUPTED 의 예약 해제와 PAUSED 전이가 다른 커밋)

검수 73 의 215 와 같은 결함이다 — 이미 고쳤다(`docs/reports/debugs/2026-09-23_2105_검수73_종료보고_경로_결함_5건.md`).

### 232 이어갈 지점 없이 PAUSED 된 Job 은 처음부터 다시 돈다 — 런북에 없다

```text
체크포인트를 하나도 안 만든 작업을 소유자가 멈춘다 -> OWNER_PREEMPTED ... resume_step=-
다음 노드에 resume_from 없는 Grant 가 나간다 -> 작업이 처음부터 다시 돈다(FAILED 가 아니다)
```

규범(`PAUSED -> RUNNING` RESUMED, "새 lease 발급")과 PURE 전제에서는 맞는 동작이다. 틀린 것은 런북이 이 경우를 설명하지 않은 것이다.
