## 무엇이 실패하나

`crates/checkpoint/tests/write_failure.rs::concurrent_startup_gc_treats_not_found_as_normal_race` — 빈 디렉터리 64개를 두 스레드가 동시에
`startup_gc` 로 치운다. 한쪽이 지운 디렉터리를 다른 쪽이 만지는 것은 **정상 경합**이고 둘 다 `Ok` 여야 한다. 워크스페이스 전체 실행에서 가끔
`Err(Io("요소가 없습니다. (os error 1168)"))` 로 실패했다(2026-09-27 · 1393 passed · 1 failed).

## 위치 — 실물 계측으로 찾았다

`crates/checkpoint/src/writer.rs:487` — `startup_gc` 가 `gc_partial` 뒤에 "디렉터리가 비었나" 를 보려고 부르는 `retry_tolerating_race(|| fs::read_dir(&dir))`.

- 표준 `fs::read_dir` 은 Windows 에서 `FindFirstFileExW` 를 부른다. 다른 스레드가 **방금 지운** 디렉터리에 대해 이 호출이 `ERROR_NOT_FOUND`(1168)를
  낸다. Rust 는 1168 을 `ErrorKind::NotFound` 로 매핑하지 않는다(`Uncategorized`) — 계측 출력이 그대로 보여 준다: `raw=Some(1168) kind=Uncategorized`.
- `retry_tolerating_race`(`crates/checkpoint/src/atomic.rs:426`)는 `NotFound` 를 "없다" 로, `raw 5` 를 경합으로 재시도하고 **그 밖은 즉시 오류로 올린다** —
  1168 은 그 밖이라 곧바로 실패한다.
- 앞선 두 경로(2026-08-24)는 **우리 코드가 직접 부르는** `CreateFileW` · `GetFileInformationByHandle` 였고 `crates/runtime-windows/src/beneath.rs` 의
  `normalize_not_found` 로 닫았다. 이번 것은 **표준 라이브러리 안**이라 그 정규화를 거치지 않는다.
- ★ 같은 호출이 `gc_partial` 안에도 있다 — `crates/checkpoint/src/atomic.rs` 의 `retry_tolerating_race(|| fs::read_dir(checkpoint_dir))`. 이번 표본(실패 5건)에서는
  나오지 않았지만 같은 원시 호출 · 같은 경합 창이다. 표준 `fs::symlink_metadata`(열기 → 정보 조회)도 같은 모양의 창을 가진다 — 이번 표본에서 나오지 않았다.
  확인 범위: 아래 계측 200회. 놓칠 수 있는 것: 더 드문 경로 — 수정은 한 지점이 아니라 **판정 함수**에서 한다(아래 "고칠 방향").

### 계측 방법

`startup_gc` · `gc_partial` 의 오류가 올라가는 12곳 전부에 호출 위치 꼬리표(`[site:S5.read_dir(dir) raw=… kind=…]`)를 **임시로** 붙여 빌드하고(패치는 커밋하지
않았다 — 측정 뒤 `git checkout` 으로 되돌렸다), 같은 시험 바이너리를 8개 동시에 25회 돌렸다.

```text
r1p4  site:S5.read_dir(dir) raw=Some(1168) kind=Uncategorized
r4p6  site:S5.read_dir(dir) raw=Some(1168) kind=Uncategorized
r6p6  site:S5.read_dir(dir) raw=Some(1168) kind=Uncategorized
r9p6  site:S5.read_dir(dir) raw=Some(1168) kind=Uncategorized
r25p2 site:S5.read_dir(dir) raw=Some(1168) kind=Uncategorized
RESULT fail=5 total=200
```

실패 5건이 **전부** 한 곳이다.

## 위험도

**중간.** 운영 경로의 `startup_gc` 는 Agent 기동 때 한 번 돈다(`gc_partial` 주석). 같은 체크포인트 루트를 두 프로세스가 동시에 치우는 경우
(두 Agent 가 같은 루트를 가리키거나, 백신 · 인덱서가 같은 디렉터리를 잡고 있다가 놓는 경우 — 후자는 확인하지 않았다)에 **정상 경합이
기동 실패**가 된다. 데이터를 지우는 쪽이 아니라 **멈추는 쪽**의 실패다(오류를 올릴 뿐 잘못 지우지 않는다).

## 고칠 방향 (수정 전에 적는다)

`retry_tolerating_race` 가 **Windows 1168 을 `NotFound` 와 같게** 본다 — 호출 지점마다 고치지 않고 판정 한 곳에서. 이유: 이번 표본에서 나온 곳은
하나지만 같은 원시 호출(`read_dir` · `symlink_metadata`)이 `startup_gc` · `gc_partial` 에 여러 번 있다. 지점마다 고치면 2026-08-17 처럼
"한 파일만 고치고 다른 파일은 놓치는" 일이 되풀이된다(`writer.rs:470` 주석이 그 기록이다).

★ 넓게 보지 않는다 — 1168 만 더한다. `raw 5`(접근 거부)처럼 재시도할 것은 아니다(1168 은 "없다" 이지 "아직 지우는 중" 이 아니다).
★ 디렉터리 순회 중의 항목 오류(`startup_gc` 의 `children.next()` · 항목 반복)는 `is_not_found` 로만 거르므로 같은 판정을 쓰게 한다.
