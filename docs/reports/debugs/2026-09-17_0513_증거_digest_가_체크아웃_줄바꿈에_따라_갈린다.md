# 증거 digest 가 체크아웃 줄바꿈에 따라 갈린다

> **작성** 2026-09-17 05:13 · **고치기 전에 쓴다**(RULE.md §5.3) · 작업 브랜치 `fix/evidence-digest-eol`(ce880d5 에서)

## 1. 위치

```text
scripts/verify_evidence.py:394  sha256_file — _raw/ 원문을 **작업 트리 바이트 그대로** 해시한다
scripts/verify_evidence.py:318  load_grandfathered — 유예 목록도 작업 트리 바이트 그대로 해시해 GRANDFATHER_DIGEST(:42)와 대조한다
scripts/test_verify_evidence.py:180  부정 테스트도 원문을 작업 트리에서 읽는다 — CRLF 체크아웃에서는 기준선부터 어긋난다
RULE.md:462                     "`raw_output_digest` = 실제 sha256" — 무엇의 sha256 인지(작업 트리 바이트) 적지 않았다
```

이 저장소에는 `.gitattributes` 가 없고 `core.autocrlf=true` 다. 그래서 같은 커밋도 **체크아웃마다 작업 트리 바이트가 다르다.**

## 2. 재현

```text
새 worktree(CRLF 체크아웃)      python scripts/verify_evidence.py              -> 스키마 위반 76건
같은 커밋을 LF 로 내보낸 폴더   git -c core.autocrlf=false archive HEAD | tar -x
                               python scripts/verify_evidence.py              -> 스키마 위반 7건
원문을 처음 쓴 메인 체크아웃     python scripts/verify_evidence.py              -> 스키마 위반 없음
```

## 3. 실측 (2026-09-17, HEAD = ce880d5 · 모든 evidence 의 raw_output_digest 를 네 형태와 대조)

```text
                       커밋된 blob   기록 digest 가 맞는 형태        LF 체크아웃   CRLF 체크아웃
원문 72건               LF           blob(= LF)                     통과          실패
원문 4건(DoD-20 61 62 63) LF         어느 형태와도 안 맞음            실패          실패
유예 목록               LF           CRLF 판                        실패(ENV-01 · ENV-02 · P0-06)  통과
```

★ 4건의 원인은 **줄바꿈이 섞인 원본**이다 — 메인 체크아웃에서 직접 쟀다(읽기만):

```text
DoD-20  파일 55534B · 1063줄 중 295줄 CRLF   파일 바이트 digest = 기록값 · LF 정규화 = 커밋된 blob(55239B)
DoD-61  파일  8236B ·  109줄 중  31줄 CRLF   같음 · 같음(8205B)
DoD-62  파일  4342B ·   64줄 중  16줄 CRLF   같음 · 같음(4326B)
DoD-63  파일  3987B ·   74줄 중  26줄 CRLF   같음 · 같음(3961B)
유예 목록 LF 정규화 = 커밋된 blob — sha256:7936fdc6fb9c623a8395ca9f31942a12f554fe486b912ccc6a8f03ef3b3eea18
```

즉 digest 를 기록한 뒤 **내용이 바뀐 것이 아니다.** 섞인 줄바꿈 파일로 digest 를 기록했고, 커밋할 때 autocrlf 가 LF 로 정규화했다.
그 바이트는 원문을 처음 쓴 체크아웃에만 남아 있다 — 다른 체크아웃에서는 어떤 방법으로도 기록값을 다시 만들 수 없다.

## 4. 위험도

- 검사기 결과가 **체크아웃에 따라 다르다** — 새 worktree · CI(리눅스 LF 체크아웃)에서는 PASS evidence 가 위반으로 보이고, 반대로 메인 체크아웃의 "위반 0" 은
  다른 곳에서 재현되지 않는다. 규칙을 강제하는 장치가 재현 가능하지 않다
- 기존 변조 탐지 자체는 약해지지 않았다 — 오탐(가짜 위반)과 재현 불가가 문제다. 단 오탐이 늘 76건이면 **진짜 변조가 그 속에 묻힌다**

## 5. 잘못 보고했던 수치의 정정
