## 2. 재현(코드 대조)

### 223 데이터 확정 뒤 서명 매니페스트 쓰기가 실패하면 그 체크포인트는 영원히 서명되지 않는다

```text
1. publish_directory 가 데이터 + manifest.json 을 공유 저장소에 확정한다
2. 직후 write_signed_manifest 만 실패한다(NAS 끊김 · 디스크 참)
3. 다음 회차가 다시 시도하지만 StagedCheckpoint::begin 이 AlreadyCommitted 로 거부한다 — 서명 단계에 다시 닿지 못한다
4. Coordinator 는 서명된 .checkpoint.pb 만 이어갈 지점 후보로 보므로 이 체크포인트는 없는 것과 같다
```

### 224 `step-N` 이름만 보고 아직 쓰는 중인 폴더를 완결로 서명할 수 있다

```text
작업이 step-7 을 직접 만들어 model.bin 을 쓰고, optimizer.bin 을 쓰기 전에 게시기가 훑으면
model.bin 하나짜리 체크포인트가 정상 서명된다. 게시된 step 은 다시 안 올리므로 잘린 채로 남고, 모든 검증을 통과해 이어가기에 쓰인다
```

★ 워크로드 약속("다 쓴 뒤 rename")은 문서에만 있고 **코드로 강제할 수 없다**(게시기는 작업이 쓰기를 끝냈는지 알 길이 없다).
  계획 문서 · 모듈 주석의 "완성된 체크포인트를 옮긴다" 가 구현보다 강한 주장이었다.

### 225 공유 저장소 밖으로 쓰거나 읽는 경로가 둘

```text
A  checkpoint_id 에 ':' 가 있으면(Windows 드라이브 접두사 — 예: attempt_id "C:") publish_directory 가 검사 없이 join 해 공유 루트 밖에
   데이터를 확정한다. 서명 매니페스트 쓰기에서야 거부된다
B  <공유 루트>/<job_id> 가 밖을 가리키는 심볼릭 링크 · junction 이면 게시 · 서명 매니페스트 · 복원이 모두 링크를 따라간다.
   read_beneath 는 "이미 고른 폴더 아래" 만 지킨다
```

### 226 저장 이름의 내용 주소 표식을 대조하지 않는다

```text
verify_on_disk 는 이름이 "<논리>.b3-<64 hex>" 모양인지만 보고, 그 64자가 실제 digest 와 같은지는 안 본다.
주석은 "저장 이름의 내용 주소 표식까지 검증한다" 고 적었다
```
