# K1 키 보관 시험 셋이 "systemd-creds 가 있다" 를 "봉인이 된다" 로 읽는다 — 비-root 리눅스에서 실패

> **발견** 2026-09-21 23:37 (GitHub Actions 우분투 러너에서 워크스페이스 시험이 처음 돌았다) · **기록** 2026-09-22 08:38 ·
> **상태** CI 로그로 확인 · 코드 대조 완료 · **결함 번호** 205

## 1. 위치

```text
crates/crypto/tests/keyring.rs:344  linux_k1_round_trips_through_systemd_creds
crates/crypto/tests/keyring.rs:455  another_signers_keypair_cannot_be_transplanted_into_this_slot (linux 분기)
crates/crypto/tests/keyring.rs:613  a_public_key_only_entry_cannot_be_swapped_in_either (linux 분기)
```

셋 다 전제를 이렇게 잡는다:

```rust
let available = std::process::Command::new("systemd-creds").arg("--version") … .status.success()
```

즉 **바이너리가 있으면 봉인이 된다고 가정한다.** 실제 전제는 그것이 아니다 —
`--with-key=host` 봉인은 `/var/lib/systemd/credential.secret`(0600 root)를 읽어야 하므로 **root 여야 성립한다.**
이 사실은 `CLAUDE.md` §0.4 의 키 보관 표에 이미 적혀 있다("Linux K1 은 **Agent 가 root 여야 성립한다**").
시험이 그 조건을 안 본 것이다.

★ 개발 기계(Windows)와 x600 WSL2(root 로 돌렸다)에서는 안 나왔다 — **비-root 리눅스에서 처음 돌렸기 때문에** 지금 나왔다.

## 3. 실측 — 무엇이 결함이고 무엇이 아닌가

- **제품 코드는 옳게 동작했다.** 봉인할 수 없을 때 `OsProtectionFailed` 로 **실패**했다 — 조용히 K0 로 내려가지 않았다.
  `CLAUDE.md` §0.4 가 "systemd-creds 가 없는 Linux 는 조용히 K0 로 내려가지 않고 실패한다" 고 적은 그대로다.
- **결함은 시험의 전제 판정에 있다.** 환경이 막은 것(`ENVIRONMENT-BLOCKED`)을 코드 결함으로 보고한다 —
  `CLAUDE.md` §4 의 "`ENVIRONMENT-BLOCKED` 를 `PASS` 로 계상하지 않는다" 와 **반대 방향의 같은 오류**다.
- 동시에 지금의 건너뛰기 분기도 약하다 — 이식 검사 둘(455 · 613)은 환경이 없으면 **아무것도 확인하지 않고** 돌아간다.
