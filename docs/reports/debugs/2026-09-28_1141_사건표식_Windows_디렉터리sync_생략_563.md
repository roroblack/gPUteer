# 컨테이너 사건 표식이 Windows 에서 디렉터리 sync 를 건너뛴다 — 561 과 같은 틀린 전제 (결함 563)

> **상태** 수정함(아래 조치) · **결함 번호** 563 · 앞 문서 [`2026-09-28_1127_보고outbox_디렉터리sync_누락_561.md`](2026-09-28_1127_보고outbox_디렉터리sync_누락_561.md)

## 위치

`crates/agent/src/container.rs:1685~1696` — 사건 표식을 쓰는 `write_incident_at`(`:1649`)이 부르는 모듈 안 `sync_dir`:

```rust
/// 새 파일 이름을 디스크에 확정한다(리눅스 — 폴더 fsync). Windows 에는 폴더 fsync 가 없다.
#[cfg(unix)]     fn sync_dir(dir) { File::open(dir)?.sync_all() }
#[cfg(not(unix))] fn sync_dir(_dir) { Ok(()) }
```

**주석의 근거가 틀렸다** — 561 과 같다. `gputeer_checkpoint::sync_dir`(`crates/checkpoint/src/atomic.rs:381`)가 Windows 에서도 디렉터리를
`FILE_FLAG_BACKUP_SEMANTICS` · 쓰기 권한으로 열어 `FlushFileBuffers` 한다(`durability_chaos.rs:432` 가 이 기계에서 동작함을 시험한다).

## 반례

```text
Windows 노드(Docker Desktop · S3) · 컨테이너 종료를 확인하지 못함 → write_incident_at 이 <이름>.<시각>.0.incident 를 create_new · sync_all
→ (새 이름이 디렉터리에 아직 확정되지 않음) → 전원 차단
→ 재부팅 뒤 표식이 없다 → 기동 관문(`agent/src/lib.rs:656` open_incidents)이 열린 사건 0건으로 보고 새 작업을 받는다
   · 남은 컨테이너 정리가 사람에게 넘겼어야 할 컨테이너를 정리한다(보수 규칙 — "사람에게 넘긴 것을 재기동이 덮지 않는다" 가 깨진다)
```

## 위험도

**중간.** 전원 차단이라는 드문 조건이지만, 나면 이 브랜치의 보수 규칙(사람이 봐야 하는 것은 표식으로 새 작업을 막는다)이 조용히 풀린다.
리눅스는 이미 sync 한다 — Windows 만의 공백이다.

## 고칠 방향 (수정 전에 적는다)

모듈 안 `sync_dir` 두 벌을 지우고 `gputeer_checkpoint::sync_dir` 를 부른다(561 과 같다). 실패하면 지금처럼 오류 — 파일은 이미 생겼으니 지우지 않는다
(`CONTAINER_INCIDENT_NOT_RECORDED` 로 agent-loop 가 다음 회차를 돌리지 않는다 — 보수 쪽). 주석을 고친다.

★ 표식 **삭제**(`clear_incidents`)에도 디렉터리 sync 가 없다 — 전원 차단으로 삭제가 사라지면 표식이 되살아나 새 작업을 막는다(보수 쪽 — 사람이 다시 해제).
해가 없어 고치지 않는다.

## 안 해본 것

- 전원 차단 실측 — 이 수정은 전원 차단에서만 달라진다. 기능 시험 · 뮤테이션으로는 차이가 드러나지 않는다
- 저장소 전체에서 **디렉터리 sync 없이 새 이름을 만드는 다른 쓰기**는 찾지 않았다 — 찾은 것은 "Windows 에 수단이 없다" 는 주석 · 가짜 구현(`crates` 아래
  `fn sync_dir` 전수 grep — `container.rs` 두 벌 · `atomic.rs` 세 벌)뿐이다. rename · create_new 뒤 sync 를 아예 부르지 않는 곳은 이 검색이 못 잡는다
