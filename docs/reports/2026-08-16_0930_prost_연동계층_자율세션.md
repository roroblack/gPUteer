## 2. 왜 이 작업을 먼저 했는가

`DoD-01` 은 canonical 규칙이 결정론적임을 두 독립 구현으로 증명했다.
그런데 그 증명은 **손으로 만든 `Fields`/`Value` 자료구조** 위에서 이뤄졌다.

```text

미증명       "실제 protobuf 메시지가 그 규칙을 실제로 지킨다"
```

후자가 없으면 전자는 종이 위의 사실이다.
그리고 **규칙이 깨진다면 바로 이 변환 계층에서 깨진다.**

## 4. 발견 2 — 내 negative test 의 주장이 틀렸다

처음 쓴 테스트는 이것이고, **실패했다.**

```rust
assert_ne!(prost_bytes, canon, "prost 인코딩과 canonical 이 같다면 ...");
```

```text
map 없는 매니페스트: prost 113B, canonical 113B, 동일=true
```

**prost 도** 필드 번호 오름차순으로 쓰고, 기본값을 생략하고, 최소 varint 를 쓴다.
map 이 없으면 두 인코딩은 바이트 단위로 일치한다.

여기서 두 갈래가 있었다.

```text
(a) 테스트를 지운다                     -> 근거를 잃는다
(b) assert 를 느슨하게 고친다            -> RULE.md §4.3 위반
(c) 주장을 정확하게 다시 세운다          <- 이것을 했다
```

### 정확한 근거

```text
틀린 근거   "prost 출력은 canonical 과 다르다"
맞는 근거   "map 이 있으면 prost 는 실행마다 다른 바이트를 낸다"
```

같은 내용의 매니페스트를 500회 재구축했다.

| 인코더 | 서로 다른 바이트 |
|---|---|
| `prost::Message::encode` | **495 종** |
| `canonical_encode` | **1 종** |

prost 는 map 을 `HashMap` 으로 만들고 순회 순서대로 쓴다.
`HashMap` 순회 순서는 인스턴스마다 다르다.
→ **같은 매니페스트에 서명해도 매번 다른 서명이 나오고 검증이 랜덤하게 실패한다.**

이것이 v5 검토가 지적한 그 결함이고, `to_fields.rs::norm_map()` 의
`HashMap → BTreeMap` 변환이 그것을 막는 **단 하나의 지점**이다.

★ 이 테스트에는 **비공허성 단언**을 넣었다. prost 가 500회 전부 같은 바이트를 냈다면
테스트는 "canonical 이 안정적이다" 만 보인 것이지 "prost 가 불안정하다" 를 보인 게 아니다.
그 경우 조용히 통과시키지 않고 **실패시킨다.**

## 5. 발견 3 — 컴파일러가 못 잡는 결함이 정확히 하나 있다

`to_fields.rs` 는 손으로 쓴다(`signing.md` §13.1).
손으로 쓰면 실수가 3종류 나오는데, **2종류는 컴파일러가 잡고 1종류는 못 잡는다.**

| 실수 | 컴파일러 | |
|---|---|---|
| 타입 불일치 (`put_bytes` 에 `String`) | **잡는다** | 이번에 실제로 잡혔다 |
| 없는 필드 | **잡는다** | |
| **잘못된 번호** | ❌ **못 잡는다** | 가장 위험 |

번호 오타는 코드가 돌고, 서명이 만들어지고, **자기 자신과는 검증도 통과한다.**
다른 구현체와 붙는 순간에만 깨지는데, 그때는 이미 서명된 매니페스트가 돌아다닌다.

→ `crates/protocol/tests/field_number_audit.rs` 가 `.proto` 소스와 `to_fields.rs` 소스를
**둘 다 파싱해 번호↔이름을 대조**한다.

### 통과하는 테스트는 아무것도 증명하지 않는다 — 뮤테이션 2종

```text
A  issued_at_unix_ms  field 61 -> 62
   -> "field number 62 이 두 번 쓰였다"                        (중복 경로)

B  entrypoint         field 13 -> 12
   -> "field 12 이 proto 에서는 `dataset` 인데
       to_fields 는 `self.entrypoint` 을 넣었다"                (이름 불일치 경로)
```

두 경로 모두 동작함을 확인하고 원복했다.
`parsers_are_not_vacuous` 로 파서 자체가 빈 결과를 내지 않음도 별도 검사한다.

## 8. 신규 스파이크 제안 — P0-08

`CLAUDE.md` §0.2 는 이렇게 못박는다.

> **`SCHEMA_TOO_NEW` 를 `VALID` 로 취급하지 않는다.** 모르는 필드가 있으면 검증 불가를 선언한다.
> 조용히 통과시키면 새 보안 필드를 구버전이 무시한다.

그런데 **prost 의 기본 동작은 모르는 필드를 조용히 버리는 것**이다.
proto3 는 unknown field 를 보존하지 않는 구현이 흔하고, prost 도 기본적으로 버린다.

```text
구버전이 신버전 매니페스트를 받는다
  -> prost 가 모르는 필드(예: 새 network 제약)를 버린다
  -> canonical 재구성 시 그 필드가 없다
  -> 서명 검증이 실패한다        (그나마 안전한 쪽)
     또는
  -> 발신자가 구버전 스키마로 서명했다면 통과한다  (위험)
```

두 시나리오 중 어느 쪽인지 **실측하지 않았다.**
`CLAUDE.md` §0.2 와 prost 기본 동작이 정면으로 충돌하므로 별도 스파이크가 필요하다.

```text
P0-08  SCHEMA_TOO_NEW × prost unknown-field
       - prost 가 unknown field 를 버리는지 보존하는지 실측
       - 버린다면 SCHEMA_TOO_NEW 를 무엇으로 탐지할 것인가
         (schema_version 만으로 충분한가? 그것도 위조 가능한데?)
       - signing.md §7.2 버전 협상 설계를 여기에 맞춰 확정
```

★ 이것은 **아키텍처를 뒤집을 수 있는 급**이다. `signing.md` §7.2 가 구현 불가능한
절차를 규정하고 있을 수 있다.

## 13. 자기 검수 기록

라고 물었을 때 답할 근거가 없었을 것이다. 495 대 1 이라는 숫자는 그 질문의 최종 답이다.
