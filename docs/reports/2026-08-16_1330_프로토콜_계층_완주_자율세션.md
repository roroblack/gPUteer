## 2. 발견 상세

### 2.1 proto 가 한 번도 컴파일된 적이 없었다

```text
"Lease" is not defined
```

`proto/` 는 규범 문서다(`CLAUDE.md` §2). 그런데 **문법 검사조차 받지 않고 있었다.**
5개 파일을 쓴 이래 `protoc` 를 한 번도 돌리지 않았기 때문이다.

→ 이제 `cargo build` 가 항상 `protoc` 를 돌린다.

★ 교훈: **"규범 문서" 라고 선언하는 것과 그것이 검사받는 것은 다르다.**
검사 경로가 없는 규범은 규범이 아니라 주석이다.
이 교훈이 이 세션 전체를 관통한다 (§2.4 · §2.6 도 같은 부류다).

### 2.2 ★ 서명 밖에 보안 필드 3건

`DoD-02` 에서 **선언**하고 `DoD-03` 에서 **제거**했다. 지금 `UNIMPLEMENTED_FIELDS` 는 비었다.

### 2.3 prost 는 map 에서 결정론적이지 않다 — 495 대 1

처음 쓴 negative test 는 `assert_ne!(prost_bytes, canonical)` 이었고 **실패했다.**
map 이 없으면 두 인코딩은 바이트 단위로 같다(113B/113B).

테스트를 느슨하게 고치는 대신 **근거를 다시 세웠다.**

```text
같은 내용 500회 재구축
  prost::encode      495~498 종의 서로 다른 바이트
  canonical_encode     1 종
```

→ `signing.md` §13.1 의 근거를 "출력이 다르다" 에서
**"map 이 있으면 prost 는 결정론적이지 않다"** 로 정정했다.

★ 만약 `assert_ne!` 를 지우거나 완화했다면 §13.1 의 근거가 영영 없는 채로 남았을 것이고,
나중에 "prost 써도 되지 않나?" 라는 질문에 답할 수 없었을 것이다.

### 2.4 ★ §7.3 은 강제할 수 없는 규칙이었다 (P0-08)

`CLAUDE.md` §0.2 와 prost 기본 동작이 충돌해 **아키텍처를 뒤집을 수 있는 급**이라
미루지 않고 확인했다.

```text
q1  prost 는 미지 필드를 조용히 버린다        118B -> 148B(주입) -> 118B
q2  미지 필드는 canonical 에 흔적이 없다
    => 구버전은 본문만으로는 새 필드를 알 수 없다. 유일한 신호는 schema_version
q3  schema_version 상향은 탐지 가능
q6  버전 강등은 서명을 깬다 (canonical + sig_input 양쪽에 묶임)
    => §7.2 SCHEMA_TOO_NEW 는 구현 가능하다. **아키텍처 재검토 불필요**

q4  ★ schema_version 을 올리지 않은 필드 추가는 **프로토콜 수준에서 탐지 불가**
```

`.proto` 에 한 줄 추가하고 버전 상수를 그대로 두면 **조용한 보안 우회**가 된다.

→ `proto/SCHEMA_FINGERPRINT.txt`(66 메시지 · 389 필드) + 대조 테스트로 **빌드 시점 강제.**
뮤테이션(`bool require_attestation = 63` 추가)으로 실효성을 확인했다 —
"추가된 줄: 63 bool require_attestation" 을 출력하며 실패한다.

**"다르다" 만 말하는 가드는 쓸모가 없다.** 무엇이 달라졌는지 보여야 고칠 수 있다.

### 2.5 검사 순서의 근거를 정정했다

```text
버전 먼저 (규범대로)   SCHEMA_TOO_NEW      "업그레이드가 필요하다"   맞다
서명 먼저 (순서 위반)  INVALID_SIGNATURE   "서명이 위조됐다"        틀렸다
```

**둘 다 거부한다. 안전성은 순서와 무관하다.**
순서를 지켜야 하는 이유는 **진단 정확성**이다 (`CLAUDE.md` §3).
`signing.md` §8 의 근거 문구를 그렇게 고쳤다.

### 2.6 ★ 내가 스트림 소유권을 어겼다

`RULE.md` §4.1 은 **Ed25519 를 Crypto 스트림(`crates/crypto/`) 소유**로 정한다.
그런데 `crates/protocol/src/signing.rs` 에 넣었다.

**테스트 100건이 전부 통과했고 아무도 알아채지 못했다.**

```text
잘못된 대응   "단일 구현자니까 괜찮다" 로 넘어간다
              소유권 표를 protocol 쪽으로 고친다      <- 규칙을 코드에 맞추는 것
올바른 대응   코드를 규칙에 맞춘다                    <- 이것을 했다
```

`RULE.md` §4.3 마지막 줄 — "다른 스트림의 테스트를 통과시키려고 계약이나 assertion 을
완화하지 않는다." 같은 정신이다.

→ trait 는 protocol, 구현은 crypto (§4.3).

```text
crates/protocol   Signable · SignatureVerifier · Verified<M> · VerifyOutcome
                  = 무엇을 서명하는가 · 어떤 순서로 검증하는가
                  **암호 라이브러리에 의존하지 않는다** (blake3 만 예외)

crates/crypto     Ed25519Verifier · sign() · InMemoryKeyring        (신설)
                  = 그 서명을 실제로 만들고 확인하는 법
```

→ 그리고 경계를 **코드로 강제**했다 (`stream_ownership.rs` 5건).
`cargo add` 한 줄이면 경계가 무너지고 테스트는 여전히 초록색이므로,
`Cargo.toml` 의존성을 파싱해 검사한다. 뮤테이션으로 실효성을 확인했다.

## 3. 이 세션의 방법론 — 뮤테이션 5회

**통과하는 테스트는 아무것도 증명하지 않는다.** 새로 만든 가드는 전부 일부러 깨봤다.

| 가드 | 뮤테이션 | 결과 |
|---|---|---|
| `field_number_audit` | `issued_at` 을 field 61 → 62 | 중복 검출로 실패 |
| `field_number_audit` | `entrypoint` 를 field 13 → 12 | 이름 불일치로 실패 |
| `schema_fingerprint` | `bool require_attestation = 63` 추가 | 추가된 줄을 출력하며 실패 |
| `Verified<M>` compile_fail | 필드를 `pub` 으로 | 독테스트 FAILED |
| `stream_ownership` | protocol 에 ed25519 재추가 | 위반 크레이트명 출력하며 실패 |

전부 원복 후 통과를 재확인했다.

### 비공허성 단언을 테스트 안에 넣었다

뮤테이션은 사람이 해야 한다. **테스트가 스스로 공허함을 감지하게** 만든 것들:

```text
prost_encode_is_not_deterministic_for_maps
    prost 가 500회 전부 같은 바이트를 내면 실패시킨다
    (그 경우 "canonical 이 안정적이다"만 보인 것이지 "prost 가 불안정하다"를 보인 게 아니다)

tampering_security_fields_breaks_signature
    assert_ne!(변조본, 원본) — 변조하지 않는 변조 테스트를 잡는다
    ★ 실제로 이 실수를 했다: minimum_security_tier = 0 은 기준값이 이미 0

working_replay_guard_rejects_reuse
    다른 nonce 는 통과함을 함께 확인 — guard 가 무조건 거부하는 게 아님을 보인다

parser_is_not_vacuous  (3개 파일)
    파서가 빈 결과를 내면 그 위의 모든 검사가 공허해진다
```

## 4. 내가 틀렸던 것 5건

1. **`put_bytes(f, 60, &self.submitter_device_id)`** — proto 를 안 보고 계획서 §15.2 를
   따랐다. 컴파일러가 잡았다. (계획서 쪽이 드리프트였다 → D-5 4번)
2. **`assert_ne!(prost_bytes, canon)`** — "당연히 다를 것" 이라 가정했다. 실측이 반박했다.
3. **`minimum_security_tier = 0` 변조** — 기준값이 이미 0이라 아무것도 바꾸지 않았다.
4. **`compile_fail` 독테스트를 `tests/` 에 뒀다** — 통합 테스트의 독테스트는 실행되지 않는다.
   **검증하지 않는 것을 주장하고 있었다.** `src/` 로 옮겼다.
5. **Ed25519 를 `crates/protocol` 에 넣었다** — 소유권 위반. 100건이 통과 중이었다.

★ 2번과 5번이 중요하다. 둘 다 **"고치기 쉬운 쪽" 이 규범이었다.**
테스트를 완화하거나 소유권 표를 고쳤다면 이 세션은 훨씬 빨리 끝났고,
그만큼 나쁜 상태로 남았을 것이다.

## 8. 검수 기록

단일 실행자 작업이라 교차 검수 대상이 아니다.
§4 의 오판 5건은 **모두 스스로 발견해 정정**한 것이며 발견 경로를 함께 기록했다.

특히 **5번(스트림 소유권 위반)은 테스트로는 영영 드러나지 않았을 것**이다 —
계약 문서를 다시 읽다가 발견했다. 그래서 그 경계를 **다시는 문서에만 두지 않도록**
`stream_ownership.rs` 로 코드화했다.

★ 이 세션의 한 줄 요약:
**강제 장치가 없는 규범은 규범이 아니라 희망이다.**
이번에 3개를 만들었다 — `field_number_audit` · `SCHEMA_FINGERPRINT` · `stream_ownership`.
