### 검증 중 스스로 정정한 것

★ **P2 를 1차에 오판했다.** `GENERIC_READ` 로만 디렉터리를 열어 `FlushFileBuffers` 가

권한 조합 3가지를 순차 시도하도록 프로브를 고쳐 재측정한 결과
**`GENERIC_READ|GENERIC_WRITE` 로는 성공**했다. 결론이 뒤집혔다.

한 번의 실패를 결론으로 삼지 않은 것이 중요했다. 그대로 두었다면 규범에
"Windows 에서는 디렉터리 동기화 불가" 라는 **틀린 제약**이 들어갔을 것이다.

## 4. 핵심 발견

### 발견 1 — Windows rename 은 열린 파일을 대체하지 못한다

POSIX 에서는 다른 프로세스가 파일을 열고 있어도 rename 이 성공한다.
Windows 는 `ERROR_ACCESS_DENIED(5)` / `ERROR_SHARING_VIOLATION(32)` 로 실패한다.
`FILE_RENAME_FLAG_POSIX_SEMANTICS` 로도 해결되지 않았다.

### 발견 2 — 원자성 자체는 깨지지 않는다

**모든 시나리오에서 `부분 내용` 관측 0건.** rename 이 성공하면 항상 원자적이고,
실패하면 아무 일도 일어나지 않는다.

> 문제는 "찢어진 데이터" 가 아니라 "확정이 거부된다" 는 것이다.
> **데이터 무결성 위험이 아니라 가용성 위험**이다.

이 구분이 해법을 결정했다.

### 발견 3 — 기준선 §18.6 이 이미 해법을 갖고 있었다

> **모든 artifact 는 immutable. canonical 은 pointer 만 갱신한다.**

불변 artifact 는 덮어쓸 일이 없다. 데이터 파일을 고유 이름으로 write-once 하면
`rename` 대상이 존재하지 않고, 그 조건은 **3000/3000 성공**했다.
`replace-over-existing` 이 필요한 곳은 **포인터 파일 하나뿐**이고 작아서 재시도가 싸다.

→ **ADR-026** 으로 기준선 §18.2 수정 요청.
