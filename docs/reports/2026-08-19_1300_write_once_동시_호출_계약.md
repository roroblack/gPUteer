## 1. 왜 이 조각이 필요했나

`write_once()` 는 같은 `(dir, name)` 으로 동시에 호출되면 안전하지
않다는 결함이 있었다(`DoD-08` 이 이전에 찾았으나, 실제 호출부가
전부 순차적이라 "결함을 고정하는 테스트" 로만 등록하고 코드는
고치지 않았다). `ENV-03`(Linux 실측)이 같은 테스트를 Linux 에서
돌려보니 재현되지 않는 걸 확인하면서 — 플랫폼별 `rename` 시맨틱
차이로 증상만 다르게 나타날 뿐 근본 원인(tmp 경로 공유)은 그대로
라는 게 재확인됐다. "코드를 고치기 전에 이 함수가 동시 호출을
지원해야 하는지부터 계약으로 정해야 한다" 는 게 두 evidence 문서의
공통 결론이었다.

## 2. 무엇을 했나

1. **설계** — 코덱스(`p127`)에게 실제 호출부 실측·Lease/fencing 이
   이 문제를 대신 해결해주는지 조사를 맡겼다. 결론: 실제 호출부는
   전부 순차적이고 Lease/fencing 은 파일 쓰기 상호 배제를 보장하지
   않으므로, **정책 A(동시 호출 미지원 + 명시적 거부)** 를 파일
   잠금으로 강제하는 쪽을 추천받아 채택했다.
2. **구현** — `std::fs::File::try_lock()`(Rust 1.89+ 표준 라이브러리,
   외부 크레이트 불필요) 기반 프로세스 간 락을 `final_path.exists()`
   첫 검사보다 먼저 잡고, 실패 시 새 `CheckpointError::WriteInProgress`
   를 즉시 반환하도록 `write_once()` 를 고쳤다.
3. **독립 검수 5라운드** — 아래 §3.

**전부 "구현자(나)가 놓쳤지만 독립 검수가 잡은 것"이다.**

| # | 결함 | 발견 라운드 | 어떻게 |
|---|---|---|---|
| 1 | `Cargo.toml` 이 Rust 1.85 를 선언하는데 `try_lock()` 은 1.89+ 필요 | `p128` | 코드·`Cargo.toml` 대조 |
| 2 | `k1c` 재설계 버전이 `Barrier` 만으로 "패자는 반드시 `WriteInProgress`" 를 주장 — 스케줄링에 우연히 의존하는 비결정적 주장 | `p128` | 테스트 설계 자체를 논리적으로 재검토 |
| 3 | `gc_partial` 이 죽은 락 파일을 영원히 보존해 PARTIAL 디렉터리가 절대 청소되지 않는 회귀(내가 만든 1차 수정 자체의 결함) | `p128` | 코드 경로 추적 |

5건 중 3건(#1~3)은 1라운드에서, 1건(#4)은 2라운드에서, 근본 원인(#5)은
3~4라운드에 걸쳐 발견됐다 — **매 라운드가 새 결함을 찾았다.** 5라운드
(`p132`)에서 비로소 `ACCEPTED`.

## 4. 의도적으로 고치지 않은 것

`gc_partial()` 은 checkpoint 디렉터리 전체를 보호하지 않는다 —
`write_once()` 의 락은 그 호출이 쓰는 한 파일만 보호하므로, 매니페스트
없는(PARTIAL) 디렉터리에서 GC 가 활성 writer 와 동시에 돌면 writer 가
지금 쓰는 `.tmp` 파일을 GC 가 지울 수 있다(코덱스 `p129` 지적).
**일부러 고치지 않았다** — 이건 `write_checkpoint()` 전체를 감싸는
디렉터리 단위 락이 필요한, 계획 문서가 이미 예고한 범위 밖 문제다.
코드에 명시적으로 문서화만 하고, 다중 Agent 실행이 시작되는 시점을
재검토 트리거로 남겼다.

  판단했고 단독 15회 재실행은 15/15 통과, 코덱스 5라운드도 동의했다.
