# 신뢰망 파티 — 설치 · 운영 런북

> **최종 갱신** 2026-09-23 · **성격** 실행 절차 · **범위** 서로 믿는 몇 사람이 GPU 를 나눠 쓰는 풀(v0.1)
> **짝** `docs/plans/2026-09-23_1816_신뢰망_100_남은_일.md`(무엇을 만들었나) · 시험 `crates/cli/tests/trusted_party_*.rs`(이 절차가 실제로 도는가)

★ **이 풀이 막지 않는 것부터 읽는다.** 참여자를 믿는다는 전제다 — 악의적인 작업이 호스트를 공격하는 것,
  작정하고 자원 상한을 빠져나가는 것, 통신 도청(TLS 없음)은 막지 않는다(`CLAUDE.md` §0.4). 모르는 사람의 PC 나
  작업을 붙이지 않는다.

## 0. 구성 한눈에

```text
한 대   Coordinator(풀 모드)      계속 떠 있다 — Agent 들의 인사 · Grant · 갱신 · 보고를 받는다
        scheduler-loop             큐를 돌며 빈 노드에 예약하고, 끊긴 노드의 작업을 되돌린다
        control DB                 SQLite 파일 하나(작업 · 예약 · Lease · 생존 관측 전부)
GPU 마다 agent-loop                되풀이해 붙는다 — 일이 있으면 실행 · 보고, 없으면 기다렸다 다시
모두    공유 저장소                 체크포인트를 옮기는 곳(NAS · 동기화 폴더 · 네트워크 드라이브).
                                   Coordinator 와 **모든** Agent 가 같은 경로 내용을 볼 수 있어야 한다
```

★ 이 문서의 `<...>` 는 자리 표시다. **실제 IP · 호스트 이름 · 계정 · 키 경로를 이 저장소의 파일에 적지 않는다**
  (전역 규칙). 실제 값은 각 기계의 서비스 설정 파일(저장소 밖)에만 둔다.

## 1. 키 만들기 — 기계마다 한 번

```bash
gputeer keygen --out <시드 파일>
```

`SEED_FILE` · `PUBLIC_KEY` 두 줄이 나온다. 시드 파일은 그 기계 밖으로 옮기지 않는다(유닉스에서는 0600 으로 만들어진다 ·
Windows 는 사용자 프로필 아래에 둔다). 이미 있는 파일은 덮지 않는다 — 잃으면 그 기계의 신원이 바뀐다.

| 누구 | 키 | 공개키를 누구에게 |
|---|---|---|
| Coordinator | `coordinator.seed` | 모든 Agent(`--peer-pubkey`) |
| 노드(GPU 하나마다) | `<node>.seed` | Coordinator(`--pool-agents`) · 모든 Agent(`--pool-peer-keys`) · scheduler(`--pool-agents`) |
| 제출자 | `<submitter>.seed` | Coordinator 의 제출자 keyring |

★ 비밀 시드는 **`--own-seed-file`** 로 준다. `--own-seed <hex>` 는 같은 기계의 다른 사용자가 프로세스 목록에서 볼 수 있다.

## 2. 노드 등록 — GPU 여러 장 기계는 GPU 마다 노드 하나

`import-inventory` 로 노드를 등록한다(형식은 `crates/cli/tests/trusted_party_pool.rs` 의 `bootstrap.json`).

```text
node_id       그 노드 Agent 의 --agent-device-id 와 **같게** 둔다(Grant 의 holder 가 이것이다)
GPU 두 장     "lab-gpu0" · "lab-gpu1" 두 노드로 등록하고, CPU · RAM · 디스크를 둘로 나눠 적는다
              Agent 도 둘 — 각각 --gpu-pin 0 · --gpu-pin 1 (작업에 CUDA_VISIBLE_DEVICES 로 그 GPU 만 보인다)
```

★★ `isolation_class` 는 **그 노드가 실제로 주는 격리**로 적는다(결함 267 · 2026-09-25). 호스트에서 작업을 돌리는 노드(컨테이너 런타임이
  없거나 `--container-only true` 가 아닌 노드)는 `RESTRICTED` 다 — 작업이 소유자와 같은 권한 · 파일시스템 · 네트워크에서 돈다(메모리 상한뿐).
  `CONTAINED` 는 `--container-runtime … --container-only true` 로 띄우는 노드에만 적는다. 거꾸로 적으면 `--minimum-isolation-class CONTAINED`
  작업이 호스트 실행 노드에 배치된다 — 스케줄러는 등록된 값을 믿는다.
★ GPU 를 **나눠** 쓰는 것(한 장에 작업 둘)은 하지 않는다 — 노드 단위 배타 배정이다. `--gpu-pin` 은 보이게 하는 것이지
  강제가 아니다(작업이 다른 GPU 를 열면 막지 못한다).

## 3. Coordinator 띄우기

```bash
gputeer coordinator-stub --pool-mode true \
  --pool-agents "<node1>=<pubkey1>;<node2>=<pubkey2>" \
  --listen <바인드 주소>:<포트> --own-seed-file <coordinator.seed> \
  --coordinator-device-id <coordinator id> \
  --grant-from-control-db <control.sqlite3> --lease-db <control.sqlite3> --liveness-db <control.sqlite3> \
  --submitter-keyring <submitters.keyring> \
  --accept-report-sessions true --release-on-exit-report true \
  --shared-checkpoint-root <공유 저장소> --replay-db <replay.sqlite3> \
  --max-connections 0 --accept-timeout-ms 0
```

- `--lease-db` · `--liveness-db` 는 control DB 와 **같은 파일**이어야 한다(아니면 시작을 거부한다 — `POOL_LEASE_DB_MISMATCH` ·
  `POOL_LIVENESS_DB_MISMATCH`). 스케줄러가 거기서 Hello 관측을 읽는다
- `--pool-agents` 의 공개키는 노드마다 달라야 한다(`POOL_AGENTS_DUPLICATE_KEY`)
- `--release-on-exit-report` — 종료 보고가 오면 같은 커밋에서 예약을 푼다. 완료 작업은 Manifest 가 `--durability LOCAL` 일 때만
  푼다(이 풀은 복제를 하지 않는다 — `RESERVATION_KEPT reason=ARTIFACT_DURABILITY_...` 가 찍히면 그 이유다)
- `--replay-db` — 재시작해도 옛 메시지(인사 · ACK · 갱신)를 다시 받지 않는다(풀 모드 전용)
- ACK 를 기록한 뒤 **서명된 수신 확인**을 보낸다 — Agent 가 `--require-ack-receipt true` 면 그것을 받아야 실행한다
- 순차 리스너다 — 신뢰망의 몇 대에는 충분하다. 수십 대는 범위 밖

## 4. 스케줄러 띄우기

```bash
gputeer scheduler-loop --interval-ms 1000 --max-ticks 0 \
  --control-db <control.sqlite3> --submitter-keyring <submitters.keyring> --submitter-member <owner id> \
  --max-snapshot-age-ms 86400000 --best-fit-axes vram,gpu_count,cpu,ram,workspace \
  --coordinator-id <coordinator id> --coordinator-term 1 \
  --lease-ttl-ms 120000 --lease-renew-after-ms 40000 --lease-max-total-duration-seconds 86400 \
  --silent-after-ms 60000 \
  --failover-grace-ms 30000 --shared-checkpoint-root <공유 저장소> \
  --pool-agents "<node1>=<pubkey1>;<node2>=<pubkey2>" --pool-mode true
```

- `--silent-after-ms` — 이만큼 인사가 없는 노드에는 새 일을 주지 않는다(주지 않으면 이 축을 안 본다)
- `--pool-mode true` — 풀 스케줄러임을 **명시**한다(control DB 에 풀 표식을 적는다 · 풀 Coordinator 도 기동 때 적는다). 풀이면 Manifest 가
  `LOCAL` 이 아닌 작업을 **배치 전에** 내린다 — QUEUED 는 FAILED(PERMANENTLY_INFEASIBLE, `DURABILITY_*_NOT_SUPPORTED_BY_POOL`), PAUSED 는
  건너뛴다(`TICK_SKIPPED`). 이 풀은 복제하지 않아서, 배치하면 끝난 뒤 그 노드가 묶인다(결함 217 · 235 · 236 · 249). `--pool-agents` 는 이어받기용 키 목록이다
- ★ 건너뛴 PAUSED 작업은 **영원히 PAUSED 로 남는다** — Job 을 취소하는 명령이 아직 없다(알려진 공백 · 결함 250). 이런 작업은 풀 표식 전에
  배치된 경우에만 생긴다
- `--failover-grace-ms` — 실행 중인 작업의 Lease 가 만료되고 이만큼 지나면 그 노드를 잃은 것으로 본다. 이어갈 체크포인트가 있으면 큐로
  되돌리고, **실행 중(RUNNING)인데 체크포인트가 없으면 FAILED** 로 끝낸다(재시도 정책 0회 · 결함 259).
  짧게 잡으면 잠깐 끊긴 노드의 작업을 뺏는다
- Lease TTL 은 Agent 의 `--renew-during-execution-ms` 보다 **충분히** 길게(갱신 두세 번이 들어갈 만큼)

## 5. Agent 띄우기 — GPU 마다 하나

먼저 **점검한다**(2026-09-25) — 아래 Agent 명령에 줄 값을 그대로 준다. FAIL 이 하나라도 있으면 종료 코드가 0 이 아니다.

```bash
gputeer node-doctor --seed-file <node.seed> --node-dir <node 전용 폴더> --connect <coordinator 주소>:<포트>   --shared-checkpoint-root <공유 저장소> --owner-panel-port <로컬 포트> [--gpu-pin <GPU 번호>]   [--container-runtime <podman|docker> --container-runtime-kind podman|docker]
```

```text
seed                    시드를 읽고 공개키를 찍는다(유닉스에서 다른 사용자가 읽을 수 있으면 WARN)
node_dir                폴더를 만들고 쓸 수 있는지(임시 파일을 쓰고 곧 지운다)
coordinator             TCP 로 붙는지만 본다 — 서명 교환은 하지 않는다
shared_checkpoint_root  있고 쓸 수 있는지(루트 자체가 링크면 WARN)
owner_panel_port        127.0.0.1 의 그 포트가 비었는지
gpu                     NVML 로 보이는지 · --gpu-pin 의 GPU 가 있는지(NVML 을 못 열면 "0개" 가 아니라 "모른다" 다)
container_*             런타임이 도는지 · rootless 인지(rootful 이면 WARN) · GPU 를 넘길 설정이 보이는지(보였다까지다 — 실행 확인 아님)
```

```bash
gputeer agent-loop --interval-ms 5000 --max-rounds 0 -- \
  --connect <coordinator 주소>:<포트> --own-seed-file <node.seed> \
  --peer-pubkey <coordinator pubkey> --coordinator-device-id <coordinator id> --agent-device-id <node id> \
  --fence-db <node 전용 폴더>/fence.sqlite3 --checkpoint-root <node 전용 폴더>/checkpoints \
  --submitter-pubkey <submitter pubkey> \
  --i-understand-this-executes-untrusted-code true \
  --report-over-session true --renew-during-execution-ms 30000 --max-reconnect-attempts 1 \
  --require-ack-receipt true \
  --shared-checkpoint-root <공유 저장소> --pool-peer-keys "<node1>=<pubkey1>;<node2>=<pubkey2>" \
  --owner-panel-port <로컬 포트> [--gpu-pin <GPU 번호>] [--workload-commit-limit-bytes <바이트>]
```

- Owner Panel 은 `127.0.0.1` 에만 열린다 — 그 PC 의 주인만 본다(§0.1)
- 노드마다 `--fence-db` · `--checkpoint-root` 를 **따로** 둔다. 같은 루트를 **동시에** 쓰면 거부된다(잠금). 순차로 바꿔 쓰는 것은 막지 않는다 —
  그 경우 남의 보고는 격리하지 않고 그대로 둔다(`ATTEMPT_REPORT_OUTBOX_FOREIGN` · 결함 264)
- ★ 풀에서는 `--require-ack-receipt true` 와 `--renew-during-execution-ms`(예 30초 — Lease TTL 보다 충분히 짧게)가 **필수**다.
  수신 확인을 끄면 ACK 가 기록되기 전에 끊겼을 때 같은 시도가 두 번 돌 수 있다. 갱신을 끄면 시작하지 않는다(`POOL_AGENT_NEEDS_RENEW`) —
  Coordinator 는 **실행 직전 갱신**을 "실행을 시작한다" 로 보고 그때 Job 을 RUNNING 으로 옮긴다. Agent 는 그 갱신이 **성공해야** 워크로드를
  띄운다 — 못 받으면 `PROCESS_START_NOT_CONFIRMED` 로 시작하지 않는다(결함 218 · 268). 수신 확인을 요구하는 Agent 는 갱신을 켜야 시작하고(270), 실행 직전 갱신이 성공해야 띄우며, 확인받은 Lease 가 5초도 안 남았으면 띄우지
  않는다(`LEASE_TOO_SHORT_AFTER_CONFIRM` · 289 — 이때 Job 은 RUNNING 으로 남아 체크포인트가 없으면 FAILED 가 된다: 두 번 도는 대신 가용성을 잃는 쪽).
  ★ **풀에서는 수신 확인이 필수다** — 이 관문들은 수신 확인 Agent 에만 선다(풀 밖 lane 은 ACK 가 Job 을 옮겨 필요 없다 · 293). 수신 확인을 끈 채
    풀에 붙이면 막지 못한다 — Agent 는 상대가 풀인지 모른다. **설정 오류**다(계약 변경 없이는 막지 못한다)
- ★ 운영 조건(결함 294) — Coordinator `--renew-extension-ms`(기본 60초)는 Agent `--renew-during-execution-ms` 의 **두 배 + 노드 간 시계 차이**
  보다 길게 둔다. Agent 는 Coordinator 가 정한 만료 시각을 **자기 시계로** 재서 다음 갱신 시각을 정한다 — 모든 기계에 시계 동기화(NTP)를 켠다
- 실행 직전 Lease 남은 시간이 "실행 중 갱신 주기 + 5초" 보다 짧으면 시작하지 않는다(`LEASE_TOO_SHORT_TO_START` · 결함 246). 그 시도는 한 번도
  안 돌았으므로 Job 이 STAGING 에 남고, Lease 만료 뒤 **큐로 돌아가 처음부터** 돈다(결함 256 닫힘)

### 5a. 컨테이너로 돌리기 (권장 · 2026-09-25)

작업을 호스트에서 소유자와 같은 권한으로 돌리지 않고 컨테이너에 가둔다. Agent 에 런타임을 알려 주면 **컨테이너 Job

★ `--container-only true` 를 같이 준다 — 없으면 컨테이너가 아닌 Job 은 여전히 **호스트에서** 돈다(결함 280). 그 노드만 `CONTAINED` 로 등록한다(§2).

- ★ **rootless podman 을 권한다.** docker(rootful)를 쓰면 Agent 계정이 docker 그룹에 있어야 하고, **docker 그룹은 곧 root 다**
- 컨테이너 안에서 `GPUTEER_CHECKPOINT_DIR` 는 `/gputeer/checkpoints`, `GPUTEER_RESUME_DIR` 는 `/gputeer/resume`(읽기 전용)이다. 작업 디렉터리는 `/tmp`
- 소유자 정지(Owner Panel)는 컨테이너를 `kill` 한다 — 안의 프로세스 트리가 같이 끝난다. 이미 스스로 끝난 뒤에 누르면 정지 **실패**(`ALREADY_EXITED`)로
  보인다 — 그 정지는 종료 원인이 아니었다(결함 277)
- 종료는 `inspect` 로 주기 확인한다(명령마다 시한). 다섯 번 연속 확인하지 못하면 kill · rm 을 시도하고 그 결과를 오류에 적는다(결함 276)
- 컨테이너 이름은 시도에서만 만든다. 라벨은 둘이다 — `gputeer.node=<노드 id>`(사람이 알아보는 용도)와 `gputeer.owner=<노드 id>.<루트 해시>`.
  Agent 는 회차를 시작할 때 체크포인트 루트를 **잠근 뒤** `gputeer.owner` 라벨로 남은 컨테이너를 모두 지운다 — 죽은 회차가 남긴 컨테이너가 GPU 를
  물고 도는 것을 치운다(결함 290 · 291 · 295). 같은 루트를 잠근 Agent 는 하나뿐이라 잘못 겹쳐 뜬 두 번째 Agent 가 정상 작업을 지우지 않는다.
  목록을 못 읽으면 시작하지 않는다(`CONTAINER_LEFTOVERS_UNKNOWN`)
- ★ 업그레이드(결함 296) — Agent 를 새 판으로 바꿀 때는 **먼저 멈추고**, 옛 판이 남긴 컨테이너를 사람이 지운다:
  `<런타임> ps -a --filter label=gputeer.managed=1` 로 보고 `<런타임> rm -f -v <id>`. 옛 판의 라벨이 새 판의 정리 열쇠(`gputeer.owner`)와 다를 수
  있다 — 이 판(2026-09-25) 전의 컨테이너 판은 배포된 적이 없다
- ★ 체크포인트를 공유 저장소로 올릴 때 파일을 **링크를 따라가지 않고** 연다(리눅스 openat2 · Windows reparse 거부 — 결함 287). 작업이
  step 폴더나 파일을 호스트 파일 링크로 바꿔치기해도 그 내용이 올라가지 않는다
- ★ **`--container-gpu` 는 아직 실측하지 않았다**(podman `--device nvidia.com/gpu=<핀>` · docker `--gpus device=<핀>`). NVIDIA Container
  Toolkit 이 깔린 노드에서 먼저 확인한다. 켜면 그 GPU 드라이버 표면이 컨테이너에 열린다
- ★ 컨테이너는 호스트 커널을 같이 쓴다(S3). 커널 · 드라이버 취약점까지 막지는 못한다
- ★ 무엇을 실제로 쟀는지 — **2026-09-25 CI 실행 36103061402(GitHub Actions ubuntu 러너 · 비-root 사용자)에서 docker 와 rootless podman
  둘 다** `crates/agent/tests/container_isolation_real.rs` 5개가 실제로 돌았다(`ENVIRONMENT-BLOCKED` 없음 — 정보용 단계에 `CONTAINER_ISOLATION_MEASURED`
  가 두 런타임 × 5 로 찍혔다):
  ```text
  읽기 전용 루트 · 붙인 폴더 밖 쓰기 불가 · 체크포인트 폴더 쓰기   docker O   podman O
  네트워크 인터페이스 = lo 뿐                                       docker O   podman O
  CapEff 0 · NoNewPrivs 1                                           docker O   podman O
  64MiB 상한에서 200MB 잡기 → 작업이 죽는다(종료 99)                docker O   podman O   ★ OOMKilled 표시는 docker true · podman false
  소유자 정지 → 137 로 끝남                                         docker O(710ms) podman O(201ms)
  ```
  ★ 한 번 · 한 환경(CI 러너)이다. GPU 를 넘기는 경로(`--container-gpu`)는 여기서 재지 않았다. 개발 기계(Windows)에서는 가짜 런타임으로 명령 순서 ·
    정지 · 거부만 잰다
- podman 에 `--memory-swap` = `--memory` 를 준다(스왑 0) — podman 문서는 "더 커야 한다" 고 적지만 위 CI 에서 podman 이 받아들였고 상한을 넘긴
  작업이 죽었다(결함 275 — 그 러너의 podman 판에서). ★ OOM 판정을 `OOMKilled` 표시에 기대지 않는다 — podman 은 컨테이너 안의 한 프로세스가 죽은
  경우 false 로 보고했다. 작업의 종료 코드가 실패를 알린다

컨테이너 Job 내기 — `gputeer submit` 에 `--image-ref <참조> --image-sha256 <64자리 16진수>` 를 더한다. 이미지의 digest 는
`docker image inspect --format '{{index .RepoDigests 0}}' <이미지>` 로 읽는다. `--entrypoint` 는 **컨테이너 안의** 실행 파일이다.

## 6. 작업 내기

### 화면으로(2026-09-25)

```bash
# 제출자 기계 — 자기 키로 서명한 작업 파일을 만든다
gputeer submit-ui --submitter-device-id <submitter id> --submitter-seed-file <submitter.seed> --out-dir <작업 파일 폴더> --port <로컬 포트>
# Coordinator 기계 — 운영자가 받은 파일을 올려 반입 · 계획까지
gputeer dashboard --control-db <control.sqlite3> --port <로컬 포트> --allow-import true \
  --submitter-keyring <keyring> --submitter-member <owner id> --max-snapshot-age-ms 86400000
```

- 시작할 때 찍히는 **토큰이 든 주소**(`SUBMIT_UI_OPEN http://127.0.0.1:<포트>/#token=…` · 대시보드는 `DASHBOARD_IMPORT_ENABLED open=…`)로 연다 —
  토큰은 HTTP 로 주지 않는다(같은 PC 의 다른 프로세스가 물어 얻지 못하게 · 결함 298). `#` 뒤는 서버로 가지 않고, 화면이 읽은 뒤 주소창에서 지운다
- 제출자는 폼에서 실행할 것 · 인자(한 줄에 하나) · (선택) 이미지 · 자원 · 분류를 넣고 "서명해 만들기" 를 누른다 → `<작업 파일 폴더>/<Job id>.manifest` 가
  생기고 내려받기 링크가 나온다. 그 파일을 운영자에게 건넨다. Job id 는 화면이 만들어 두고, 같은 id 로 다시 누르면 새로 만들지 않는다(두 번 도는 것을 막는다 · 결함 299)
- ★ **호스트 실행 작업(RESTRICTED)이 도는 PC 에서 제출 화면을 띄우지 않는다** — 그 작업은 소유자와 같은 권한이라 시드 파일과 시작 출력(토큰 주소)을
  읽을 수 있다. 제출은 작업을 돌리지 않는 기계나 컨테이너 전용(`--container-only true`) 노드에서 한다
- 운영자는 대시보드의 "작업 올리기" 에서 그 파일을 올린다 → `import-manifest` · `plan-job` 과 **같은 판정**(제출자 keyring 검증 · 자원 판정)으로
  QUEUED 가 된다. 반입만 되고 계획이 실패하면(맞는 노드 없음 등) 그 둘을 갈라 보여 준다. 같은 파일을 두 번 올려도 한 번만 반입된다(내용 해시가 멱등 키)
- 두 화면 다 127.0.0.1 전용 · Host 가 loopback 이 아니면 거부 · 만드는/올리는 요청은 시작할 때 만든 토큰 헤더가 있어야 받는다(다른 사이트 페이지가
  브라우저로 보내는 요청을 막는다). 서명 시드는 파일로만 받고 브라우저로 가지 않는다
- ★ 인자 안에 쉼표를 쓸 수 없다(지금 제출 형식의 한계 — 화면이 거부한다). Job id 는 영숫자 · `.` `_` `-` 만(파일 이름이 된다)
- ★ 네트워크로 제출을 받는 경로(Job ingress)는 없다 — 파일을 건네는 지금 모양을 화면으로 옮겼을 뿐이다

### 명령줄로

```bash
gputeer submit --job-id <id> --entrypoint <실행 파일 절대 경로> --args "<a,b,c>" \
  --submitter-device-id <submitter id> --submitter-seed <hex> \
  --issued-at-unix-ms <ms> --expires-at-unix-ms <ms> --out <manifest.pb> \
  --workload-class TRAINING --side-effect-class PURE --durability LOCAL \

gputeer import-manifest --manifest <manifest.pb> --submitter-keyring <keyring> --job-db <control.sqlite3> --idempotency-key <hex16>

```

### 작업이 지켜야 할 약속 — 다른 GPU 에서 이어가려면

```text
GPUTEER_CHECKPOINT_DIR   여기에 체크포인트를 `step-<N>` 폴더로 쓴다. 다 쓴 뒤에 그 이름으로 **바꾼다**
                         (예: `step-3.tmp` 에 쓰고 `step-3` 으로 rename). 폴더 안에는 파일만
GPUTEER_RESUME_DIR       이어서 시작할 때만 있다 — 마지막 체크포인트의 파일들이 검증된 채로 있다
```

체크포인트를 **쓰지 않는** 작업도 돈다 — 다만 노드를 잃으면 이어갈 것이 없어 FAILED(`NO_COMMITTED_CHECKPOINT`)로 끝난다.
★ **rename 약속은 강제되지 않는다**(결함 224). 게시기는 실행 중 같은 `step-N` 이 **두 번 연속 같은 모습**(이름 · 크기 · 수정 시각)일
  때만 올려 완화할 뿐이다 — `step-N` 에 바로 쓰다가 훑기 간격보다 오래 멈추는 작업은 **잘린 체크포인트가 올라가고 거기서 이어간다**
  (FAILED 가 아니다). 같은 크기로 덮어쓰는 작업은 수정 시각 해상도(파일시스템 · NAS)에 따라 바뀌는 중에도 올라갈 수 있다.
  `step-01` 처럼 앞자리 0 이 있는 이름도 받는다. 같은 번호의 폴더가 둘이면(`step-01` · `step-1`) 둘 다 올리지 않고
  `CHECKPOINT_STEP_NAME_CONFLICT` 를 남긴다(결함 242 · 255).
★ 작업이 끝날 때 서명까지 못 올린 step 은 `CHECKPOINT_PUBLISH_LOST` 로 찍힌다(약 15초 동안 여섯 번 해 본 뒤 — 결함 240 · 252). 그 step 에서는
  이어갈 수 없다 — 작업 폴더는 작업이 끝나면 지운다. 공유 저장소가 그보다 오래 끊기면 끝나기 직전의 체크포인트를 잃는다(실행 중 올린 것은 남는다).
★ `--shared-checkpoint-root` 자체가 링크(junction · symlink)면 그 **대상**이 공유 저장소다 — 코드는 그 아래(Job 폴더 · 체크포인트 폴더 ·
  서명 매니페스트)의 링크만 거부한다(결함 225 · 243 · 244).
★ PURE 작업만 이어받기를 전제한다 — 옛 노드가 살아서 계속 돌 수도 있다(막지 못한다).

## 8. 일이 틀어졌을 때

| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| `FAILOVER_REQUEUED ... resume_step=N` | 노드를 잃어 마지막 체크포인트에서 다시 큐로 | 기다린다. 다른 노드가 이어간다 |
| `FAILOVER_FAILED ... NO_COMMITTED_CHECKPOINT` | 노드를 잃었고 이어갈 체크포인트가 없다 | 다시 제출한다(재시도 정책은 0회다) |
| status 에서 노드가 `reservation_expired=yes` 인데 계속 예약됨 | 잃은 노드의 옛 예약 — 좀비가 돌 수 있어 자동으로 안 푼다 | 그 PC 를 보고 멈췄음을 확인한 뒤 `gputeer release-lost-node --control-db <db> --node <id> --operator-statement "<누가 무엇을 확인했나>"` |
| `RESERVATION_KEPT reason=...` | 보고는 저장했지만 예약은 안 풀었다(사유가 그 뒤에) | 사유대로 — `ARTIFACT_DURABILITY_*` 면 Manifest 를 LOCAL 로 |
| Agent 가 `OWNER_RECLAIMED` 로 안 붙는다 | 그 PC 주인이 Owner Panel 로 작업을 멈췄다(GPU 를 되찾음) | 주인이 다시 켤 때 `gputeer owner-resume --checkpoint-root <그 노드의 체크포인트 루트>` |
| `OWNER_PREEMPTED ... resume_step=N` | 주인이 멈춘 작업을 다른 노드로 옮기는 중(PAUSED -> RESUMED) | 기다린다 |
| `OWNER_PREEMPTED ... resume_step=-` | 멈춘 작업에 이어갈 체크포인트가 없다 — 다른 노드에서 **처음부터 다시** 돈다(FAILED 가 아니다 · 결함 232) | PURE 작업이면 기다린다. 앞부분을 다시 도는 게 문제면 작업이 체크포인트를 쓰게 한다 |

## 10. 알려진 한계 (신뢰망 범위)

```text
TLS 없음 · 악의적 참여자 방어 없음 · 과반 합의 없음(Coordinator 하나)
공유 저장소 하나를 복제본 하나로 본다(완화) · 체크포인트 파일을 통째로 메모리에 읽는다
옛 노드가 살아 계속 도는 것을 막지 못한다(PURE 전제) · GPU 한 장을 나눠 쓰지 않는다
Agent 의 리눅스 실행 경로는 CI(비-root)에서만 검증된다 — 실행 관문이 cgroup 위임을 요구한다
ACK 수신 확인이 유실되면(기록 직후 끊김) 그 작업은 실행되지 않고 Job 은 STAGING 에 남는다 — Lease 만료 뒤 큐로 돌아가 **처음부터** 돈다
  (결함 218 닫힘, 2026-09-25). 그 노드의 예약은 만료 표시만 남아 운영자가 release-lost-node 로 푼다(좀비 방지 원칙 그대로)
  ★ 2026-09-25 재검수 87 — 처음 수정은 첫 갱신을 기다리지 않고 워크로드를 띄워, 첫 갱신이 유실 · 거부되면 **실제로 도는** 작업이 STAGING 으로
    남아 한 번 더 돌 수 있었다(결함 268 · 269 · 271). 이제 실행 직전 갱신이 성공해야 띄운다 — 못 받으면 띄우지 않는다.
  ★ 남는 것 — Coordinator 가 시작을 기록한 뒤 그 갱신의 **결과 프레임만** 잃으면 안 돈 시도가 RUNNING 이다. 이어받기에서 체크포인트가 없으면
    FAILED 로 끝난다(두 번 돌지는 않는다 — 가용성 쪽 한계). 실행 중 Lease 를 잃었을 때 워크로드를 멈추지 않는 것(정책 미정)은 그대로다
같은 번호의 step 폴더가 둘이면(불완전한 쪽이 하나라도) 둘 다 올리지 않는다 — 완성된 쪽까지 잃을 수 있다(결함 265)
이어갈 지점 찾기는 공유 저장소 **목록** 오류만 "지점 없음" 으로 받는다. 목록이 일부만 읽히면 전체를 못 읽은 것으로 보고, 체크포인트 파일 읽기
  오류는 그 체크포인트를 건너뛴다(결함 263)
```
