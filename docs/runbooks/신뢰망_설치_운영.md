# 신뢰망 파티 — 설치 · 운영 런북

> **최종 갱신** 2026-09-23 · **성격** 실행 절차 · **범위** 서로 믿는 몇 사람이 GPU 를 나눠 쓰는 풀(v0.1)
> **짝** `docs/plans/2026-09-23_1816_신뢰망_100_남은_일.md`(무엇을 만들었나) · 시험 `crates/cli/tests/trusted_party_*.rs`(이 절차가 실제로 도는가)

★ **이 풀이 막지 않는 것부터 읽는다.** 참여자를 믿는다는 전제다 — 악의적인 작업이 호스트를 공격하는 것,
  작정하고 자원 상한을 빠져나가는 것, 통신 도청(TLS 없음)은 막지 않는다(`CLAUDE.md` §0.4). 모르는 사람의 PC 나
  작업을 붙이지 않는다.

## 0. 구성 한눈에

```text
한 대   Coordinator(풀 모드)      계속 떠 있다 — Agent 들의 인사 · Grant · 갱신 · 보고를 받는다
        scheduler-loop             큐를 돌며 빈 노드에 예약하고, 끊긴 노드의 작업을 되돌린다
        control DB                 SQLite 파일 하나(작업 · 예약 · Lease · 생존 관측 전부)
GPU 마다 agent-loop                되풀이해 붙는다 — 일이 있으면 실행 · 보고, 없으면 기다렸다 다시
모두    공유 저장소                 체크포인트를 옮기는 곳(NAS · 동기화 폴더 · 네트워크 드라이브).
                                   Coordinator 와 **모든** Agent 가 같은 경로 내용을 볼 수 있어야 한다
```

★ 이 문서의 `<...>` 는 자리 표시다. **실제 IP · 호스트 이름 · 계정 · 키 경로를 이 저장소의 파일에 적지 않는다**
  (전역 규칙). 실제 값은 각 기계의 서비스 설정 파일(저장소 밖)에만 둔다.

## 1. 키 만들기 — 기계마다 한 번

```bash
gputeer keygen --out <시드 파일>
```

`SEED_FILE` · `PUBLIC_KEY` 두 줄이 나온다. 시드 파일은 그 기계 밖으로 옮기지 않는다(유닉스에서는 0600 으로 만들어진다 ·
Windows 는 사용자 프로필 아래에 둔다). 이미 있는 파일은 덮지 않는다 — 잃으면 그 기계의 신원이 바뀐다.

| 누구 | 키 | 공개키를 누구에게 |
|---|---|---|
| Coordinator | `coordinator.seed` | 모든 Agent(`--peer-pubkey`) |
| 노드(GPU 하나마다) | `<node>.seed` | Coordinator(`--pool-agents`) · 모든 Agent(`--pool-peer-keys`) · scheduler(`--pool-agents`) |
| 제출자 | `<submitter>.seed` | Coordinator 의 제출자 keyring |

★ 비밀 시드는 **`--own-seed-file`** 로 준다. `--own-seed <hex>` 는 같은 기계의 다른 사용자가 프로세스 목록에서 볼 수 있다.

## 2. 노드 등록 — GPU 여러 장 기계는 GPU 마다 노드 하나

`import-inventory` 로 노드를 등록한다(형식은 `crates/cli/tests/trusted_party_pool.rs` 의 `bootstrap.json`).

```text
node_id       그 노드 Agent 의 --agent-device-id 와 **같게** 둔다(Grant 의 holder 가 이것이다)
GPU 두 장     "lab-gpu0" · "lab-gpu1" 두 노드로 등록하고, CPU · RAM · 디스크를 둘로 나눠 적는다
              Agent 도 둘 — 각각 --gpu-pin 0 · --gpu-pin 1 (작업에 CUDA_VISIBLE_DEVICES 로 그 GPU 만 보인다)
```

★★ `isolation_class` 는 **그 노드가 실제로 주는 격리**로 적는다(결함 267 · 2026-09-25). 호스트에서 작업을 돌리는 노드(컨테이너 런타임이
  없거나 `--container-only true` 가 아닌 노드)는 `RESTRICTED` 다 — 작업이 소유자와 같은 권한 · 파일시스템 · 네트워크에서 돈다(메모리 상한뿐).
  `CONTAINED` 는 `--container-runtime … --container-only true` 로 띄우는 노드에만 적는다. 거꾸로 적으면 `--minimum-isolation-class CONTAINED`
  작업이 호스트 실행 노드에 배치된다 — 스케줄러는 등록된 값을 믿는다.
★ GPU 를 **나눠** 쓰는 것(한 장에 작업 둘)은 하지 않는다 — 노드 단위 배타 배정이다. `--gpu-pin` 은 보이게 하는 것이지
  강제가 아니다(작업이 다른 GPU 를 열면 막지 못한다).
★ `--gpu-pin` 에는 장치 번호를 **하나만** 준다(결함 439 · 재검수 115). Grant 는 어느 GPU 를 배정했는지 싣지 않아서, 한 노드에 여러 장을 고정하면
  한 장만 예약된 작업에 고정한 GPU 전부가 넘어간다. Agent · node-doctor · 설치기가 여러 장을 거부한다 — 두 장이면 노드 둘이다

## 3. Coordinator 띄우기

```bash
gputeer coordinator-stub --pool-mode true \
  --pool-agents "<node1>=<pubkey1>;<node2>=<pubkey2>" \
  --listen <바인드 주소>:<포트> --own-seed-file <coordinator.seed> \
  --coordinator-device-id <coordinator id> \
  --grant-from-control-db <control.sqlite3> --lease-db <control.sqlite3> --liveness-db <control.sqlite3> \
  --submitter-keyring <submitters.keyring> \
  --accept-report-sessions true --release-on-exit-report true \
  --shared-checkpoint-root <공유 저장소> --replay-db <replay.sqlite3> \
  --max-connections 0 --accept-timeout-ms 0
```

- `--lease-db` · `--liveness-db` 는 control DB 와 **같은 파일**이어야 한다(아니면 시작을 거부한다 — `POOL_LEASE_DB_MISMATCH` ·
  `POOL_LIVENESS_DB_MISMATCH`). 스케줄러가 거기서 Hello 관측을 읽는다
- `--pool-agents` 의 공개키는 노드마다 달라야 한다(`POOL_AGENTS_DUPLICATE_KEY`)
- `--release-on-exit-report` — 종료 보고가 오면 같은 커밋에서 예약을 푼다. 완료 작업은 Manifest 가 `--durability LOCAL` 일 때만
  푼다(이 풀은 복제를 하지 않는다 — `RESERVATION_KEPT reason=ARTIFACT_DURABILITY_...` 가 찍히면 그 이유다)
- `--replay-db` — 재시작해도 옛 메시지(인사 · ACK · 갱신)를 다시 받지 않는다(풀 모드 전용)
- ACK 를 기록한 뒤 **서명된 수신 확인**을 보낸다 — Agent 가 `--require-ack-receipt true` 면 그것을 받아야 실행한다
- 순차 리스너다 — 신뢰망의 몇 대에는 충분하다. 수십 대는 범위 밖

## 4. 스케줄러 띄우기

```bash
gputeer scheduler-loop --interval-ms 1000 --max-ticks 0 \
  --control-db <control.sqlite3> --submitter-keyring <submitters.keyring> --submitter-member <owner id> \
  --max-snapshot-age-ms 86400000 --best-fit-axes vram,gpu_count,cpu,ram,workspace \
  --coordinator-id <coordinator id> --coordinator-term 1 \
  --lease-ttl-ms 120000 --lease-renew-after-ms 40000 --lease-max-total-duration-seconds 86400 \
  --silent-after-ms 60000 \
  --failover-grace-ms 30000 --shared-checkpoint-root <공유 저장소> \
  --pool-agents "<node1>=<pubkey1>;<node2>=<pubkey2>" --pool-mode true
```

- `--silent-after-ms` — 이만큼 인사가 없는 노드에는 새 일을 주지 않는다(주지 않으면 이 축을 안 본다)
- ★ `--max-snapshot-age-ms` 는 **등록 정보(import-inventory)를 넣은 시각**부터 잰다 — 인사(Hello)는 그 시각을 새로 하지 않는다. 그대로 두면
  등록 하루 뒤부터 어느 노드에도 배치하지 않는다(결함 301 · `plan_job.rs` 시험으로 확인). 운영자 기계에서 `refresh-inventory`(§9a)를
  이 값보다 자주 돌린다(예 6시간마다). ★ main 123802d 부터 GPU 노드는 Agent `--attest-gpus true`(§5)로 닫힌다 — 인사의 NVML 관측이 가입
  파일과 맞으면 스케줄러가 그 시각까지 신선하다고 본다. `refresh-inventory` 는 **관측을 켜지 않은 노드**(CPU 전용 · 관측 전 판 Agent)에만 쓴다.
  ★ 결함 440 (재검수 115) — 관측이 선언과 **어긋난** 노드는 `refresh-inventory` · 재선언으로 되살아나지 않는다(전에는 refresh 가 틀린 선언을 계속
  신선하게 만들었다). 선언을 고쳐 다시 받고(admit-node), 관측을 켠 Agent 가 **불일치보다 새** 맞는 관측을 싣고 인사해야 풀린다. 관측은 처리 순서가
  아니라 관측 시각(그 노드의 시계) 순서로 판정한다 — 늦게 처리된 옛 관측은 더 새 판정을 뒤집지 않는다(결함 449). GPU 를 빼고 CPU 전용으로 다시
  선언하면(가입 파일의 gpus 가 비었다) 불일치는 접히지 않는다(450). ★ 관측을 끄면 불일치는 풀리지 않는다 — 지우는 운영자 명령은 아직 없다
- `--pool-mode true` — 풀 스케줄러임을 **명시**한다(control DB 에 풀 표식을 적는다 · 풀 Coordinator 도 기동 때 적는다). 풀이면 Manifest 가
  `LOCAL` 이 아닌 작업을 **배치 전에** 내린다 — QUEUED 는 FAILED(PERMANENTLY_INFEASIBLE, `DURABILITY_*_NOT_SUPPORTED_BY_POOL`), PAUSED 는
  건너뛴다(`TICK_SKIPPED`). 이 풀은 복제하지 않아서, 배치하면 끝난 뒤 그 노드가 묶인다(결함 217 · 235 · 236 · 249). `--pool-agents` 는 이어받기용 키 목록이다
- ★ 건너뛴 PAUSED 작업은 **영원히 PAUSED 로 남는다** — Job 을 취소하는 명령이 아직 없다(알려진 공백 · 결함 250). 이런 작업은 풀 표식 전에
  배치된 경우에만 생긴다
- `--failover-grace-ms` — 실행 중인 작업의 Lease 가 만료되고 이만큼 지나면 그 노드를 잃은 것으로 본다. 이어갈 체크포인트가 있으면 큐로
  되돌리고, **실행 중(RUNNING)인데 체크포인트가 없으면 FAILED** 로 끝낸다(재시도 정책 0회 · 결함 259).
  짧게 잡으면 잠깐 끊긴 노드의 작업을 뺏는다
- Lease TTL 은 Agent 의 `--renew-during-execution-ms` 보다 **충분히** 길게(갱신 두세 번이 들어갈 만큼)

## 5. Agent 띄우기 — GPU 마다 하나

먼저 **점검한다**(2026-09-25) — 아래 Agent 명령에 줄 값을 그대로 준다. FAIL 이 하나라도 있으면 종료 코드가 0 이 아니다.

```bash
gputeer node-doctor --seed-file <node.seed> --node-dir <node 전용 폴더> --connect <coordinator 주소>:<포트>   --shared-checkpoint-root <공유 저장소> --owner-panel-port <로컬 포트> [--gpu-pin <GPU 번호>]   [--container-runtime <podman|docker> --container-runtime-kind podman|docker]
```

```text
seed                    시드를 읽고 공개키를 찍는다(유닉스에서 다른 사용자가 읽을 수 있으면 WARN)
node_dir                폴더를 만들고 쓸 수 있는지(임시 파일을 쓰고 곧 지운다)
coordinator             TCP 로 붙는지만 본다 — 서명 교환은 하지 않는다
shared_checkpoint_root  있고 쓸 수 있는지(루트 자체가 링크면 WARN)
owner_panel_port        127.0.0.1 의 그 포트가 비었는지
gpu                     NVML 로 보이는지 · --gpu-pin 의 GPU 가 있는지(NVML 을 못 열면 "0개" 가 아니라 "모른다" 다) · 핀이 **하나**인지(결함 439)
container_*             런타임이 도는지 · rootless 인지(rootful 이면 WARN) · GPU 를 넘길 설정이 보이는지(보였다까지다 — 실행 확인 아님)
```

```bash
gputeer agent-loop --interval-ms 5000 --max-rounds 0 -- \
  --connect <coordinator 주소>:<포트> --own-seed-file <node.seed> \
  --peer-pubkey <coordinator pubkey> --coordinator-device-id <coordinator id> --agent-device-id <node id> \
  --fence-db <node 전용 폴더>/fence.sqlite3 --checkpoint-root <node 전용 폴더>/checkpoints \
  --submitter-pubkey <submitter pubkey> \
  --i-understand-this-executes-untrusted-code true \
  --report-over-session true --renew-during-execution-ms 30000 --max-reconnect-attempts 1 \
  --require-ack-receipt true [--attest-gpus true] \
  --shared-checkpoint-root <공유 저장소> --pool-peer-keys "<node1>=<pubkey1>;<node2>=<pubkey2>" \
  --owner-panel-port <로컬 포트> [--gpu-pin <GPU 번호>] [--workload-commit-limit-bytes <바이트>]
```

- Owner Panel 은 `127.0.0.1` 에만 열린다 — 그 PC 의 주인만 본다(§0.1)
- 노드마다 `--fence-db` · `--checkpoint-root` 를 **따로** 둔다. 같은 루트를 **동시에** 쓰면 거부된다(잠금). 순차로 바꿔 쓰는 것은 막지 않는다 —
  그 경우 남의 보고는 격리하지 않고 그대로 둔다(`ATTEMPT_REPORT_OUTBOX_FOREIGN` · 결함 264)
- ★ 풀에서는 `--require-ack-receipt true` 와 `--renew-during-execution-ms`(예 30초 — Lease TTL 보다 충분히 짧게)가 **필수**다.
  수신 확인을 끄면 ACK 가 기록되기 전에 끊겼을 때 같은 시도가 두 번 돌 수 있다. 갱신을 끄면 시작하지 않는다(`POOL_AGENT_NEEDS_RENEW`) —
  Coordinator 는 **실행 직전 갱신**을 "실행을 시작한다" 로 보고 그때 Job 을 RUNNING 으로 옮긴다. Agent 는 그 갱신이 **성공해야** 워크로드를
  띄운다 — 못 받으면 `PROCESS_START_NOT_CONFIRMED` 로 시작하지 않는다(결함 218 · 268). 수신 확인을 요구하는 Agent 는 갱신을 켜야 시작하고(270), 실행 직전 갱신이 성공해야 띄우며, 확인받은 Lease 가 5초도 안 남았으면 띄우지
  않는다(`LEASE_TOO_SHORT_AFTER_CONFIRM` · 289 — 이때 Job 은 RUNNING 으로 남아 체크포인트가 없으면 FAILED 가 된다: 두 번 도는 대신 가용성을 잃는 쪽).
  ★ **풀에서는 수신 확인이 필수다** — 이 관문들은 수신 확인 Agent 에만 선다(풀 밖 lane 은 ACK 가 Job 을 옮겨 필요 없다 · 293). 수신 확인을 끈 채
    풀에 붙이면 막지 못한다 — Agent 는 상대가 풀인지 모른다. **설정 오류**다(계약 변경 없이는 막지 못한다)
  ★★ 2026-09-25 (결함 288 닫힘 · Grant v4) — 이제 풀 Coordinator 의 Grant 는 **풀 신호**(`pool_mode`)를 서명해 싣는다. 수신 확인이나 실행 중
    갱신을 끈 Agent 는 그 Grant 를 ACK 전에 거부하고 멈춘다(`POOL_GRANT_NEEDS_ACK_RECEIPT` · `POOL_GRANT_NEEDS_RENEW`). 위의 "막지 못한다" 는 그 전의
    기록이다. ★ **업그레이드 순서는 하나다 — ① Agent(관측 끔) → ② Coordinator → ③ Agent 관측 켬**(결함 444). 구버전 Agent 는 풀 Grant(v4)를
    `SCHEMA_TOO_NEW` 로 거부하고(그래서 Agent 먼저), 구버전 Coordinator 는 관측을 실은 인사(Hello v2)를 거부한다(그래서 관측은 마지막).
    node-doctor 는 TCP 만 보므로 이 순서를 대신 확인해 주지 않는다.
    ★ 운영 조건(결함 451) — ③ 전까지는 관측이 없으므로 스케줄러는 **등록된 선언을 믿는다**(관측 관문 이전과 같다). 선언이 실제 GPU 와 다를 수
    있으면 ②~③ 사이 스케줄러(`scheduler-loop`)를 멈추거나, 선언을 먼저 실제에 맞춰 다시 받는다
    풀 표식이 있는 DB(제어 · Lease · 생존 · 이웃 신고 · replay · Hello replay 어느 것이든)는 `--pool-mode true` 없이 띄우면 시작하지 않는다(`POOL_DB_WITHOUT_POOL_MODE` · 결함 410 · 412 · 414). DB 경로는 파일 경로로만 준다 — SQLite URI(`file:…`)는 받지 않는다(`SQLITE_URI_PATH` · 415).
    ★ 운영 조건(결함 413) — **비풀 Coordinator 가 쓰던 DB 를 풀로 바꿀 때는 그 Coordinator 를 먼저 멈추고 진행 중 시도를 끝낸 뒤** 바꾼다. 풀 표식을
    처음 적는 순간 이미 도는 비풀 Coordinator 는 그 사이 풀 신호 없는 Grant 한 건을 낼 수 있다(코드로 막지 않았다)
- ★ 2026-09-25 (결함 301) — `--attest-gpus true` 면 Agent 가 일을 받으러 올 때마다(FRESH Hello) NVML 로 읽은 GPU 목록을 서명해 싣는다. 풀
  Coordinator 는 등록된 가입 파일의 GPU(모델 · VRAM — `gpu_id` 는 번호여도 된다. `GPU-…` UUID 로 적었으면 그 GPU 여야 한다)와 **맞을 때만** 그 선언 판에 확인 기록을 남기고, 스케줄러는 그

- ★ 운영 조건(결함 294) — Coordinator `--renew-extension-ms`(기본 60초)는 Agent `--renew-during-execution-ms` 의 **두 배 + 노드 간 시계 차이**
  보다 길게 둔다. Agent 는 Coordinator 가 정한 만료 시각을 **자기 시계로** 재서 다음 갱신 시각을 정한다 — 모든 기계에 시계 동기화(NTP)를 켠다
- ★ 운영 조건(결함 431 · 433) — `scheduler-tick` · `scheduler-loop` · `plan-job` 을 돌리는 기계는 **실행 중 벽시계를 뒤로 되돌리지 않는다.**
  큐 순서(FIFO)와 큐 시한은 벽시계로 적힌다 — 시계가 한 번에 뒤로 가면 먼저 들어온 작업이 뒤로 밀린다. 시작하기 **전에** 시계를 맞추고, NTP 는
  한 번에 뛰지 않고 천천히 맞추는 방식으로 둔다(Windows 는 첫 동기화가 끝난 뒤 띄운다). 노드 간 시계 차이(결함 294)와는 다른 조건이다
- 실행 직전 Lease 남은 시간이 "실행 중 갱신 주기 + 5초" 보다 짧으면 시작하지 않는다(`LEASE_TOO_SHORT_TO_START` · 결함 246). 그 시도는 한 번도
  안 돌았으므로 Job 이 STAGING 에 남고, Lease 만료 뒤 **큐로 돌아가 처음부터** 돈다(결함 256 닫힘)

  ```text
                    해제하면 다음 기동이 남은 컨테이너를 멈추고 로그를 건진 뒤 지운다(결함 489 · 492). 민감 데이터면 해제 전에 소유자가 직접 지운다(§0.5)
  ```
  ★ **표식이 닿지 않는 곳**(결함 497 · 498 뒤에 남는 것) — (1) 판정이 난 뒤 표식 파일을 **만들기 전에** Agent 나 기계가 죽으면 표식이 없다.
    (2) 표식을 못 써 agent-loop 가 멈춘 뒤, 서비스 관리자가 다시 띄울 때 폴더가 **다시 쓸 수 있게 돼 있으면** 기동 관문을 지난다.
    두 경우 모두 작업 폴더는 남아 있고(계약상 출력 · 체크포인트는 마운트된 그 폴더에 있다), 다음 기동의 남은 컨테이너 정리는 **멈춤을 확인하고 로그를
    건진 뒤에만** 지운다(결함 492). 다만 사람이 보기 전에 컨테이너가 치워질 수 있고, 작업이 마운트 밖(컨테이너 안)에 쓴 것은 그때 사라진다.
  ★ **이것이 막지 못하는 것** — 종료를 모르는 컨테이너가 이 노드에 남아 있는 동안 Lease 가 끝나면 Coordinator 가 같은 작업을 다른 노드에 줄 수 있다
  (두 벌 실행). 이 브랜치는 그것을 막는다고 **주장하지 않는다**. 런타임을 거치지 않는 정지 · 회차 밖의 상시 소유자 화면 · 실행 중 로그 받기와 함께
  별도 설계 과제다: `docs/plans/2026-09-27_2306_컨테이너_런타임_불확실_상태_설계.md`
  node-doctor 의 GPU 점검도 같은 경우 점검 폴더를 지우지 않고 컨테이너 이름과 지우는 명령을 FAIL 에 적는다(476). 이때 종료 보고는 가지 않는다: 운영자가 `<런타임> ps -a --filter label=gputeer.owner=…` 로 확인해 지우고 폴더를 치운다.
  ★ 그 사이 Lease 가 끝나고 `--failover-grace-ms` 가 지나면 Coordinator 가 그 작업을 다른 노드로 옮길 수 있다 — 두 벌이 돌 수 있다(네트워크가 끊긴
  노드와 같은 한계 · fence 로 산출물 확정만 막는다)
- 컨테이너 이름은 시도에서만 만든다. 라벨은 둘이다 — `gputeer.node=<노드 id>`(사람이 알아보는 용도)와 `gputeer.owner=<노드 id>.<루트 해시>`.
  Agent 는 회차를 시작할 때 체크포인트 루트를 **잠근 뒤** `gputeer.owner` 라벨로 남은 컨테이너를 모두 지운다 — 죽은 회차가 남긴 컨테이너가 GPU 를
  물고 도는 것을 치운다(결함 290 · 291 · 295). 같은 루트를 잠근 Agent 는 하나뿐이라 잘못 겹쳐 뜬 두 번째 Agent 가 정상 작업을 지우지 않는다.
  목록을 못 읽으면 시작하지 않는다(`CONTAINER_LEFTOVERS_UNKNOWN`)
- ★ 업그레이드(결함 296) — Agent 를 새 판으로 바꿀 때는 **먼저 멈추고**, 옛 판이 남긴 컨테이너를 사람이 지운다:
  `<런타임> ps -a --filter label=gputeer.managed=1` 로 보고 `<런타임> rm -f -v <id>`. 옛 판의 라벨이 새 판의 정리 열쇠(`gputeer.owner`)와 다를 수
  있다 — 이 판(2026-09-25) 전의 컨테이너 판은 배포된 적이 없다
- ★ 체크포인트를 공유 저장소로 올릴 때 파일을 **링크를 따라가지 않고** 연다(리눅스 openat2 · Windows reparse 거부 — 결함 287). 작업이
  step 폴더나 파일을 호스트 파일 링크로 바꿔치기해도 그 내용이 올라가지 않는다
- ★ `--container-gpu` — 2026-09-25 x600 WSL2 · docker 29.7.2 · Toolkit 1.19.0(CDI 사양만 만듦)에서 **`cdi-all` 로만** GPU 가 컨테이너 안에서
  열렸다(아래 fork 줄 · 결함 303). docker 의 `--gpus`(기본값)와 번호별 CDI(`nvidia.com/gpu=0`)는 그 기계에서 거부됐다. 노드마다 되는 모양이 다르니
  `node-doctor --container-gpu-probe-image` 로 먼저 확인하고 `--container-gpu-request` 를 고른다. 네이티브 리눅스 · podman 에서는 아직 재지 않았다.
  켜면 그 GPU 드라이버 표면이 컨테이너에 열린다
- ★ 컨테이너는 호스트 커널을 같이 쓴다(S3). 커널 · 드라이버 취약점까지 막지는 못한다
- ★ 무엇을 실제로 쟀는지 — **2026-09-25 CI 실행 36103061402(GitHub Actions ubuntu 러너 · 비-root 사용자)에서 docker 와 rootless podman
  둘 다** `crates/agent/tests/container_isolation_real.rs` 5개가 실제로 돌았다(`ENVIRONMENT-BLOCKED` 없음 — 정보용 단계에 `CONTAINER_ISOLATION_MEASURED`
  가 두 런타임 × 5 로 찍혔다):
  ```text
  읽기 전용 루트 · 붙인 폴더 밖 쓰기 불가 · 체크포인트 폴더 쓰기   docker O   podman O
  네트워크 인터페이스 = lo 뿐                                       docker O   podman O
  CapEff 0 · NoNewPrivs 1                                           docker O   podman O
  64MiB 상한에서 200MB 잡기 → 작업이 죽는다(종료 99)                docker O   podman O   ★ OOMKilled 표시는 docker true · podman false
  소유자 정지 → 137 로 끝남                                         docker O(710ms) podman O(201ms)
  ```
  ★ 한 번 · 한 환경(CI 러너)이다. GPU 를 넘기는 경로(`--container-gpu`)는 여기서 재지 않았다. 개발 기계(Windows)에서는 가짜 런타임으로 명령 순서 ·
    정지 · 거부만 잰다
- podman 에 `--memory-swap` = `--memory` 를 준다(스왑 0) — podman 문서는 "더 커야 한다" 고 적지만 위 CI 에서 podman 이 받아들였고 상한을 넘긴
  작업이 죽었다(결함 275 — 그 러너의 podman 판에서). ★ OOM 판정을 `OOMKilled` 표시에 기대지 않는다 — podman 은 컨테이너 안의 한 프로세스가 죽은
  경우 false 로 보고했다. 작업의 종료 코드가 실패를 알린다
- ★ (2026-09-25 fork) GPU 를 넘기는 인자 — podman 은 고정한 장치마다 `--device=nvidia.com/gpu=<n>` 을 따로, docker 는
  `--gpus "device=<n,m>"`(값 전체를 큰따옴표로 — docker 는 이 값을 CSV 로 읽어 `device=0,1` 을 두 필드로 쪼갠다). 전에는 여러 장 고정에서
  두 런타임 다 받지 않는 모양이었다(결함 300 · 코드 읽기 · 여러 장은 실측 전). ★ 2026-09-26 부터 핀은 하나만 받는다(결함 439) — 여러 장 모양은 쓰이지 않는다
- ★ (2026-09-25 fork) `node-doctor … --gpu-pin <n> --container-runtime … --container-gpu-probe-image <이미지>` — Agent 와 **같은 create 인자**
  (위 격리 옵션 전부 + GPU 인자 + 체크포인트 폴더)로 컨테이너를 띄워 `nvidia-smi -L` 을 돌린다(`container_gpu_probe`). 고정한 수만큼 GPU 가
  보이면 OK, 못 열면 FAIL, **더 많이 보여도 FAIL**(고정하지 않은 GPU 가 작업에 새어 나간다 — 결함 441 · 전에는 WARN 이라 설치기가 등록을 이어 갔다). 이미지를 받아 오는 일이라 이미지를 줄 때만 한다. 컨테이너 이름 · 정리 열쇠가 Agent 와 겹치지 않는다
- ★ (2026-09-25 fork) x600(WSL2 · docker 29.7.2)에서 쟀다 — `scripts/container_gpu_probe/`(`run_on_x600.cmd` · `probe.sh`).
  **NVIDIA Container Toolkit 이 없어** `--gpus` 가 `failed to discover GPU vendor from CDI` 로 거부됐다(`ENVIRONMENT-BLOCKED` — PASS 아님).
  docker 29 는 `--gpus` 를 **CDI 사양**(`/etc/cdi/nvidia.yaml` — `nvidia-ctk cdi generate`)으로 푼다. nvidia 런타임 등록만으로는 모자랄 수 있다
  (결함 302 · 예상). GPU 를 넘기는 노드는 Toolkit 설치와 CDI 사양 생성이 먼저다. 근거 `docs/evidence/_raw/컨테이너_GPU_실측_x600_2026-09-25.txt`.
  → 사용자 허가로 Toolkit 1.19.0 을 설치하고 CDI 사양만 만든 뒤(daemon.json · docker 재시작 없음) 다시 쟀다: `--gpus` 는 모든 모양이
  `AMD CDI spec not found`, `nvidia.com/gpu=0` 은 `unresolvable`(WSL 의 CDI 사양은 `nvidia.com/gpu=all` 하나다), **`--device=nvidia.com/gpu=all`
  만 Agent 격리 옵션 그대로 컨테이너 안에서 RTX 4070 SUPER 를 열었다.** 그래서 GPU 를 청하는 방식을 고른다(결함 303):
  ```text
  --container-gpu-request gpus     docker --gpus "device=<n>"        (docker 기본 — 전과 같다)
                          cdi      --device=nvidia.com/gpu=<n>       (podman 기본 · 번호별 CDI 가 있는 기계)
                          cdi-all  --device=nvidia.com/gpu=all       (WSL2 — --gpu-pin 0 이고 NVML 이 GPU 한 장을 볼 때만 Agent 가 받는다.
                                                                     시작 · Manifest 해석 · 이미지를 받은 뒤 create 직전 · create 직후에 다시 본다 ·
                                                                     관측은 GPU 전부를 싣는다 — 결함 454 · 462 · 468. ★ create 한 번 동안
                                                                     GPU · CDI 장치가 바뀌는 것은 닫지 못한다 — 확인 네 번이지 격리 보장이 아니다.
                                                                     GPU 를 꽂고 빼는 기계에서는 cdi-all 을 쓰지 않는다)
  ```
  ★ `cdi-all` 로 **우리 Agent 바이너리가** 컨테이너 GPU 를 연 것은 아직 재지 못했다(x600 E: 공간 부족으로 새 판 빌드가 멈췄다) — 위 확인은 같은
    인자를 docker 명령으로 준 것이다

컨테이너 Job 내기 — `gputeer submit` 에 `--image-ref <참조> --image-sha256 <64자리 16진수>` 를 더한다. 이미지의 digest 는
`docker image inspect --format '{{index .RepoDigests 0}}' <이미지>` 로 읽는다. `--entrypoint` 는 **컨테이너 안의** 실행 파일이다.

## 6. 작업 내기

### 화면으로(2026-09-25)

```bash
# 제출자 기계 — 자기 키로 서명한 작업 파일을 만든다
gputeer submit-ui --submitter-device-id <submitter id> --submitter-seed-file <submitter.seed> --out-dir <작업 파일 폴더> --port <로컬 포트>
# Coordinator 기계 — 운영자가 받은 파일을 올려 반입 · 계획까지
gputeer dashboard --control-db <control.sqlite3> --port <로컬 포트> --allow-import true \
  --submitter-keyring <keyring> --submitter-member <owner id> --max-snapshot-age-ms 86400000
```

- 시작할 때 찍히는 **토큰이 든 주소**(`SUBMIT_UI_OPEN http://127.0.0.1:<포트>/#token=…` · 대시보드는 `DASHBOARD_IMPORT_ENABLED open=…`)로 연다 —
  토큰은 HTTP 로 주지 않는다(같은 PC 의 다른 프로세스가 물어 얻지 못하게 · 결함 298). `#` 뒤는 서버로 가지 않고, 화면이 읽은 뒤 주소창에서 지운다
- 제출자는 폼에서 실행할 것 · 인자(한 줄에 하나) · (선택) 이미지 · 자원 · 분류를 넣고 "서명해 만들기" 를 누른다 → `<작업 파일 폴더>/<Job id>.manifest` 가
  생기고 내려받기 링크가 나온다. 그 파일을 운영자에게 건넨다. Job id 는 화면이 만들어 두고, 같은 id 로 다시 누르면 새로 만들지 않는다(두 번 도는 것을 막는다 · 결함 299)
- ★ **호스트 실행 작업(RESTRICTED)이 도는 PC 에서 제출 화면을 띄우지 않는다** — 그 작업은 소유자와 같은 권한이라 시드 파일과 시작 출력(토큰 주소)을
  읽을 수 있다. 제출은 작업을 돌리지 않는 기계나 컨테이너 전용(`--container-only true`) 노드에서 한다
- 운영자는 대시보드의 "작업 올리기" 에서 그 파일을 올린다 → `import-manifest` · `plan-job` 과 **같은 판정**(제출자 keyring 검증 · 자원 판정)으로
  QUEUED 가 된다. 반입만 되고 계획이 실패하면(맞는 노드 없음 등) 그 둘을 갈라 보여 준다. 같은 파일을 두 번 올려도 한 번만 반입된다(내용 해시가 멱등 키)
- 두 화면 다 127.0.0.1 전용 · Host 가 loopback 이 아니면 거부 · 만드는/올리는 요청은 시작할 때 만든 토큰 헤더가 있어야 받는다(다른 사이트 페이지가
  브라우저로 보내는 요청을 막는다). 서명 시드는 파일로만 받고 브라우저로 가지 않는다
- ★ 인자 안에 쉼표를 쓸 수 없다(지금 제출 형식의 한계 — 화면이 거부한다). Job id 는 영숫자 · `.` `_` `-` 만(파일 이름이 된다)
- ★ 네트워크로 제출을 받는 경로(Job ingress)는 없다 — 파일을 건네는 지금 모양을 화면으로 옮겼을 뿐이다

### 명령줄로

```bash
gputeer submit --job-id <id> --entrypoint <실행 파일 절대 경로> --args "<a,b,c>" \
  --submitter-device-id <submitter id> --submitter-seed <hex> \
  --issued-at-unix-ms <ms> --expires-at-unix-ms <ms> --out <manifest.pb> \
  --workload-class TRAINING --side-effect-class PURE --durability LOCAL \
  --dataset-sensitivity INTERNAL --minimum-security-tier S2 --minimum-isolation-class CONTAINED \
  --minimum-key-protection K1 --gpu-count 1 --gpu-min-vram-bytes <bytes> \
  --cpu-cores <n> --ram-bytes <bytes> --workspace-bytes <bytes>
gputeer import-manifest --manifest <manifest.pb> --submitter-keyring <keyring> --job-db <control.sqlite3> --idempotency-key <hex16>
gputeer plan-job --job-id <id> --control-db <control.sqlite3> --submitter-keyring <keyring> --submitter-member <owner id> --max-snapshot-age-ms 86400000
```

### 작업이 지켜야 할 약속 — 다른 GPU 에서 이어가려면

```text
GPUTEER_CHECKPOINT_DIR   여기에 체크포인트를 `step-<N>` 폴더로 쓴다. 다 쓴 뒤에 그 이름으로 **바꾼다**
                         (예: `step-3.tmp` 에 쓰고 `step-3` 으로 rename). 폴더 안에는 파일만
GPUTEER_RESUME_DIR       이어서 시작할 때만 있다 — 마지막 체크포인트의 파일들이 검증된 채로 있다
```

체크포인트를 **쓰지 않는** 작업도 돈다 — 다만 노드를 잃으면 이어갈 것이 없어 FAILED(`NO_COMMITTED_CHECKPOINT`)로 끝난다.
★ **rename 약속은 강제되지 않는다**(결함 224). 게시기는 실행 중 같은 `step-N` 이 **두 번 연속 같은 모습**(이름 · 크기 · 수정 시각)일
  때만 올려 완화할 뿐이다 — `step-N` 에 바로 쓰다가 훑기 간격보다 오래 멈추는 작업은 **잘린 체크포인트가 올라가고 거기서 이어간다**
  (FAILED 가 아니다). 같은 크기로 덮어쓰는 작업은 수정 시각 해상도(파일시스템 · NAS)에 따라 바뀌는 중에도 올라갈 수 있다.
  `step-01` 처럼 앞자리 0 이 있는 이름도 받는다. 같은 번호의 폴더가 둘이면(`step-01` · `step-1`) 둘 다 올리지 않고
  `CHECKPOINT_STEP_NAME_CONFLICT` 를 남긴다(결함 242 · 255).
★ 작업이 끝날 때 서명까지 못 올린 step 은 `CHECKPOINT_PUBLISH_LOST` 로 찍힌다(약 15초 동안 여섯 번 해 본 뒤 — 결함 240 · 252). 그 step 에서는
  이어갈 수 없다 — 작업 폴더는 작업이 끝나면 지운다. 공유 저장소가 그보다 오래 끊기면 끝나기 직전의 체크포인트를 잃는다(실행 중 올린 것은 남는다).
★ `--shared-checkpoint-root` 자체가 링크(junction · symlink)면 그 **대상**이 공유 저장소다 — 코드는 그 아래(Job 폴더 · 체크포인트 폴더 ·
  서명 매니페스트)의 링크만 거부한다(결함 225 · 243 · 244).
★ PURE 작업만 이어받기를 전제한다 — 옛 노드가 살아서 계속 돌 수도 있다(막지 못한다).

## 8. 일이 틀어졌을 때

| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| `FAILOVER_REQUEUED ... resume_step=N` | 노드를 잃어 마지막 체크포인트에서 다시 큐로 | 기다린다. 다른 노드가 이어간다 |
| `FAILOVER_FAILED ... NO_COMMITTED_CHECKPOINT` | 노드를 잃었고 이어갈 체크포인트가 없다 | 다시 제출한다(재시도 정책은 0회다) |
| status 에서 노드가 `reservation_expired=yes` 인데 계속 예약됨 | 잃은 노드의 옛 예약 — 좀비가 돌 수 있어 자동으로 안 푼다 | 그 PC 를 보고 멈췄음을 확인한 뒤 `gputeer release-lost-node --control-db <db> --node <id> --operator-statement "<누가 무엇을 확인했나>"` |
| `RESERVATION_KEPT reason=...` | 보고는 저장했지만 예약은 안 풀었다(사유가 그 뒤에) | 사유대로 — `ARTIFACT_DURABILITY_*` 면 Manifest 를 LOCAL 로 |
| Agent 가 `OWNER_RECLAIMED` 로 안 붙는다 | 그 PC 주인이 Owner Panel 로 작업을 멈췄다(GPU 를 되찾음) | 주인이 다시 켤 때 `gputeer owner-resume --checkpoint-root <그 노드의 체크포인트 루트>` |
| `OWNER_PREEMPTED ... resume_step=N` | 주인이 멈춘 작업을 다른 노드로 옮기는 중(PAUSED -> RESUMED) | 기다린다 |
| `OWNER_PREEMPTED ... resume_step=-` | 멈춘 작업에 이어갈 체크포인트가 없다 — 다른 노드에서 **처음부터 다시** 돈다(FAILED 가 아니다 · 결함 232) | PURE 작업이면 기다린다. 앞부분을 다시 도는 게 문제면 작업이 체크포인트를 쓰게 한다 |

```powershell
  -NodeId <노드 id> -OwnerMemberId <내 id> -GpuPin 0 -CpuCores <내놓을 코어> -RamGiB <내놓을 GiB> -WorkspaceGiB <내놓을 GiB> `
  [-ContainerRuntime <docker|podman 경로> -ContainerRuntimeKind docker|podman -ContainerGpu [-GpuProbeImage <이미지>]] [-Register]
```

- 등록 값은 **실제 격리로** 적는다 — 컨테이너 런타임을 주면 `S3 · CONTAINED`, 아니면 `S0 · RESTRICTED`. 키 보호는 기본 `K0`(시드가 평문
  파일이다). 그래서 §6 예시처럼 `--minimum-security-tier S2 · --minimum-key-protection K1` 로 낸 작업은 이 노드들에 배치되지 않는다 — 작업의
  최소 요구를 노드가 **실제로 주는 것**에 맞춘다(노드 등급을 올려 적지 않는다)
- 자원 수치는 **소유자가 내놓는 양**이다(기계 전체가 아니다). 기본값을 두지 않았다 — 지어내지 않는다
- ★ 설치 폴더(`-ConfigDir` · `--config-dir` · 노드 폴더)는 **전용 폴더**만 받는다(결함 438 · 442 · 446 · 448) — 경로를 **실제 경로**로 풀어
  (Linux `cd -P` · Windows 최종 경로 — 8.3 이름 · junction 이 풀린다) 시스템 경로 · 드라이브 루트를 거부하고, 대상 자체가 링크 · junction 이면
  거부한다. 이미 있는 폴더는 비었거나 전에 설치기가 쓴 폴더(`.gputeer-install-dir` 표식)여야 한다. 상위 폴더는 만들지 않는다.
  Windows 는 설치 폴더(밖에 둔 노드 폴더 포함)와 시드의 소유자를 현재 사용자로 바꾸고 권한을 **현재 사용자 · SYSTEM · Administrators** 로 좁혀(상속
  끊음), 그 아래 **이미 있는 파일 · 폴더도** 소유자를 바꾸고 명시 항목을 지워 좁힌 폴더에서 물려받게 한 뒤(결함 456) 하나씩 다시 읽어 확인한다 —
  다른 소유자 · 다른 계정의 허용 항목이 남아 있으면 `ACL_OPEN`, 폴더 안에 junction · 링크가 있으면 `INSTALL_DIR_REFUSED` 로 멈춘다.
  ★ 이것이 막는 것은 **같은 PC 의 다른 일반 계정**이다 — 관리자 · SYSTEM · 같은 사용자로 도는 프로그램 · 좁히기 전에 이미 열려 있던 핸들은 막지 않는다.
  Linux 설치기는 **일반 계정으로** 돈다(root 로 부르면 멈춘다). `--register`(sudo)는 두 단계다 — 폴더 · 키 · 설정 · 점검 · 가입 파일은 부른 계정으로
  다시 돌려 그 계정 권한으로 쓰고, root 는 `/etc` 아래만 쓴다(결함 455 — root 가 사용자 폴더의 설정 · 키 파일을 읽거나 쓰거나 넘기지 않는다).
  ★ 결함 464 — 그래도 root 는 **설치 스크립트와 유닛 틀 자체**를 실행 · 복사한다. 그래서 `--register` 는 **root 소유 사본**에서만 돈다 — 스크립트 · 틀과
  그 상위 폴더가 root 소유가 아니거나 다른 계정이 쓸 수 있으면 `INSTALLER_NOT_ROOT_OWNED` 로 멈춘다.
  ★ 결함 505 — root 로 돌면 **첫 명령 전에** `PATH` 를 `/usr/sbin:/usr/bin:/sbin:/bin` 으로 고정하고 `IFS` 를 기본값으로 되돌린다(root 인지는
  `/usr/bin/id` 로 본다 — 그 경로에 `id` 가 있는 배포판을 전제한다). 부른 계정의 `PATH`(예 `$HOME/bin`)에 심어 둔 `dirname` · `sudo` · `systemctl` 을
  root 가 실행하지 않게 한다.
  ★★ 결함 507 — **root 로 돌릴 설치기는 사용자 체크아웃에서 복사하지 않는다.** Agent 계정(그 계정으로 돈 작업 포함)이 쓸 수 있는 곳의 파일을 `sudo cp`
  하면, 바뀐 스크립트가 root 소유가 되어 소유권 검사 전에 root 로 돈다 — 계정 권한 안의 변조가 root 실행으로 올라간다. root 가 **직접** 받고, 운영자가
  **저장소 밖의 경로**(메신저 · 전화 등)로 알려 준 커밋 id 와 대조한 뒤 쓴다.
  ★ 결함 509 — root 로 들어가는 명령은 sudo 와 **sudo 가 실행할 프로그램까지 절대 경로로** 쓴다. `sudo sh …` 처럼 이름만 쓰면 sudoers 에 `secure_path` 가
  없는 시스템(기본값이 아니다)에서 sudo 가 부른 계정의 PATH 로 `sh` · `git` 을 찾아, 그 계정의 작업이 `$HOME/bin` 등에 둔 가짜를 root 로 실행한다
  (설치기 안의 PATH 고정은 설치기가 돈 **뒤**에야 효과가 있다):
  ```bash
  /usr/bin/sudo /usr/bin/git clone --branch <릴리스 태그> <저장소 주소> /usr/local/share/gputeer-src
  /usr/bin/sudo /usr/bin/git -C /usr/local/share/gputeer-src rev-parse HEAD   # 운영자가 따로 알려 준 커밋 id 와 같은지 눈으로 대조한다 — 다르면 멈춘다
  /usr/bin/sudo /usr/bin/install -d -m 0755 /usr/local/share/gputeer
  /usr/bin/sudo /bin/cp -r /usr/local/share/gputeer-src/deploy/trusted-party /usr/local/share/gputeer/
  /usr/bin/sudo /bin/sh /usr/local/share/gputeer/trusted-party/install/install-node.sh <같은 인자> --register
  ```
  (`/bin/sh` · `/bin/cp` · `/usr/bin/{sudo,git,install}` 은 주요 배포판의 표준 위치다 — 다르면 `ls -l` 로 root 소유인 실제 위치를 확인해 쓴다.)
  ★ **이것이 막지 못하는 것** — 명령을 치는 셸 자체도 그 계정의 것이다. 그 계정의 작업은 셸 설정 파일(`~/.bashrc` 등)을 바꿔 **다음에 치는 명령**을
  가로챌 수 있다(절대 경로도 우회된다). 그래서 등록은 그 계정이 **작업을 받기 전**(처음 설치할 때)에 한다. 그 뒤에 다시 등록해야 하면 설정 파일을 읽지
  않는 셸(`/bin/bash --noprofile --norc`)을 새로 열어 하되, 그 계정의 작업이 이미 돌았다면 보증이 없다. 근본 대책은 아래의 "Agent 는 sudo 권한이 없는
  전용 계정으로" 다 — `--register` 는 부른 계정(`SUDO_USER`)을 Agent 계정으로 쓰므로 등록할 때는 그 계정에 sudo 가 필요하다. Agent 서비스는 sudo 를 쓰지 않으므로 등록이 끝나면 그 권한을 거둔다(다시 등록할 때만 준다)
  비공개 저장소라 root 가 받을 수 없으면 운영자가 건넨 묶음 파일을 root 로 풀되, 운영자가 따로 알려 준 `sha256sum` 값과 대조한 뒤에 쓴다.
  소유권 검사(`INSTALLER_NOT_ROOT_OWNED`)는 스크립트 안에 있어 **이미 바뀐 스크립트**는 막지 못한다 — 막는 것은 사용자 소유 체크아웃에서 sudo 로 부르는
  실수다. 바뀌지 않았다는 보증은 위의 받기 · 대조 절차가 준다(코드가 아니라 절차다).
  Windows 설치기는 **상승된 관리자 창에서 돌면 멈춘다**(`INSTALL_ELEVATED` · 결함 465 — 폴더 정리와 같은 사용자 프로그램의 경쟁이 있어도 그 사용자
  권한을 넘지 않게). 컨테이너 런타임을 주면 `--container-gpu`(`-ContainerGpu`)도 줘야 한다(469 — 핀이 필수라 없으면 어떤 작업도 못 받는다).
  다른 계정이 쓰던 노드 폴더 · 파일이면 이어 쓰지 않고 멈춘다(`NODE_OWNED_BY_OTHER` · 457 — 계정을 바꾸려면 새 노드 id · 새 폴더로 설치한다).
  ★ 호스트에서 작업을 돌리는 노드(S0 · RESTRICTED)는 작업이 **그 계정의 권한 전부**를 갖는다 — 그 계정이 sudo 를 쓸 수 있으면 작업이 다음 sudo 를
    가로챌 수 있다. Agent 는 sudo 권한이 없는 전용 계정으로 돌리거나 컨테이너 전용(S3)으로 둔다
- ★ Linux `--register` 는 같은 PC 의 다른 노드를 건드리지 않는다(결함 445 · 453) — 실행 계정은 `gputeer-agent@<노드>.service.d/10-user.conf` 에,
  이 노드의 값은 `/etc/gputeer/agent-<노드>.env` 에 쓴다. 공유 유닛 틀은 **없을 때만** 놓고, 있는데 다르면 덮지 않고 멈춘다(`UNIT_DIFFERS` — 운영자가
  비교해 바꾼다). `/etc/gputeer/gputeer.env`(운영자 PC 등)가 있으면 인스턴스 파일에는 노드 값만 넣어 공통 파일이 이기게 하되, 그 파일의 주소 · id ·
  공개키 · 공유 저장소가 초대와 **다르거나 없으면 멈춘다**(`COMMON_ENV_DIFFERS` · 결함 458 — 풀 목록만 달라도 된다). 공통 파일이 없으면 초대의 공통
  값까지 인스턴스 파일에 넣는다 — 출력의 `POOL_AGENTS_FILE` 이 풀 노드 목록을 고칠 파일이다
- GPU 이름 · VRAM 은 `nvidia-smi` 로 읽는다. 없으면 `-GpuModel · -GpuVramMiB` 로 직접 준다
- `install-node` 는 GPU 관측을 **기본으로 끈다**(결함 444 — 옛 Coordinator 는 관측을 실은 인사를 거부한다). Coordinator 를 올린 뒤(§5 의 순서 ③)
  `-AttestGpus`(`--attest-gpus`)로 다시 설치해 켠다 — 인사의 NVML 관측이 가입 파일의 모델 이름 · VRAM 과 맞으면 등록 정보가 낡지 않는다.
  켜기 전까지는 운영자가 `refresh-inventory` 로 신선도를 준다.
  ★ 결함 459 — 다시 설치해도 **이미 도는 Agent 는 바뀐 설정을 읽지 않는다**(설치기는 실행 중인 작업을 끊지 않으려고 다시 띄우지 않고 `RESTART_NEEDED` 로
    알린다). 작업이 끝난 뒤 다시 띄우고(Linux `systemctl restart gputeer-agent@<노드>` · Windows `schtasks /End` 뒤 `/Run`), Coordinator 로그에
    그 노드의 `GPU_ATTESTATION_RECORDED` 가 찍힌 것을 **본 다음에** 그 노드의 refresh 를 멈춘다
  ★ 가입 파일의 모델 이름을 손으로 바꾸면(`-GpuModel`) NVML 이름과 달라져 관측이 맞지 않는다(`GPU_ATTESTATION_MISMATCH`)
- ★ `admit-node` 는 서명을 검증하지 않는다 — 가입 파일을 **누가 보냈는지** 운영자가 확인한다(공개키를 대면 · 전화로 한 번 맞춰 본다)
- `admit-node` 는 반입(import-inventory)이 **성공한 뒤에만** 받아 둔 가입 파일(`admitted/join-<노드>.json`)을 바꾼다(결함 443). 반입이 거부되면
  그 전 사본이 그대로 남아 refresh 가 계속 돈다. 반입과 교체 사이에 끊기면 후보(`admitted/.candidate-<노드>.json`)가 남고, `refresh-inventory` 는
  **그 노드만** 넣지 않고 나머지는 갱신한 뒤 실패로 끝난다(`ADMIT_INCOMPLETE` · 결함 452 · 463 — 옛 사본이 방금 받은 선언을 되돌리지 않게). 그 노드로
  `admit-node` 를 다시 돌린다. ★ 예약 실행은 출력을 **로그 파일에 남기고** 실패를 본다 — refresh 스크립트 머리말의 예시(Linux cron `>> <로그> 2>&1`
  · Windows 작업의 `*>> <로그>`)대로 걸고, 로그의 `ADMIT_INCOMPLETE` · `REFRESH_FAILED` 와 작업 스케줄러의 "마지막 실행 결과" 를 확인한다
- `admit-node` · `refresh-inventory` 는 둘 다 `admitted/.lock` 을 **환경 파일 · 풀 목록을 읽기 전에** 잡고 돈다(refresh 는 결함 479 에서 옮겼다) — 동시에 돌면 뒤의 것이 `ADMITTED_LOCKED` 로
  멈춘다(결함 466 · 472 — refresh 가 방금 받은 선언을 옛 사본으로 덮거나, 동시에 받은 두 노드 중 하나가 풀 목록에서 빠지지 않게). 도는 것이 없는데
  `.lock` 이 남았으면(전원이 나간 경우) 지우고 다시 돌린다. 받아 둔 사본 · 환경 파일은 임시 파일에 쓴 뒤 **바꿔 넣는다**(Linux `mv` · Windows
  `File.Replace` — 결함 474 · 477 · 479. PowerShell 5.1 의 `Move-Item -Force` 는 지우고 옮기는 두 단계라 쓰지 않는다). 바꿔 넣다 끊겨 `join-*.json.tmp`
  만 남았으면 refresh 가 되살린다(`RECOVERED`). 받아 둔 사본의 revision 을 읽지 못하면 admit 이 멈춘다(478 — 백업에서 되살린다)
- revision 은 벽시계와 떼어 적는다 — `max(지금, 받아 둔 사본의 revision + 1, 남은 후보의 revision + 1)`, 관측 시각만 지금이다(결함 467 · 473).
  운영자 시계가 한 번 미래로 갔다 돌아와도 다음 refresh 가 바른 시각을 적어 스스로 풀린다. 반입 뒤 사본을 옮기기 전에 끊겨 후보만 남았으면 그 노드로
  `admit-node` 를 다시 돌린다 — 후보의 revision 보다 큰 값으로 다시 반입한다(쓰다 끊겨 읽지 못하는 후보는 반입 전의 것이라 건너뛴다).
  ★ 이 자동 복구는 DB 의 revision 이 받아 둔 사본 · 후보보다 크지 않을 때다 — 가입 파일을 거치지 않고 `import-inventory` 로 직접 더 큰 revision 을
  넣었다면 그보다 큰 revision 의 가입 파일로 한 번 직접 넣는다
- ★ 받은 뒤 Coordinator · scheduler 를 **다시 띄운다**(`--pool-agents` 는 시작할 때만 읽는다). 다른 Agent 들의 `GPUTEER_POOL_AGENTS` 도
  새 줄로 바꾸고 다시 띄워야 새 노드의 체크포인트에서 이어받는다
- ★ 초대 파일에는 Coordinator 주소가 들어간다 — 저장소 · 공개 채널에 올리지 않고 팀원에게 직접 건넨다
- 확인한 것(2026-09-25 개발 기계 Windows) — PowerShell 5.1 · Git Bash 에서 초대 → 설치(node-doctor 까지 · GPU 가 없는 기계라 gpu FAIL 에서
  멈추는 것까지) → 받기(백업 · 목록 추가 · 같은 키 다른 id 거부 · 같은 노드 다시 받기) → 다시 넣기 → `status` 에 노드가 보임.
  x600 WSL2 Ubuntu(**root** · GPU 보임)에서 `install-node.sh` 가 node-doctor 를 통과하고 `nvidia-smi` 로 GPU 를 읽어 가입 파일을 만들었고,
  그 파일을 `import-inventory` 가 받았다(`docs/evidence/_raw/설치_자동화_x600_WSL_가입파일_2026-09-25.txt`).
  ★ 그것은 2026-09-25 판이다 — 2026-09-27 부터 설치기는 root 로 부르면 멈춘다(결함 455). 지금 판은 Linux 에서 다시 재지 않았다.
  2026-09-27 개발 기계 Git Bash 에서 가짜 root · 가짜 `sudo` · 가짜 `systemctl` 과 시험용 `/etc` 접두(`GPUTEER_TEST_ETC_PREFIX`)로 `--register` 의
  두 단계를 흉내 냈다 — 인스턴스 env · drop-in · 유닛 틀 설치, `RESTART_NEEDED` · `UNIT_DIFFERS` · `COMMON_ENV_DIFFERS` 가 의도대로 나왔다(진짜 root ·
  systemd 는 아니다)
  **확인하지 않은 것** — GPU 가 있는 Windows 에서 `install-node.ps1` 의 가입 파일 부분 · `-Register`/`--register`(작업 스케줄러 · systemd 를
  바꾸는 일이라 돌리지 않았다) · 비-root 리눅스 · 컨테이너 런타임을 준 설치

## 10. 알려진 한계 (신뢰망 범위)

```text
TLS 없음 · 악의적 참여자 방어 없음 · 과반 합의 없음(Coordinator 하나)
공유 저장소 하나를 복제본 하나로 본다(완화) · 체크포인트 파일을 통째로 메모리에 읽는다
옛 노드가 살아 계속 도는 것을 막지 못한다(PURE 전제) · GPU 한 장을 나눠 쓰지 않는다
Agent 의 리눅스 실행 경로는 CI(비-root)에서만 검증된다 — 실행 관문이 cgroup 위임을 요구한다
ACK 수신 확인이 유실되면(기록 직후 끊김) 그 작업은 실행되지 않고 Job 은 STAGING 에 남는다 — Lease 만료 뒤 큐로 돌아가 **처음부터** 돈다
  (결함 218 닫힘, 2026-09-25). 그 노드의 예약은 만료 표시만 남아 운영자가 release-lost-node 로 푼다(좀비 방지 원칙 그대로)
  ★ 2026-09-25 재검수 87 — 처음 수정은 첫 갱신을 기다리지 않고 워크로드를 띄워, 첫 갱신이 유실 · 거부되면 **실제로 도는** 작업이 STAGING 으로
    남아 한 번 더 돌 수 있었다(결함 268 · 269 · 271). 이제 실행 직전 갱신이 성공해야 띄운다 — 못 받으면 띄우지 않는다.
  ★ 남는 것 — Coordinator 가 시작을 기록한 뒤 그 갱신의 **결과 프레임만** 잃으면 안 돈 시도가 RUNNING 이다. 이어받기에서 체크포인트가 없으면
    FAILED 로 끝난다(두 번 돌지는 않는다 — 가용성 쪽 한계). 실행 중 Lease 를 잃었을 때 워크로드를 멈추지 않는 것(정책 미정)은 그대로다

이어갈 지점 찾기는 공유 저장소 **목록** 오류만 "지점 없음" 으로 받는다. 목록이 일부만 읽히면 전체를 못 읽은 것으로 보고, 체크포인트 파일 읽기
  오류는 그 체크포인트를 건너뛴다(결함 263)
```
