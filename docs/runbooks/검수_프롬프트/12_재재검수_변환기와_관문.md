동의가 아니라 **반박**을 원한다. 재검수(10번)가 세 수정을 **전부
과장**이라고 판정했고, 다시 고쳤다. 이번 수정이 **또 과장인지**를
확인해 달라.

# 배경 — 10번의 판정과 이번 수정

```text
D  "UndeclaredAmount 수정을 되돌려도 실패하는 테스트가 없다"
   -> each_undeclared_resource_amount_is_refused_by_its_own_name 추가.
      세 자원을 하나씩 0 으로 두고 각각 그 이름으로 거부되는지 본다.
      대조군 a_zero_vram_floor_is_still_accepted_as_no_floor
   ★ 수정 쪽이 잰 것: 자원 하나씩 nonzero 를 빼는 뮤테이션 3/3 이 잡혔고,
     VRAM 에도 nonzero 를 거는 뮤테이션을 대조군이 잡았다

E  "stage_job 테스트는 상태 거부가 아니라 점유 거부를 고정한다"
   -> 테스트는 그대로 두었다. 테스트가 정직했고 **결함 리포트가
      틀렸다** — 없는 테스트 이름을 인용하고 "상태 관문이 걸린다" 고
      적었다. 리포트를 정정했다.
      두 번째 요청의 ID 를 같은 파일 형제 줄과 같은 길이로 맞췄다.
   ★ 수정 쪽 주장: 상태 관문은 **저장소 계층이 잰다.**
     staging_store.rs 의 관문 3줄을 지우니 테스트 2건이 실패했다
       invalid_state_identity_lifetime_and_clock_leave_state_unchanged
       two_connections_stage_one_queued_job_exactly_once

F  "Shared 거부가 proto 조건 둘 중 하나만 옮겼다"
   -> 코드는 그대로(전부 거부). 주석을 "입력 칸이 없어 둘 다 판단 못
      하므로 전부 막는 잠정 제한" 으로 고쳤다
```

# 물을 것 — 네 가지

1. **D 의 새 테스트가 정말 그 수정을 고정하나.** 세 경우가 서로 다른
   경로를 타나, 아니면 하나만 걸려도 셋 다 통과하는 구조인가?
   대조군이 **경로가 갈라지는** 대조군인가?

2. **E 에서 "저장소 계층이 잰다" 는 주장이 맞나.** 그 두 테스트가
   `JobNotQueued` 를 **특정해서** 확인하나, 아니면 다른 이유의 실패로도
   통과하나? "CLI 로는 상태 관문에 못 닿는다" 가 맞나 — 다른 CLI 경로가
   있나?

3. **F 의 새 주석이 맞나.** "scope 커널에 동일 소유자 관계를 담을 입력
   칸이 없다" 와 "`filter.rs` 의 `owner_member_id` 는 다른 관계다" 를
   코드로 확인하라. **다른 계층에서 이미 동일 소유자를 판단하고 있다면**
   "잠정 제한" 이라는 설명도 틀린다.

4. **정정한 결함 리포트(③·④·⑫)에 아직 측정보다 강한 문장이 있나.**
