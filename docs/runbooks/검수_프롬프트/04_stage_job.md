동의가 아니라 **반박**을 원한다. `stage-job` 이 예약을 만들 때 무엇을
빠뜨렸는지 찾아 달라.

# 배경

`stage-job` 은 큐에 있는 Job 을 실제 노드에 **예약**한다. 이 저장소에서
`orchestrate` 를 production 에서 처음 부르는 자리다.

두 가지 설계 결정이 검토 대상이다.

**하나 — 시계를 읽지 않는다.** Lease 의 세 시각(발급·갱신·만료)을 상대값이
아니라 **절대값으로 인자로 받는다**(`stage_job.rs:83~85`). 처음엔
`--lease-duration-ms` 를 받아 `now()` 에 더했는데, 그러면 재시도할 때마다
값이 달라져 **멱등이 아니었다** — 저장소가 `operation key payload conflict`
로 거부했고 그게 옳은 거부였다.

**둘 — 저장된 Manifest 를 지금 다시 검증한다**(`stage_job.rs:147`).
계획할 때 믿었다고 예약할 때도 믿지 않는다. 그 사이에 서명자가 폐기됐을
수 있다.

# 읽을 파일 — 이것만 읽어라

```text
crates/cli/src/stage_job.rs      (301줄)
crates/cli/tests/stage_job.rs    (686줄)
```

다른 crate 로 범위를 넓히지 마라.

# 물을 것 — 네 가지

1. **시계를 정말 안 읽는가.** `stage_job.rs:103` 이 `now_unix_ms()` 를
   한 번 읽는다(신선도 판정용). 그 값이 **durable 하게 저장되는 것에
   영향을 주는 경로**가 있나? 있으면 위 "재시도가 멱등하다" 는 주장이
   깨진다. 파일:줄로 지목하라.

2. **`operation_key` 를 운영자가 준다.** 두 번의 서로 다른 예약이 같은
   key 를 쓰면 어떻게 되나? 반대로 같은 예약을 재시도하면서 key 를 바꾸면?
   둘 다 안전하게 끝나는가, 아니면 한쪽이 조용히 이상한 상태를 만드나?

3. **재검증이 무엇을 재검증하는가.** `stage_job.rs:147` 의 재검증이
   "그 사이 서명자가 폐기됐을 수 있다" 를 실제로 막는가? 폐기 여부를
   어디서 읽는지 코드로 따라가라 — 읽는 곳이 없다면 그 주석은 과장이다.

4. **테스트가 이유까지 확인하는가.** `crates/cli/tests/stage_job.rs` 의 실패 확인
   단언 중 `!ok` 만 보는 것이 있으면 지목하라. `STAGE_REFUSED:` 로 시작하는
   메시지가 여럿인데, 서로 다른 관문이 **같은 접두사**를 쓴다 — 접두사만
   확인하는 단언은 관문을 구분하지 못한다.

# 못 찾았으면

**못 찾았다고 말하고, 어디까지 확인했는지 적어라.** 없는 문제를 지어내지
마라 — "확인했고 문제없다" 도 유효한 답이다.

# 답의 형식

각 지적마다 `파일:줄` 과 구체적 반례를 붙여라.

마지막 줄에 `ACCEPTED` 또는 `CHANGES_REQUESTED` 중 하나를 써라.
