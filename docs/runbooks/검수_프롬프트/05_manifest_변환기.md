동의가 아니라 **반박**을 원한다. 이 변환기가 **조용히 값을 지어내는
자리**가 있는지 찾아 달라.

# 배경

`job_requirements_from_manifest()` 는 서명이 검증된 `JobManifest` 를
스케줄러가 쓰는 `JobRequirements` 로 바꾼다. 순수 함수다 — 시계·I/O·DB 가
없다.

이 저장소의 가장 강한 규칙 하나가 여기 걸려 있다
(`CLAUDE.md` §1 — **"지어내지 않는다"**):

> 값을 모르면 **비워 둔다.** 추정으로 채우면 그 오류가 조용히 스케줄링
> 결정까지 간다.

그래서 이 변환기는 **`UNSPECIFIED` 를 값으로 바꾸지 않는다.** 선언 안 된
축은 기본값으로 메우지 않고 `Unspecified(...)` 오류로 거부한다.

각 enum 변환 함수는 **exhaustive `match`** 다 — proto 에 새 변형이 생기면
컴파일이 깨져서 알게 된다.

# 읽을 파일 — 이것만 읽어라

```text
crates/coordinator/src/manifest_requirements.rs   (496줄, 테스트 포함)
```

이 파일 하나만 본다. `proto/job.proto` 의 enum 정의를 확인해야 하면
그것만 추가로 본다.

# 물을 것 — 네 가지

1. **지어내는 자리가 있나.** 선언되지 않은 축이 오류가 아니라 **어떤
   값으로** 넘어가는 경로가 하나라도 있으면 파일:줄로 지목하라.
   특히 `manifest_requirements.rs:125` 근처 — proto 가 "기본 1" 이라
   적었다는 이유로 `0` 을 `1` 로 바꾸는 곳이 있다. **그게 정당한가,
   아니면 지어내기인가?** proto 를 직접 확인하고 답하라.

2. **`match` 가 정말 exhaustive 인가.** `_ =>` 나 catch-all 이 섞여 있으면
   proto 에 변형이 추가돼도 컴파일이 안 깨진다 — 그러면 새 값이 조용히
   기존 분기로 흡수된다. 지목하라.

3. **`submitter_member_id` 를 인자로 받는다.** 메시지 안에서 읽지 않고
   바깥에서 받는 이유가 파일 머리말에 적혀 있다. 그 이유가 **코드와
   맞는가**? 받은 값을 검증 없이 그대로 쓰는가, 아니면 대조하는가?
   검증 없이 쓴다면 잘못된 값을 넣었을 때 무슨 일이 생기나?

4. **테스트가 축을 전수로 덮는가.** 이 파일의 테스트가 각 enum 의
   **모든 변형**을 도는가, 아니면 대표값 몇 개만 보는가? 안 덮인 변형이
   있으면 지목하라. 그리고 `manifest_requirements.rs:317` 근처가
   "기대값을 손으로 적는다" 고 했는데, 실제로 그런가 — 변환 함수를 다시
   돌려 기대값을 만드는 테스트가 있으면 그건 **자기가 자기를 확인하는
   것**이라 아무것도 증명하지 않는다.

# 못 찾았으면

**못 찾았다고 말하고, 어디까지 확인했는지 적어라.** enum 을 몇 개 봤고
각각 몇 개 변형인지 쓰면 된다. 없는 문제를 지어내지 마라.

# 답의 형식

각 지적마다 `파일:줄` 과 **구체적 입력**(이런 Manifest 를 넣으면 이런
값이 나온다)을 붙여라.

마지막 줄에 `ACCEPTED` 또는 `CHANGES_REQUESTED` 중 하나를 써라.
