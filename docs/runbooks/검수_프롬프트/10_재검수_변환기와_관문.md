동의가 아니라 **반박**을 원한다. 지적을 받고 고쳤는데, **그 수정이
지적을 실제로 닫았는지** 확인해 달라. 그리고 **수정이 새로 만든 문제**를
찾아 달라.

# 배경 — 2026-09-10 에 두 지적을 받고 고쳤고, 하나는 스스로 찾아 고쳤다

```text
지적 D (Manifest 변환기)
  proto3 의 숫자에는 presence 가 없어 **생략과 0 이 구분되지 않는다.**
  그런데 변환기가 생략된 cpu_cores·ram_bytes·workspace_bytes 를
  Some(0) 으로 확정했다 — scheduler 는 그것을 "이 Job 은 0 을
  요구한다" 는 **선언된 사실**로 읽는다.

  -> 셋을 `UndeclaredAmount` 로 거부하게 고쳤다.
  ★ 판단 근거는 proto 가 **기본값을 의도한 자리마다 주석을 달아 둔
    것**이었다(min_count "기본 1", allocation_mode "미지정 시
    EXCLUSIVE" 등). 주석 없는 셋이 정확히 의미를 지어낸 자리였다.

지적 E (stage-job 테스트)
  "QUEUED 에서만 예약한다" 관문이 **한 번도 안 돌았다.** 노드가
  하나뿐이라 점유 관문이 늘 먼저 걸린다.
  -> 노드 둘짜리 fixture 를 만들어 상태 관문이 실제로 걸리게 했다.

스스로 찾은 것 F (scope 커널)
  `Partitioned` 는 `PartitionedAllocationUnproven` 으로 거부하는데
  **`Shared` 는 enum 선언 한 줄이 전부였다.** proto 가
  "Linux+MPS 확인 시에만" 이라고 적었지만 강제하는 코드가 없었다.
  -> `SharedAllocationUnproven` 을 넣었다.
```

# 물을 것 — 네 가지

1. **지적 D 의 수정이 과했나, 모자랐나.**
   - `min_vram_bytes` 는 **일부러 남겼다** — "하한 없음" 이라는 읽기가
     쓸모 있고 0 말고 표현할 방법이 없어서다. 그런데 proto 에 그
     근거가 없다. **이 예외가 정당한가, 아니면 같은 병인가?**
   - `cpu_cores` 를 `u32 -> u64 -> u32` 로 왕복시킨다. 그 캐스팅에
     문제가 있나?
   - 거부하면 **정상적인 Job 이 막히는 경우**가 있나? 예컨대 CPU 를
     정말 안 쓰는 워크로드는 어떻게 선언해야 하나?

2. **지적 E 의 수정이 실제로 그 관문을 재나.**
   - `prepared_two_nodes()` 가 만드는 두 번째 노드가 **첫 노드와
     구별되는 모든 필드**를 갖췄나? (같은 키를 쓰다 한 번 거부당했다)
   - 두 번째 시도가 **정말 상태 관문**에 걸리나, 아니면 다른 이유로
     실패하고 우연히 문자열이 맞는 것인가?
   - `!output2.contains("already reserved")` 단언이 **의미가 있나**?

3. **F 의 관문이 규범과 맞나.**
   - `proto/common.proto` 의 `GPU_ALLOCATION_MODE_SHARED` 주석을 읽고,
     `SharedAllocationUnproven` 거부가 **그 규범을 옮긴 것인지**
     아니면 **새 정책을 만든 것인지** 판정하라.
   - `Partitioned` 거부와 **대칭인가**? 비대칭이면 어디가?
   - 이 거부 때문에 **지금 동작하던 무언가가 깨지나**?

4. **셋 중 하나라도 "고쳤다" 가 과장인 것이 있나.**
   각각에 대해 **수정 전이었다면 실패했을 테스트**가 실제로 있는지
   확인하라. 없으면 그 수정은 고정되지 않은 것이다.
