동의가 아니라 **반박**을 원한다. 재검수(9번)가 1차 수정에서 구멍 셋과
새 결함 셋을 찾았고, 그것을 다시 고쳤다. **2차 수정이 정말 닫았는지**,
그리고 **2차 수정이 또 새로 만든 문제**를 찾아 달라.

# 배경 — 9번이 찾은 것과 2차 수정

```text
⑧ 원자적 파일 쓰기의 1차 수정이 모자랐다
   (1) target.exists() 확인과 rename 사이가 벌어져 있었다
   (2) 임시 파일 <이름>.tmp.<pid> 를 fs::write 로 만들어 남의 것을 덮었다
   (3) 덮어쓰기에서 remove_file 뒤 rename — 둘 다 없는 창이 있었다
   -> 임시 파일은 create_new 배타 생성(이름 충돌 시 64번까지 재시도)
      덮어쓰기 금지는 hard_link 로 확정(대상이 있으면 링크가 실패)
      덮어쓰기 허용은 rename 한 번(먼저 지우지 않는다)
⑨ seed 검사가 바이트 길이만 보고 문자 경계를 갈라 패닉했다
   -> 먼저 ASCII hex 인지 본다
⑩ 자원 플래그 일부만 주면 선언한 자원을 말없이 버렸다
   -> 여섯 플래그 중 하나라도 있으면 선언한 것으로 보고,
      필수 셋이 빠지면 SUBMIT_REFUSED: RESOURCE_PARTIAL
⑪ 값 대조 테스트가 "누가 서명했는지" 를 안 봤다
   -> 선언한 seed 의 공개키만 담은 keyring 으로 검증하는 테스트
```

# 읽을 파일 — 이것만 읽어라

```text
crates/cli/src/out_file.rs
crates/cli/src/submit.rs
crates/cli/src/issue_grant.rs
crates/cli/tests/submit.rs
crates/cli/tests/issue_grant.rs
```

# 물을 것 — 다섯 가지

1. **⑧ 이 닫혔나.**
   - `hard_link` 가 성공한 뒤 `remove_file(&tmp)` 가 실패하거나 그 사이에
     프로세스가 죽으면? 남은 임시 파일이 **다음 실행을 막거나 산출물을
     망가뜨리는** 경로가 있나?
   - Windows 에서 `std::fs::rename` 이 대상을 교체할 때 **원자적**이라고
     주석에 적었다. 그 주장이 맞나? 대상 파일을 다른 프로세스가 열고
     있으면 어떻게 되나?
   - `create_exclusive_temp` 의 이름에 pid 와 시도 번호만 쓴다. 두 프로세스가
     같은 디렉터리에 동시에 쓰면 어떻게 되나?
   - hard link 를 지원하지 않는 파일시스템에서 **덮어쓰기 금지 경로가
     조용히 덮는** 경우가 있나, 아니면 항상 실패하나?

2. **⑨ 가 닫혔나.** `submit.rs` 에 **바이트 인덱스로 문자열을 자르는
   곳이 또** 있나? 사용자 입력이 닿는 곳을 전부 찾아라.

3. **⑩ 이 닫혔나.** 자원을 선언했는데 Manifest 에 안 들어가는 조합이
   남았나? 반대로 **자원을 안 쓰는 정상 제출**이 `RESOURCE_PARTIAL` 로
   막히는 경우가 있나?

4. **⑪ 이 닫혔나.** 새 테스트가 **정말 서명 키를 고정하나**, 아니면
   keyring 에 다른 키가 섞여도 통과하나?

5. **2차 수정이 새로 만든 결함이 있나.** 각 수정마다 **수정 전이었다면
   실패했을 테스트**가 실제로 있는지도 확인하라. 없으면 그 수정은
   고정되지 않은 것이다.

# 못 찾았으면

**못 찾았다고 말하고, 어디까지 확인했는지 적어라.** 반례를 못 만든
것과 결함이 없는 것은 다르다 — 그 둘을 구분해 써라.

# 답의 형식

각 지적마다 `파일:줄` 과 구체적 입력을 붙여라.
마지막 줄에 `ACCEPTED` 또는 `CHANGES_REQUESTED` 중 하나를 써라.
