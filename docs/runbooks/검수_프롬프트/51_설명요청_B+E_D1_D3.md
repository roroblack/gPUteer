이것은 판정이 아니라 **설명 요청 겸 독립 판단**이다. 사용자가 B+E 변경 제안을 승인했고, 남은 세 결정 D1 · D2 · D3 에 대해
"코덱스가 설명하라" 고 했다. D3 에서는 **"왜 FAILED 를 권장하나 — 코덱스와 합의했나"** 고 물었다.
★ 합의하지 않았다. FAILED 권장은 이 세션(Claude)의 판단이었다. 그러니 **내 권장을 따르지 말고** 처음부터 판단하라.

# 읽는 사람

이 저장소의 코드를 읽지 않는 사람이다. 전문 용어 없이, 무슨 일이 일어나는지 **장면으로 그려지게** 써라.
용어가 꼭 필요하면 처음 나올 때 한 줄로 풀어라. 결론을 먼저, 근거를 뒤에.

# 설명할 것 — 셋 각각

```text
D1  Lease 만료 뒤 REPORT 연결로 온 보고를 받는가
D2  FRESH 연결도 Agent 가 먼저 Hello(무슨 용건인지)를 보내게 하는가 — 설정으로 켤 때만 / 항상
D3  "종료는 관측했는데(exit 0) 산출물 확정이 실패" 한 보고의 outcome
      후보: FAILED · 새 outcome 값 추가(proto) · 이번엔 보류(⑲ 는 따로)
```

각 결정마다:
1. **무엇을 정하는 것인지** — 실제로 어떤 장면에서 차이가 나는지 한 문단.
2. **선택지마다 얻는 것 · 잃는 것** — 특히 나중에 무엇이 곤란해지는지(재시도 정책, 정산, 중복 실행, 호환성).
3. **규범과의 관계** — 규범 문서가 이미 답을 주는지, 규범에 없는 판단인지. `파일:줄` 로.
4. **너의 권장과 이유** — 결정은 사용자다.

D3 에서는 추가로:
- 내가(Claude) FAILED 를 권장한 근거 — "규범의 WORKLOAD_EXITED_OK 는 HASH_VERIFIED 를 요구하므로 COMPLETED 는 아니다,
  FAILED 는 새 값이 필요 없다" — 가 맞는지, **놓친 것**이 있는지(예: FAILED 가 "작업 자체가 틀렸다" 와 "노드의 저장이
  실패했다" 를 섞어 재시도 판단을 흐리는가, INTERRUPTED 가 더 맞는가).

# 답의 형식

- 한국어. 사실에는 `파일:줄` 을 괄호로 짧게.
- 확인하지 못한 것은 못 했다고 적어라.
- 마지막 줄에는 판정어 대신 `EXPLAINED` 라고 써라.
