이것은 판정이 아니라 **설명 요청**이다. 사용자가 아래 두 결정 질문을 받고 "무슨 말인지 모르겠다 —
코덱스가 설명하라" 고 했다. 이 분야를 모르는 사람이 읽고 바로 그림이 그려지는 말로 설명해 달라.

# 사용자에게 던진 두 질문

```text
질문 1  ID 26자 규칙을 어디까지 강제할까?
          (가) job · attempt · lease · grant 만 강제, node · device · member · peer · checkpoint ID 는 예외로
               두되 proto 에 예외를 명시하는 변경 제안부터
          (나) 모든 ID 강제
          (다) 강제하지 않음 — 테스트 fixture 만 26자로 맞춤
질문 2  강제한다면 검사를 어디에 둘까?
          (가) 공통 검사 함수 하나 + CLI 인자와 저장소 입력 검사 둘 다
          (나) 저장소 입력 검사만
          (다) CLI 인자만
```

# 먼저 할 일 — 설명의 전제를 코드로 **다시 확인**하라

아래는 내(Claude)가 조사한 결과다. 틀렸으면 틀렸다고 먼저 말하고, 맞는 사실로 설명하라.

```text
1 규칙 원문 proto/common.proto:20 — "ID는 별도 명시가 없으면 ULID 26자 문자열"
2 26자 검사는 crates/protocol/src/fenced_operation.rs(job · attempt) 와
  crates/scheduler/src/reassignment.rs(require_ulid_identifier, job · attempt) 두 곳뿐이고,
  evaluate_fenced_operation · evaluate_reassignment 를 제품 코드가 부르는 곳을 찾지 못했다(재수출 · 테스트뿐)
3 CLI 인자(stage-job · issue-grant · submit · coordinator-stub · agent-stub 등)와 저장소 입력 검사
  (job_store · staging_store · inventory_store · attempt_report_store 등)는 ID 가 **비어 있지 않은지만** 본다
4 agent::start_checkpoint_id(crates/agent/src/lib.rs:1705)는 "start-" + BLAKE3 hex 64 = 70자를 만든다 —
  서명되는 CheckpointManifest.checkpoint_id 에 들어간다. proto 에 이 필드의 예외 명시는 찾지 못했다
5 proto 가 26자가 아니라고 따로 적은 ID 는 peer_id("libp2p PeerId") 하나를 찾았다
6 coordinator::validate_device_id 는 64자 상한과 허용 문자만 본다
7 테스트 fixture 의 ID 는 23~27자가 섞여 있고(01J 로 시작하는 서로 다른 값 67개 중 26자는 20개),
  "job-1" 같은 짧은 값도 많다
```

# 설명할 것

1. **이 규칙이 무엇을 지키려고 있는가** — ID 가 26자가 아니면 실제로 무엇이 잘못될 수 있는지. 오늘 코드에서
   그 위험이 실제로 드러나는 경로가 있는지, 아니면 아직 잠재적인지 구분해서.
2. **질문 1 의 세 선택지** — 각각 무엇을 얻고 무엇을 잃는지. 특히 checkpoint_id 70자와 device ID 64자 상한이
   어느 선택지와 부딪히는지. proto 를 고친다는 것이 이 저장소에서 왜 무거운 일인지(RULE.md §3.5 · §4.2).
3. **질문 2 의 세 선택지** — "CLI 에서만 막으면 뚫리는 길" 이 무엇인지 구체적으로(예: 라이브러리 호출,
   파일 반입, 서명 메시지를 바로 소비하는 Agent).
4. **너의 추천과 그 이유** — 추천은 추천일 뿐이고 결정은 사용자가 한다는 전제로.
