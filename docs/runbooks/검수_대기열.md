```text
사용자 입력을 그대로 넣는 오류   **모든 명령**에 있다
                                 (`알 수 없는 인자: {key}` 등)
문자열로 사유를 보는 단언        CLI 테스트에 58군데
지금 실제로 겹치는가             **아니다** — 어느 명령에서도 테스트가 쓰는
                                 사유 문자열이 그 명령의 다른 오류 메시지에
                                 겹치지 않는다
```

  ★ 이 확인의 한계: **고정된 메시지끼리만 비교했다.** `{key}` 로 들어가는
    사용자 입력까지는 못 본다. 즉 지금은 멀쩡하고, **나중에 테스트 인자를
    고치면 깨질 수 있는** 상태다.

  -> 그래서 **한 번에 쓸어 고치지 않는다.** 각 명령이 검수 차례가 될 때
     그 명령에만 거부 코드를 붙인다(2번에서 한 방식 그대로). 검수 대기 중인
     사슬 위에 큰 손질을 얹지 않는다는 원칙과 같다.

### 회귀 테스트를 만들며 두 번 틀렸다 — 기록해 둔다

```text
1차  사유 문구만 심었다 -> **뮤테이션이 안 잡혔다.**
     단언은 코드를 보는데 사유 문구를 심었으니 헬퍼가 어느 방식이든 같았다
2차  코드를 축 이름에 심었다 -> 전제가 깨졌다.
     **축 파서가 입력을 소문자로 바꾼다**(뜻밖의 방어)
3차  입력을 **그대로** 출력하는 자리를 찾았다 — 알 수 없는 인자 오류.
     거기로 심으니 옛 방식에서 정확히 실패한다
```
교훈: **뮤테이션이 안 잡히면 테스트가 약한 것이지 코드가 튼튼한 게 아니다.**

## ★★ 판정을 받으면 **고치기 전에** 결함 리포트를 연다

2026-09-10 에 이걸 어겼다. 검수 다섯 건이 찾은 결함을 **전부 고친 뒤에**
리포트를 썼다. `RULE.md` §230 은 **발견 즉시, 고치기 전에도** 쓰라고 한다.

왜 어겼는지 분명하다 — **검수를 순차로 돌리는 데 집중하느라 문서 규칙을
확인하지 않았다.** 사용자가 "문서 갱신 누락 없나 체크" 라고 지시하고 나서야
알았다.

```text
판정 받음 -> ① docs/reports/debugs/ 에 결함 리포트를 연다 (재현·위치까지)
          -> ② 지적이 성립하는지 테스트로 확인
          -> ③ 성립하는 것만 고친다
          -> ④ 같은 리포트의 §6 조치 칸을 채운다
```

★ ①을 먼저 하는 이유는 **못 고치는 결함일수록 기록이 남아야** 하기
  때문이다. 고친 것만 적으면 못 고친 것이 사라진다.
