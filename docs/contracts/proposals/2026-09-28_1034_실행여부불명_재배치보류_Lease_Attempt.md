## 한 줄 요약

Agent 가 "이 시도가 지금 돌 수 있는데 모른다" 를 **서명해 알리고 그 알림이 먼저 커밋되면**, Coordinator 는 그 시도를 `RUN_UNKNOWN` 으로 적고 **그 Job 에 새 시도를 만들지 않는다**
(Lease 만료로도, 이미 큐로 돌아간 뒤에도). 정지 · 부재를 **확인한 증거**와 함께 해제(`STOP_CONFIRMED`)가 오면 그때 체크포인트에서 이어간다.
★ **알리지 못한 경우**(Agent 가 Coordinator 에 닿지 못한 채 끝남)는 이 계약으로도 막지 못한다 — 그 경우의 선택이 결정 D6 이다.

## 1. 메시지 — `AttemptRunNotice` 와 `AttemptRunNoticeAck`

### `AttemptRunNotice` (FrameType 19 · 노드 서명 · **Evidence** 등급)

```text
1  schema_version  1
2  job_id  3 attempt_id  4 node_id  5 fence_epoch
6  kind            RUN_UNKNOWN = 1 · STOP_CONFIRMED = 2 (0 · 모르는 값 = 거부)
7  origin          RUN_UNKNOWN 일 때만: STARTING = 1 · RUNNING = 2 · PAUSED = 3 (D1 — 저장 모델이 출발을 잃지 않게)
8  reason          RUN_UNKNOWN 일 때만: 불명 조건 (a) EXIT_UNOBSERVED = 1 · (b) START_REQUEST_UNRESOLVED = 2 · (c) PRIOR_RUN_UNCONFIRMED = 3
9  stop_evidence   STOP_CONFIRMED 일 때만: CONTAINER_ABSENT_CONFIRMED = 1 (0 · 모르는 값 = 거부 — 아래 §4. 호스트 경로 증거는 이 계약 밖 — §4)
10 sequence        같은 시도의 알림 순번(1 부터 · 영속 · 재전송은 같은 번호 · 같은 바이트)
11 observed_at_unix_ms   Agent 가 불명을 알아챈 때 · 해제가 정지를 확인한 때
12 issued_at_unix_ms
90 node_signature                      domain_tag "gputeer/v1/attempt-run-notice"
```

- ★ **Evidence 등급이다 — nonce · replay 캐시를 쓰지 않는다**(v1 은 ShortLived 로 적어, "받았다" 응답을 잃으면 같은 바이트의 재전송이 replay 로 영원히
  거부되고 60초가 지나면 시각 검증에서도 만료됐다 — b1 ①). 기존 `AttemptReport` 가 같은 이유로 Evidence 다(`crates/coordinator/src/lib.rs:2039~2050`).
  재전송 방어는 **소비 측 멱등 키** `(attempt_id, node_id, sequence)` 와 그 자리의 바이트 대조가 한다(같으면 멱등 · 다르면 거부).
  ★ 순서(b9 ②): 서명 검증 뒤 **그 키가 이미 있으면 바이트 대조가 먼저다** — 같으면 `created=false` ACK 만 발급하고 상태 · Lease · 예약 · 보류 효과를
    **다시 실행하지 않으며** sequence 규칙도 보지 않는다(그 뒤 더 높은 알림이 와 있어도 재전송은 거부되지 않는다). 다르면 거부. sequence 규칙은 **새 행에만** 적용한다
- 세션 재생 방어는 ACK 가 진다 — ACK 에 그 REPORT 세션 Hello 의 nonce 를 echo 한다(`AttemptReportAck` 와 같은 방식).
- `STOP_CONFIRMED` 도 **노드 키**로 서명한다 — 등급은 WORKER_REPORTED 다. 노드 서명은 "소유자가 실제로 확인했다" 를 증명하지 않는다. 증명하는 것은
  "그 노드의 Agent 코드가 §4 의 확인 절차를 거쳤다고 서명했다" 까지다.

### `AttemptRunNoticeAck` (FrameType 20 · Coordinator 서명 · **ShortLived** · replay nonce = `session_nonce` · domain_tag "gputeer/v1/attempt-run-ack" — 26바이트)

★ b8 ① — v1~v8 은 `gputeer/v1/attempt-run-notice-ack`(33바이트)를 적었다. domain_tag 는 ASCII **32바이트 고정 · 우측 0 패딩**이라(`signing.md` §5)
`canonical.rs` 가 받지 못한다. 알림 쪽 `gputeer/v1/attempt-run-notice` 는 29바이트다

```text
1 schema_version 1 · 2 job_id · 3 attempt_id · 4 node_id · 5 fence_epoch · 6 notice_hash(BLAKE3-256 of sig_input) · 7 kind · 8 sequence
9 created(첫 저장 true · 같은 바이트 재전송 false) · 10 coordinator_id · 11 issued_at_unix_ms · 12 session_nonce(REPORT 세션 Hello nonce echo) · 90 coordinator_signature
```

정확한 형태(b5 ④ — 타입이 canonical 서명 바이트와 스키마 지문을 정한다. enum 은 최상위로 둔다 — 지문 파서가 중첩 선언을 못 읽는다, signing.md §7.3):

```proto
enum RunNoticeKind   { RUN_NOTICE_KIND_UNSPECIFIED = 0; RUN_NOTICE_KIND_RUN_UNKNOWN = 1; RUN_NOTICE_KIND_STOP_CONFIRMED = 2; }
enum RunUnknownOrigin { RUN_UNKNOWN_ORIGIN_UNSPECIFIED = 0; RUN_UNKNOWN_ORIGIN_STARTING = 1; RUN_UNKNOWN_ORIGIN_RUNNING = 2; RUN_UNKNOWN_ORIGIN_PAUSED = 3; }
enum RunUnknownReason { RUN_UNKNOWN_REASON_UNSPECIFIED = 0; RUN_UNKNOWN_REASON_EXIT_UNOBSERVED = 1; RUN_UNKNOWN_REASON_START_REQUEST_UNRESOLVED = 2; RUN_UNKNOWN_REASON_PRIOR_RUN_UNCONFIRMED = 3; }
enum RunStopEvidence  { RUN_STOP_EVIDENCE_UNSPECIFIED = 0; RUN_STOP_EVIDENCE_CONTAINER_ABSENT_CONFIRMED = 1; }

message AttemptRunNotice {          // domain_tag "gputeer/v1/attempt-run-notice" · Lifetime Evidence
  uint32 schema_version = 1;        // 1
  string job_id = 2;  string attempt_id = 3;  string node_id = 4;  uint64 fence_epoch = 5;
  RunNoticeKind kind = 6;  RunUnknownOrigin origin = 7;  RunUnknownReason reason = 8;  RunStopEvidence stop_evidence = 9;
  uint64 sequence = 10;  uint64 observed_at_unix_ms = 11;  uint64 issued_at_unix_ms = 12;
  bytes node_signature = 90;
}
message AttemptRunNoticeAck {       // domain_tag "gputeer/v1/attempt-run-ack" · Lifetime ShortLived
  uint32 schema_version = 1;        // 1
  string job_id = 2;  string attempt_id = 3;  string node_id = 4;  uint64 fence_epoch = 5;
  Digest notice_hash = 6;           // BLAKE3-256(AttemptRunNotice 의 sig_input) — AttemptReportAck.report_hash 와 같은 모양
  RunNoticeKind kind = 7;  uint64 sequence = 8;  bool created = 9;  string coordinator_id = 10;
  uint64 issued_at_unix_ms = 11;    // 만료 = issued_at + GRANT_TTL_MS(AttemptReportAck 와 같다 — protocol/src/signable.rs:526)
  bytes session_nonce = 12;         // replay nonce(16바이트) — REPORT 세션 Hello 의 nonce echo
  bytes coordinator_signature = 90;
}
```
조합 규칙(서명 검증 뒤): 두 메시지 모두 **sequence ≥ 1**(0 은 거부 — b6 ③). kind 가 RUN_UNKNOWN 이면 origin · reason 이 0 이 아니고 stop_evidence 는 0 · STOP_CONFIRMED 면 stop_evidence 가 0 이 아니고 origin · reason 은 0.
모르는 enum 값은 거부한다(fail closed).

`AttemptRunNoticeAck` 의 수명 · 재생 방어는 `AttemptReportAck` 와 같다 — ShortLived 이고 그 REPORT 세션 Hello 의 nonce 를 replay nonce 로 쓴다(다른 세션으로 재생하지 못한다).
`AttemptRunNotice` 자신은 **Evidence** 다 — 시각으로 만료시키지 않고 replay 캐시도 쓰지 않는다. 같은 알림의 재전송은 기본키 (attempt_id, node_id, sequence) 가
멱등으로 거른다(b8 ③ — 전에는 주어 없이 적어 알림까지 ShortLived 로 읽혔다)
ingress 매핑: FrameType 19 → `AttemptRunNotice`(Coordinator 가 받는다) · 20 → `AttemptRunNoticeAck`(Agent 가 받는다) — 요청과 응답을 다른 타입으로 둔다(지금 17 · 6 과 같다).
★ schema_version 상한은 **프레임 종류마다** 고른다(b14 ③). 지금 `read_frame` 은 호출자가 준 상한 하나를 모든 종류에 쓴다(`crypto/src/framed_ingress.rs:262 · 299`)
  — REPORT 세션은 AttemptReport 의 상한(v2 — `protocol/src/constants.rs:136`)으로 부른다(`coordinator/src/lib.rs:3099`). 19 분기만 더하면 AttemptRunNotice v2 가
  통과하고, 상한을 1 로 낮추면 AttemptReport v2 가 깨진다. 그래서 프레이밍 계층이 종류별 상한 표(6 → AttemptReport 상한 · 19 → 1 · 20 → 1)를 받아 서명 필드를
  쓰기 **전에** 적용하게 바꾼다(crates/crypto 변경 — 이 계약의 구현 범위)

★ v1 은 "`AttemptReportAck` 의 kind 칸 재사용" 을 적었는데 **그 메시지에 kind 칸은 없다**(`proto/artifact.proto:267~282` — 내가 틀렸다, b1 ⑥). 또 Agent 는 그 ACK 를
`report_hash` 로 AttemptReport 와 대조하므로(`crates/agent/src/lib.rs:2700~2749`) 재사용하면 그 의미가 흐려진다. 새 메시지로 둔다.

## 2. Coordinator — 받기 · 저장 · 전이

```text
세션       REPORT 세션에서 AttemptReport 와 **나란히** 받는다(지금 그 세션은 AttemptReport 만 받는다 — lib.rs:3078~3185 에 FrameType 19 분기를 더한다)
검증 순서   서명(§0.2 — 이전엔 어떤 필드도 쓰지 않는다) → 그 노드가 그 시도의 노드인가 · fence 가 그 시도의 fence 인가 → **그 시도가 단일 노드인가**
           → kind · origin · reason · stop_evidence 조합 · sequence ≥ 1
           ★ 단일 노드(b10 ①) — 이 계약은 참여 노드가 **알림을 보낸 그 노드 하나**인 시도만 다룬다. 여러 노드 시도(`CreateAttempt.node_ids` · Lease
             `member_node_ids` — proto 는 허용한다)의 알림은 거부한다(Agent 원장에 OPEN 으로 남아 그 노드는 계속 막힌다). 보류 · sequence 가 시도 단위라
             한 노드의 STOP 이 다른 노드의 불명을 풀 수 있기 때문이다. 지금 코드는 단일 노드 시도만 만든다(`staging_store.rs:815 · :1097`).
             ★ 여러 노드 시도를 만드는 코드가 들어오기 **전에** 이 계약을 넓혀야 한다 — 보류 · sequence 를 (attempt_id, node_id) 단위로, Job 보류는 모든 노드의
             보류가 사라져야 풀린다(활성화 선행 조건 — "호환성")
저장       coordinator_attempt_run_notices — 기본키 (attempt_id, node_id, sequence) · 추가 전용. 칸: canonical 서명 입력(`sig_input` 바이트 — 수신 frame
           을 그대로 두지 않는다) · `node_signature` · `notice_hash`(= BLAKE3(sig_input) — ACK 가 echo) · 해석한 필드.
           ★ "같은 바이트" 의 뜻(b10 ④) — **sig_input 과 서명이 둘 다 같다**. 같은 의미를 다른 protobuf 인코딩(필드 순서 등)으로 보내도 canonical 이 같아 멱등이다.
             ★ 모르는 **필드**는 거부되지 않는다(b11 ③ — v11 이 틀렸다) — prost 가 오류 없이 버리고 canonical 에 흔적이 없다(`protocol/tests/schema_evolution.rs` ·
               `signing.md` §7 실측 "유일한 신호는 schema_version"). 그래서 필드만 덧붙인 재전송은 canonical 이 같아 **같은 알림**으로 멱등 처리된다. 거부되는 것은
               지원 범위를 넘는 `schema_version`(SCHEMA_TOO_NEW)이다. 지금 `attempt_report_store.rs` 는 재인코딩을 저장한다 —
             이 표는 비교 대상을 처음부터 canonical 로 정한다
           같은 키에 같은 바이트면 멱등, 다르면 거부. 저장과 아래 전이 · ACK 발급 준비는 **한 트랜잭션**(BEGIN IMMEDIATE)
```

### 전이 — 한 트랜잭션 안에서 (지금 상태별)

★ **Job 에 관여하는 것은 그 Job 의 최신 시도(가장 높은 fence — `failover.rs:145` · `job_store.rs:1444` 와 같은 판별)의 알림뿐이다**(b2 ①). 알림의 시도보다
높은 fence 의 시도가 있으면 — 늦은 도착(§7) — RUN_UNKNOWN · STOP_CONFIRMED 모두 **옛 시도의 상태 · 옛 Lease · 옛 시도가 쥔 예약**만 다루고 Job 상태 · Job 보류는
건드리지 않는다. 그 옛 시도가 아래 "진입 행이 없는 상태" 면 **시도 상태도 바꾸지 않고** 증거만 저장한다(b10 ③). 아래 표는 알림의 시도가 최신 시도일 때다.

| 시도의 지금 상태 | 알림 | 한 일 |
|---|---|---|
| STARTING · RUNNING · PAUSED(현재 fence) | RUN_UNKNOWN | 시도 → RUN_UNKNOWN(단계 1 행 · PAUSED 는 "단계 1 개정") · 그 Job 에 **보류 표식** — 종류 `NOTICE_RUN_UNKNOWN`(시도 id · 알림 hash) · Job 상태는 그대로 |
| RUN_UNKNOWN | RUN_UNKNOWN(더 높은 sequence) | 저장만(사유 · 관측 갱신 기록) |
| RUN_UNKNOWN | STOP_CONFIRMED(더 높은 sequence · 증거 있음) | §3 해제 |
| STARTING · RUNNING · PAUSED | STOP_CONFIRMED(먼저 옴 — 불명 알림을 못 받음 · ★ v18: Agent 기동의 자동 증거(§5)가 내는 알림이 이 행으로 온다) | 한 트랜잭션에서 RUN_UNKNOWN 으로 적고 곧바로 §3 해제 |
| STALE | — | Coordinator 가 기록하지 않는 LOCAL 상태다(아래 "단계 1 개정" 절) — Coordinator 표에는 나오지 않는다 |
| FAILED(STOP_CONFIRMED 로 끝남) | RUN_UNKNOWN — 그 시도의 가장 큰 STOP 번호보다 **낮다** | **저장만** — STOP_CONFIRMED 는 흡수 상태다. 늦게 도착한 옛 알림이 되돌리지 않는다(b1 ⑨) |
| FAILED(STOP_CONFIRMED 로 끝남) | RUN_UNKNOWN — 가장 큰 STOP 번호보다 **높다**(정지를 확인한 뒤 다시 불명이라 알림 — 정상 Agent 는 보내지 않는다) | ★ b7 ① — 시도 상태는 그대로(흡수) · **아래 마지막 행과 같이** Job 이 최종 상태가 아니면 NOTICE 보류를 다시 건다 · `RECONCILE_NEEDED` 사건. 그 보류는 이 번호보다 높은 STOP 으로만 풀린다(fail closed — 가장 최근의 서명된 사실이 "불명" 이면 재배치하지 않는다) |
| FAILED(STOP_CONFIRMED 로 끝남) | STOP_CONFIRMED — 그 시도의 가장 큰 RUN_UNKNOWN 번호보다 높다 | 시도는 그대로 · 그 시도의 NOTICE 보류만 해제(위 행이 다시 건 보류를 푸는 길) |
| CREATED(Grant 받아들임이 아직 기록되지 않음 — ACK 유실 등) | RUN_UNKNOWN · STOP_CONFIRMED | ★ b16 ① — 그 노드 · fence 로 서명된 알림은 Agent 가 Grant 를 **받아들였다**는 증거다(단계 1 — "GRANT_ACCEPTED 전에는 아무것도 띄우지 않는다"). 같은 트랜잭션에서 기존 행 `CREATED -> STARTING | GRANT_ACCEPTED`(조건 "Agent 17단계 검증 통과" — 알림이 그 증거가 된다)를 적고, 그 뒤는 위 STARTING 행과 같다(RUN_UNKNOWN 이면 진입 · STOP 이 먼저면 "먼저 옴" 행 — 시도 종결 · Lease 폐기 · 예약 해제까지). v11~v16 은 CREATED 를 종료 상태들과 한 칸에 두어 STOP 이 시도 · 자원을 닫지 못했다 |

**해제 증거 일반화**(b1 ⑦): 지금 원자 해제 API 는 `Verified<AttemptReport>` 와 저장된 종료 보고를 요구하고 그 report hash 를 해제 기록에 남긴다

로 넓히고 해제 기록에 `evidence_kind · evidence_hash` 를 남긴다.
★ 해제 기록을 둘로 나눈다(b15 ①). 지금 표 `coordinator_reservation_releases` 는 attempt_id 기본키에 `report_hash` 가 **필수**이고(reservation_release.rs:274~281)
  다른 해시는 충돌로 처리한다(:367~379 · :524~534) — 운영자 해제 · 정지 확인을 담을 자리가 없다:
    해제 사실   (attempt_id 기본키 · job_id · node_id · fence_epoch · released_at) — 한 시도에 한 행
    해제 증거   추가 전용 (attempt_id, evidence_kind, evidence_hash) — kind: TERMINAL_REPORT(report_hash) · STOP_CONFIRMED(notice_hash) ·
                OPERATOR_RELEASE(BLAKE3(payload)) · 기존 행은 TERMINAL_REPORT 로 옮긴다. 증거 행은 해시와 함께 **payload 원문**을 보존한다
    OPERATOR_RELEASE payload(b16 ③) — 필드 순서 고정 · 문자열은 u32 BE 길이 + UTF-8 · 정수는 u64 BE:
                명령("release-lost-node" · "release-held-job") · 운영자 진술 · node_id · job_id · attempt_id · fence_epoch · released_at_unix_ms
    운영자 해제 경로 둘 다(release-lost-node · release-held-job) 예약을 지우는 **같은 트랜잭션**에서 해제 사실 + OPERATOR_RELEASE 증거를 쓴다 — release-lost-node 는
    판정 규칙은 그대로 두고 **기록 방식만** 바꾼다(지금은 `coordinator_operator_releases` 에만 적는다 · failover.rs:349~437)
    이관 — 기존 `coordinator_operator_releases`(node_id · attempt_id · job_id · 진술 · 시각 — fence 없음) 행마다 해제 사실 + OPERATOR_RELEASE 증거를 만든다. fence_epoch 는
                시도 표(coordinator_attempts)에서 채우고, 시도 행이 없으면 이관을 멈춘다(fail closed — 사람). 옛 표는 지우지 않는다(감사 원본)
  규칙: 같은 신원(job · attempt · node · fence)의 해제 사실이 이미 있으면 **증거 해시가 달라도** "이미 해제됨"(새 증거 행만 더한다). 신원이 다르면 충돌이다
★ **예약이 이미 없을 때**(b2 ⑤): 같은 시도의 해제 기록이 있으면(`release-lost-node` 가 먼저 풀었다 · 또는 최종 Job 에서 `release-held-job` 이 풀었다 — 그 감사 행을
**같은 해제 기록 표**에 쓴다 · b14 ④) "이미 해제됨" 으로 멱등 처리하고 나머지(알림 저장 · 시도 종결 ·

풀에서는 쓰지 않는다). 1~6 이 **같은 SQLite 트랜잭션**을 실제로 공유해야 한다 — 저장소 API 가 트랜잭션을 받게 바꾸는 것이 이 조각의 코드 절반이다.

## 4. 해제 전 증거 — 미종결 기동 요청 (b1 ④ · v18 결정 D)

`STOP_CONFIRMED` 는 **명령 하나만으로 만들지 않는다.** 아래 절차를 밟은 뒤에만 서명한다. ★ v18 — 이 절차를 밟는 길은 둘이고 **같은 절차**다:
(1) Agent 기동(§5 기동 관문 — 전 Agent 가 실행 중 죽은 컨테이너 행) · (2) 해제 명령(`gputeer container-incidents --clear` — 소유자). v17 까지는 (2) 뿐이라

```text
              원장에 행을 둔다(시작 → 종료 확인 → CLOSED) — 기동 때 started-attempts 의 시도마다 원장 행이 있는지 전수 대조하고, 없으면 새 작업 거부

불명 발생   한 트랜잭션: 사건 OPEN + RUN_UNKNOWN 알림 바이트. 실패하면 CONTAINER_INCIDENT_NOT_RECORDED 와 같게 루프를 멈춘다
해제       한 트랜잭션: §4 확인 뒤 STOP_CONFIRMED 바이트 + 상태 STOP_PENDING. ACK 를 받으면 ACKED(이때 차단이 풀린다). ★ v18 — 해제 명령(OPEN 에서)과
           Agent 기동(ACTIVE 에서)이 같은 절차 · 같은 트랜잭션 모양을 쓴다
           ★ ACK 대조(b10 ②) — ACK 의 attempt_id · node_id · sequence · kind · notice_hash 가 원장의 **그 시도의 가장 최신 알림**과 같을 때만 ACKED 로 간다.
             더 낮은 sequence 의 ACK(늦게 온 옛 STOP 의 ACK)는 그 알림의 "보냄" 표시만 하고 상태는 그대로다. 해제 뒤 같은 시도에 새 불명이 생기면(정상 Agent 는
             만들지 않는다 — 원장이 같은 시도의 새 실행을 거부한다) 행은 OPEN 으로 돌아가고 새 RUN_UNKNOWN 이 가장 최신 알림이 된다
보내기     회차 시작 때 원장의 미전송 알림을 먼저 보낸다(sequence 순)
옛 표식     기존 `<루트>.container-incidents/` 파일(시도 신원 없음 — 단계 1 목록 19 · 20)은 원장으로 옮기지 않는다 — 계속 기동을 막고, 소유자는 옛 명령으로 지운다
            (중앙에는 알림이 없으므로 보류도 없다 — 지금과 같다)
```

## 되돌리는 방법

`--send-run-notice` 를 끄면 Agent 는 알리지 않는다 — Coordinator 는 지금처럼 동작한다(새 표 · 보류는 비어 있다). 원장은 노드 로컬이고 기동 관문만 바꾼다.
규범 행 · 새 표를 되돌리는 것은 저장된 알림 · 보류가 있으면 옮기는 절차가 필요하다.
