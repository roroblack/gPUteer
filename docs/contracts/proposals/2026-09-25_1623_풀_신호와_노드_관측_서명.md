# 변경 제안 · 풀 신호(Grant)와 노드 관측 서명(Hello) — 결함 288 · 301

- 제안자 스트림: Coordinator · Agent · Scheduler (proto 는 Protocol 스트림 소유)
- 유형: schema | protocol
- 상태: **제안(2026-09-25 16:23) — 적용 전.** 계약 변경이라 사용자 결정을 기다린다(선택지는 아래)

## 왜 — 계약 없이 닫지 못한 둘

```text
288  Agent 는 상대 Coordinator 가 풀인지 모른다. 그래서 "수신 확인 없이 풀에 붙은 Agent" 는 실행 전 확인 관문이 서지 않아 한 번 더 돌 수 있다.
     지금은 런북의 설정 규칙(풀 = 수신 확인 필수)으로만 막는다 — 코드가 강제하지 않는다
     (docs/reports/debugs/2026-09-25_0220_재검수90_결함_288_292.md · 0240_재검수91)
301  스케줄러의 신선도 검사는 inventory 의 observed_at(= 운영자가 import-inventory 한 시각)을 본다. 노드의 인사는 이 값을 바꾸지 않는다 —
     등록 하루 뒤(런북의 86400000)부터 모든 노드가 SnapshotNotFresh 로 떨어져 배치가 멈춘다(fork 세션이 시험으로 확인 · 결함 301).
     운영 완화: fork 가 가입 파일을 6시간마다 다시 넣는 예약 작업을 더했다(fork-install-gpu 3c25cb2). 그러나 그건 "운영자가 다시 적었다" 일 뿐
     노드가 실제로 그 GPU 를 갖고 있다는 관측이 아니다
```

## 선택지

### 288 — Grant 에 풀 신호

| 안 | 무엇 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A(권장)** | `ExecutionGrant` 에 서명 필드 `pool_mode`(bool) 추가 — 풀 Coordinator 만 true. Agent 는 true 인데 수신 확인 · 실행 중 갱신이 꺼져 있으면 ACK 전에 거부 | 설정 오류를 코드가 막는다. 서명 필드라 위조 불가 | Grant 스키마 한 단계(벡터 · 참조 구현 · 지문 · signing.md 갱신) |
| B | 계약 그대로 · 런북 규칙만 | 변경 없음 | 설정 오류가 두 번 실행으로 이어질 수 있다(지금 상태) |

### 301 — 노드 관측을 서명해 싣기

| 안 | 무엇 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A(권장)** | FRESH `AgentSessionHello` 에 선택 필드로 **노드가 NVML 로 잰 GPU 목록**(uuid · 총 VRAM · 모델)과 관측 시각을 싣고 서명한다. Coordinator 는 등록된 선언과 **맞을 때만** 그 노드의 관측 시각을 갱신한다(선언은 바꾸지 않는다 — 운영자 선언과 노드 관측을 섞지 않고 "선언이 지금도 사실이다" 의 증거로만 쓴다) | 신선도가 실제 관측에 묶인다. GPU 가 빠지면(선언과 다르면) 갱신이 멈춰 자연히 배치에서 빠진다 | Hello 스키마 변경 · NVML 이 없는 노드(CPU 전용)는 갱신 근거가 없다 — 그 노드는 지금처럼 운영자 재선언에 기댄다 |
| B | 서명된 FRESH 인사(생존)만으로 observed_at 을 갱신 | 계약 변경 없음 | 생존과 하드웨어 사실을 섞는다 — GPU 가 빠져도 "신선" 하다(fork 가 지적한 바로 그 섞임) |
| C | 신선도 검사를 선언에 적용하지 않고 `--silent-after-ms` 만 쓴다 | 가장 단순 | 선언이 틀려져도 알 방법이 없다 |

## 권장

288-A 와 301-A 를 **한 번의 스키마 변경**으로 묶는다(Grant · Hello 둘 다 서명 대상 · 벡터 · 참조 구현을 한 번에 갱신). 순서: 계약(proto · canonical ·
signing.md) → Coordinator(관측 대조 · 갱신) → Agent(관측 싣기 · 풀 관문) → 시험(가짜 NVML 로 선언 일치 · 불일치 · CPU 전용) → 독립 검수.

★ 적용 전까지: 288 은 런북 §5(풀 = 수신 확인 필수), 301 은 fork 의 재선언 예약 작업(§9a)으로 운영한다.
