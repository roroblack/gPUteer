# 변경 제안 · 머클 루트를 **잎 digest** 로 계산하는 입구 — 체크포인트 스트리밍의 선행 조건 (결함 544 · 558 후속)

- 제안자 스트림: Runtime(checkpoint) (대상은 Protocol 스트림 소유 — `crates/protocol`)
- 대상 파일: `crates/protocol/src/canonical.rs`(함수 하나 추가 · 기존 함수가 그것을 부르게 정리)
- 유형: cross-stream(공개 함수 추가 — 서명 · 스키마 · 규범 변경 없음)
- 상태: **제안 — 사용자(통합 책임자) 승인 대기.** 코드는 고치지 않았다.
- 설계: [`docs/plans/2026-09-28_0939_체크포인트_스트리밍_읽기_해시_쓰기.md`](../../plans/2026-09-28_0939_체크포인트_스트리밍_읽기_해시_쓰기.md) "바꾸는 것" 1

## 무엇을 바꾸려는가

```text
추가   pub fn merkle_root_from_leaves(leaves: &[[u8; 32]]) -> Option<[u8; 32]>
         잎이 이미 BLAKE3(0x00 ‖ 내용) 으로 만들어져 있을 때 — 내부 노드 BLAKE3(0x01 ‖ 왼 ‖ 오) · 홀수 승격(signing.md §6.3) 만 한다
정리   merkle_root(chunks) 는 잎을 만든 뒤 merkle_root_from_leaves 를 부른다 — 알고리즘은 한 곳에만 있다(두 벌이면 한쪽만 고쳐진다)
추가   pub fn merkle_leaf_hasher() -> blake3::Hasher   0x00 을 먼저 넣은 Hasher — 호출부가 버퍼마다 update 해 잎을 만든다(잎 규칙도 한 곳에)
```

## 왜 필요한가

체크포인트 게시 · 검증 · 복원이 파일을 통째로 메모리에 올리는 이유 하나가 `merkle_root(&[&[u8]])` 가 **파일 내용 전체**를 받는다는 것이다(결함 558 — 지금은 1GiB 상한으로 억제).
잎은 조금씩 이어 계산할 수 있으므로(BLAKE3 Hasher), 내부 노드가 잎 digest 만 받으면 파일을 버퍼 단위로 흘려 읽으며 digest 와 잎을 한 번에 얻을 수 있다.
이 함수가 없으면 체크포인트 크레이트가 머클 규칙을 **다시 구현**해야 하고, 그러면 규칙이 두 곳에 생긴다(`RULE.md` §3.3).

## 영향받는 스트림

- Protocol — 함수 추가 · 기존 함수 정리. `merkle_root` 의 호출부 4곳은 그대로다(시그니처 불변)
- Runtime(checkpoint) — 스트리밍 조각이 새 함수를 쓴다

## 호환성 영향

- schema_version 증가 필요? **아니오**
- 기존 서명이 무효화되는가? **아니오** — 같은 알고리즘이다. `tests/vectors/canonical_v1.json` 의 Merkle 벡터 `v13_merkle_promotion`(signing.md §12 표 13번 — 청크 1 · 2 · 3개)이 그대로 통과해야 한다
- 멀티 바이너리 스큐 창에 영향? **아니오**(바이트 형식 변화 없음)
- 테스트 벡터 재생성 필요? **아니오**

## 시험

- 기존 벡터(1 · 2 · 3개) 통과 · 참조 구현(`tools/canonical/`) 대조 그대로
- 새 시험: 임의의 청크 목록에 대해 `merkle_root(chunks) == merkle_root_from_leaves(잎들)` · 잎을 버퍼 여러 개로 나눠 만든 것과 한 번에 만든 것이 같다
- 빈 목록 → `None`(기존과 같다)
