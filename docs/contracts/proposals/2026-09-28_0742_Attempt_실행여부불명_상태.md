## 무엇을 바꾸려는가

### 상태의 뜻 — 먼저 정한다

```text
RUN_UNKNOWN   이 시도의 워크로드가 **지금 돌고 있거나, 나중에 돌 수 있다** — 종료를 관측하지 못했고 정지도 확인하지 못했거나,
              **아직 종결되지 않은 기동 요청**(보냈는데 답을 받지 못한 start)이 남아 있다. 뒤의 것은 지금 멈춰 보여도(created) 접수된 요청이
              뒤늦게 적용될 수 있어 "안 돈다" 로 볼 수 없다 — 이 브랜치 코드가 그렇게 다룬다(container.rs:1303~1316 — 결함 532).

아닌 것       "돌았는지는 모르지만 지금은 멈췄다" — 이것은 RUN_UNKNOWN 이 아니다. 정지는 확인했고 종료 코드만 없으므로
              `OBSERVED_NO_CODE`(proto/artifact.proto:241~250 — 종료는 관측, 코드 없음)로 FAILED 를 보고한다. 지금 코드가 그렇게 한다:
              start 실패 뒤 멈춤 확인 · 로그 받기가 되면 exec.rs:574 가 ExitObserved::NoCode 를 만들고, Coordinator 는 종료가 관측됐으므로
              RUNNING 을 거치는 실패로 읽는다(attempt_report_store.rs:673~680 — 결함 210). Job 은 "돌았다" 로 본다.
              ★ 이 경우를 받는 규범 행이 지금 **없다** — RUNNING -> FAILED 의 WORKLOAD_EXITED_ERROR 는 guard 가 "exit code != 0" 이라 코드 없는 종료를
              담지 못한다(state-machines.md:252). Coordinator 가 받아 온 것은 전이 쌍만 보고 guard 를 보지 않기 때문이다. 그래서 행을 하나 더한다
              (아래 EXITED_WITHOUT_CODE).
              RUN_UNKNOWN 의 EXIT_UNOBSERVED 는 그 반대다 — 종료도 정지도 못 봤다(`NOT_OBSERVED` 에 해당).
```

★ 이렇게 좁히는 이유: 요구가 갈리는 지점이 "지금 돌 수 있는가" 이기 때문이다. 멈춤을 확인했으면 재배치해도 두 벌이 되지 않는다.

### Agent 사건과 Attempt 상태를 가른다

```text
노드 사건(Agent · 노드)   사람이 봐야 하는 일을 Agent 가 **그 자리에서** 영속 표식으로 남긴다. Attempt 상태 전이가 아니다 — ControlStore 에
                          기록하지 않으며, Coordinator 에 닿지 않아도 남는다. 노드 차단 · 보존 · 소유자 해제가 이것에 걸린다(아래 MUST 1~5).
                          이 브랜치의 `<루트>.container-incidents` 표식이 이것이다(컨테이너 경로만 — 아래 "규범에 못 미치는 곳").
                          ★ **RUN_UNKNOWN 보다 넓다.** 표식은 세 종류다(container.rs:1555~ `record_incident_if_needed`):
                            EXITED       종료 코드를 관측했는데 로그 · 삭제를 확인하지 못함           — 지금 돌지 않는다
                            NOT_STARTED  이 호출에서 작업은 돌지 않았는데 남은 컨테이너를 못 치움       — 대부분 돌지 않는다(아래 예외)
                            UNOBSERVED   실행 · 종료가 불명                                         — stopped=false 면 지금 돌 수 있다
                          그중 규범 절의 **불명 조건**(아래 "새 설명 절")을 채우는 것만 RUN_UNKNOWN 보고 후보다 — 컨테이너 경로로 풀면: UNOBSERVED 이고 멈춤을 확인하지 못한 것(stopped=false),
                          그리고 NOT_STARTED 중 **만들기 전부터** 같은 이름의 컨테이너가 남아 있어 이 시도의 앞선 실행일 수 있는 것(container.rs:1160~1171).
                          EXITED 와 나머지 NOT_STARTED — 이 호출이 만든, start 를 보내지 않은 컨테이너를 못 치운 것(예 결함 537 분기에서 부재 확인 실패) —
                          는 보고 후보가 아니다(분류 규칙 — 단계 2 목록 22). ★ 지금 exec.rs:531~544 는 사람 확인이 필요한 NOT_STARTED(needs_human)를 **전부** WaitFailed 로, 나머지는 SpawnFailed 로 올린다 —
                          규칙보다 보수적이고, 보고가 없으므로 어긋남이 밖으로 나가지 않는다.
                          ★ 보고 후보가 아닌 사건도 **노드 사건으로는 남는다** — 보존 · 노드 차단 · 소유자 해제 의무(MUST 1 · 4)는 그대로다.
RUN_UNKNOWN(Attempt)      Coordinator 가 Agent 의 **보고를 받아** 적는 시도 상태다. 재배치 판단(단계 2)이 이것에 걸린다. COMMITTED.
```

두 기록은 **범위도 시점도** 다르다 — 노드 사건이 더 넓고(위), Agent 가 보고하기 전 · 보고가 유실된 동안 · 소유자가 로컬에서 먼저 해제한 뒤 어긋난다. 그 구간을 닫는 것이 단계 2 의 핵심이다(아래 목록 7~9 · 15 · 16).

### 표 — 추가하는 행 (§3 Attempt, 각 행은 **물리적으로 한 줄**이다 — §0 파서는 줄마다 한 행으로 읽는다)

```text
STARTING | RUN_UNKNOWN | START_UNCONFIRMED | Agent 가 보고했다 — 이 시도에 "불명 조건"(§3 RUN_UNKNOWN 의 의미 (a)(b)(c))이 성립한다 | 재배치 판단에 불명을 반영(단계 2) | COMMITTED
RUNNING | RUN_UNKNOWN | EXIT_UNOBSERVED | Agent 가 보고했다 — 이 시도에 "불명 조건"(§3 RUN_UNKNOWN 의 의미 (a)(b)(c))이 성립한다(wait 실패 · 정지 요청 뒤 정지 미확인 · 실행기 무응답 등) | 재배치 판단에 불명을 반영(단계 2) | COMMITTED
RUN_UNKNOWN | FAILED | STOP_CONFIRMED | 노드 소유자가 정지 또는 부재를 확인하고 명시적으로 해제했다는 보고 | 산출물을 확정하지 않는다, 종료는 관측 못 함으로 남긴다 | COMMITTED
```

### 표 — 바꾸는 행 (§3 Attempt · `START_FAILED` 의 guard 를 좁힌다)

```text
전  STARTING | FAILED | START_FAILED | 환경 준비 실패 또는 프로세스 기동 실패 | workspace 정리 | COMMITTED
후  STARTING | FAILED | START_FAILED | 작업이 돌지 않았음이 확실하다 — 환경 준비 단계에서 실패 · 기동 요청이 실행기에 닿지 않았음이 확인됨 · 그리고 이 시도에 대해 "불명 조건"(§3 RUN_UNKNOWN 의 의미)이 하나도 성립하지 않음(같은 절의 우선순위 · 호환 예외) | workspace 정리 — 단 열린 노드 사건이 있으면 해제까지 보존 | COMMITTED
```

★ "정지 · 부재를 확인함" 은 여기 넣지 않는다 — 정지 확인은 "지금 안 돈다" 의 증거이지 "한 번도 안 돌았다" 의 증거가 아니다(OCI poststart). v4~v6 은
넣었다가 코덱스 a6 이 짚었다. 기동 요청이 닿았을 수 있고 뒤에 정지를 확인한 경우는 아래 새 행(EXITED_WITHOUT_CODE)이다.

### 표 — 추가하는 행 하나 더 (§3 Attempt · 기존 전이 쌍 `RUNNING -> FAILED` 에 trigger 를 더한다)

```text
RUNNING | FAILED | EXITED_WITHOUT_CODE | 정지는 관측했지만 종료 코드가 없다 — 신호 종료 · 코드 조회 실패 · 기동이 실패로 답한 뒤 정지를 확인함(돌았을 수 있다). 그리고 "불명 조건" 이 성립하지 않는다 — 특히 종결되지 않은 기동 요청이 없다(무응답 start 가 남았으면 한 번의 정지 조회로 여기 오지 않는다) | 로그 보존, 산출물은 확정 규칙대로, Job 은 "돌았다" 로 본다 | COMMITTED
```

★ 기동 쪽(STARTING)에서 이 경우가 생기면 Coordinator 는 지금처럼 RUNNING 을 거쳐 읽는다(결함 210 — 종료가 관측됐으면 프로세스는 떴다고 본다).
  새 상태를 만들지 않고 기존 쌍에 trigger 만 더하므로 `transition_triggers` 의 `(Running, Failed)` 목록에 한 줄이 는다.

★ 이것은 **기존 행의 의미 변경이다**(새로 보고를 만드는 쪽에 대해). v2 · v3 는 문구를 그대로 두고 규범 절의 우선순위로만 풀었는데, 그러면 표만 보고
구현한 호출자가 실패 응답에 `START_FAILED` 를 고를 수 있다 — 순수 커널은 guard 를 보지 않는다(`attempt_state.rs:19~24`). 그래서 guard 자체를 좁힌다.
옛 보고의 해석은 규범 절의 **호환 예외**로 따로 남긴다.

### 새 설명 절 — `### RUN_UNKNOWN 의 의미` (§3 의 "STALE 의 의미" 다음)

```text
RUN_UNKNOWN 은 "돌았다" 도 "안 돌았다" 도 아니다. "지금 돌고 있거나, 종결되지 않은 기동 요청 때문에 나중에 돌 수 있는데, 확인할 수 없다" 다.

불명 조건 (이 절의 정의 — 표의 START_UNCONFIRMED · EXIT_UNOBSERVED · START_FAILED guard 가 이것을 가리킨다. 실행기와 무관하게 적는다)
  한 시도에 대해 아래 중 **하나라도** 성립하면 불명 조건이 성립한다:
    (a) 워크로드가 실행됐거나 기동 요청이 실행기에 닿았을 수 있고, 종료를 관측하지 못했으며 정지 · 부재도 확인하지 못했다(확인의 기준은 아래 MUST 3).
        ★ 기동 요청 **전**의 실패(환경 준비 실패)와 요청이 **닿지 않았음이 확인된** 실패는 (a) 가 아니다 — (c) 가 성립하지 않으면 START_FAILED 다
    (b) 종결되지 않은 기동 요청이 있다 — 보냈는데 답을 받지 못했다(지금 멈춰 보여도 뒤늦게 적용될 수 있다)
    (c) 기동을 준비하기 **전부터** 같은 시도의 실행 흔적(같은 이름의 컨테이너 · 프로세스)이 남아 있고, 그것의 정지 · 부재를 확인하지 못했다
  성립하지 않는 것(불명이 아니다):
    · 종료를 관측했다(코드가 있든 없든) — 로그 · 정리만 못 했어도 불명이 아니다(노드 사건으로만 남는다)
    · 이번 호출이 스스로 만든 실행 흔적이고 기동 요청을 **보내지 않았다** — 정리만 못 했어도 불명이 아니다(노드 사건으로만 남는다)
  불명 조건이 성립하면 Agent 는 불명(START_UNCONFIRMED · EXIT_UNOBSERVED)만 고를 수 있고, 불명 보고의 후보는 정확히 이것이다.
Agent 쪽에서는 Attempt 상태가 아니라 **노드 사건**(영속 표식)으로 남는다 — 그 표식은 이 상태보다 넓다(위 "Agent 사건과 Attempt 상태를 가른다").

기동 실패와 불명의 우선순위 (MUST — 좁힌 START_FAILED guard 의 풀이)
  기동 요청이 실행기에 **닿았을 수 있고**, 정지 · 부재를 **긍정적으로** 확인하지 못했으면 → 불명(START_UNCONFIRMED). START_FAILED 를 고르지 않는다.
  START_FAILED 는 둘 중 하나일 때만: 환경 준비 단계에서 실패했다, 또는 기동 요청이 실행기에 닿지 않았음이 확인됐다(띄우지 못함 · 보내기 전에 멈춤).
  ★ 그리고 **둘 다에 붙는 조건**(표의 guard 에도 적었다) — 위 **불명 조건이 하나도 성립하지 않을 때만**이다. 하나라도 성립하면 START_UNCONFIRMED 가
    우선한다 — 이번 호출이 요청을 못 보냈다는 것은 앞선 실행이 없다는 증거가 아니다(불명 조건 (c)).
  ★ 미시작은 확실한데 **정리만 못 한** 경우(이 호출이 만든, start 를 보내지 않은 컨테이너를 못 치움)는 START_FAILED 다 — 단 노드 사건이 열려 있으므로
    workspace · 컨테이너는 사건이 해제될 때까지 보존하고 노드는 새 작업을 받지 않는다(표의 effect · MUST 1 · 4).
  기동 요청이 **실패로 답했고**(종결됨) 뒤에 정지를 **확인했으면** → EXITED_WITHOUT_CODE(돌았을 수 있다). 기동 요청이 답하지 않았거나(종결되지 않음 — (b))
  정지를 확인하지 못했으면 → START_UNCONFIRMED.
  ★ 실패 응답 · 무응답 · 시한 초과 · "그런 것 없음" 은 닿지 않았다는 증거도, 정지의 증거도 아니다(OCI poststart — 결함 490).

호환 예외 — 옛 보고의 해석 (좁힌 guard 의 예외. 옛 형식 지원 종료 조건 — 미전송 보관의 배출 확인 · 최소 Agent 버전 — 을 채울 때까지 유지한다)
  Coordinator 는 STARTING 시도에 대한 기존 보고 — v1 FAILED(관측 칸 없음) · v2 FAILED + NOT_OBSERVED — 를 지금처럼 START_FAILED 로 읽는다.
  이 읽기는 guard 를 확인한 것이 아니라 **옛 형식의 해석 규칙**이다.
  RUNNING 시도에 대한 같은 보고도 지금처럼 RUNNING -> FAILED 로 읽는다. 어느 쪽이든 **옛 형식의 FAILED + NOT_OBSERVED 는 RUN_UNKNOWN 을 뜻하지 않는다** —
  RUN_UNKNOWN 은 단계 2 의 새 보고 형식으로만 들어간다.
  ★ (MUST · Coordinator) 시도가 이미 **RUN_UNKNOWN 이면 옛 형식 보고는 그 상태를 바꾸지 않는다** — 옛 FAILED 는 STOP_CONFIRMED 의 증거가 아니다.
    RUN_UNKNOWN 에서 나가는 입력은 STOP_CONFIRMED 보고 하나뿐이다. 보고 버전 · 종류로 trigger 를 고르고, 상태 쌍만으로 STOP_CONFIRMED 를 추론하지 않는다
    (지금 코드는 상태 쌍만 본다 — attempt_report_store.rs:631 · :662~ — 단계 2 목록 25).
  그 보고 형식에는 불명을 표현할 칸이 없기 때문이다. 그 보고가 **최신 시도의 것이고 Job 이 STAGING · RUNNING 이면** Job 은 FAILED 로 끝나고 재배치하지 않는다
  (job_store.rs:1441~1459). 이전 시도의 늦은 보고는 보고와 그 시도만 적고 지금 Job 은 바꾸지 않는다 — 어느 쪽이든 이 해석이 두 벌을 새로 만들지는 않는다.
  잃는 것은 "지금 돌 수 있다" 는 정보다. 이 예외는 Coordinator 의 **옛 보고 읽기**에만 적용된다 — 새로 보고를 만드는 쪽(Agent)은 좁힌 guard 와 위 우선순위를 따른다.

MUST (Agent · 소유자 쪽 — 시도가 RUN_UNKNOWN 이거나, 그 노드에 불명 사건이 열려 있는 동안)
  1  자동 파괴 금지 — workspace · 컨테이너 · 로그를 **자동으로** 지우지 않는다.
     예외: 노드 소유자의 명시적 정리(CLAUDE.md §0.1), SENSITIVE 데이터의 폐기(§0.5).
  2  성공 확정 금지 — RUN_UNKNOWN 에서 COMPLETED 로 가는 행이 없다.
  3  정지 · 부재의 증거는 **따로 보낸 새 조회**(inspect)가 "돌지 않는다" · "그런 것 없음" 이라고 답한 것뿐이다. 실패한 명령(start · kill · rm)
     자신의 실패 응답 · 무응답 · "없음" 문구는 증거가 아니다. 이 기준으로 불명에 **들어갈지** 정한다 — 이 브랜치 코드가 그렇게 한다

     ★ 조회의 "없음" 도 런타임의 답이다 — 이름을 같은 시도로만 만들어(결함 290) 다른 컨테이너와 섞이지 않게 한 것이 기대는 전제다.
     ★ **종결되지 않은 기동 요청이 있으면 한 시점의 조회는 증거가 아니다** — 지금 멈춰(또는 없어) 보여도 요청이 뒤늦게 적용될 수 있다(결함 532).

     ★ 해제한 사실을 잃지 않고 전하는 순서(미전송 보관 → 로컬 해제 → 전송)는 단계 2 가 정한다(아래 목록 16).
```

## 왜 필요한가 — 지금 표로는 쓸 수 없는 사실이 있다

### 1. 표에는 「지금 돌 수 있는데 확인할 수 없다」 칸이 없다

`STARTING` 과 `RUNNING` 에서 나가는 행은 전부 "돌기 시작했다 / 끝났다(코드 있음) / 실패했다(정리한다)" 중 하나를 확정한다. OCI `poststart` 훅은 사용자
프로세스가 **돈 뒤에** 실행되고, 실패하면 `start` 가 실패로 답한다(결함 490 — `crates/agent/src/container.rs:1270` 주석). 무응답 · 시한 초과 · `wait`
실패도 같다. 이때 멈춤까지 확인하지 못하면, 표에 쓸 수 있는 행이 없다. 그래서 지금 코드는 **아무 행도 쓰지 않는다** — 아래 2.

### 2. 지금 무슨 일이 일어나나 — 두 벌 실행이 생기는 실제 경로

워크로드가 뜰 때 시도는 이미 `RUNNING` 이다. 풀 방식 Agent 는 실행 **전에** 첫 갱신을 동기로 확인받고(`crates/agent/src/lib.rs:1497~1508`), 그 갱신이
Coordinator 에서 시도 `STARTING -> RUNNING` · Job `STAGING -> RUNNING` 을 먼저 적는다(`crates/coordinator/src/staging_store.rs:466`).

```text
Agent        컨테이너가 도는 중 멈춤을 확인하지 못함(container::run 의 Unobserved, stopped=false)
               -> exec.rs:549~552 가 ExecutionError::WaitFailed
               -> lib.rs:3200~3205 가 WORKLOAD_MAY_BE_RUNNING 을 찍고 Err 로 끝냄 — 종료 보고(AttemptReport)를 보내지 않는다
               -> 회차가 끝나 실행 중 갱신이 멈춘다 · 사건 표식이 남아 이 노드는 새 작업을 받지 않는다
Coordinator  갱신이 멈춘 것만 본다 -> Lease 만료 + grace 경과(failover.rs:173)
               -> Job RUNNING 이고 이어갈 체크포인트가 있으면 RUNNING -> INTERRUPTED -> REPLANNING -> QUEUED(job_store.rs:1233~1238)
                  -> 다른 노드에 새 시도 ★ 옛 컨테이너가 돌고 있으면 두 벌
               -> 체크포인트가 없으면 RUNNING -> INTERRUPTED -> FAILED — 두 벌은 아니지만 "FAILED" 로 끝난 Job 이 옛 노드에서 계속 돌 수 있고,
                  "모른다" 는 사실은 Coordinator 어디에도 남지 않는다
```

★ 옛 노드의 예약은 풀리지 않는다(`failover.rs:40~41` — 만료 표시만). 그래서 두 벌은 **다른 노드**에서 일어난다 — 노드를 막는 것만으로는 못 막는다는
설계 문서 P0 가 이것이다. 이어갈 체크포인트는 공유 저장소가 있을 때만 생기므로(`FailoverPolicy.shared_checkpoint_root`), 두 벌 경로는 그 배치에서 열린다.

★ 풀 밖 lane(수신 확인을 요구하지 않는 Agent)은 실행 전 관문이 없어(`lib.rs:1505~1507` 주석 — 결함 293) 첫 갱신 전에 워크로드가 뜰 수 있다.
그 lane 에서는 불명이 시도 `STARTING` 에서 생길 수 있다 — 그래서 `STARTING -> RUN_UNKNOWN` 행도 둔다. 규범 `PROCESS_STARTED` 의 guard("프로세스 기동 +
첫 progress")대로라면 모든 lane 에서 워크로드는 `STARTING` 중에 뜬다 — 풀 경로가 실행 전에 `RUNNING` 을 적는 것은 결함 218 대응의 구현 선택이다.

### 3. 종료 보고의 wire 는 이 구분을 싣지 못한다

`AttemptReport.exit_observation` 에 `EXIT_OBSERVATION_NOT_OBSERVED` 가 있고 조합 규칙은 `FAILED` 에 모든 관측을 허용한다(`crates/protocol/src/attempt_report_rules.rs:136`).
이 값은 "종료를 못 봤다" 이지 "지금 돌 수 있다" 가 아니다 — 멈춤을 확인했는지 싣는 칸이 없다. 시도가 `STARTING` 이면 Coordinator 는 관측 없는 실패를
`RUNNING` 을 거치지 않는 `START_FAILED` 로 읽고(`crates/coordinator/src/attempt_report_store.rs:656` `normative_path`), `RUNNING` 이면 `RUNNING -> FAILED` 로
읽는다. 최신 시도의 보고이고 Job 이 `STAGING` · `RUNNING` 이면 Job 은 `FAILED` 로 끝나고(`crates/coordinator/src/job_store.rs:1441~1459`) 재배치하지 않는다.
이전 시도의 늦은 보고는 Job 을 바꾸지 않는다 — 그러니 이 wire 경로 자체는 두 벌을 만들지 않는다. 잃는 것은 "지금 돌 수 있다" 는 정보다.
확인 범위: `crates/agent/src` 에서 `ExitObservation::NotObserved` 를 만드는 곳을 grep 으로 찾았고 0건 — 이 저장소의 Agent 는 이 조합을 보내지 않는다.
놓칠 수 있는 것: 옛 v1 Agent · 다른 송신자(v1 `FAILED` 는 관측 칸 자체가 없다).

### 4. 지금 Agent 가 기동 실패를 가르는 방식 — 우선순위 규칙과의 차이

```text
start 요청을 띄우지 못함(결함 537, container.rs:1288~)          만든 컨테이너를 ID 로 지우고 부재 확인 — 되면 NotStarted -> SpawnFailed(규칙과 맞다 — 닿지 않았다),
                                                                   못 하면 NotStarted(사람 필요) -> WaitFailed + 노드 사건(container.rs:948~956 · :1032~1053 · :1285~1295 · exec.rs:531~541)
만들기 전 같은 이름이 남음 · create 결과 확인 불명(container.rs:1168~) NotStarted(사람 필요) -> WaitFailed(exec.rs:531~539)  보수적 — 불명 쪽으로 간다
start 가 실패로 답함 · 뒤에 멈춤 확인 · 로그 받음                    Unobserved(stopped) -> NoCode 보고(exec.rs:574)   규칙과 맞다(EXITED_WITHOUT_CODE — RUN_UNKNOWN 아님)
start 가 실패로 답함 · 멈춤 미확인                                     Unobserved(not stopped) -> WaitFailed · 보고 없음    불명이다((a)) — 보고 길이 없다(단계 2)
start 가 답하지 않음                                                  멈춤 확인을 **시도하지 않고** Unobserved(not stopped)    불명이다((b)) — 뒤늦은 적용 가능성(container.rs:1303~1316)
                                                                     -> WaitFailed · 보고 없음
```

★ `SpawnFailed` · `WaitFailed` 모두 지금은 종료 보고를 보내지 않는다(`lib.rs:3200~3211`). 즉 Agent 가 `START_FAILED` 에 해당하는 보고를 보내는 경로는 지금
없다 — 우선순위 규칙은 단계 2 에서 보고가 생길 때 Agent 가 따를 의무다.

## 설계 판단 — 왜 이 모양인가

| 판단 | 이유 |
|---|---|
| 상태 **하나**가 `STARTING` · `RUNNING` 두 출발을 받는다 | 요구가 같다(보존 · 성공 확정 금지 · 사람 해제). ★ 지금 저장 모델은 최종 상태만 적어(`staging_store.rs:271` · `:1015`) **어디서 왔는지 복구할 수 없다** — 결정 D1 |
| 진입을 Agent 의 **보고로** 정의하고 COMMITTED 로 | 재배치 판단(단계 2)이 기댈 기록은 Coordinator 에 있어야 한다. Agent 가 혼자 아는 사실은 Attempt 상태가 아니라 불명 사건으로 따로 둔다 — v2 는 진입을 LOCAL 로 두어, Coordinator 가 그 상태를 적는 순간 §0 의 LOCAL 뜻("ControlStore 에 기록하지 않음")과 어긋났다 |
| `RUN_UNKNOWN -> COMPLETED` 를 두지 않는다 | 로그는 끝난 뒤 한 번 받고(결함 492) 런타임 로그가 회전하면 받은 것이 완결이 아니다(결함 551). 설계 P1(follow · 완결 표식)이 생기면 다시 본다 |
| `RUN_UNKNOWN -> RUNNING` 을 두지 않는다 | 다시 붙을 수단(로그 · 진행 신호 · 갱신의 재부착)이 없다 |
| `RUN_UNKNOWN -> CANCELLED` 를 두지 않는다 | 취소는 정지를 확인하지 않는다 |
| `CREATED -> RUN_UNKNOWN` 을 두지 않는다 | `GRANT_ACCEPTED` 전에는 아무것도 띄우지 않는다 |
| 호스트 프로세스 경로도 이 상태에 든다 | "지금 돌 수 있다" 는 실행기와 무관하다. ★ 그러나 **지금 코드가 못 따른다** — 아래 "규범에 못 미치는 곳" |
