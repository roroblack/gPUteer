흐름(풀 모드): `Hello -> Grant -> ACK -> (Coordinator 가 ACK 검증 · 시도 STARTING · Job RUNNING 기록) -> GrantAckReceipt -> 닫는다`.
★ 2026-09-24 (결함 233 · 218) — 수신 확인은 기록 결과가 RECORDED(방금 적음)이거나 STARTING_STILL_CURRENT(유실 뒤 같은 노드의 재발급 ACK)일 때만
  보낸다. 아무것도 적지 않은 결과(대체된 시도 · 시계가 뒤 · 이미 끝난 시도)에는 보내지 않는다(`ACK_RECEIPT_WITHHELD`) — 전에는 결과를 안 봤다.
  재발급이 두 번째 실행이 되지 않게 하는 것은 Agent 의 시작 기록이다(`--require-ack-receipt` 를 켠 Agent 만 본다).
  ★ 2026-09-24 (재검수 82 · 결함 246 · 247 · 248) — 그 기록은 **체크포인트 루트**에 묶인다 — 같은 node id 로 루트를 바꿔 띄운 Agent 에는 안 보인다.
  그래서 재발급은 Lease 가 한 번도 갱신되지 않았고 ACK 뒤 갱신 간격이 조용히 지났을 때만 한다(돌고 있는 Agent 는 그 전에 갱신한다).
  시작 기록 뒤 · 실제 실행 전에 죽은 시도는 다시 돌지 않는다(노드 유실과 같게 처리). Agent 는 Lease 가 첫 갱신 전에 만료될 만큼 짧으면 시작하지 않는다.
Agent 는 `--require-ack-receipt` 면 받고 대조(grant · attempt · 자기 · Coordinator · **ack_nonce**)한 뒤에만 실행한다.

## 왜 필요한가

결함 131 — Agent 는 ACK 를 보낸 뒤 Coordinator 가 받아들였는지 알 방법이 없었다. 거부된 ACK(옛 Coordinator · 대조 실패 · 저장 실패) 뒤에도
작업을 돌렸다. 논의 71 은 88 과 **묶지 않고 배포 순서로 묶으라**고 했다 — 선례는 REPORT 세션의 `AttemptReportAck`(저장 뒤에만 서명).

## 호환성

- 옛 Agent + 새 Coordinator(풀 모드): Coordinator 가 보내지만 옛 Agent 는 읽지 않는다 — FRESH 연결은 곧 닫힌다. 해 없음
- 새 Agent(`--require-ack-receipt`) + 옛 Coordinator: 확인이 오지 않는다 -> `ACK_RECEIPT_MISSING` 으로 **실행하지 않는다**(fail-closed,
  시험 `an_agent_that_requires_an_ack_receipt_does_not_run_without_one`).
  ★ 2026-09-24 정정(재검수 78) — 여기 "시도는 CREATED 로 남는다" 고 적었는데 틀렸다. ACK 기록(STARTING · RUNNING)은 풀 밖 control DB lane 에도
  있어, 그 조합에서는 시도가 STARTING 으로 남고 Lease 만료 뒤 장애 판정이 처리한다(체크포인트가 없으면 FAILED)
- 요구하지 않는 Agent 는 전과 같다

## 결함 88 과의 관계 (2026-09-23 판단)

88 의 C(ACK 에 grant_nonce 칸)는 **이 변경에 넣지 않았다.** 풀 모드는 Grant id 를 발급마다 난수로 뽑아(신뢰망 K) 88 이 짚은
유도 nonce 겹침이 그 lane 에서 생기지 않는다 — 그래서 풀 모드에서는 계약 변경 없이 `--replay-db`(모든 단수명 메시지의 재시작을 넘는 방어)를
켰다(88 조각 3). 계획이 D 를 보류한 이유(`start_checkpoint_id` 의 grant id 의존)는 풀 모드에서 성립하지 않는다 — 풀 모드는 **CREATED 인
시도에만** Grant 를 다시 낸다(받아들여진 시도는 다시 내주지 않는다). 풀 밖의 순차 · 다중 lane 에는 여전히 C 가 남아 있다.
