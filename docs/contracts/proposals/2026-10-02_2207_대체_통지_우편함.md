## 왜 필요한가 (이것 없이 막히는 것)

소유자가 PURE 작업에 "계속 돌리기" 를 고르고 끊긴 채 Lease 가 끝나면, 갱신 함수는 연결 **전에** 스스로 만료를 보고(LOCAL_EXPIRED) 갱신 스레드가 끝난다
(`crates/agent/src/lib.rs` 갱신 스레드). 그 사이 장애 이어받기가 작업을 큐로 되돌려 다른 노드가 맡아도, 다시 연결된 옛 노드는 "그 시도는 폐기됐다" 를 들을 길이
없어 소유자가 멈출 때까지 같은 작업을 돌린다(두 벌). 서명된 REVOKED 는 다음 갱신이 Coordinator 에 **닿아야** 전해진다 — 갱신을 그만둔 노드에는 닿지 않는다.

## 무엇을 통지하는가 (mb1 ④)

**"그 시도는 폐기됐다"** 다 — "다른 노드에 재배정됐다" 가 아니다. 장애 이어받기는 같은 커밋에서 새 시도를 만들지 않고 Job 을 큐로 되돌리거나(이어갈 체크포인트가
있으면) 실패로 둔다(`failover.rs`). 어느 쪽이든 **옛 시도는 더는 유효하지 않다** — 통지는 그 사실과 Job 의 처분(REQUEUED · FAILED)을 싣는다. 재배정된 새 시도의 신원은
그때 없으므로 싣지 않는다(계획 v3 §2 의 "대체한 시도" 문구는 이 뜻으로 고친다).

## 1. 메시지

```text
SupersedeNotice      FrameType 21 · Coordinator 서명 · **Evidence**(만료 · replay 캐시 없음 — 며칠 뒤 전해져도 유효. 재전달은 소비 측 멱등 키 notice_id)
  1  schema_version 1
  2  notice_id        hex(BLAKE3-256( "gputeer/supersede-notice-id/v1\0" · u32 BE 길이 + UTF-8 attempt_id · u32 BE 길이 + UTF-8 node_id · u64 BE fence_epoch ))
                      — 같은 시도 · 노드 · fence 의 폐기는 같은 ID. 같은 ID 를 다시 쓰려 하면 **서명 대상 내용이 같을 때만 멱등**, 다르면 오류
  3  job_id  4 attempt_id  5 node_id  6 fence_epoch  7 lease_id      폐기된 옛 시도의 신원
  8  cause            SupersedeCause: NODE_LOST = 1(장애 이어받기) · 0 · 모르는 값 거부
  9  job_disposition  SupersedeJobDisposition: REQUEUED = 1(이어갈 체크포인트로 큐) · FAILED = 2(이어갈 것 없음) · 0 · 모르는 값 거부
  10 decided_at_unix_ms   폐기를 커밋한 Coordinator 시각 — **Evidence 의 관측 시각**(`Signable::observed_at_unix_ms` 가 이 칸을 돌려준다 · signing.md §9.1)
  11 coordinator_id
  12 issued_at_unix_ms    = decided_at_unix_ms
  90 coordinator_signature                         domain_tag "gputeer/v1/supersede-notice"(27바이트)

MailboxDelivery      FrameType 22 · Coordinator 서명 · ShortLived(만료 issued_at + GRANT_TTL_MS · replay nonce = session_nonce 16바이트 — MAILBOX 세션 Hello 의 nonce echo)
  1  schema_version 1
  2  node_id          = Hello 의 node_id
  3  notices          repeated SupersedeNotice — 그 노드 앞으로 와서 **받아들여진 답이 없는 것 전부**(decided_at 오래된 순 · notice_id 중복 없음) · 비면 "지금 우편함은 비었다"
  4  coordinator_id  5 issued_at_unix_ms  6 session_nonce
  90 coordinator_signature                         domain_tag "gputeer/v1/mailbox-delivery"(27바이트)
  ★ 겉 서명(이 세션 · 지금 · 이 목록이 전부)과 안의 통지 서명(영속 사실)을 **각각** 검증한다 — Grant 안의 Lease 와 같은 방식(규칙 i)

MailboxAck           FrameType 23 · 노드 서명 · ShortLived(만료 issued_at + GRANT_TTL_MS · replay nonce = session_nonce — 같은 세션의 Hello nonce)
  1  schema_version 1
  2  node_id          = Hello 의 node_id = 서명자
  3  handled          repeated SupersedeHandled { notice_id · notice_hash(BLAKE3-256 of 그 통지의 sig_input) · action }
                      action: STOPPED = 1(돌던 것을 멈췄다 — 정지 성공 뒤에만) · NOT_RUNNING = 2(§4 의 확인을 거쳐 이 노드에서 돌지 않는다)
  4  issued_at_unix_ms  5 session_nonce
  90 node_signature                                domain_tag "gputeer/v1/mailbox-ack"(22바이트)

MailboxAckReceipt    FrameType 24 · Coordinator 서명 · ShortLived(만료 issued_at + GRANT_TTL_MS · replay nonce = session_nonce — mb2 ③)
  1  schema_version 1  2 node_id  3 accepted(repeated notice_id — 이번 답으로 받아들여 커밋한 것)  4 coordinator_id  5 issued_at_unix_ms  6 session_nonce
  90 coordinator_signature                         domain_tag "gputeer/v1/mailbox-receipt"(26바이트)
  ★ mb1 ② · mb2 ② — 답을 보낸 뒤 끊기면 Agent 는 커밋 여부를 모른다. 수신 확인을 받은 notice_id 는 "처리 끝" 이다. 못 받았으면 **다음 MAILBOX 세션의 배달**을 본다 —
    배달은 서명된 "그 노드의 미확인 **전부**(지금)" 이므로, 거기 **없으면 커밋됐다**(처리 끝) · **있으면 커밋되지 않았다**(같은 처리를 되풀이 — 멱등 · §4).
    v2 는 "같은 통지가 다시 온다" 고만 적어, 커밋되고 수신 확인만 잃은 경우(다시 오지 않는다)를 설명하지 못했다
```

조합 규칙(서명 검증 뒤 · 모두 거부가 기본):
- 통지: node_id = 받는 노드 · cause · job_disposition ≠ 0 · issued_at = decided_at · notice_id 가 위 식으로 다시 계산한 값과 같다
- 배달: node_id = Hello 의 node_id · 안의 통지가 모두 그 node_id · notice_id 중복 없음 · session_nonce = 그 세션 Hello 의 nonce
- 답: node_id = Hello 의 node_id · handled 의 notice_id 는 **그 세션에서 실제로 배달한 것**만 · 중복 없음 · notice_hash 가 배달한 그 통지와 같음 · action ≠ 0
- 수신 확인: accepted ⊆ 답의 handled · session_nonce = 그 세션의 nonce
- 모르는 enum 값 거부(fail closed)

## 2. 세션 — `AgentSessionHello.mode = MAILBOX(5)`

```text
Agent        새 연결 → Hello(MAILBOX) → MailboxDelivery(겉 · 안 검증) → 통지마다 처리(§4) → MailboxAck → MailboxAckReceipt(검증) → 닫는다
Coordinator  Hello 검증 → 그 노드의 미확인 통지를 읽어 배달 → 답 검증 → handled 마다 acked_at · action · 답 바이트를 적는다(한 BEGIN IMMEDIATE) →
             커밋 뒤 수신 확인 → 닫는다. 답에 없는 통지는 다음 세션에 다시 간다
```

## 3. Coordinator — 서명과 영속 (mb1 ①)

```text
표          coordinator_supersede_notices — 기본키 notice_id · node_id · job_id · attempt_id · fence_epoch · lease_id · cause · job_disposition · decided_at ·
            **signed_bytes(서명 포함 전체 · 필수)** · acked_at_unix_ms · ack_action · ack_bytes. 추가 전용(감사) — 답이 온 행은 배달에서 빠질 뿐 지우지 않는다
쓰는 때     장애 이어받기(failover)가 옛 Lease 를 폐기하는 **같은 트랜잭션**에서 **서명한 통지 바이트까지** 쓴다 — 폐기는 됐는데 서명된 통지가 없는 상태가 없다
서명 키     failover 는 scheduler-tick 프로세스에서 돈다. 지금 그 명령은 Coordinator 서명 키를 받지 않는다(`--coordinator-id` 만) — 이 제안이 **`--coordinator-key-file`
            (Coordinator 와 같은 키 파일 · 같은 보호 등급)** 을 더하고, `--failover-grace-ms` 를 주면 이 키를 **필수**로 한다(없으면 기동 거부 — 서명 없이 폐기하지 않는다).
            ★ 배포 파일(유닛 · coordinator.ps1 · 스케줄러 서비스)도 같은 키를 넘기게 고친다. 서명자 신원 = `--coordinator-id` — Agent 가 아는 Coordinator 키로 검증한다
쓰지 않는 때  소유자 선점(OWNER_PREEMPT — 노드가 스스로 멈추고 보고했다) · 정상 종료 · 취소(이 제안 밖 — 필요하면 cause 를 더한다)
```

## 4. Agent — 처리 · 순서 (mb1 ② ③)

```text
적용 범위      ★ mb2 ① — **풀 모드에서만**이다. 관문(아래)은 풀 경로의 ACK 기록(`record_grant_accepted` — `--grant-from-control-db` 일 때만 불린다)에 있고, 수신 확인도 풀 모드에서만
              간다. 풀 밖 순차 lane(수신 확인 없이 ACK 뒤 실행) · 다중 Agent lane(별도 ACK 처리) 에는 이 관문이 없다 — 그래서 Coordinator 는 `--mailbox-gate` 를 `--pool-mode`
              없이 주면 **기동을 거부**하고, Agent 는 `--use-mailbox` 를 `--require-ack-receipt` 없이 주면 기동을 거부한다. 풀의 Grant(v4 · pool_mode)는 어떻게 발급됐든
              (`issue-grant` 파일 포함) Agent 가 수신 확인 없이 실행하지 않으므로(`POOL_GRANT_NEEDS_RENEW` · 수신 확인 대조) 풀 안에서는 이 관문이 모든 새 실행을 덮는다
새 작업 관문   (Coordinator 쪽 · 직렬화 경계) 풀 모드의 실행은 Coordinator 의 **ACK 수신 확인 뒤에만** 일어난다(`--require-ack-receipt`). ACK 를 기록하는
              트랜잭션(BEGIN IMMEDIATE) 안에서 **그 노드의 미확인 통지**를 다시 본다 — 하나라도 있으면 ACK 를 기록하지 않고 수신 확인을 보내지 않는다(Agent 는 실행하지
              않는다 · 사유 MAILBOX_NOT_EMPTY). 여러 lane 이 동시에 FRESH 를 열어도 각 ACK 기록이 같은 관문을 지난다
              ★ 그래서 "빈 배달을 받은 직후 통지가 커밋됐다" 는 경합은 ACK 기록에서 걸린다 · 통지가 ACK 기록 **뒤**에 커밋되면 그 통지는 옛 시도 것이고, 새 시도의 실행은
                그대로 둔다(그 옛 시도는 이 노드에서 이미 끝났거나, 아래 실행 중 묻기가 맡는다)
              (Agent 쪽) 회차마다 FRESH 전에 MAILBOX 세션을 연다 — 수신 확인을 받기 전에는 FRESH 를 열지 않는다(관문을 헛되이 두드리지 않게). 실패하면 다음 회차에 다시
실행 중 묻기   그 시도의 실행 동안 **갱신 스레드와 따로** 우편함 감시 스레드를 둔다 — 실행이 끝날 때까지 갱신 주기로 MAILBOX 세션(LOCAL_EXPIRED · 갱신 거부 · 연결 실패와
              무관하게 계속). 연결 실패는 다음 주기에 다시
처리          통지의 attempt 가 이 Agent 가 지금 돌리는 시도면 → 소유자 "계속" 도 무시하고 멈춘다(서명된 거부와 같은 경로 — renew_refused · DISCONNECT_STOPPED) →
              정지가 **성공한 뒤** STOPPED. 정지가 실패하면 답하지 않는다(다음에 다시 · 새 작업 관문이 계속 닫힌다)
              지금 돌리지 않으면 — **확인 뒤에만** NOT_RUNNING:
                원장(run-ledger)에 그 시도 행이 없거나 CLOSED · 그리고 그 노드의 실행 목록(Owner Panel 등록)에 없다 → NOT_RUNNING
                원장에 ACTIVE · OPEN · STOP_PENDING · LOCAL_BLOCKED 가 있다(재기동 뒤 살아 있는 컨테이너일 수 있다) → **답하지 않는다** — 그 행을 닫는 것은 실행 알림 계약
                  (v17 · 계획 v3 §1 자동 증거)의 몫이고, 닫힌 뒤 다음 세션에서 NOT_RUNNING. 그동안 새 작업 관문이 닫힌다
                원장을 켜지 않은 노드(`--run-ledger` 꺼짐) → 실행 목록만으로는 재기동 뒤를 알 수 없다 — **우편함 기능은 원장을 요구한다**(`--use-mailbox` 는 `--run-ledger` 없이 기동 거부)
소유자 주권    우편함 오류 · 정지 실패 · 답 보류는 **새 작업**만 막는다. Owner Panel 의 즉시 비우기 · 강제 종료는 언제나 된다(§0.1)
```

## 규칙 (MUST)

1. 통지는 폐기(failover 의 Lease 폐기)와 **같은 커밋**에서 **서명된 바이트로** 영속한다
2. Coordinator 는 받아들인 답이 올 때까지 그 노드의 배달에 통지를 넣고, 그 노드의 ACK 기록(새 실행의 관문)을 거부한다
3. Agent 는 실행 중에도 그 시도가 끝날 때까지 묻는다 · NOT_RUNNING 은 원장과 실행 목록을 대조한 뒤에만
4. 통지는 Evidence(관측 시각 decided_at) · 배달 · 답 · 수신 확인은 ShortLived(세션 nonce echo)
5. 통지 · 답으로 예약을 풀지 않는다 — 예약 해제는 지금처럼 종료 보고 · 정지 확인 증거로만(답의 STOPPED 는 증거로 저장할 뿐)

## 영향받는 스트림

Protocol(메시지 넷 · 도메인 넷 · FrameType 21~24 · MODE 5 · 벡터) · Coordinator(failover 의 서명 통지 쓰기 · scheduler-tick 키 · MAILBOX 세션 · ACK 관문 · 표) ·
Agent(회차 전 묻기 · 실행 중 감시 스레드 · 처리 · 원장 대조) · 배포 파일.

## 호환성 영향

- schema_version: 새 메시지 넷 v1. Hello 는 mode 값만 늘어난다(mode 는 이미 서명 대상)
- 기존 서명 무효화: 아니오
- 스큐: 옛 Coordinator 는 MODE 5 Hello 를 거부한다 → `--use-mailbox` 를 켠 Agent 는 우편함을 비울 수 없어 새 작업을 받지 않는다(fail closed). Coordinator 를 먼저 올린다
- 범위: 풀 모드 전용(`--mailbox-gate` 는 `--pool-mode` · `--use-mailbox` 는 `--require-ack-receipt` 를 요구 — 아니면 기동 거부). 풀 밖 lane 은 이 보장이 없다
- scheduler-tick: `--failover-grace-ms` 에 `--coordinator-key-file` 이 **필수**가 된다 — 기존 배포는 키를 넘기도록 함께 고친다(빠지면 기동 거부라 조용히 깨지지 않는다)
- Coordinator 의 ACK 관문: 통지가 없는 노드에는 지금과 같다. `--use-mailbox` 를 끈 Agent 에게 통지가 쌓이면 **그 노드의 새 실행이 막힌다** — 그래서 Coordinator 쪽에도
  `--mailbox-gate`(기본 꺼짐)를 두고, 모든 Agent 가 우편함을 켠 뒤 켠다
- 벡터: 통지(REQUEUED · FAILED) · 배달(0개 · 2개) · 답 · 수신 확인 — 각각과 값 하나만 바꾼 짝 · notice_id 계산 벡터

## 남는 구멍

- Coordinator 디스크를 잃으면 통지도 잃는다(D9 — 단일 Coordinator 의 로컬 확정)
- 옛 노드가 영영 돌아오지 않으면 배달되지 않는다(그 노드는 돌지도 않는다)
- 통지를 받기 **전**(끊긴 동안)의 두 벌은 막지 못한다 — 정지는 다시 붙은 뒤다. 끊긴 동안은 끊김 시한 · 소유자 선택이 맡는다
- 키를 바꾸면(교체) 옛 통지의 서명은 옛 키다 — Agent 는 Coordinator 키 목록으로 검증하므로 교체 기간에는 두 키를 둔다(지금 키 교체 절차와 같다)
- 런타임이 답하지 않아 정지가 실패하면 답하지 않고 새 작업도 막힌다 — 런타임 밖 정지는 관문 5 ⑥

## 되돌리는 방법

`--use-mailbox`(Agent) · `--mailbox-gate`(Coordinator)를 끄면 묻지도 막지도 않는다 — **이 보장도 사라진다**(소유자 "계속 돌리기" 의 넘어간 시도는 다시 소유자가 멈출
때까지 돈다). 표의 행은 쌓이기만 한다. scheduler-tick 의 키 요구는 남는다(서명 통지는 계속 쓴다).
