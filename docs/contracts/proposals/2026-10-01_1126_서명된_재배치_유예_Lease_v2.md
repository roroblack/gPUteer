## 왜 필요한가 (이것 없이 막히는 것)

끊긴 노드는 Lease 만료 − 여유(S)에 스스로 멈춘다. Coordinator 는 만료 + 유예가 지나야 다른 노드에 다시 맡긴다. 그 사이(유예)는 지금 **노드가 모른다** —
유예는 재배치 명령(`scheduler-tick --failover-grace-ms`)의 실행 옵션일 뿐 서명돼 노드에 오지 않는다. 그래서 판단표 ④ "곧 끝나는 작업은 계속" 이 쓸 수 있는
시한 H(= 만료 + 유예 − 여유)가 S 와 같아 아무것도 바꾸지 못한다. 작업 → Agent 진행 보고 통로(2026-10-01)가 생겨 ④ 를 판정할 근거는 들어왔다.

## 규칙 (MUST)

```text
Coordinator
  1  운영자 스위치 `--signed-reassignment-grace-ms`(기본 0 · 꺼짐)가 0 보다 크면 발급 · 갱신하는 모든 Lease 에 34 를 그 값으로 채우고 schema 2 로 서명한다.
     0 이면 34 를 비우고 schema 1 — 지금과 같다
  2  34 는 저장 행(coordinator_leases)에도 남긴다. 옛 파일은 열 때 열을 더한다(revoked_at 과 같은 자동 보정)
재배치(failover)
  3  재배치 시각 = 만료 + max(정책 유예 `--failover-grace-ms`, 저장된 34). 서명해 알린 유예보다 **일찍 다시 맡기지 않는다**
Agent
  4  중첩 Lease 를 schema 2 까지 받는다. 34 를 쓰는 곳은 판단표 ④ 의 H 하나다 — 끊김 시한 S · 정지 · 일시정지는 바꾸지 않는다
  5  H = (S 와 같은 보내기 시각 보정을 한) 만료 + 34 − 여유. PURE · IDEMPOTENT 이고 완료 예상(작업 자기보고 ETA — 위조 가능)이 H 보다 앞일 때만
     S 를 넘겨 H 까지 계속한다. SIDE_EFFECTING · 등급 모름 · 진행 보고 없음은 S 그대로
Protocol
  6  schema < 2 인데 34 가 차 있으면 거부. 34 = 0 이면 canonical 이 v1 과 같다(기존 서명 · 벡터 무변경)
```

## 영향받는 스트림

Protocol(스키마 · 벡터) · Coordinator(발급 · 저장 · 재배치) · Agent(중첩 Lease 검증 3곳 · 판단표 ④).

## 호환성 영향

- schema_version 증가 필요? **예** — Lease 2. 스위치가 꺼져 있으면 1 그대로
- 기존 서명이 무효화되는가? **아니오** — 34 = 0 이면 canonical 이 전과 같다
- 멀티 바이너리 스큐 창에 영향? **예**, 두 갈래(Codex 지적):
  - 옛 Agent 는 Lease v2 를 SCHEMA_TOO_NEW 로 거부한다 → 실행 허가가 시끄럽게 실패한다(조용한 두 벌이 아니다). 스위치를 켜기 전에 모든 Agent 를 올린다
  - 옛 `scheduler-tick` 은 34 를 모르고 정책 유예만 본다 → 서명 유예가 정책 유예보다 길면 **두 벌**이 될 수 있다. 스위치를 켜기 전에 재배치 명령을 올리고,
    런북에 "서명 유예 ≤ 정책 유예" 로 맞추라고 적는다(그러면 옛 재배치 명령도 안전하다)
- 테스트 벡터 재생성 필요? **예** — Lease v2(34 채움) · 값만 다른 것 · v2 에 34 = 0 추가

## 남는 구멍

- 작업 자기보고 ETA 는 위조할 수 있다 — 거짓 보고로 H 까지 GPU 를 더 쥘 수 있다(H 를 넘지는 못한다 · 두 벌은 아니다). 소유자 화면에 "곧 끝남 판정 중" 을 보인다
- 끊긴 노드가 실제로 죽었으면 재배치가 유예만큼 늦다 — 스위치 값이 그 비용이다
- 노드 시계 · 잠자기(단조 시계가 흐르는가)는 S 와 같은 한계를 갖는다

## 되돌리는 방법

스위치를 0(기본)으로 두면 Lease 가 v1 로 돌아가고 Agent 의 H 는 S 와 같다. 이미 v2 로 발급된 Lease 는 만료까지 v2 다.
