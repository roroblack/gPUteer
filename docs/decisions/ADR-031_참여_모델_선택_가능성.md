# ADR-031 · 참여 모델 — 사설 팀 우선, 공개 풀 확장 가능

- **상태:** 개정됨(2026-08-27) — 이음매 아홉 곳의 **판정 규칙은 전부 정해졌고**,
  남은 공백은 "멤버십 사실의 생산자" 하나다.
  §검수 반영 · §이음매 지도 다시 그리기 · §이음매 지도 갱신 참조
- **날짜:** 2026-08-24
- **관련:** 기준선 §1.3 원칙 14 · §5.5.1 · §6.1 · §6.3 · §7.2 · §7.3.5 · §7.4 ·
  `CLAUDE.md` §0.1 · §0.2 · ADR-028 · ADR-029

## 배경

기준선(`gputeer_master_plan_FINAL.md`)은 참여 모델을 **사설 팀** 하나로만
정의한다.

```text
§7.2   Owner 가 Genesis 에 서명. Genesis 해시가 팀의 루트 신뢰 앵커다.
§5.5.1 Owner 가 `gputeer team init` 실행 -> Coordinator 3개 주소를 직접 기재
       "최초 3개는 자동 선출하지 않는다. Owner 가 명시 지정한다. 순환 의존 없음."
§7.4   Join Request(invite 서명) -> Preflight -> Owner Approval -> Raft 커밋
       -> Device Certificate 발급
```

즉 **Owner 는 선출되지 않는다. 팀을 만든 사람이 곧 Owner 다.** 참여자는
서로 아는 사이라고 전제하며, 다중 팀·공개 풀·모르는 사람 매칭 개념은
기준선에 **없다**(검색으로 확인. `third-party workload` 는 스케줄러에서
**제외**한다는 맥락에서 한 번 등장한다).

그런데 제품 방향으로 **"사용자가 처음 들어오면 GPU 풀 파티를 배정받는다"**
가 논의됐다. 이것은 다른 모델이다.

| | 사설 팀(기준선) | 공개 풀(논의) |
|---|---|---|
| 참여자 | 아는 팀원 | 서로 모르는 사람 |
| 진입 | Owner 초대·승인 | 시스템이 배정 |
| 방장 | 만든 사람 | **정하는 절차가 필요** |
| 신뢰 | 팀 내부 전제 | 상호 불신 전제 |

**위협 모델이 다르다.** 공개 풀에서는 내 GPU 에서 모르는 사람의 코드가
돌고, 방장이 악의적일 수 있으며, 기여도·분쟁 조정이 필요해진다. 기준선이
"장기 옵션"으로 미뤄 둔 BFT·블록체인이 필요해지는 지점이 정확히 여기다
(§1.3 원칙 14, 그리고 기각표의 "모든 상태를 Blockchain -> Raft + Signed
Audit/Merkle + 장기 BFT").

## 결정

**사설 팀 모델을 먼저 구현한다. 다만 공개 풀을 나중에 붙일 수 있도록
이음매(seam)를 지금 정의한다. 두 모델은 런타임에 선택 가능해야 한다.**

기준선을 수정하지 않는다(읽기 전용). 이 ADR 이 기준선의 사설 팀 정의를
**부분집합으로 포함하는 상위 구조**를 정의한다.

### 1. 참여 모델을 명시적 타입으로 만든다

모드는 **추론하지 않는다.** 어딘가에 반드시 명시되고, 검증된 값으로만
읽는다.

```text
ParticipationModel
  PrivateTeam    기준선 §7 그대로. Owner = 생성자.
  PublicPool     미구현. 지금은 선언만 하고 모든 경로에서 거부한다.
```

`PublicPool` 은 **지금 거부한다.** 열어두고 "아직 구현 안 됨"으로 조용히
지나가면, 언젠가 그 경로가 검증 없이 열린다. 이 저장소의 규율(`CLAUDE.md`
§0.2 "검증 전에는 아무것도 신뢰하지 않는다")과 같은 정신이다.

### 2. 신뢰 앵커를 추상화한다 — 그러나 지금은 구현체가 하나뿐이다

두 모델의 진짜 차이는 **"이 레코드가 권위 있다는 것을 무엇이 보증하는가"**
다.

```text
TrustAnchor
  GenesisOwner   Genesis 해시 + Owner 공개키. 기준선 §7.2.
  PoolGovernance 미정. 공개 풀의 방장 선정·교체 규칙이 정해져야 채워진다.
```

`PoolGovernance` 는 **의도적으로 비워 둔다.** 지금 그럴듯하게 채우면
검증되지 않은 신뢰 가정이 코드에 굳는다. 비어 있다는 사실 자체가 "아직
결정되지 않았다"는 정직한 표시다.

### 3. 위협 모델을 모드에 묶는다

모드마다 **최소 격리 요구**가 다르다. 이것을 코드가 알아야 한다.

```text
PrivateTeam   팀 정책이 정한 SecurityTier 를 따른다(기준선 §11 대로)
PublicPool    최소 요구를 낮출 수 없다 — 모르는 사람의 코드가 돌기 때문
```

**모드 혼동은 fail-closed 다.** 노드가 자기가 어느 모드인지 확신하지 못하면
작업을 받지 않는다. "팀 모드인 줄 알고 낯선 코드를 돌리는" 사고가 가장
위험하다.

### 4. 기존 계층은 대부분 모드 무관이다 — 그대로 둔다

지금까지 만든 것 중 다음은 **두 모델 모두에서 그대로 유효하다.**

- 서명 검증 순서와 `Verified<M>`(`DoD-50`~`DoD-53`)
- durable 저장소들 — 무엇을 저장하느냐는 같고, 누가 권위를 갖느냐만 다르다
- 순수 kernel 들(`DoD-41`·`45`·`54`·`55`, watch cursor, FencedOperation)
- fencing·replay 방어

**모드에 의존하는 것은 "누가 멤버인가" 와 "그것을 무엇이 보증하는가" 뿐이다.**
그래서 이음매를 그 두 곳에만 두면 된다. 나머지를 모드로 오염시키지 않는다.

### 5. 연결 중개는 신뢰 앵커가 아니다

기준선 §6.1 의 연결 사다리(LAN -> 직접 -> hole punch -> Team Relay -> Hub)와
§6.3 의 Team Relay 는 **데이터 평면**이며, **팀 서명된 device certificate 가
있어야 쓸 수 있다.** 즉 멤버십이 선행 조건이지 멤버십을 만들어 주지 않는다.

외부 호스팅(예: Vercel/Neon/Blob)은 **서명된 Invite Bundle 을 배포하는
우체통** 역할까지만 허용한다. Bundle 에 `owner_signature` 가 있으므로
호스팅이 침해돼도 위조는 서명 검증에서 걸린다.

```text
허용   초대 링크 배포 · Genesis 번들 전달 · 가입 안내 UI
금지   키 발급 · 멤버십 승인 · 인증서 발급
```

금지 항목을 외부에 두면 **신뢰 앵커가 그 서버로 이동한다.** 서버가 뚫리면
아무나 팀원이 된다. 기준선 §6.3 이 공개 relay 를 거부한 이유("제3자 의존 및
metadata 유출 회피")와 같은 판단이다.

## 결과

- 지금 구현하는 것은 **`PrivateTeam` 하나**다. 기준선 §7 을 그대로 따른다.
- `PublicPool` 은 **타입으로만 존재하고 모든 경로에서 거부**된다.
- 공개 풀을 열려면 이 ADR 을 개정해야 하며, 최소한 다음이 먼저 정해져야
  한다.

```text
방장(Owner 상당) 선정·교체·축출 규칙
악의적 방장에 대한 방어
기여도 산정과 분쟁 조정
낯선 코드에 대한 최소 격리 강제
BFT 필요 여부 (기준선 §1.3 원칙 14 의 "장기 옵션" 을 앞당기는가)
```

## 이 ADR 이 하지 않는 것

- 기준선을 수정하지 않는다(읽기 전용).
- 공개 풀의 거버넌스를 정하지 않는다. 정할 정보가 없다.
- Raft 를 대체하지 않는다. `PrivateTeam` 의 멤버십 커밋은 기준선대로
  Raft 다. 그 비용(추정 9~13일)은 이 ADR 로 줄어들지 않는다.
- 구현을 포함하지 않는다. 이 문서는 이음매의 위치와 원칙만 정한다.

## 미해결

`PoolGovernance` 가 비어 있다는 것은 **공개 풀이 아직 설계되지 않았다**는
뜻이다. 이 ADR 은 그것을 숨기지 않고 드러내는 것이 목적이다. 언젠가
채우려면 위 다섯 항목에 답해야 하고, 그 답 없이 코드를 먼저 쓰면 검증되지
않은 신뢰 가정이 굳는다.

## ★ 독립 검수 반영 (2026-08-24) — `CHANGES_REQUESTED`

### "이음매는 두 곳뿐" — **반증됐다**

§4 는 서명 검증·`Verified<M>`·durable 저장소·순수 kernel·fencing 이
모드 무관이라고 주장했다. **물리적 저장 형식 수준에서는 일부
맞지만, 권위·provenance·scope·현재 권한 판정까지 포함하면
틀리다.** 코드 근거는 다음과 같다.

**셋째 이음매 — Owner 의미론.** `owner_member_id` 가 스케줄링
데이터 모델에 이미 박혀 있다(`crates/coordinator/src/inventory_store.rs`
의 `AgentRegistry`, `crates/scheduler/src/model.rs` 의
`CandidateSnapshot`). 공개 풀에서 Owner 가 GPU 소유자인지, Broker 가
부여한 member owner 인지, 작업 제출자인지 정해지지 않았다. 이것은
멤버십 입력이 아니라 **스케줄링 의미 자체**의 이음매다.

**넷째 이음매 — membership 해석의 다치성.** `DoD-54` 는 membership 을
단순 필드로 받지 않는다. `Valid`·`NotApproved`·`MembershipUnresolved`·
`MembershipAmbiguous` 가 결과 의미를 바꾼다
(`crates/checkpoint/src/durability.rs`). 모드가 바뀌면 이 값들의
출처와 신뢰 근거가 달라진다.

**다섯째 이음매 — provenance gate.** `DoD-55` 의
`ProvenanceGate::Verified` 는 kernel 이 만든 검증 결과가 아니라
**caller 가 넣는 값**이다(`crates/scheduler/src/scope.rs`). 무엇이
그 값을 채울 자격이 있는지는 모드에 달렸다.

**여섯째 — durable load 의 재검증 경로.** 현재 저장소는 raw binding 만
저장하고 재시작 후 현재 membership authority 로 자동 승격하지
않는다(의도된 설계). 공개 풀에서는 Broker 의 membership
revision/proof 로 재검증하는 **별도 경로**가 필요하다.

### ADR-032 와의 관계 정정

§"이 ADR 이 하지 않는 것" 의 "Raft 비용은 줄지 않는다" 는
**`PrivateTeam` 에 한해 참**이다. ADR-032 가 이를 공개 풀에서
정정했으나, 그 정정 자체가 다시 반려됐다(ADR-032 §검수 반영 (A)).
공개 풀도 **스케줄링 선형화 비용을 피하지 못한다.**

또한 ADR-032 는 공개 풀에서 consensus/commit 의미와 scheduler
authority 까지 바꾸므로 **실질적으로 세 번째 이음매를 만든다.**
"이음매를 두 곳에만 둔다" 는 이 ADR 의 설계 목표는 현재 상태로는
달성되지 않았다.

### 강제되지 않는 선언

`ParticipationModel`·`PrivateTeam`·`PublicPool` 은 **이 문서에만
존재한다.** 코드에 enum·parser·runtime gate·전 ingress reject
경로·회귀 테스트가 없다. "타입으로 두고 모든 경로에서 거부" 는
현재로서는 **선언**이며, 이 저장소가 반복해서 경계해 온
"강제되지 않는 규칙" 에 해당한다(`CLAUDE.md` §0.4 정신).

### 유지되는 부분

`PrivateTeam` 을 기준선대로 먼저 구현하고, `PublicPool` 을 지금
거부하며, 신뢰 앵커 차이를 명시하고, 미결정을 숨기지 않는다는
방향 자체는 검수도 긍정했다. 이음매의 **개수와 위치**를 다시
그려야 한다는 것이 지적의 요지다.

## ★ 이음매 지도 다시 그리기 (2026-08-27)

검수의 요지는 "`PrivateTeam` 먼저" 라는 방향이 틀렸다는 것이 아니라
**§4 의 "이음매는 두 곳뿐" 이 반증됐으니 지도를 다시 그리라**는
것이었다. 여기서 다시 그린다.

### 설계 목표를 바꾼다

```text
버린 목표   이음매를 두 곳에만 둔다
새 목표     이음매를 전부 이름 붙이고, 각각에 결정이 있거나
            열려 있음이 명시돼 있게 한다
```

**"두 곳뿐" 은 달성 가능한 목표가 아니었다.** 아래 표가 보여주듯
실제 이음매는 최소 아홉 곳이고, 그중 셋은 이 지도를 그리는 과정에서
새로 드러났다. 개수를 줄이는 것을 목표로 삼으면 **찾은 이음매를
"이음매가 아니다" 라고 부르게 된다** — ADR-032 가 `COMMITTED` 문제를
"기준선이 다루지 않은 영역" 이라 불렀다가 반려당한 것이 정확히 그
실패다.

| 3 | `owner_member_id` 의 의미 | **닫힘** | ADR-033 §6 — GPU 소유자. `submitter` 와 분리 |

| 8 | 예약·fence 번호 권위 | **닫힘** | ADR-033 §(c) — 풀 생성 시 고정, 실행 중 변경 불가 |

```text
1  누가 멤버인가

   남은 것은 그 레코드의 수명·폐기·revision 규칙이다

4  membership 해석의 다치성
   DoD-54 는 Valid / NotApproved / MembershipUnresolved /

   공개 풀에서 이 네 값을 무엇이 채우는지 정해지지 않았다

5  ProvenanceGate 를 채울 자격
   DoD-55 의 ProvenanceGate::Verified 는 kernel 이 만든 값이 아니라
```

★ 4·5·6 은 **같은 성격**이다 — 셋 다 "이 사실을 채울 자격이 누구에게

지금 묶으면 근거 없이 합치는 것이므로 따로 둔다.

## ★ 나머지 검수 지적의 현재 (2026-08-27)

### ADR-032 와의 관계 — 다시 정정한다

이 문서는 "Raft 비용은 줄지 않는다" 고 적었고, ADR-032 가 공개
풀에서 이를 정정했다가 반려됐고, 그 반려가 "공개 풀도 스케줄링
선형화 비용을 피하지 못한다" 로 되돌렸다.

**ADR-033 §1 이 그 비용을 어떻게 지불하는지 정했다** — Raft 가
아니라 **Broker 단일 권위**로 지불한다. 배치를 전부 Broker 가
하므로 두 주체가 같은 GPU 를 다투는 상황 자체가 생기지 않는다.

```text
PrivateTeam   멤버십 커밋은 기준선대로 Raft. 비용 그대로
PublicPool    선형화를 Broker 로 옮겨서 지불한다
              -> Raft 비용은 없지만 Broker 가 단일 장애점이자
                 단일 침해점이 된다 (ADR-033 §5 · §미해결)
```

**비용이 사라진 것이 아니라 종류가 바뀌었다.**

### "강제되지 않는 선언" — 절반 해소

지적 당시 `ParticipationModel` 은 문서에만 있었다. 지금은 실제
코드다.

```text
있음   enum · parser · as_str() · assumes_mutual_trust()
       회귀 테스트 7건
       Default 가 없음을 compile-fail doctest 가 고정
       (crates/protocol/src/participation.rs)

없음   runtime gate — 이 타입을 읽는 호출부가 하나도 없다
       ingress reject 경로
       "PublicPool 을 모든 경로에서 거부" 의 실제 강제
```

`crates/protocol/src/lib.rs` 의 re-export 외에 사용처가 없다.
따라서 **§결과의 "`PublicPool` 은 타입으로만 존재하고 모든 경로에서
거부된다" 는 아직 선언이다.** 타입은 생겼고 거부는 아직 없다.

배선을 일부러 미룬 이유: 이음매 지도가 확정되기 전에 배선하면
잘못된 자리에 게이트가 박힌다. 위 표의 열린 넷이 닫히는 순서에
맞춰 배선한다.

### 유지되는 부분

`PrivateTeam` 을 먼저 구현하고, 신뢰 앵커 차이를 명시하고, 미결정을
숨기지 않는다는 방향은 그대로다. §5(연결 중개는 신뢰 앵커가 아니다)
도 그대로 유효하며 ADR-032·033 이 이를 바꾸지 않았다 — Broker 는
멤버십 앵커이지 **연결 중개가 앵커가 된 것이 아니다.**


## ★ 이음매 지도 갱신 (2026-08-27 저녁)

같은 날 사용자 결정 넷이 내려지고 `state-machines.md` §5.1 과
`crates/protocol/src/membership.rs` 가 생기면서 지도가 다시 바뀌었다.

### 열려 있던 넷의 현재

| # | 이음매 | 판정 규칙 | 사실의 출처 |
|---|---|---|---|
| 1 | 누가 멤버인가 | **닫힘** — `state-machines.md` §5.1 | **열림** |
| 4 | membership 해석의 다치성 | **닫힘** — `membership.rs` | **열림** |
| 5 | `ProvenanceGate` 를 채울 자격 | **닫힘** — 같은 kernel 결과로 채운다 | **열림** |
| 6 | durable load 의 재검증 경로 | **닫힘** — 같은 kernel 로 재판정 | **열림** |

### 지도가 단순해졌다 — 남은 것은 **하나**다

앞서 "4·5·6 은 같은 성격이니 묶을 수 있을지 모르나 근거 없이 합치지
않는다" 고 적었다. 이제 근거가 생겼다 — **셋 다 같은 kernel 하나로
판정된다.** 그리고 넷 모두 같은 이유로 열려 있다.

```text
닫힌 것   이 사실을 어떻게 판정하는가
          -> resolve_device_authorization() 이 답한다
          -> ACTIVE 만 권한, 사실 없음과 권한 없음을 구분,
             충돌은 fail closed, 오래된 view 는 권한 판정 불가

열린 것   그 사실이 어디서 오는가
          -> 확정된 action log 에서 MemberFact·DeviceBinding 을
             투영하는 생산자가 없다
```

**즉 이음매 아홉 곳의 판정 규칙은 전부 정해졌고, 남은 공백은
"멤버십 사실의 생산자" 하나다.** 이것을 만들려면 다음이 필요하다.

```text
action 메시지     ActivateMember·SuspendMember·ReinstateMember·
                  RemoveMember 가 proto 에 없다 (AddMember 만 있다)
확정 경로         사설 팀은 과반 합의, 공개 풀은 Broker (§0.1)
durable 저장      log 와 그 투영을 담을 저장소
```

`docs/plans/2026-08-24_1830_membership_norm_draft_v1.md` 의 남은
사용자 결정 항목(§12.1 root key 회전 · §12.4 mutation TTL ·
§12.5 tombstone 보존 · §12.8 snapshot proof)이 그 생산자의 설계를
막고 있다. 판정부는 그 결정들과 무관하게 만들 수 있었다.

### "강제되지 않는 선언" — 다시 절반

`ParticipationModel` 배선은 **여전히 없다.** 위 표의 "사실의 출처"
가 열려 있는 동안에는 게이트를 어디에 박을지 정해지지 않는다 —
판정 kernel 은 모드를 묻지 않고(모드 차이는 "누가 사실을 만드는가"
에만 나타난다), 그 생산자가 없기 때문이다.
