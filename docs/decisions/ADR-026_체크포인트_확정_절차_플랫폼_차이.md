# ADR-026 · 체크포인트 확정 절차의 플랫폼 차이

- **상태:** 제안 (기준선 §18.2 수정 요청)
- **날짜:** 2026-08-15
- **관련:** 기준선 §18.2 · `docs/protocol/state-machines.md` §4 ·
  `docs/evidence/P0-03a_windows_fs_atomicity.md`

## 배경

기준선 §18.2 와 `state-machines.md` §4 는 체크포인트 확정 절차를 다음으로 규범화했다.

```text
1. <name>.tmp 에 기록 -> fsync(file) -> rename(name) -> fsync(dir)
2. 매니페스트는 데이터 파일이 모두 확정된 뒤 마지막에 쓴다
3. 매니페스트 없는 데이터 파일은 PARTIAL 로 간주하고 부팅 시 GC
```

**이 절차는 POSIX 시맨틱을 전제한다.** gPUteer 의 주요 타깃 중 하나가 Windows 이므로
(기준선 §9 S1/S2, §44.7 플랫폼 매트릭스) Rust 구현 착수 전에 검증이 필요했다.

P0-03a 실측 결과 **규범 1번이 Windows 에서 성립하지 않는다.**

| 시나리오 | rename 성공률 |
|---|---|
| 동시 독자 없음 | 3000 / 3000 |
| 독자가 `FILE_SHARE_DELETE` 없이 열기 | **313 / 3000** |
| POSIX 시맨틱 API 사용 | **87 / 1000** |

원인은 Windows `MoveFileEx` 가 **열려 있는 대상 파일을 대체하지 못하는** 데 있다.
`FileRenameInfoEx` + `FILE_RENAME_FLAG_POSIX_SEMANTICS` 로도 해결되지 않았다.

## 결정

**데이터 파일에 대해 `rename-over-existing` 을 사용하지 않는다.**
확정 절차를 파일 종류별로 분리하고, `fsync(dir)` 을 플랫폼별로 정의한다.

## 근거

기준선 §18.6 이 이미 선언한 사실이 해법을 준다.

> **모든 artifact 는 immutable. canonical 은 pointer 만 갱신한다.**

불변 artifact 는 **덮어쓸 일이 없다.** 따라서 데이터 파일은 고유 이름으로 write-once 하면
`rename` 대상이 애초에 존재하지 않고, 이 조건은 실측에서 **3000/3000 성공**했다.

`replace-over-existing` 이 실제로 필요한 곳은 **canonical/latest 포인터 파일 하나뿐**이다.
이 파일은 수백 바이트 수준이라 재시도 비용이 무시할 만하다.

또한 실측에서 **`부분 내용` 관측이 0건**이었다는 점이 중요하다.
Windows 의 문제는 "찢어진 데이터" 가 아니라 "확정이 거부됨" 이다.
**데이터 무결성 위험이 아니라 가용성 위험**이므로, 재시도로 해결 가능한 종류의 문제다.

## 수정안

### §18.2 확정 절차 (수정 후)

```text
[데이터 파일 — 불변]
  1. <content-addressed-name>.tmp 에 기록
  2. fsync(file)
  3. rename(<content-addressed-name>)      대상이 존재하지 않는다
  4. sync_dir(<디렉터리>)                   플랫폼별 (아래)

  ★ 같은 이름이 이미 있으면 내용이 같다는 뜻이므로 tmp 를 지우고 성공 처리한다.
    rename 을 시도하지 않는다.

[매니페스트 — 불변]
  데이터 파일이 모두 확정된 뒤 같은 절차로 마지막에 기록한다.

[포인터 파일 — 가변, 유일한 replace 대상]
  1. <pointer>.tmp 에 기록 -> fsync
  2. replace(<pointer>) 시도
  3. 실패 시 지수 백오프 재시도 (기본 50ms 시작, 최대 5회, 상한 2초)
  4. 최종 실패 시 명시적 오류. 조용히 넘어가지 않는다
  5. sync_dir(<디렉터리>)
```

### `sync_dir` 플랫폼별 정의

```text
POSIX     fd = open(dir, O_RDONLY); fsync(fd)

Windows   CreateFileW(dir,
              GENERIC_READ | GENERIC_WRITE,        <- 쓰기 권한 필수
              FILE_SHARE_READ|WRITE|DELETE,
              OPEN_EXISTING,
              FILE_FLAG_BACKUP_SEMANTICS)          <- 디렉터리 열기에 필수
          FlushFileBuffers(handle)
```

★ **`GENERIC_READ` 만으로 열면 `FlushFileBuffers` 가 `ACCESS_DENIED(5)` 로 실패한다.**
실측에서 이 함정을 확인했다.

### 추가 요구사항

- gPUteer 의 모든 파일 열기는 **`FILE_SHARE_DELETE` 를 포함**해야 한다.
  자기 컴포넌트끼리 확정을 막지 않기 위해서다. (Rust `std::fs` 기본값 확인 필요 — 미검증)
- 포인터 replace 실패는 **risk signal 이 아니다.** 외부 프로세스(백신·인덱서)가 원인일 수 있다.
  재시도 소진 시에만 오류로 승격한다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| `FileRenameInfoEx` + POSIX_SEMANTICS 사용 | **실측에서 87/1000 성공. 반증됨** |
| 모든 독자에게 `FILE_SHARE_DELETE` 강제 | 외부 프로세스(백신·인덱서·탐색기)를 통제할 수 없다 |
| rename 실패 시 무한 재시도 | 데이터 파일에는 애초에 rename-over-existing 이 불필요하다. 문제를 회피하는 편이 낫다 |
| Windows 에서만 다른 저장 구조 사용 | 플랫폼별 구조 분기는 reconciliation·CAS 를 복잡하게 만든다. 절차만 분기하는 편이 작다 |

## 결과

**가능해지는 것**

- 데이터 파일 확정이 외부 프로세스 간섭에 영향받지 않는다 (P1a 조건 = 100% 성공)
- Windows 에서도 `sync_dir` 이 동작한다

**포기하는 것**

- 포인터 갱신은 여전히 실패할 수 있다. 재시도로 완화할 뿐 제거하지 못한다.
- 같은 내용의 체크포인트가 서로 다른 시점에 두 번 쓰이면 중복 tmp 가 생길 수 있다.
  (content-addressed 이므로 최종 파일은 하나)

**바꿔야 하는 것**

- 기준선 §18.2 — 확정 절차를 파일 종류별로 분리
- `docs/protocol/state-machines.md` §4 — 원자성 규칙 항목
- `crates/checkpoint` — 구현 시 이 절차를 따른다
- `tests/chaos/` — 외부 프로세스가 파일을 연 상태에서의 확정 테스트 추가

## 되돌리는 조건

- Rust `std::fs` 가 `FILE_SHARE_DELETE` 를 포함하지 않는 것으로 확인되면
  1차 요구사항을 재검토한다.
- Windows 가 향후 `MoveFileEx` 시맨틱을 변경하면 (가능성 낮음) 재검토한다.
- NTFS 외 파일시스템에서 P1a 조건이 성립하지 않으면 전면 재검토한다.

## 미해결

- **P1c 의 2393건 거부 원인 미규명.** `FILE_SHARE_DELETE` 독자가 있는데도 거부됐다.
  Windows Defender 실시간 검사 가능성이 있으나 확인하지 않았다.
  → 이 결정에는 영향이 없다 (데이터 파일은 rename-over-existing 을 하지 않으므로).
  다만 포인터 재시도 횟수를 정할 때 재조사가 필요하다.
- **전원 차단 내구성 미검증.** 프로세스 kill 만 측정했다.
- **Rust `std::fs` 공유 모드 미실측.** S2 단계에서 확인한다.
