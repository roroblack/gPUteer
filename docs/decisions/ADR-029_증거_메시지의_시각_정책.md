# ADR-029 · 증거 메시지의 시각 정책 — `Lifetime::Evidence`

- **상태:** 채택
- **날짜:** 2026-08-16
- **관련:** `docs/protocol/signing.md` §9 · §9.1 · `docs/evidence/DoD-05_T1_서명대상_확장.md` ·
  `CLAUDE.md` §0.3 · 기준선 §15.1 / ADR-021

## 배경

`signing.md` §9 는 시각 검증 정책을 세 갈래로 정한다.

```text
단수명(ShortLived)   |now − issued_at| <= 60초  AND  now < expires_at
장수명(LongLived)    now < expires_at            (issued_at 검사 안 함)
영구(Perpetual)      만료 검사 없음               (Genesis / Release Manifest)
```

그런데 T1 구현 중 **서명 대상 6종이 이 표에 없다**는 것을 발견했다
(`DoD-05` 발견 3). 더 심각한 것은 **그들에게 `expires_at` 필드 자체가 없다**는 점이다.

```text
CheckpointManifest    created_at_unix_ms(30)   fence_epoch(32)
ReplicaAck            acked_at_unix_ms(30)     ★ fence_epoch 없음
ArtifactRef           created_at_unix_ms(21)   fence_epoch(22)
AttemptReport         issued_at_unix_ms(40)    fence_epoch(5)
CanonicalDecision     decided_at_unix_ms(13)   fence_epoch(12)
RevokeLeaseNotice     issued_at_unix_ms(5)     fence_epoch(3)
```

`Lifetime` 을 추측으로 고르면 안 된다(`CLAUDE.md` §1).

```text
ShortLived 로 잘못 고르면    정상 메시지가 전부 거부된다
LongLived 로 잘못 고르면     expires_at 이 0이라 즉시 만료 -> 역시 전부 거부
Perpetual 로 잘못 고르면     만료된 증거가 영원히 유효해진다
```

그래서 `DoD-05` 는 이 6종의 `Signable` 을 **구현하지 않고** 남겨 두었다.
결과적으로 이들은 아직 `verify()` 를 통과할 수 없다. 이 ADR 이 그것을 푼다.

## 결정

**이 6종은 "권한"이 아니라 "증거"다. 시각으로 만료시키지 않는다.**

`Lifetime::Evidence` 를 신설한다.

```rust
pub enum Lifetime {
    ShortLived,   // |now - issued_at| <= skew AND now < expires_at
    LongLived,    // now < expires_at
    Evidence,     // ★ 만료 검사 없음. 단 observed_at 을 반드시 노출한다
    Perpetual,    // 만료 검사 없음. 시스템 상수 (Genesis / Release)
}
```

| 메시지 | Lifetime | 신선도 판단 근거 |
|---|---|---|
| `CheckpointManifest` | `Evidence` | `fence_epoch(32)` |
| `ReplicaAck` | `Evidence` | ★ **없음** — `acked_at` 뿐 |
| `ArtifactRef` | `Evidence` | `fence_epoch(22)` |
| `AttemptReport` | `Evidence` | `fence_epoch(5)` |
| `CanonicalDecision` | `Evidence` | `fence_epoch(12)` |
| `RevokeLeaseNotice` | `Evidence` | `fence_epoch(3)` |

## 근거

### 과거의 사실은 만료되지 않는다

`CheckpointManifest` 는 **"이 체크포인트의 내용이 이것이다"** 라는 증거다.
3년 뒤에도 그 진술은 참이다. 만료시키면 **오래된 체크포인트에서 재개할 수 없게 된다** —
그것은 이 시스템의 존재 이유(다른 GPU 에서 작업을 이어간다)를 정면으로 부순다.

`ArtifactRef` 도 같다. CAS 경로는 immutable 이다.

### 그러나 "그 시점의 사실" ≠ "지금의 사실"

★ **이것이 `Perpetual` 과 구분하는 이유다.**

```text
Perpetual (Genesis · Release Manifest)
    시스템 상수에 가깝다. "지금도 참인가" 를 물을 필요가 없다.

Evidence (이 6종)
    관측 시점의 사실이다. **소비 측이 신선도를 판단해야 한다.**
    판단하지 않으면 오래된 증거를 현재 상태로 착각한다.
```

가장 뚜렷한 예가 `ReplicaAck` 다.

```text
ReplicaAck 는 "내가 이것을 저장하고 fsync 했으며 해시를 검증했다" 는 선언이다.
그 복제본이 **나중에 삭제되어도 ACK 는 영원히 유효하다.**

=> ACK 를 "지금 durable 하다" 의 증거로 쓰면 안 된다.
   "acked_at 시점에 durable 했다" 의 증거일 뿐이다.
```

이것은 `CLAUDE.md` §0.3 이 이미 인식하고 있는 구분이다.

> `COMMITTED` 이후 replica 가 유실되어도 상태를 되돌리지 않는다. …
> **`COMMITTED_DEGRADED` 로 표시하고 복구 큐에 넣는다.**

즉 기준선은 "ACK 는 과거 사실" 을 전제로 설계되어 있다.
`Lifetime::Evidence` 는 그것을 타입에 적는 것이다.

### 신선도는 시각이 아니라 fencing 이 판단한다

6종 중 **5종이 `fence_epoch` 을 갖는다.**

```text
stale 한 증거   fence_epoch 이 현재보다 낮다 -> fencing 이 거부한다
                시각이 아니라 **단조 증가 epoch** 이 신선도의 기준이다
```

시각으로 만료시키는 것은 **잘못된 축**이다. 시계는 어긋나지만 epoch 은 어긋나지 않는다.

### ★ `ReplicaAck` 만 `fence_epoch` 이 없다 — 스키마 공백

```text
ReplicaAck    schema_version · checkpoint_id · root_digest
              holder_device_id · kind · failure_domain
              fsynced · hash_verified · stored_bytes
              acked_at_unix_ms
              ★ fence_epoch 없음
```

**6종 중 유일하게 신선도 판단 근거가 시각뿐이다.**
그런데 `ReplicaAck` 는 `REPLICATED(n)` 을 세는 근거이므로
**durability 주장의 뿌리**다. 가장 약한 곳이 가장 중요한 곳이다.

이 ADR 은 그 사실을 **기록만 한다.** 고치려면 `.proto` 에 필드를 추가해야 하고
그것은 `schema_version` 상향(§7.3)을 요구한다. 별도 결정 사항이다.
→ `TODO_VISION` V-07 로 등록.

### `RevokeLeaseNotice` 는 왜 단수명이 아닌가

회수 통지는 **명령**이라 단수명이 자연스러워 보인다. 그러나

```text
expires_at 필드가 없다        -> LongLived/ShortLived 어느 쪽도 적용 불가
fence_epoch(3) 이 있다        -> stale 한 회수는 fencing 이 거부한다
```

오래된 회수 통지를 재전송해도 `fence_epoch` 이 낮으므로 무시된다.
**시각 만료를 추가하는 것은 중복 방어이며, 필드가 없으므로 지금은 불가능하다.**

★ 단, `Evidence` 로 두면 **replay 검사 대상이 아니게 된다**(§10 은 단수명만 대상).
회수 통지의 replay 는 fencing 이 막지만, `fence_epoch` 이 **같은** 회수 통지를
반복 전송하는 것은 막지 못한다. 멱등하므로 무해하나, 그 판단을 명시해 둔다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **`Perpetual` 을 그대로 쓴다** | 동작은 같지만 **의미가 다르다.** Genesis 는 "지금도 참인가"를 물을 필요가 없고, `ReplicaAck` 는 반드시 물어야 한다. 한 이름에 두 의미를 담으면 다음 사람이 `ReplicaAck` 를 시스템 상수처럼 다룬다 |
| **`.proto` 에 `expires_at` 을 추가한다** | `schema_version` 상향 필요(§7.3). 그리고 **틀린 해법**이다 — 체크포인트 증거를 만료시키면 오래된 체크포인트에서 재개할 수 없다 |
| **`LongLived` 로 두고 `expires_at=0` 을 "무한" 으로 해석** | ★ 0 은 규칙 b 로 생략되는 기본값이다. "미설정"과 "무한"을 구분할 수 없어, **설정 실수가 무한 유효로 조용히 바뀐다.** `CLAUDE.md` §1(지어내지 않는다) 위반 |
| **6종 각각 다른 정책** | 근거가 같다(전부 증거다). 나누면 다음 메시지를 추가할 때 어디에 넣을지 판단 기준이 없어진다 |

## 결과

### 가능해지는 것

- 6종이 `Signable` 을 갖고 **`verify()` 를 통과할 수 있게 된다.**
- `Evidence` 와 `Perpetual` 이 타입 수준에서 구분되어,
  "이건 과거 사실이니 신선도를 따로 판단해야 한다" 가 코드에 드러난다.

★ **2026-08-16 정정 (독립 검수).** 이 ADR 은 `observed_at` 노출이
"타입 수준에서 강제된다" 고 적었는데 **과장이었다.**
`Signable::observed_at_unix_ms()` 에 **기본 구현이 있어**
아무것도 덮어쓰지 않아도 컴파일된다.

```text
타입이 보장하는 것       메서드 존재 · 값 반환
타입이 보장 못 하는 것   그 값이 진짜 관측 시각인가 · 발행 시각과 구분되는가
```

실제 강제는 `evidence_must_expose_observation_time` **테스트**가 한다.
새 `Evidence` 메시지를 추가하면 그 테스트에도 넣어야 하며,
넣지 않으면 기본 구현이 조용히 쓰인다.

### 포기하는 것

- **시각 기반 만료 방어를 이 6종에 대해 포기한다.** 신선도 판단을 fencing 과
  소비 측에 위임한다. `ReplicaAck` 는 fencing 조차 없어 **소비 측 전담**이다.
- `Evidence` 메시지는 §10 replay 캐시 대상이 아니다.

## 되돌리는 조건

**`ReplicaAck` 의 신선도 오판으로 인한 실제 데이터 손실이 1건이라도 관측되면**
— 즉 소비 측이 오래된 ACK 를 현재 durability 로 착각해
`COMMITTED` 를 선언했는데 복제본이 이미 없던 경우 —
`ReplicaAck` 에 `fence_epoch` 또는 `valid_until` 을 추가하고
`schema_version` 을 올린다 (V-07 즉시 실행).
