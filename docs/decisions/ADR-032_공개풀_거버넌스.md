# ADR-032 · 공개 풀 거버넌스 — Broker 앵커 · 권한 분리 · 만료되는 리더

- **상태:** 개정됨(2026-08-27) — 검수 지적 (A)(B)(D)(E) 답해짐, (C) 좁게 채택,
  (F) 부분 해소. §검수 반영 · §검수 지적 해소 현황 참조
- **날짜:** 2026-08-24
- **관련:** ADR-031 · 기준선 §1.3 원칙 14 · §5.5.1 · §5.6 · §6.3 · §7.2 · §7.4 ·
  `CLAUDE.md` §0.1 · §0.2 · `DoD-47`(CAS reservation) · `DoD-49`(fence binding)

## 배경

ADR-031 은 참여 모델을 두 갈래로 나누고 `PublicPool` 의 신뢰 앵커
(`PoolGovernance`)를 **의도적으로 비워 두었다.** 채우려면 다섯 가지에
먼저 답해야 한다고 적었다.

```text
방장(Owner 상당) 선정·교체·축출 규칙
악의적 방장에 대한 방어
기여도 산정과 분쟁 조정
낯선 코드에 대한 최소 격리 강제
BFT 필요 여부
```

사용자가 다음 구조를 제안하고 승인했다.

```text
중개서버가 멤버를 풀에 배정
  -> 풀 내부에서 리더 선출
  -> 서버가 리더를 승인
  -> 풀에서 작업 시작
```

이 ADR 은 그 구조를 안전하게 성립시키는 조건을 정한다. 위 다섯 가지 중
**넷에 답하고, 기여도·분쟁 조정은 여전히 미해결로 남긴다.**

## 결정

### 1. Broker 를 `PublicPool` 의 신뢰 앵커로 삼는다 — 명시적 선택이다

`PoolGovernance` 의 루트는 **Broker 공개키**다. 설치 시 pin 한다.

이것은 기준선이 팀 모델에서 거부한 제3자 의존(§6.3)을 **공개 풀 모드에
한해** 받아들이는 것이다. 팀 모델은 그대로 Genesis + Owner 다(ADR-031).
모드마다 앵커가 다르다는 것이 ADR-031 구조의 요점이다.

**대가를 숨기지 않는다.**

```text
Broker 침해  -> 공격자가 임의 노드를 멤버로 만들 수 있다
Broker 장애  -> 신규 가입 불가. 기존 멤버는 만료 전까지 계속 동작
```

두 번째는 감수 가능하다. 첫 번째는 감수가 아니라 **탐지 대상**이다
(§미해결 참조).

### 2. ★ 권한을 쪼갠다 — 리더는 멤버십 권한을 갖지 않는다

이 ADR 에서 가장 중요한 항목이다.

| 권한 | 보유자 | 근거 |
|---|---|---|
| 누가 풀의 멤버인가 | **Broker** | 리더가 못 건드린다 |
| 어느 작업을 어디 배치하는가 | **풀 리더** | 스케줄링만 |

리더가 멤버십까지 정하면 **자기 꼭두각시를 계속 넣어 풀을 장악한다**
(Sybil). 권한을 쪼개면 악의적 리더의 최대 피해가 "배치를 불공평하게 함"
으로 제한된다.

리더는 **반장이지 명단 관리자가 아니다.**

### 3. 리더 후보는 자기신고로 정하지 않는다

서로 모르는 참여자는 자기 스펙을 스스로 신고한다. "H100 8장, 가동률 99%"
라는 거짓말을 검증할 방법이 풀 안에는 없다.

```text
Broker 가 관측 이력(실측 가동률·완료 작업 수 등)으로 후보 집합을 좁혀
내려보낸다. 풀은 그 집합 안에서만 리더를 고른다.
```

자기신고 값은 **후보 자격 판정에 쓰지 않는다.** 기준선 §5.6 이 팀 모델에서
"30일 관측 후 실측 가동률" 을 요구하는 것과 같은 정신이다.

### 4. 리더 승인은 만료된다 — 한 번이 아니다

"한 번 승인하면 끝" 이면 승인 후 악해진 리더를 막을 수단이 없다.

```text
Broker 가 리더에게 만료 있는 Lease 를 발급하고 주기적으로 갱신한다.
갱신을 끊으면 자연히 무효화된다.
```

새 장치를 만들지 않는다. 이 저장소에는 이미 Lease 와 `fence_epoch` 가
있고(`DoD-47`·`DoD-49`), 만료·교체·stale 거부가 그 위에서 동작한다.
리더 교체는 `fence_epoch` 상승으로 표현한다 — 구 리더의 지시는 낮은
epoch 이라 거부된다.

### 5. 격리는 최고 등급을 강제한다 — 타협하지 않는다

공개 풀에서는 **모르는 사람의 코드가 내 GPU 에서 돈다.** 팀 모드의
"팀 정책이 정한 등급" 을 그대로 쓰면 안 된다.

```text
PublicPool 은 최소 격리 요구를 낮출 수 없다.
요구를 충족하지 못하는 노드는 공개 풀에 참여하지 않는다.
```

참여 문턱이 올라간다. 그것이 의도다. ADR-031 의 "모드 혼동은 fail-closed"
와 함께, 팀 모드인 줄 알고 낯선 코드를 돌리는 사고를 막는다.

### 6. `PublicPool` 은 Raft 를 요구하지 않는다

팀 모델이 Raft 를 필요로 한 이유는 **"지금 멤버 명단이 무엇인가" 에 대해
모두가 같은 답을 알아야 하는데 그것을 정해 줄 중앙이 없기** 때문이다.
공개 풀에는 Broker 가 있다.

```text
Broker 가 멤버십 레코드에 서명 + 단조 증가 일련번호를 붙여 발급한다.
각 노드는 서명과 번호만 검증한다. 순서 합의가 필요 없다.
```

**따라서 기준선의 `COMMITTED`(과반 합의)를 공개 풀에 요구하지 않는다.**
기준선 §5.5.1 의 "Coordinator 3개 · Raft" 는 팀 모델의 규정이며, 공개 풀은
별도 등급을 쓴다. 이것은 기준선 위반이 아니라 **기준선이 다루지 않은
모드에 대한 신규 정의**다(ADR-031 이 세운 구조).

일련번호는 **단조성 검사가 필수**다. 번호를 검사하지 않으면 Broker 가
침해됐을 때 과거 레코드를 재생(replay)해 취소된 멤버를 되살릴 수 있다.

## 결과

- 공개 풀 구현 비용이 팀 모델보다 **작다.** Raft 가 빠지기 때문이다.
  ADR-031 에 "이 ADR 로 Raft 비용은 줄지 않는다" 고 적은 것은 팀 모드에
  한해 여전히 참이지만, **공개 풀에는 해당하지 않는다.**
- Broker 는 구현 대상이 된다. ADR-031 이 외부 호스팅에 허용한 범위
  (서명된 번들 배포)를 **넘어선다** — 공개 풀에서 Broker 는 키·멤버십
  authority 자체다. 팀 모드의 금지 사항은 그대로 유지된다.
- 리더 선출·교체는 기존 Lease/fencing 위에 얹는다. 새 합의 계층이 없다.

## 이 ADR 이 하지 않는 것

- **기여도 산정과 분쟁 조정을 정하지 않는다.** ADR-031 이 물은 다섯 가지
  중 이것만 남는다. 공개 풀에서 누가 얼마나 기여했고 분쟁이 나면 누가
  판정하는지는 별도 결정이다. 이것 없이도 기술적으로는 동작하지만,
  제품으로는 미완이다.
- **BFT 를 도입하지 않는다.** Broker 를 신뢰하기로 했으므로 지금은
  필요 없다. Broker 없는 완전 탈중앙을 원하면 그때 다시 본다
  (기준선 §1.3 원칙 14 의 "장기 옵션").
- Broker 의 구현 스택을 확정하지 않는다. 호스팅 선택은 이 ADR 의 안전
  조건을 만족하는 한 자유다.
- 팀 모드를 바꾸지 않는다. Genesis + Owner + Raft 그대로다.

## 미해결

**Broker 침해 탐지.** 앵커가 하나뿐이면 침해됐을 때 알아낼 방법이 풀 안에
없다. 최소한 다음이 필요하다.

```text
발급 레코드의 공개 감사 로그 (추가 전용 · Merkle root)
멤버가 자기 레코드의 존재/부재를 독립 확인할 수 있는 경로
일련번호 건너뜀 탐지
```

기준선 v0.3 로드맵의 "Signed append-only audit log + Merkle root" 가 정확히
이 자리에 들어간다. 블록체인 전체가 아니라 **변조 탐지 성질만** 가져오는
것이며, 기각표가 "모든 상태를 Blockchain -> Raft + Signed Audit/Merkle"
로 정리한 것과 일치한다.

**악의적 멤버(리더가 아닌).** 격리를 최고 등급으로 강제해도 완전하지
않다. 자원 고갈, 사이드 채널, 격리 탈출은 남는다. 격리는 위험을 줄이지
없애지 못한다는 것을 제품 문구에서도 과장하지 않아야 한다.

**리더 선출의 구체 규칙.** Broker 가 후보를 좁힌 뒤 풀이 "어떻게" 고르는지
(최초 응답·결정적 해시·투표)는 정하지 않았다. 후보가 이미 Broker 검증을
통과했으므로 안전성보다 공정성 문제이며, 구현 시 결정한다.

## ★ 독립 검수 반영 (2026-08-24) — `CHANGES_REQUESTED`

이 ADR 은 검수 없이 채택됐고, 뒤늦은 적대적 검토가 **여러 주장을
무너뜨렸다.** 틀린 것을 지우지 않고 무엇이 왜 틀렸는지 남긴다.

### (A) "공개 풀은 Raft 불필요" — **철회한다**

§6 의 주장은 **멤버십 순서와 스케줄링 순서를 혼동한 것**이다.
Broker 가 정해 주는 것은 멤버십 레코드의 발급 순서뿐이고, **같은
GPU 를 동시에 예약하는 것을 막는 전역 선형화 지점**은 공개 풀에
정의돼 있지 않다.

근거: `DoD-47` 의 중복 예약 방지는 한 SQLite 파일의 단일
`BEGIN IMMEDIATE` 트랜잭션과 inventory revision CAS 에 의존하며,
구현 자체가 이를 Raft/`COMMITTED` 가 아닌 **local durable state**
라고 규정한다(`crates/coordinator/src/staging_store.rs`).
`fence_epoch` 도 coordinator 로컬에서 채번된다(같은 파일 :448).

따라서 다음이 **정의되지 않았다.**

```text
새 리더가 구 리더의 예약·Attempt·Lease 상태를 어디서 읽는가
두 리더가 같은 GPU 를 예약할 때 전역 CAS 를 누가 수행하는가
Broker 일련번호가 reservation ordering·fence_epoch 와 어떻게 결합되는가
구 리더가 살아 있는 split-brain 동안 새 리더가 무엇을 원자적으로 폐기하는가
새 리더가 같은 SQLite 를 공유하지 않을 때 fencing watermark 를 어떻게 보존하는가
```

"단일 리더 + Lease + fencing 이면 충분하다" 는 **추가로 단일
authoritative scheduler/store 가 있다는 조건에서만** 성립한다.
이 ADR 은 그 조건을 정의하지 않았다.

**따라서 ADR-031 의 "Raft 비용은 줄지 않는다" 를 정정했던 것을
다시 정정한다 — 공개 풀도 스케줄링 선형화 비용을 피하지 못한다.**
형태가 Raft 일지 다른 것일지는 미결정이다.

### (B) "악의적 리더의 최대 피해는 불공평한 배치" — **거짓이다**

리더가 멤버십을 못 건드려도 다음을 할 수 있다.

```text
특정 멤버를 굶기거나 지연시킨다
자기·공모자에게 GPU 를 계속 배정한다
큐 순서를 조작하고 작업을 누락·취소·재시도 유도한다
예약을 장시간 점유해 자원을 고갈시킨다
민감한 작업을 악성 호스트로 라우팅한다
리더 교체·Lease churn 으로 가용성을 훼손한다
유효한 결과·ACK 를 누락하거나 늦게 반영한다
```

증거 서명은 **누가 서명했는가**는 보호하지만 **누락·검열·지연**은
막지 못한다. `AttemptReport`·`ReplicaAck` 저장소는 상태 전이나
reservation release 를 수행하지 않으므로 이 공격면을 덮지 않는다.

### (C) Broker 침해 — 단조성 검사로 **불충분하다**

침해된 Broker 는 `serial = n+1` 로 **새 악성 레코드를 정상
서명해** 발급할 수 있다. 노드는 서명과 더 큰 번호를 보고 정상
최신 상태로 받아들인다. 이것은 replay 가 아니라 **권위 있는
위조**이며 단조성 검사가 막지 못한다.

**따라서 감사 로그 + Merkle root 는 "미해결 후속" 이 아니라 공개
가입을 여는 선행 조건이다.** 다만 감사 로그도 위조를 **예방**하지
않고 사후 **탐지·포크 증명**만 제공한다.

### (D) `CLAUDE.md` §0.1 소유자 주권 — 경계를 명시한다

Broker 의존이 자동으로 §0.1 위반은 아니지만, 이 ADR 이 경계를
적지 않았다. 다음을 계약으로 못박는다.

```text
로컬 Agent/Owner Panel 은 Broker 와 무관하게 즉시 drain·kill·
GPU 반환을 단독 수행한다. 네트워크·Broker·리더가 모두 죽어도 된다.

Broker 불능 시 중단되는 것은 신규 가입과 리더 Lease 갱신뿐이다.
소유자의 강제 비우기는 어떤 경우에도 중단되지 않는다.
```

"기존 멤버는 Lease 만료 전까지 계속 동작" 이라는 문구만으로는
소유자 주권을 보장하지 못한다.

### (E) 기준선 `COMMITTED` — "신규 정의" 가 아니라 **조용한 완화**였다

`docs/protocol/state-machines.md` 는 mode qualifier 없이 Job 제출,
`QUEUED -> STAGING`, Lease 발급, 최종 결과 확정에 `COMMITTED` 를
요구한다. 공개 풀에서 이를 빼려면 **대체 계약**을 규범으로 먼저
정의해야 한다.

```text
무엇이 COMMITTED 를 대체하는 선형화·내구성 보증인가
어떤 전이가 Broker serial 만으로 허용되는가
어떤 전이는 여전히 합의가 필요한가
공개 풀의 checkpoint·canonical·revoke·lease 전이 의미는 무엇인가
```

그 계약 없이는 §6 은 기준선 우회다.

### (F) 강제되지 않는 선언들

`PublicPool` 거부와 "최고 등급 격리" 는 **문서에만 있다.** 코드에
enum·parser·runtime gate·ingress reject·회귀 테스트가 없다.
현재 `SecurityTier` 와 `IsolationClass` 는 별도 축이고, 기존
filter 는 PublicPool 전역 최저선을 강제하지 않는다
(`crates/scheduler/src/filter.rs`).

## 지금 정해야 하는 것 (후속으로 미룰 수 없음)

```text
예약 선형화와 리더 교체 안전성 (split-brain 방지)
Broker serial 과 reservation/fence 의 결합
Broker 투명성 로그·키 회전·침해 후 복구
로컬 Owner drain 우선순위 (위 (D) 로 일부 확정)
PublicPool 의 실제 isolation gate (구체 값과 검증 지점)
리더의 grant/signing 권한 범위
membership revision 이 Attempt/Checkpoint/ReplicaAck 에 미치는 영향
```

기여도 산식과 일반 분쟁 조정, 리더 선출의 공정한 tie-break 은
공개 풀을 닫아 둔 상태라면 후속으로 미룰 수 있다.
**split-brain 방지와 단일 권위 결정은 미룰 수 없다.**

## ★ 검수 지적 해소 현황 (2026-08-27)

위 검수는 여섯 지적((A)~(F))과 "미룰 수 없는 것" 7건을 남겼다.
그 뒤 ADR-033 과 `docs/protocol/state-machines.md` §0.1 이 그중
일부를 답했다. **무엇이 답해졌고 무엇이 남았는지 여기 적는다.**

★ 답해진 것을 "좋아졌다" 로 읽지 않는다. 대부분은 **미정이 결정으로
바뀐 것**이고, 그 결정이 새로 만든 비용은 그대로 남는다.

### 여섯 지적

| 지적 | 현재 | 근거 |
|---|---|---|
| (A) 공개 풀 Raft 불필요 — 철회 | **답해짐** | ADR-033 §1 |
| (B) 악의적 리더 피해 — 거짓 | **답해짐(공격면 이동)** | ADR-033 §1·§3 |
| (C) Broker 침해 — 감사 로그가 선행 조건 | **좁게 채택** | ADR-033 §4 |
| (D) 소유자 주권 경계 | **답해짐** | ADR-033 §2 |
| (E) `COMMITTED` 조용한 완화 | **답해짐** | `state-machines.md` §0.1 |
| (F) 강제되지 않는 선언 | **부분 해소** | `crates/protocol/src/participation.rs` |

**(A) — 전역 선형화 지점이 이제 정의됐다.** 지적의 요지는 "같은
GPU 를 동시에 예약하는 것을 막는 심판이 공개 풀에 정의돼 있지
않다" 였다. ADR-033 §1 이 그 심판을 **Broker 하나로 못박았다** —
리더는 배치 권한이 없고, 두 리더가 같은 GPU 를 예약하는 상황 자체가
생기지 않는다. 검수가 나열한 다섯 미정 항목도 함께 사라진다(구
리더 상태 인수·전역 CAS 수행자·split-brain 폐기 범위 등은 모두
"리더가 예약한다" 를 전제한 질문이었다).

★ **이것은 Raft 를 도입해서 푼 것이 아니라, 선형화 지점을 Broker 로
옮겨서 푼 것이다.** 비용은 사라지지 않고 자리를 옮겼다 — Broker 가
단일 장애점이자 단일 침해점이 된다(§미해결·ADR-033 §5).

**(B) — 공격면이 리더에서 Broker 로 이동했다.** ADR-033 §1 이
리더에게서 배치·큐 조작·자기편향 배정을 없앴다. 그러나 검수가
나열한 공격은 **사라진 것이 아니라 Broker 가 할 수 있는 것이
됐다.** ADR-033 §3 이 그중 굶기기·검열을 **탐지 대상**으로 옮겼고,
그마저 풀 정책으로 끌 수 있다. 리더에게 남은 잔여 권한은
ADR-033 §1 이 다시 적었다.

**(C) — 검수 요구보다 좁게 채택했다.** 검수는 감사 로그를 "공개
가입의 선행 조건" 이라고 했다. ADR-033 §4 는 사용자 결정에 따라
**이해관계가 걸린 풀에만 필수**로 좁혔다. 따라서 이해관계 없는
풀에서 Broker 침해는 **탐지 수단이 없다.** 이것은 지적이 해소된
것이 아니라 **범위를 좁혀 감수하기로 한 것**이다.

**(F) — 절반만 해소됐다.** `ParticipationModel` 은 이제 실제
코드다 — enum·parser·회귀 테스트 7건이 있고, `Default` 가 없음을
compile-fail doctest 가 고정한다
(`crates/protocol/src/participation.rs`). **그러나 배선이 없다.**
`crates/protocol/src/lib.rs` 의 re-export 외에 이 타입을 읽는
호출부가 하나도 없다 — runtime gate 도, ingress reject 경로도 없다.
"최고 등급 격리 강제"(§5)는 여전히 문서에만 있다.

### "미룰 수 없는 것" 7건

| 항목 | 현재 |
|---|---|
| 예약 선형화와 리더 교체 안전성(split-brain) | **해소** — ADR-033 §1. 리더가 예약하지 않으므로 교체 경쟁이 없다 |
| Broker serial 과 reservation/fence 의 결합 | **해소** — ADR-033 §(c). Broker 단일 발급, 풀 생성 시 고정, 실행 중 변경 불가 |
| Broker 투명성 로그·키 회전·침해 후 복구 | **부분** — 감사 로그만 조건부로 정해졌다(§4). 키 회전과 침해 후 복구는 **미정** |
| 로컬 Owner drain 우선순위 | **해소** — (D) + ADR-033 §2 |
| `PublicPool` 의 실제 isolation gate | **미해소** — 구체 값도 검증 지점도 없다 |
| 리더의 grant/signing 권한 범위 | **해소** — ADR-033 §1. 리더는 연락책이며 배치·grant 권한이 없다 |
| membership revision 이 Attempt/Checkpoint/ReplicaAck 에 미치는 영향 | **미해소** |

### 이 문서에서 대체된 부분

```text
§2  "어느 작업을 어디 배치하는가" 를 리더에게 준 부분
    -> ADR-033 §1 이 대체한다. 배치는 전부 Broker 가 한다

§6  "PublicPool 은 Raft 를 요구하지 않는다"
    -> 위 (A) 로 이미 철회됐고, ADR-033 §1 이 대안을 정했다
       (Raft 가 아니라 Broker 단일 권위)
```

**이 절은 §2·§6 의 원문을 지우지 않는다.** 무엇을 왜 바꿨는지가
사라지면 같은 판단을 되풀이한다.

### 남은 것 — 이 문서 기준

```text
PublicPool isolation gate 의 구체 값과 검증 지점
Broker 키 회전과 침해 후 복구 절차
membership revision 이 Attempt/Checkpoint/ReplicaAck 에 미치는 영향
ParticipationModel 의 실제 배선 (runtime gate · ingress reject)
```
