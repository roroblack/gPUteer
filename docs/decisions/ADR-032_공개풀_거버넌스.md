# ADR-032 · 공개 풀 거버넌스 — Broker 앵커 · 권한 분리 · 만료되는 리더

- **상태:** 채택
- **날짜:** 2026-08-24
- **관련:** ADR-031 · 기준선 §1.3 원칙 14 · §5.5.1 · §5.6 · §6.3 · §7.2 · §7.4 ·
  `CLAUDE.md` §0.1 · §0.2 · `DoD-47`(CAS reservation) · `DoD-49`(fence binding)

## 배경

ADR-031 은 참여 모델을 두 갈래로 나누고 `PublicPool` 의 신뢰 앵커
(`PoolGovernance`)를 **의도적으로 비워 두었다.** 채우려면 다섯 가지에
먼저 답해야 한다고 적었다.

```text
방장(Owner 상당) 선정·교체·축출 규칙
악의적 방장에 대한 방어
기여도 산정과 분쟁 조정
낯선 코드에 대한 최소 격리 강제
BFT 필요 여부
```

사용자가 다음 구조를 제안하고 승인했다.

```text
중개서버가 멤버를 풀에 배정
  -> 풀 내부에서 리더 선출
  -> 서버가 리더를 승인
  -> 풀에서 작업 시작
```

이 ADR 은 그 구조를 안전하게 성립시키는 조건을 정한다. 위 다섯 가지 중
**넷에 답하고, 기여도·분쟁 조정은 여전히 미해결로 남긴다.**

## 결정

### 1. Broker 를 `PublicPool` 의 신뢰 앵커로 삼는다 — 명시적 선택이다

`PoolGovernance` 의 루트는 **Broker 공개키**다. 설치 시 pin 한다.

이것은 기준선이 팀 모델에서 거부한 제3자 의존(§6.3)을 **공개 풀 모드에
한해** 받아들이는 것이다. 팀 모델은 그대로 Genesis + Owner 다(ADR-031).
모드마다 앵커가 다르다는 것이 ADR-031 구조의 요점이다.

**대가를 숨기지 않는다.**

```text
Broker 침해  -> 공격자가 임의 노드를 멤버로 만들 수 있다
Broker 장애  -> 신규 가입 불가. 기존 멤버는 만료 전까지 계속 동작
```

두 번째는 감수 가능하다. 첫 번째는 감수가 아니라 **탐지 대상**이다
(§미해결 참조).

### 2. ★ 권한을 쪼갠다 — 리더는 멤버십 권한을 갖지 않는다

이 ADR 에서 가장 중요한 항목이다.

| 권한 | 보유자 | 근거 |
|---|---|---|
| 누가 풀의 멤버인가 | **Broker** | 리더가 못 건드린다 |
| 어느 작업을 어디 배치하는가 | **풀 리더** | 스케줄링만 |

리더가 멤버십까지 정하면 **자기 꼭두각시를 계속 넣어 풀을 장악한다**
(Sybil). 권한을 쪼개면 악의적 리더의 최대 피해가 "배치를 불공평하게 함"
으로 제한된다.

리더는 **반장이지 명단 관리자가 아니다.**

### 3. 리더 후보는 자기신고로 정하지 않는다

서로 모르는 참여자는 자기 스펙을 스스로 신고한다. "H100 8장, 가동률 99%"
라는 거짓말을 검증할 방법이 풀 안에는 없다.

```text
Broker 가 관측 이력(실측 가동률·완료 작업 수 등)으로 후보 집합을 좁혀
내려보낸다. 풀은 그 집합 안에서만 리더를 고른다.
```

자기신고 값은 **후보 자격 판정에 쓰지 않는다.** 기준선 §5.6 이 팀 모델에서
"30일 관측 후 실측 가동률" 을 요구하는 것과 같은 정신이다.

### 4. 리더 승인은 만료된다 — 한 번이 아니다

"한 번 승인하면 끝" 이면 승인 후 악해진 리더를 막을 수단이 없다.

```text
Broker 가 리더에게 만료 있는 Lease 를 발급하고 주기적으로 갱신한다.
갱신을 끊으면 자연히 무효화된다.
```

새 장치를 만들지 않는다. 이 저장소에는 이미 Lease 와 `fence_epoch` 가
있고(`DoD-47`·`DoD-49`), 만료·교체·stale 거부가 그 위에서 동작한다.
리더 교체는 `fence_epoch` 상승으로 표현한다 — 구 리더의 지시는 낮은
epoch 이라 거부된다.

### 5. 격리는 최고 등급을 강제한다 — 타협하지 않는다

공개 풀에서는 **모르는 사람의 코드가 내 GPU 에서 돈다.** 팀 모드의
"팀 정책이 정한 등급" 을 그대로 쓰면 안 된다.

```text
PublicPool 은 최소 격리 요구를 낮출 수 없다.
요구를 충족하지 못하는 노드는 공개 풀에 참여하지 않는다.
```

참여 문턱이 올라간다. 그것이 의도다. ADR-031 의 "모드 혼동은 fail-closed"
와 함께, 팀 모드인 줄 알고 낯선 코드를 돌리는 사고를 막는다.

### 6. `PublicPool` 은 Raft 를 요구하지 않는다

팀 모델이 Raft 를 필요로 한 이유는 **"지금 멤버 명단이 무엇인가" 에 대해
모두가 같은 답을 알아야 하는데 그것을 정해 줄 중앙이 없기** 때문이다.
공개 풀에는 Broker 가 있다.

```text
Broker 가 멤버십 레코드에 서명 + 단조 증가 일련번호를 붙여 발급한다.
각 노드는 서명과 번호만 검증한다. 순서 합의가 필요 없다.
```

**따라서 기준선의 `COMMITTED`(과반 합의)를 공개 풀에 요구하지 않는다.**
기준선 §5.5.1 의 "Coordinator 3개 · Raft" 는 팀 모델의 규정이며, 공개 풀은
별도 등급을 쓴다. 이것은 기준선 위반이 아니라 **기준선이 다루지 않은
모드에 대한 신규 정의**다(ADR-031 이 세운 구조).

일련번호는 **단조성 검사가 필수**다. 번호를 검사하지 않으면 Broker 가
침해됐을 때 과거 레코드를 재생(replay)해 취소된 멤버를 되살릴 수 있다.

## 결과

- 공개 풀 구현 비용이 팀 모델보다 **작다.** Raft 가 빠지기 때문이다.
  ADR-031 에 "이 ADR 로 Raft 비용은 줄지 않는다" 고 적은 것은 팀 모드에
  한해 여전히 참이지만, **공개 풀에는 해당하지 않는다.**
- Broker 는 구현 대상이 된다. ADR-031 이 외부 호스팅에 허용한 범위
  (서명된 번들 배포)를 **넘어선다** — 공개 풀에서 Broker 는 키·멤버십
  authority 자체다. 팀 모드의 금지 사항은 그대로 유지된다.
- 리더 선출·교체는 기존 Lease/fencing 위에 얹는다. 새 합의 계층이 없다.

## 이 ADR 이 하지 않는 것

- **기여도 산정과 분쟁 조정을 정하지 않는다.** ADR-031 이 물은 다섯 가지
  중 이것만 남는다. 공개 풀에서 누가 얼마나 기여했고 분쟁이 나면 누가
  판정하는지는 별도 결정이다. 이것 없이도 기술적으로는 동작하지만,
  제품으로는 미완이다.
- **BFT 를 도입하지 않는다.** Broker 를 신뢰하기로 했으므로 지금은
  필요 없다. Broker 없는 완전 탈중앙을 원하면 그때 다시 본다
  (기준선 §1.3 원칙 14 의 "장기 옵션").
- Broker 의 구현 스택을 확정하지 않는다. 호스팅 선택은 이 ADR 의 안전
  조건을 만족하는 한 자유다.
- 팀 모드를 바꾸지 않는다. Genesis + Owner + Raft 그대로다.

## 미해결

**Broker 침해 탐지.** 앵커가 하나뿐이면 침해됐을 때 알아낼 방법이 풀 안에
없다. 최소한 다음이 필요하다.

```text
발급 레코드의 공개 감사 로그 (추가 전용 · Merkle root)
멤버가 자기 레코드의 존재/부재를 독립 확인할 수 있는 경로
일련번호 건너뜀 탐지
```

기준선 v0.3 로드맵의 "Signed append-only audit log + Merkle root" 가 정확히
이 자리에 들어간다. 블록체인 전체가 아니라 **변조 탐지 성질만** 가져오는
것이며, 기각표가 "모든 상태를 Blockchain -> Raft + Signed Audit/Merkle"
로 정리한 것과 일치한다.

**악의적 멤버(리더가 아닌).** 격리를 최고 등급으로 강제해도 완전하지
않다. 자원 고갈, 사이드 채널, 격리 탈출은 남는다. 격리는 위험을 줄이지
없애지 못한다는 것을 제품 문구에서도 과장하지 않아야 한다.

**리더 선출의 구체 규칙.** Broker 가 후보를 좁힌 뒤 풀이 "어떻게" 고르는지
(최초 응답·결정적 해시·투표)는 정하지 않았다. 후보가 이미 Broker 검증을
통과했으므로 안전성보다 공정성 문제이며, 구현 시 결정한다.
