# DoD-04 · Ed25519 검증 순서와 타입 강제

## 무엇을 입증하려 했는가

`signing.md` §8 · §13.2 는 규범인데 **구현이 없었다.**
`DoD-01`~`DoD-03` 이 모두 limitations 에 "Ed25519 를 하지 않았다" 를 적었고,
`P0-08` 은 "`SCHEMA_TOO_NEW` 반환 경로를 구현하지 않았다" 를 남겼다.

## 이 모듈의 목적은 암호가 아니라 순서 강제다

Ed25519 자체는 `ed25519-dalek` 이 한다. 어려운 부분은 다른 곳에 있다.

> **서명 검증 전에는 어떤 필드 값도 로직에 사용하지 않는다(MUST NOT).** — §8

이것은 **규율로 지킬 수 없다.** 급할 때 `msg.job_id` 를 한 번 읽는 것을
코드 리뷰가 항상 잡지는 못한다. 그래서 타입으로 막았다.

```text
verify(...) -> Result<Verified<M>, VerifyOutcome>

Verified<M> 을 거치지 않으면 M 의 필드에 접근할 수 없다.
```

### 우회 경로가 없음을 컴파일러가 확인한다

```rust
/// ```compile_fail
/// let v: Verified<u32> = Verified { inner: 1, ... };   // 필드 비공개
/// ```
```

★ **뮤테이션으로 확인했다.** `Verified` 의 필드를 `pub` 으로 바꾸면
이 독테스트가 **FAILED** 가 된다(컴파일에 성공해버리므로). 원복하면 통과한다.
누군가 나중에 필드를 열거나 `pub fn new()` 를 추가하면 즉시 드러난다.

★ 처음에 이 독테스트를 `tests/ed25519_verify.rs` 에 두었는데,
**통합 테스트 파일의 독테스트는 실행되지 않는다.** 검증하지 않는 것을
주장하고 있었다. `src/signing.rs` 로 옮겨 실제로 실행되게 했다.

### `VerifyOutcome` 에 `VALID` 를 두지 않았다

```rust
pub enum VerifyOutcome {
    InvalidSignature, UnknownSigner, Expired,
    ClockSkew, Replay, WrongDomain, SchemaTooNew,
}
```

성공은 [`Verified`] 라는 **다른 타입**이다.
열거형에 `VALID` 를 두면 `if outcome != INVALID` 같은 코드가 생기고,
**새 실패 값이 추가될 때 조용히 통과한다.**

### `explain()` — P0-08 의 교훈

```text
SCHEMA_TOO_NEW  "발신자가 더 새로운 스키마를 쓴다 —
                 서명 문제가 아니라 업그레이드가 필요하다"
```

`CLAUDE.md` §3 — "오류 메시지가 사실을 잘못 전하지 않게 한다."

## ★ 발견 2건 — 둘 다 테스트가 처음에 실패해서 드러났다

### 1. 변조하지 않는 변조 테스트

`minimum_security_tier = 0` 으로 "낮추는" 케이스가 **아무것도 바꾸지 않았다.**
기준 매니페스트가 이미 0이었기 때문이다. 테스트는 "거부되어야 하는데 통과했다" 로
실패했고, 원인을 보니 **변조 자체가 없었다.**

이 부류는 조용히 통과하는 것이 더 흔하다. 다른 케이스들이 모두 실제 변조였기에
드러났을 뿐이다.

→ 모든 케이스에 **비공허성 단언**을 넣었다.

```rust
assert_ne!(m, original, "이 변조는 메시지를 바꾸지 않는다 — 테스트가 공허하다: {desc}");
```

### 2. Grant 의 TTL 과 skew 허용치가 같다

```text
signing.md §9    ExecutionGrant 기본 TTL = 60초
                 clock_skew_tolerance    = 60초
```

두 값이 같으므로 `now > issued_at + 60s` 인 시점은 **이미 `now >= expires_at`** 이다.
즉 **미래 방향 skew 검사는 만료 검사에 가려져 도달할 수 없다.**

```text
now = NOW + 60s   ->  Expired   (ClockSkew 가 아니다)
now = NOW - 60s-1 ->  ClockSkew (과거 방향은 도달 가능)
```

안전성 문제는 아니다 — 둘 다 거부한다.
그러나 **"skew 검사가 동작한다" 고 잘못 믿게 된다.** 실제로는 절반만 동작한다.

→ `default_ttl_masks_forward_skew_with_expiry` 로 이 사실을 고정했다.
§9 의 TTL 표를 바꾸면 이 테스트가 실패해 알린다.
→ 실제 단수명 메시지(ExecutionGrant) 구현 시 **재검토 항목**이다.

## 이 실험이 증명하지 "않는" 것

- ★ **§8-8 replay 검사가 실제로는 없다.** §10 이 요구하는 로컬 SQLite 와
  원자적 트랜잭션이 없다. 조용히 빠뜨리지 않기 위해
  `ReplayGuard` 를 타입으로 강제하고 `NoReplayCheck` 라는 이름으로 사실을 드러내며,
  `Verified::require_replay_checked()` 가 미검사 값의 부작용 경로 사용을 막는다.
  **그러나 단수명 메시지의 실제 replay 방어는 존재하지 않는다.**
- ★ **§8-6 신원 확인이 인터페이스뿐이다.** 팀 멤버십 · 키 폐기 · quarantine
  판단의 실제 구현이 없다. 테스트는 `HashMap` 더미를 쓴다.
- **단수명 메시지가 하나도 구현되지 않았다.** `Signable` 을 구현한 것은
  `JobManifest` 와 `Lease` 둘뿐이고 **둘 다 장수명**이다.
  단수명 경로는 테스트 전용 타입으로만 검증했다.
- **키 저장·로딩·회전을 다루지 않았다** (§11 미구현).
- **테스트 키가 결정론적이다.** 실제 CSPRNG 키 생성 경로는 미검증이다.
- `ed25519-dalek` 2.x 한 버전. 배치 검증 · strict 모드 차이 미검토.
- Windows 단일 플랫폼.

## 결정

1. **`signing.md` §8 · §9 · §13.2 를 변경하지 않는다.** 구현 가능하며
   각 실패 경로가 발동함이 실증되었다.
2. **§10 replay 는 저장소 계층 착수 시 구현한다.** 그때까지
   `Verified::replay_checked()` 가 그 사실을 값과 함께 전파한다.
