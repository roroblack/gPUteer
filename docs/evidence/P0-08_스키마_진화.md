# P0-08 · 스키마 진화와 미지 필드

## 왜 이 스파이크가 필요했는가

`DoD-02` 를 쓰다가 **규범 두 개가 정면으로 충돌하는 것**을 발견했다.

`CLAUDE.md` §0.2 / `signing.md` §7.2:

> **"모르는 필드는 무시하고 통과" 가 아니라 "모르면 검증 불가를 선언" 한다.**
> 보안 필드가 추가됐는데 구버전이 그것을 무시한 채 통과시키는 상황을 막기 위해서다.

그런데 **prost 의 기본 동작은 모르는 필드를 조용히 버리는 것**이다.
구현이 "모르는 필드가 있다" 를 알 수 없다면, 규범은 **구현 불가능한 절차를
규정하고 있는 것**이다. 그러면 §7.2 를 다시 써야 한다.

★ 이것은 아키텍처를 뒤집을 수 있는 급이라 미루지 않았다.

## 실험 설계

신버전 메시지를 흉내내기 위해 **와이어 바이트에 직접 미지 필드를 덧붙였다.**
실제 v2 `.proto` 를 만들지 않은 이유는, 필요한 것이 "v1 디코더가 미지 필드를
만났을 때의 행동" 이지 v2 스키마 자체가 아니기 때문이다.

```text
q1  prost 는 미지 필드를 만나면 어떻게 하는가
q2  미지 필드가 canonical 에 흔적을 남기는가
q3  schema_version 상향은 탐지 가능한가
q4  schema_version 을 올리지 않은 필드 추가는?
q5  검사 순서(버전 vs 서명)가 결과를 바꾸는가
q6  버전 강등 공격이 가능한가
```

## 결과

### q1 · q2 — prost 는 조용히 버린다

```text
원본 118B -> 미지 필드 2개 주입 148B -> 디코드 후 재인코딩 118B
디코드 결과가 원본과 완전히 같다
canonical 도 완전히 같다
```

**구버전 검증자는 메시지 본문만 보고는 새 필드의 존재를 알 수 없다.**
디코드가 실패하지도, 경고가 나오지도 않는다. 30바이트가 그냥 사라진다.

→ **유일한 신호는 `schema_version` 이다.**

### q3 · q6 — 그래도 §7.2 는 구현 가능하다

`schema_version` 은 canonical(필드 1)과 `sig_input` **양쪽**에 들어간다.

```text
발신자가 version 2 로 서명    sig_input(Manifest, 2, canonical)
구버전이 version 1 로 재구성  sig_input(Manifest, 1, canonical)   -> 다르다
공격자가 2 -> 1 로 강등       canonical 도 sig_input 도 달라진다   -> 서명 깨짐
```

**이중으로 묶여 있다.** 버전 검사를 빠뜨려도 서명 검증이 막는다.

→ **§7.2 를 변경하지 않는다. 아키텍처 재검토 불필요.**

### ★ q4 — 그런데 §7.3 은 강제할 수 없다

가장 중요한 결과다.

```text
발신자가 field 63 에 새 보안 제약을 넣고 schema_version 은 1로 둔다
  -> 구버전이 디코드. field 63 은 사라진다
  -> canonical 은 구버전 필드만으로 만들어진다
  -> 발신자도 같은 canonical 로 서명했다면
  -> **서명 검증이 통과한다**
```

구버전은 새 보안 제약을 무시한 채 Job 을 실행한다. **아무도 알아채지 못한다.**

`signing.md` §7.3 이 "schema_version 증가 없는 필드 추가" 를 **금지**하는 이유가
정확히 이것이다. 그런데 그 금지를 **프로토콜은 강제하지 못한다.**

```text
.proto 에 필드 한 줄 추가 + 버전 상수 그대로 두기
= 한 줄짜리 실수
= 조용한 보안 우회
```

★ `CLAUDE.md` §0.4 — "강제할 수 없는 것을 보장으로 선언하지 않는다."
같은 정신으로, **강제할 수 없는 규칙을 규범으로 두지 않는다.**

### q5 — 검사 순서의 근거를 정정한다

```text
버전 먼저 (규범대로)   SCHEMA_TOO_NEW
서명 먼저 (순서 위반)  INVALID_SIGNATURE
```

**둘 다 거부한다. 안전성은 순서와 무관하다.**
그러나 운영자에게 전하는 사실이 다르다.

```text
SCHEMA_TOO_NEW     "업그레이드가 필요하다"      -> 맞다
INVALID_SIGNATURE  "서명이 위조됐다"            -> 틀렸다. 며칠 헤맨다
```

`CLAUDE.md` §3 — "오류 메시지가 사실을 잘못 전하지 않게 한다.
stale lease 를 '서명 실패' 로 보고하면 한참 헤맨다." 같은 부류다.

→ §8 검증 순서의 근거를 **"안전성" 에서 "진단 정확성" 으로 정정**했다.

## 대응 — 강제 장치를 만들었다

발견만 기록하고 넘어가면 다음 사람이 같은 실수를 한다.

```text
proto/SCHEMA_FINGERPRINT.txt                  66개 메시지 · 389개 필드
crates/protocol/tests/schema_fingerprint.rs   대조. 다르면 실패
```

스키마가 바뀌면 테스트가 **무엇이 추가/삭제됐는지 출력하며** 실패하고,
둘 중 하나를 강제한다.

```text
(a) 필드 추가 · 타입 변경 · 의미 변경   -> schema_version 을 올린다
(b) 그 외 (주석 · 서식)                -> 지문만 갱신하고 사유를 커밋에 적는다
```

### 가드가 공허하지 않음을 확인

```text
결과       추가된 줄:
             63 bool require_attestation
           사라진 줄:
             (없음)
           "필드 추가 · 타입 변경 · 의미 변경이라면 schema_version 을 올려야 한다"
원복 후    통과
```

**"다르다" 만 말하는 가드는 쓸모가 없다.** 무엇이 달라졌는지 보여야 고칠 수 있다.

## 이 실험이 증명하지 "않는" 것

- ★ **q4 는 "막을 수 없음" 을 증명했을 뿐 "막았다" 를 증명하지 않는다.**
  프로토콜 수준 방어는 존재하지 않는다. `SCHEMA_FINGERPRINT` 는
  **이 저장소 안에서만** 강제된다. 다른 조직의 구현체가 규칙을 어기면 막을 수 없다.
- **지문 파서는 정규식이다.** 남은 구멍은 세 가지다.
  ★ 처음에 "`oneof` 를 다루지 못한다" 고 적었는데 **틀렸다** — `control.proto` 에
  `oneof` 가 5개 있고 파서는 그 안의 필드를 전부 잡는다(뮤테이션으로 확인).
  실제 구멍은 (a) 중첩 `message` 선언 (b) `reserved` (c) `oneof` 안팎 이동이며,
  (a)·(b) 는 현 스키마에 **0건**이다.
- **실제 v2 `.proto` 로 검증하지 않았다.** 와이어 바이트를 직접 조작해 흉내냈다.
- **prost 0.13 한 버전**에서만 확인했다. 버전 상향 시 q1 이 변화를 잡는다.
- **Ed25519 실제 서명이 아니다.** `sig_input` 바이트 비교로 성공/실패를 흉내냈다.
- **`SCHEMA_TOO_NEW` 반환 경로를 구현하지 않았다.** 구현 가능함을 보였을 뿐이다.
- Windows 단일 플랫폼.

## 결정

1. **`signing.md` §7.2 를 변경하지 않는다.** 구현 가능함이 실증되었다.
   **아키텍처 재검토 불필요.**
2. **§7.3 에 빌드 시점 강제 장치를 규범으로 추가했다** (`SCHEMA_FINGERPRINT`).
3. **§8 검증 순서의 근거를 정정**했다 — 안전성이 아니라 진단 정확성.
4. **중첩 `message` 선언 · `reserved` 를 도입하려면 먼저 지문 파서를 고친다.**
   (`oneof` 는 이미 5개 있고 정상 처리된다.) → `TODO_VISION` V-05 로 등록.
