§1  왜 쟀나
════════════════════════════════════════════════════════════════════
`CLAUDE.md` §0.4 가 "소비자 GPU 에는 VRAM quota 강제 수단이 **없다**"
고 적어 뒀다. 같은 날 MPS 가 WSL 에서 불가능함을 확정했고
(`WSL_GPU_MPS_실측_2026-09-08.txt`), remote5090 는 남의 작업이 점유 중이다.

리서치에서 네 번째 수단 후보를 찾았다 — 유저스페이스 CUDA API 가로채기
(`HAMi-core`, CNCF sandbox). 남의 코드를 믿지 않고 직접 재려고, 원리만
뽑아 최소 shim 을 만들어 쟀다.

  가로채는 것  `cuMemAlloc_v2` · `cuMemFree_v2` 둘뿐
  거절 방법    지금 쓰는 양이 상한을 넘으면 rc=2 (CUDA_ERROR_OUT_OF_MEMORY)
  설정         환경변수 `GPUTEER_VRAM_LIMIT_MIB`

★ 재는 쪽은 평범한 CUDA 앱처럼 `-lcuda` 로 링크한다. **ctypes 로
  dlopen 하면 안 된다** — 그건 심볼 가로채기를 우회해서, "가로채기가
  되는가" 를 재는 실험 자체가 성립하지 않는다.

§2  ★★ 1차 판이 틀렸다 — 무엇을 놓쳤나
════════════════════════════════════════════════════════════════════
1차 판의 `cuMemFree_v2` 는 진짜 함수로 **전달만 하고 `used` 를 줄이지
않았다.** 그리고 1차 probe 는 free 를 **한 번도 부르지 않았다.**

  그래서 1차가 실제로 잰 것  "프로세스 **생애 누적 할당** 상한"
  1차가 잰 줄 알았던 것      "**동시 사용량** 상한"

무슨 차이인가:

    512MiB 를 잡았다 풀었다 8번 반복하는 정상 작업은 **실제로는
    512MiB 만 쓴다.** 그런데 1차 판은 상한 2048 에서 그 작업을
    5회차에 거부한다. **막는 게 아니라 죽인다.**

★★ **대조군을 셋이나 뒀는데 못 잡았다.** 이유가 분명하다 —
   **셋 다 free 를 안 부르는 같은 경로만 밟았다.** 대조군은 개수가
   아니라 **경로가 갈라져야** 뜻이 있다. 이 교훈이 이번에 얻은 것 중
   가장 값지다.

2차 판이 고친 것:
   (1) free 가 `used` 를 실제로 줄인다 (포인터별 크기를 장부에 남긴다)
   (2) 검사와 할당을 **한 락 안에서** 한다 — 1차는 검사 후 락을 풀고
       할당해서, 여러 스레드가 동시에 통과하면 상한을 넘을 수 있었다
   (3) **`loop` 대조군을 새로 넣었다** — 잡았다 푸는 것을 반복한다.
       동시 사용량은 늘 512MiB 다. 이게 막히면 상한이 아니라 고장이다

§3  2차 결과 (2026-09-09)
════════════════════════════════════════════════════════════════════
  1. 대조군 A — shim 없이 512MiB x 8 을 잡고 안 푼다
       10회 반복:  8회 all_ok(4096MiB) · **2회 3584MiB 에서 rc=2**
       ★★ **기준선이 흔들린다.** GPU 는 매번 `11 MiB used` ·
          `free_mib=11051` 로 보고하는데도 20% 확률로 4GiB 를 못 잡는다.
          남의 프로세스 때문이 아니다(WSL 에서 호스트 프로세스가 안
          보이는 한계는 있으나, 사용량 보고는 일정하다).
          WSL2 의 GPU 파라버추얼라이제이션 쪽 사정으로 보이나
          **원인을 규명하지 않았다.**
       -> 그래서 **4GiB 근처는 기준선으로 못 쓴다.** 아래 판정은
          그보다 한참 아래(2048 · 1024 · 512MiB)에서만 한다

  2. 대조군 B — shim 켜되 상한 없음
       all_ok  allocated_mib=4096
       -> shim 이 경로에 실제로 끼어 있고(로그가 증명) 아무것도
          망가뜨리지 않는다

  3. 본 실험 — 상한 2048MiB, 4GiB 를 잡고 **안 푼다**
       [shim] 허용: 512MiB (지금 2048MiB, 최대 2048MiB)
       [shim] 거부: 512MiB 요청, 지금 2048MiB 쓰는 중, 상한 2048MiB
       RESULT stopped at_mib=2048 rc=2
       -> 정확히 상한에서 멈춘다

  4. ★ 새 대조군 — 상한 2048MiB, 잡았다 푸는 것을 8번
       [shim] 허용: 512MiB (지금 512MiB, 최대 512MiB)
       [shim] 해제: 512MiB (지금 0MiB, 최대 512MiB)
       RESULT all_ok iterations=8 cumulative_mib=4096 peak_concurrent_mib=512
       -> **누적 4GiB 를 흘려보내면서 통과한다.** 즉 2차 판은
          누적이 아니라 **동시 사용량**을 센다. 1차의 결함이 닫혔다

  5. 경계 — 상한 2048MiB 에서 1024MiB 만 잡는다
       all_ok  allocated_mib=1024
       -> 상한이지 고장이 아니다

§4  그래서 무엇이 확정됐나 — 한정어를 붙여서
════════════════════════════════════════════════════════════════════
확정된 문장은 이것뿐이다:

    **x600 의 WSL2 에서, `cuMemAlloc_v2`/`cuMemFree_v2` 만 부르는
    단일 스레드·단일 프로세스 프로그램에 대해, 유저스페이스 심볼
    가로채기로 동시 VRAM 사용량 상한이 걸린다. MIG·MPS·root·
    드라이버 변경은 필요 없었다.**

따라서 `CLAUDE.md` §0.4 의 "강제 수단이 **없다**" 는 불완전하다.
그러나 아래 §5 때문에 **결론(Exclusive 기본값)은 바뀌지 않는다.**

════════════════════════════════════════════════════════════════════
§5  ★★ 증명하지 않은 것 — 이쪽이 더 길다
════════════════════════════════════════════════════════════════════
`CLAUDE.md` §4 는 "한 **플랫폼** 통과를 다른 플랫폼 통과로 세지 않는다"
고 한다. 여기서 필요한 것은 그보다 좁은 원칙이다 — **한 할당 경로
통과를 다른 할당 경로 통과로 세지 않는다.** 그 원칙은 §4 에 없다.

■ 잡지 못하는 할당 진입점 (전부 VRAM 을 먹는다)
    cuMemCreate / cuMemAddressReserve / cuMemMap / cuMemSetAccess
        -> **PyTorch 의 `expandable_segments:True` 가 이 경로다**
    cuMemAllocAsync / cuMemAllocFromPoolAsync
        -> `cudaMallocAsync` · PyTorch `backend:cudaMallocAsync`
    cuMemAllocManaged · cuMemAllocHost_v2 · cuMemHostAlloc
    cuMemAllocPitch_v2 · cuArrayCreate_v2 · cuMipmappedArrayCreate
    cuModuleLoad* · cuCtxCreate_v2 자체가 먹는 VRAM
        -> 이 실험도 컨텍스트 생성분을 0 으로 셌다

■ 심볼 해석 자체를 우회하는 경로 (후킹한 심볼조차 도달 불가)
    **cuGetProcAddress / _v2 (CUDA 11.3+)**  조회가 libcuda **안에서**
        일어나 내부 주소를 그대로 준다. ELF 인터포지션이 **원리적으로**
        관여할 수 없다. HAMi-core 는 바로 이것 때문에 `cuGetProcAddress`
        자체를 후킹한다 — 이 shim 은 안 한다
    dlopen + dlsym(handle)  TensorFlow · JAX · numba · cupy · 모든
        `ctypes.CDLL`. ★ **이 저장소가 같은 날 자기 손으로 이 경로를
        탔다** — WSL_GPU_MPS 실측이 ctypes 로 libcuda 를 직접 불렀다
    cuGetExportTable  런타임이 쓰는 비공개 디스패치 테이블

■ 회계 자체의 한계
    다중 프로세스     카운터가 **프로세스 로컬**이다. 공유 상태가 없다.
                      `torchrun --nproc_per_node=8` 이면 상한 2048MiB 가
                      실효 16GiB 가 된다. **노드 단위 예산은 이 방식으로
                      강제 불가**다(HAMi 는 이걸 위해 공유메모리를 쓴다)
    다중 스레드       2차에서 락을 넓혀 고쳤으나 **멀티스레드로 재지
                      않았다.** 고쳤다는 주장은 코드 읽기 근거뿐이다
    장치별 구분       단일 전역 카운터다. GPU 2장 이상이면 오계상
    카운터 != 실제    컨텍스트·모듈·cuBLAS/cuDNN workspace 미계상

■ 플랫폼
    Windows 네이티브  **재지 않았고, 쓸 만한 등가물이 없다.**
                      LD_PRELOAD 는 리눅스 기제다. Windows 대안은
                      nvcuda.dll 프록시(드라이버 업데이트마다 깨짐·
                      미서명) 또는 DLL 주입(남의 개인 PC 프로세스에
                      미서명 DLL 주입 — §0.1 위반이고 EDR 이 악성으로
                      본다)뿐이다. 그리고 WDDM 은 초과분을 OOM 대신
                      시스템 메모리로 강등해 **성공시키는** 경우가 많다
                      (ADR-027 이 "quota 가 아니라 총 커밋 상한" 이라
                      부른 것이 이것이다)
                      ★ x600 의 주 환경이 Windows 다. **주 노드에서는
                        이 수단이 기존 Job Object 이상을 아무것도 더하지
                        않는다**
    네이티브 리눅스   **재지 않았다.** 잰 것은 WSL2 이고, 그건
                      `/usr/lib/wsl/lib` 의 dxgkrnl 파라버추얼라이제이션
                      스텁 libcuda 다. 네이티브 드라이버가 아니다
    프레임워크        torch 가 이 배포판에 설치돼 있지도 않다

■ 작정한 우회 — 전부 성립한다
    `env -u LD_PRELOAD python train.py` 한 줄이면 끝이다.
    그 외 unsetenv+execve · 진짜 libcuda 사본 dlopen · dlmopen ·
    /proc/self/maps 로 실주소 계산.
    ★ WSL2 의 `/dev/dxg` 는 `crw-rw-rw-` 즉 **0666** 이다(같은 날
      MPS 실측이 기록). 드라이버로 직행하는 문이 world-writable 이다
    ★ 그러나 이건 새 위험이 아니다 — §0.4 가 이미 "테넌트는 설계상
      임의 네이티브 코드를 돌린다" 를 받아들였다

■ 우리가 새로 만드는 위험
    자식에게 LD_PRELOAD 를 심는 구조 자체가 CVE-2025-23266
    (NVIDIAScape, CVSS 9.0)이 이용한 벡터를 새로 만든다

■ 바깥 근거도 같은 말을 한다
    HAMi 문서        "CUDA API 수준 메모리 강제이지 MIG 같은
                      하드웨어 보안 경계가 아니다"
    HAMi 문서        "신뢰할 수 없는 멀티테넌트 보안 설계로 취급하면
                      안 된다"
    GPU-Virt-Bench   "격리는 근사적이다" — 메모리 98~99% · SM 85~93%
    (arXiv 2512.22125) 처리량 18.5% 저하 · 커널 실행 지연 3.6배

§6  결론
════════════════════════════════════════════════════════════════════
이 저장소가 cgroup·Job Object 에 이미 써 둔 문장이 그대로 적용된다:

    막는다     실수로 메모리를 너무 먹는 작업 — **협조하는 할당 경로에서만**
    못 막는다  빠져나가려고 작정한 코드, 그리고 협조하지 않는 할당 경로

★ 그러므로 §0.4 의 **결론(Exclusive 기본값)은 유지된다.** 바뀌는 것은
  "수단이 없다" 가 "**한 플랫폼(WSL2)의 한 할당 경로에서** 수단이
  확인됐고, 그 등급은 낮다" 로 정확해지는 것뿐이다.

★ 그리고 이 실측은 `GPU_ALLOCATION_MODE_SHARED` 를 여는 근거로는
  **아직 모자란다.** 노드 단위 예산을 강제하려면 최소한 다중 프로세스
  회계가 필요한데 이 방식엔 그것이 없다.
