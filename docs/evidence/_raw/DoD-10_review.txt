검수자 원문 (그대로)
--------------------------------------------------------------------------

독립 검수 결론: SQL 축출 조건과 트랜잭션 원자성은 대체로 맞지만, 메모리/영속 구현 불일치와 테스트 공백이 있습니다.

1. §10 MUST/MUST NOT

- `DELETE`는 `retain_until_ms <= effective` 조건입니다 (`durable_replay.rs:373-379`). 따라서 `retain_until_ms > effective`인 미만료 항목을 SQL이 직접 축출하는 경로는 확인되지 않았습니다.
- 상한 도달 시 삭제하지 않고 `CacheFull`을 반환합니다 (`:457-459`). 이 부분은 §10과 일치합니다.
- 단, 문서 §10.2는 영속 저장소가 아직 미구현이라고 명시합니다 (`signing.md:695-709`). 실제 검증 경로가 여전히 `InMemoryReplayGuard`를 사용한다면 §10의 “로컬 SQLite” 요구는 충족되지 않습니다. 이 파일 범위만으로 실제 wiring은 확인할 수 없습니다.

2. `SignerQuotaExceeded`의 early return

문제 아님 — 경미한 구현 냄새.

`BEGIN IMMEDIATE` 뒤에 `SignerQuotaExceeded`로 바로 반환합니다 (`durable_replay.rs:407-447`). 그러나 `Transaction`이 Drop되면서 암묵적으로 rollback되고, 함수 반환 시 트랜잭션과 SQLite 락이 해제됩니다. 따라서 정상적인 rusqlite 동작에서는 열린 트랜잭션이 남지 않습니다.

실제로 quota 오류 뒤 다른 signer 기록을 수행하는 테스트도 있습니다 (`durable_replay.rs:160-189`).

다만 Drop 중 rollback 실패는 호출자에게 보고되지 않는다는 한계는 있습니다. 이 경로에서는 아직 쓰기가 없어 실질 영향은 작습니다.

3. 시계 되감김/앞으로 튐

- 되감김: 영속 구현은 카운터만 증가시키고 삭제하지 않습니다 (`durable_replay.rs:352-355`). 메모리 구현과 동일합니다 (`replay.rs:205-209`).
- 미래 점프: 둘 다 `MAX_GC_ADVANCE_MS`로 제한합니다 (`durable_replay.rs:358-369`, `replay.rs:217-227`).

중대 — 큰 `u64` 시각에서 동작이 다릅니다.

`gc()`는 실제 clamp 전에 `now_unix_ms`를 `i64`로 변환합니다 (`durable_replay.rs:342-344`). 예를 들어 `u64::MAX`를 넘기면 영속 구현은 `Io`를 반환하고 `clock_jumps`도 증가시키지 않습니다. 메모리 구현은 jump로 처리하고 clamp합니다.

또한 `now_sql`은 이후 사용되지 않습니다 (`:343`, `:385`). 변환 위치가 잘못 배치된 흔적입니다.

4. `busy_timeout = 1초`

경미 — 정책과 테스트가 부족합니다.

두 GC가 동시에 실행되면 `BEGIN IMMEDIATE`에서 하나가 락을 얻고, 다른 하나는 최대 1초 기다립니다 (`durable_replay.rs:44`, `:345-348`). 첫 번째 GC가 FULL sync나 대량 DELETE로 1초를 넘기면 두 번째는 `LockTimeout`이 됩니다.

호출자는:

- GC: 짧은 backoff를 둔 제한적 재시도 가능
- 검증: 재시도 실패 시 반드시 거부
- `LockTimeout`을 `Fresh`로 바꾸거나 무시하면 안 됨

현재 구현 자체에는 fail-open 경로가 없습니다. `Fresh`는 commit 성공 뒤에만 반환됩니다 (`:461-476`). 다만 동시 락 테스트와 재시도 정책은 없습니다.

5. DELETE journal과 FULL sync

선택 자체는 보수적인 선택으로 보입니다.

코드는 rollback journal과 Windows 파일 교체 제약을 이유로 제시합니다 (`durable_replay.rs:211-217`). 그러나 WAL을 명시적으로 비교하거나, 왜 WAL의 `-wal`/`-shm` 파일과 checkpoint 문제보다 DELETE가 필요한지 설명하지는 않습니다.

따라서 “선택은 존재하지만 근거가 충분히 문서화되었다”고 보기는 어렵습니다. §10 자체도 WAL 금지를 요구하지 않습니다.

6. 공허한 테스트

중대 — `two_connections_race_on_the_same_nonce`는 race 테스트가 아닙니다.

두 연결을 만들지만 호출은 순차적입니다 (`durable_replay.rs:481-486`). 실제 동시 락 경쟁, `busy_timeout`, `LockTimeout`은 검증하지 않습니다.

경미 — crash 테스트는 “부분 기록”이 아닙니다.

자식은 완전한 INSERT를 수행한 뒤 commit 없이 종료합니다 (`durable_replay.rs:434-458`). 즉, “부분적으로 찢어진 row”가 아니라 “완전히 작성됐지만 미커밋된 row”입니다.

그래도 rollback journal을 남기고 재시작 후 nonce 2가 `Fresh`인지 확인하므로, 미커밋 트랜잭션 rollback 자체는 실제로 검사합니다 (`:400-419`). 다만 `DurableReplayGuard::check_and_record`가 INSERT와 commit 사이에서 죽는 경우나 전원 장애 중 torn write는 검증하지 않습니다.

7. 16바이트 nonce를 `Io`로 분류

중대 — 분류가 부정확합니다.

nonce 길이 오류는 로컬 디스크 장애가 아니라 입력/프로토콜 위반인데 `ReplayStoreError::Io`로 반환합니다 (`durable_replay.rs:398-401`). 테스트도 이 분류를 그대로 고정합니다 (`durable_replay.rs:236-245`).

운영적으로 디스크 장애와 malformed request가 같은 저장소 장애 계열로 보고될 수 있습니다. 별도의 입력 오류 또는 정책 위반 분류가 필요합니다.

8. 메모리 구현과 영속 구현의 계약 일치 여부

일치하지 않습니다.

구체적인 반례:

- 15바이트 nonce  
  - 영속: `Io` (`durable_replay.rs:398-401`)
  - 메모리: `Fresh` (`replay.rs:260-289`)
- `retain_until_ms = u64::MAX`  
  - 영속: `i64` 변환 실패로 `Io` (`durable_replay.rs:404`)
  - 메모리: `Fresh` (`replay.rs:287-289`)
- `gc(u64::MAX)`  
  - 영속: `Io` (`durable_replay.rs:343`)
  - 메모리: clock jump로 clamp 후 GC (`replay.rs:217-227`)
- `capacity = 0`  
  - 영속: `open_with_capacities` 자체가 오류 (`durable_replay.rs:194-203`)
  - 메모리: 생성은 성공하고 이후 요청이 quota/cache 오류가 됨 (`replay.rs:137-151`, `:273-285`)

최우선 수정 후보는 nonce 검증을 메모리 구현에도 넣고, `gc()`의 `now`를 clamp 판단 후 필요한 경우에만 SQL 범위로 변환하는 것입니다.

확인 범위: `crates/crypto/src/durable_replay.rs`, `crates/crypto/tests/durable_replay.rs`, `docs/protocol/signing.md` §10, 비교 대상 `crates/crypto/src/replay.rs`를 정적 검토했습니다. 실제 애플리케이션이 어느 ReplayGuard를 wiring하는지는 이 범위에 없어 단정하지 않았습니다.
