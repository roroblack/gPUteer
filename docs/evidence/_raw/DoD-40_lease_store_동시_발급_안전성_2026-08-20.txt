=== 설계 조사 (p206, read-only) 결론 요약 ===

로드맵 조각 7("다중 Agent selftest")의 진짜 "다중 Agent 동시 경쟁"은 현재 Coordinator 아키텍처로 표현 자체가 불가능하다:
- Coordinator run()은 accept_with_deadline() → serve_one_connection() 동기 호출 → 완료 후 다음 accept()로, 의도적으로 순차 처리(coordinator/lib.rs:315,331,419에 "deliberately sequential" 명시).
- Coordinator 설정에는 agent_device_id·Agent 검증 키가 각각 하나뿐(coordinator/lib.rs:38,321) — 두 번째 독립 Agent는 identity/key 계약에서 먼저 막힘.
- connection_attempt가 Agent별이 아니라 Coordinator 전체 accept 순번(coordinator/lib.rs:343)이라 여러 Agent 동시 접속 자체가 지금 계약 밖.
- 동일 identity 복제 Agent의 active-session owner 선정도 별도 설계 필요(classify_resume()은 session_id를 durable owner로 저장 안 함).

DoD-24 시나리오 34(IdentityConflict)는 "순차 실행된 별도 프로세스 쌍이 같은 lease_id를 다른 holder로 주장하면 거부"만 증명 — "비어 있는 DB를 두 연결이 거의 동시에 보고 INSERT 경쟁"은 검증 안 됨.

권장 최소 조각: CoordinatorLeaseStore::get_or_issue()에 별도 SQLite 연결 두 개가 동시에 같은 lease_id·다른 holder_node_id를 최초 발급하려 할 때, 정확히 한 후보만 저장되고 다른 후보는 fail-closed되며 저장값을 덮어쓰지 못한다는 storage-level 경쟁 테스트로 좁힘. 로드맵 조각 7 원안 전체는 scheduler/다중 Agent 아키텍처 단계까지 명시적으로 이월.

=== 독립 검수 1라운드 (p208) — CHANGES_REQUESTED ===

차단 결함: 두 후보가 holder_node_id만 다르고 fence_epoch·모든 시각 필드·coordinator_term·max_total_duration_seconds는 전부 같은 값이라, 최종 assert_eq!(stored, winner)에서 패자의 동일한 값과 승자 값을 구별할 방법이 없음 — 패자 경로가 실수로 expires_at_unix_ms나 coordinator_term을 덮어써도 테스트가 통과함. "패자 값의 부분 덮어쓰기 없이 승자 전체가 남는다"는 주장이 실제로는 입증되지 않았음.
