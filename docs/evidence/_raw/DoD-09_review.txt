1. `find_resume_point`가 잘못된 체크포인트를 고를 수 있는가? — 예

- `root` 아래 모든 디렉터리의 매니페스트를 검사하고, `job_id`·`attempt_id`를 필터링하지 않습니다. 가장 큰 `step`을 선택합니다.  
  `writer.rs:102-133`

  반례: 다른 job의 `step=100` 체크포인트와 현재 job의 `step=10` 체크포인트가 같은 `root`에 있으면 다른 job 것을 선택합니다.

- `LATEST` 포인터도 사용하지 않습니다.  
  `writer.rs:137-142`와 `writer.rs:102-133`

- `files: []`인 매니페스트는 `verify_files`의 반복문을 통과합니다. 따라서 데이터 파일이 하나도 없어도 후보가 됩니다.  
  `durability.rs:127-140`

- `checkpoint_id`와 실제 디렉터리 이름이 같은지도 검증하지 않습니다. 디렉터리 `dir-A`에 `checkpoint_id: "dir-B"`인 매니페스트를 두면 해시 검증은 통과하지만, 반환된 ID로 재개하려 할 때 파일 위치가 어긋날 수 있습니다.  
  `writer.rs:110-129`, `durability.rs:106-119`

2. `startup_gc`가 지워서는 안 될 것을 지우는가? — 예

PARTIAL 판정은 사실상 다음뿐입니다.

- 매니페스트가 없으면 해당 디렉터리의 모든 일반 파일 삭제
- 이름이 `.tmp`로 끝나면 매니페스트가 있어도 삭제

`atomic.rs:303-323`

반례:

- `manifest.json`이 일시적으로 사라졌거나 이름이 바뀐 동안 실행되면 정상 데이터 파일도 삭제됩니다.
- `payload.tmp`가 실제 체크포인트 데이터 파일이고 매니페스트에도 등록되어 있어도 무조건 삭제됩니다.
- 매니페스트가 존재하지만 손상됐거나, 매니페스트가 가리키는 데이터 파일이 없어도 삭제하지 않습니다. 즉 false negative도 있습니다.
- root 아래의 임의 디렉터리도 모두 체크포인트로 간주합니다.  
  `writer.rs:153-164`

동시 실행 시:

- 두 프로세스가 같은 `.tmp`를 보면 한쪽이 먼저 삭제하고, 다른 쪽의 `remove_file`이 `NotFound`로 실패할 수 있습니다.  
  `atomic.rs:319-321`
- 한 프로세스가 디렉터리를 삭제한 뒤 다른 프로세스가 `read_dir`하면 `NotFound`가 반환될 수 있습니다.  
  `writer.rs:162-164`

3. `write_checkpoint` 실패 경로 — 문제 있음

파일과 매니페스트를 먼저 쓰고, 마지막에 포인터를 갱신합니다. 포인터 갱신 실패 시 앞서 쓴 데이터와 매니페스트를 되돌리지 않습니다.  
`writer.rs:37-55`

반례:

1. `ckpt-10`의 데이터 파일 작성 성공
2. `manifest.json` 작성 성공
3. `LATEST` 교체 실패
4. 호출자는 `Err` 수신
5. 디스크에는 완전한 `ckpt-10`이 남음

`replace_with_retry`도 실패 시 포인터용 임시 파일만 지우며 체크포인트 디렉터리는 정리하지 않습니다.  
`atomic.rs:214-255`

재시작하면 현재 구현에서는 그 체크포인트에서 재개할 수 있습니다. `find_resume_point`가 `LATEST`를 무시하고 모든 유효 매니페스트를 스캔하기 때문입니다.  
`writer.rs:102-133`

즉 호출자는 “실패”를 받았지만, 재시작 시 실패한 것으로 보였던 체크포인트가 선택될 수 있습니다.

4. `DurabilityState` 전이가 실제 파일 상태와 연결되어 있는가? — 연결 코드를 못 찾았다

- `DurabilityState::transition`은 메모리상 enum 값만 반환합니다.  
  `durability.rs:55-81`
- `CheckpointManifest`에는 `DurabilityState` 필드가 없습니다.  
  `durability.rs:106-119`
- `write_checkpoint`는 상태 전이를 호출하지 않고, 데이터·매니페스트·포인터만 씁니다.  
  `writer.rs:28-57`

따라서 `Writing → LocalWritten → HashVerified → ...` 전이가 실제 파일 생성·검증·포인터 갱신과 기록상 연결되어 있지 않습니다.
