Windows 에도 감시 프로세스 없이 강제되는 시한이 있는가 — 실측
측정일 2026-09-09 · 기계 x600 (Windows 11) · 방법 E:\gputeer-work\wintime\probe.cmd
소스   scripts/os_deadline_probe/windows_job_time_probe.ps1

════════════════════════════════════════════════════════════════════
§1  왜 쟀나 — 그리고 내가 한 번 잘못 접었다
════════════════════════════════════════════════════════════════════
같은 날 리눅스에서 `systemd-run -p RuntimeMaxSec` 이 **띄운 프로세스를
SIGKILL 해도 시한대로 발동**함을 실측했다. 그래서 "허가증 만료를 추측이
아니라 장치로 바꿀 수 있다" 고 보고했다.

★ 그런데 그 방법은 **리눅스 + root** 에서만 된다. 이 프로젝트가 노리는
  노드는 팀원 개인 PC 이고 대부분 Windows 다. x600 도 Windows 다.
  즉 **주력 플랫폼에서 안 되는 것을 자랑한 셈**이었다.

Windows 를 찾아보니 이런 사실들이 나왔다:
  · Job Object 에 **벽시계** 시한은 없다 (Microsoft 문서)
  · 이 문제를 다루는 알려진 도구도 **감시 프로세스가 주기적으로 시계를
    확인**하는 방식이다 — 그 감시가 죽으면 시한이 사라진다
  · 작업 스케줄러의 실행시간 제한은 **직접 실행한 작업에는 적용 안 된다**
    (우리가 띄우는 방식이 정확히 그것이다)

★ 여기서 "Windows 는 답이 없다" 고 결론지었다. **너무 일렀다.**
  사용자가 더 찾아보라고 해서 다시 봤더니, 벽시계는 없어도
  **`JOB_OBJECT_LIMIT_JOB_TIME`(CPU 시간)은 커널이 직접 강제**한다.
  Microsoft 문서: "The system periodically checks ... the action
  specified in EndOfJobTimeAction is carried out" — 감시 프로세스가
  필요하다는 말이 **없다.**

  그것이 사실인지 쟀다.

§2  결과
════════════════════════════════════════════════════════════════════
★ `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 는 **일부러 안 걸었다.** 걸면
  손잡이가 닫힐 때 작업이 죽어서, **커널 타이머가 죽인 것**과
  **손잡이가 닫혀 죽은 것**을 구분할 수 없다. 이 실험이 재려는 것은
  타이머 쪽이다.

  A. 대조군 — 시한 없이 CPU 를 태운다 (8초 관찰)
       8초 뒤 살아 있나  True
       누적 CPU 시간     8.1초
       -> 실험 장치가 동작한다. 이 작업은 실제로 CPU 를 태운다

  B. 본 실험 — CPU 시한 5초, 그리고 **띄운 쪽이 손잡이를 놓는다**
       작업 개체에 넣음  True (pid 25528)
       손잡이 닫음       -> 이제 이 작업을 쥐고 있는 것은 **커널뿐**이다
       7.6초에 강제 종료  종료코드 -1073741756 (0xC0000044,
                          STATUS_QUOTA_EXCEEDED)
       -> **커널이 죽였다.** 살아 있는 감시 프로세스가 없었다

  C. 대조군 — 시한 60초, 3초짜리 작업
       종료코드 0
       -> 넉넉한 시한은 정상 작업을 방해하지 않는다.
          이 대조군이 없으면 "시한이 있다" 와 "다 죽인다" 를 구분 못 한다

§3  두 플랫폼을 나란히 놓으면
════════════════════════════════════════════════════════════════════
                         Linux (systemd)      Windows (Job Object)
  재는 것                 **벽시계**            **CPU 시간**
  정확도                  정확                  **어림**(7.6초 벽시계에
                                                5초 CPU 시한이 발동)
  감시 프로세스 필요?     아니오                **아니오**
  정지 여유(체크포인트)   있다(TimeoutStopSec)  없다 — 즉시 종료
  신호 무시하는 작업      죽는다                죽는다
  권한                    **root 필요**         **불필요**
  손자까지                죽는다                죽는다(job 전체)

★ 서로 다른 구멍을 덮는다:

                              커널 CPU시한   살아 있는 감시
    에이전트가 죽는다              O              O
    에이전트가 얼어붙는다          O(계산 중이면)  X
    감시가 얼어붙는다              O(계산 중이면)  X
    작업이 멈춰 VRAM 만 쥔다       **X**          O

  둘 다 못 잡는 경우 = "감시도 얼고 작업도 계산을 안 한다".
  그건 아무것도 계산하지 않으면서 VRAM 만 붙들고 있는 상태다 —
  가장 덜 해로운 경우다.

════════════════════════════════════════════════════════════════════
§4  못 하는 것 · 안 재 본 것
════════════════════════════════════════════════════════════════════
  · **CPU 시간은 벽시계가 아니다.** 계산을 안 하고 VRAM 만 쥐고 있는
    작업은 영원히 안 잡힌다. 이건 원리적 한계다
  · **정지 여유가 없다.** Windows 쪽은 규범 §209 의 "체크포인트 후
    정지" 를 못 지킨다 — 즉시 종료된다. Linux 는 지킨다(실측함)
  · 어림값이다. 5초 CPU 시한이 7.6초 벽시계에 발동했다. 여러 스레드가
    돌면 CPU 시간이 벽시계보다 **빨리** 쌓여 일찍 죽을 수 있다 —
    **다중 스레드로 재지 않았다**
  · Linux 의 대응물 `RLIMIT_CPU`(root 불필요)를 **재지 않았다.**
    per-process 이지 per-tree 가 아니라 job object 보다 약할 것으로
    보이나 확인하지 않았다
  · 현재 코드는 이 플래그를 **안 건다.** `runtime-windows/src/lib.rs:674`
    가 `JOB_OBJECT_LIMIT_JOB_MEMORY | JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
    만 건다. 한 줄 추가할 자리다
  · 작업 스케줄러의 **트리거 단위** 실행시간 제한(`Trigger.ExecutionTimeLimit`)
    은 작업 단위 설정과 별개다. 시각 트리거로 등록하면 살아날 수
    있으나 **재지 않았다**

§5  결론
════════════════════════════════════════════════════════════════════
**두 플랫폼 모두 감시 프로세스 없이 커널이 강제하는 시한을 가진다.**
Linux 는 정확하고 여유까지 주지만 root 가 필요하고, Windows 는 어림이고
여유가 없지만 권한이 필요 없다.

그래서 "만료됐다" 를 **추측이 아니라 장치로** 만드는 것이 두 플랫폼에서
모두 가능하다 — 등급은 다르다.

★ 그러나 이것만으로 예약을 지워도 된다는 뜻은 **아니다.** 독립 검수가
  든 기각 사유 셋 중 ①(예약 행이 증거 저장소의 외래키다)은 그대로 남는다.
  둘을 닫은 것을 셋을 닫은 것으로 세지 않는다(`CLAUDE.md` §4).
