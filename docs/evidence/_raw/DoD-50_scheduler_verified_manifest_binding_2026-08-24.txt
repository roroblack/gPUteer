=== 설계 조사와 범위 결정 ===

설계 조사는 strict `JobManifest -> JobRequirements` 변환기 자체는 하루 안에 만들 수
있지만, authoritative device→member 해석과 기본 `MIRRORED` durability를 실제로 소비하는
경로가 없는 상태에서는 orchestration에 안전하게 연결할 수 없다고 판정했다. 현재 Job
row에는 Manifest hash만 있어 재시작 뒤 strict projection이나 Grant 입력을 복원할 원본도
없었다. 따라서 이번 조각은 변환기나 wire 연결보다 먼저, 이미 서명이 검증된 signed
`JobManifest`를 accepted Job·idempotency와 같은 transaction에 durable하게 묶는 저장
경계로 제한했다.

=== 구현 ===

- `StoredManifestBinding`, `ManifestBoundSubmitResult`, typed `ManifestCorruption`을 추가했다.
- `CoordinatorJobStore::submit_verified_manifest()`와 `get_manifest_binding()`을 추가했다.
- 신규 schema
  `coordinator_job_manifests(job_id PK/FK, verified_signer_id, manifest_body)`가 signed
  Manifest protobuf body와 submission-time signer identity를 저장한다.
- production 저장 API는 raw `pb::JobManifest`가 아니라 오직
  `&Verified<pb::JobManifest>`만 받는다. fault-injection을 받는 inner 함수는 private이다.
- `Verified::get()` 전에는 Manifest의 `job_id`나 `submitter_device_id`를 읽지 않는다.
  그 전에 실행되는 submission validation은 durable side effect를 만들지 않는다.
- `Verified::get()` 뒤 Manifest `job_id`와 `submitter_device_id`를 accepted submission과
  대조하고, `Verified::signer_id()`도 accepted `submitter_device_id`와 대조한다.
- caller가 준 hash를 저장값으로 신뢰하지 않는다.
  `blake3_256(signing_input(manifest))`를 다시 계산해 supplied hash와 대조하고 그
  재계산값을 Job row와 결과 binding에 저장한다.
- Job row, Manifest body/signer row, idempotency row를 하나의 `BEGIN IMMEDIATE`
  transaction에 저장한다. Manifest insert 직후 fault는 세 row를 모두 rollback한다.
- exact replay는 최초 Job과 Manifest binding을 복원한다. 같은 idempotency key의 다른
  submission/Manifest는 `IdempotencyConflict`, 같은 job ID와 다른 key는
  `JobIdConflict`로 거부한다.
- `get_manifest_binding()`은 의도적으로 `Verified`를 반환하지 않는다. 반환 타입은 raw
  `StoredManifestBinding`이며, 재시작 뒤 authoritative key directory로 다시 서명을
  검증하기 전에는 scheduler 또는 Grant 생성에 쓸 수 없다.
- load는 빈/해독 불가 body, hash, job ID, submitter device identity, submission-time
  signer identity 손상을 typed `ManifestCorruption`으로 fail closed한다. Manifest row가
  없는 legacy Job도 `LegacyManifestMissing`으로 거부한다.

=== 자체 재검토에서 발견하고 닫은 테스트 공백 ===

자체 재검토에서 두 공백을 발견했다.

1. pre-existing schema migration 뒤 Manifest row가 없는 legacy Job에 대한 테스트가
   typed `LegacyManifestMissing` 전체 값을 assertion하지 않았다. 정확한 job ID까지
   포함한 오류 대조로 보강했다.
2. 저장된 protobuf body의 `submitter_device_id` 손상을 직접 만들고
   `ManifestCorruption::SubmitterDeviceIdMismatch`를 확인하는 fixture가 없었다. body의
   device identity를 변조한 뒤 load가 fail closed하는 테스트를 추가했다.

=== negative test와 뮤테이션 판별력 ===

- `identity_and_supplied_hash_mismatches_create_no_rows`: accepted job ID, accepted device ID,
  supplied hash 불일치는 typed error이고 Job/Manifest/idempotency row가 0개다.
- `verified_manifest_replay_returns_original_and_changed_manifest_conflicts`: exact replay는
  최초 binding을 반환하고 changed Manifest는 conflict로 거부된다.
- `fault_after_manifest_insert_rolls_back_job_body_and_idempotency`: Manifest insert 뒤 fault가
  Job/body/idempotency를 전부 rollback한다.
- `empty_and_undecodable_manifest_bodies_fail_closed`: 빈 body와 protobuf decode 실패를
  구분해 fail closed한다.
- hash, job ID, submitter device ID, signer ID의 durable corruption을 각각 typed
  `ManifestCorruption`으로 거부한다.
- legacy schema migration 뒤 Manifest child row가 없는 Job은 exact
  `LegacyManifestMissing { job_id }`로 거부한다.
- 뮤테이션 1: load의 recomputed hash 대조를 제거하면 body corruption test가 실패했다.
- 뮤테이션 2: submit의 verified signer 대조를 제거하면 signer/device mismatch test가
  실패했다.
- 두 뮤테이션은 즉시 원복했고 관련 suite가 다시 통과했다.

=== 범위와 제한 ===

- load 시 서명을 재검증하지 않는 것은 의도된 설계다. 호출자가 authoritative key
  directory로 재검증해야 한다.
- membership validity와 authoritative device→member 해석은 범위 밖이다.
- strict `JobRequirements` projection과 기본 `MIRRORED` durability 소비는 범위 밖이다.
- Grant/Lease scope, `COMMITTED` submission, production wire 연결은 범위 밖이다.
- 저장소가 보존하는 submission-time signer ID는 현재 membership 유효성이나 key
  rotation 뒤의 권위를 증명하지 않는다.

결론: verified signed `JobManifest`는 accepted Job 및 idempotency binding과 같은 local
SQLite transaction에 durable하게 저장되고 restart/replay 뒤 raw binding으로 복원된다.
미검증 Manifest를 이 API로 저장할 수 없고 load 결과도 재검증 전에는 권한 있는
`Verified` 값으로 승격되지 않는다. 이는 membership resolution, projection, Grant 생성,
Raft `COMMITTED` 또는 production 연결 완료를 뜻하지 않는다.
