=== 왜 반복하나 ===

이 저장소의 교착 버그는 **전부 특정 시나리오 조합에서만** 드러났다:

  DoD-22  --revoke-after-round 0 + 양쪽 do_renew=true 조합
  DoD-23  renew_rounds > 1 이고 SUPERSEDED 가 마지막이 아닌 회차
  DoD-27  같은 부류 세 번째

셋 다 "기존 시나리오들이 그 조합을 우연히 피해가 안 드러났었다" 로
기록돼 있다. 한 번 돌려 통과하는 것과 **늘 통과하는 것**은 다르다.

=== 1차: 200회 ===

  SOAK_DONE runs=200 failures=2
    RUN 1   FAILED
    RUN 151 FAILED

★★ **151회차가 중요하다.** 1회차만 실패했으면 "첫 실행 특유"(바이너리
  최초 로드 · 백신 검사 등)로 설명할 수 있다. 그런데 151 은 중간이다.
  **약 1% 확률로 실패하는 무언가가 있다.**

★ **원인은 아직 모른다.** 1차 스크립트가 매 회차 출력을 같은 파일에
  덮어써서 실패한 회차의 내용이 남지 않았다. **내 스크립트 설계
  잘못이다** — 소크의 목적은 드문 실패를 잡는 것인데, 잡고도 증거를
  버리게 짜 놨다.

=== 2차: 300회 (실패 출력 보존) ===

  SOAK2_DONE runs=300 failures=1
    RUN 50 FAILED

  ★★ **이번엔 내용이 남았다.** 실패한 회차의 출력 전문:

    coordinator-agent-selftest 실패: 51) reconnect revoke failed:
      coordinator="coordinator-stub 실패: accept timeout exceeded
"
      agent=""

  51번은 **"연결이 끊긴 뒤 다시 붙는" 시나리오**다(첫 ACK 직후 durable
  revoke → 재접속 시 get_or_issue 가 revoked 로 거부해야 한다).
  Coordinator 가 연결을 기다리다 5초에 포기했고, **Agent 는 오류조차
  내지 않았다.**

=== 3차: 300회 (같은 빌드, 같은 기계) ===

  SOAK2_DONE runs=300 failures=0

  ★★ **한 번도 안 났다.** 이것이 판단을 바꿨다 — 아래 참조.

=== 합계와 판정 ===

  1차 200회  실패 2 (그중 1건은 감독자 수동 실행 겹침 가능성 있음)
  2차 300회  실패 1 (시나리오 51, accept timeout)
  3차 300회  실패 0
  ──────────────────────────────────────────────
  합계 800회  실패 3  ≈ 0.4%

★ **가설**(확인 안 함): 흐름이 이렇다.

    1  Coordinator 를 띄운다 -> READY 를 찍는다
    2  ★ 그다음에 Agent 프로세스를 띄운다
    3  Coordinator 의 accept 5초는 **이미 세고 있다**

  `accept_with_deadline()`(`coordinator/src/lib.rs:1738`)은 호출마다
  5초를 새로 준다(누적 아님). Agent 쪽 재시도는 base 10ms · cap 25ms 라
  여유가 200배다. 그런데도 실패했다는 것은 **Agent 가 아직 뜨지도
  못했을 가능성**을 가리킨다 — Agent stderr 가 빈 것과도 맞는다.
  300회 연속 실행이면 디스크·백신 부하로 프로세스 기동이 늦어질 수 있다.

★★ **그러나 이 가설을 검증하지 못했다.** 3차 300회가 깨끗해서다.

  0.4% 를 대상으로 "대기 시간을 늘리면 사라지는가" 를 가리려면
  **한 갈래당 1000회 이상**이 필요하다(그래야 기대 실패가 4건 대 0건
  수준으로 갈린다). 5000 -> 30000 실험을 준비까지 해 놓고 **돌리지
  않았다** — 300회로는 어느 쪽이든 아무 말도 못 하기 때문이다.
  준비한 것을 돌렸다는 이유만으로 결론을 쓰지 않는다.

=== 그래서 무엇을 했나 / 안 했나 ===

  했다    현상을 시나리오 하나(51)와 오류 문구 하나로 특정
          재현 절차를 `scripts/soak_selftest.cmd` 로 남김
          빈도를 800회 표본으로 냄(0.4%)

  안 했다 **고치지 않았다.** 원인을 모르는 채 대기 시간을 늘리는 것은
          증상을 덮는 것이고, 그러면 진짜 결함이었을 때 영영 안 보인다
          가설 검증도 안 했다 — 표본이 모자란다

★ **심각도 판단**: 낮게 본다. 재접속 대기가 한 번 시간 초과되면
  Coordinator 는 다음 accept 로 넘어갈 뿐이고, 데이터 손실이나 중복
  실행으로 이어지는 경로가 아니다. 다만 **CI 에 넣으면 0.4% 로 붉게
  뜬다** — 그때는 원인을 알아야 한다.

=== 이 기록이 말하지 않는 것 ===

★ **원인을 말하지 않는다.** 실패가 교착인지, 포트 고갈인지, 타이밍
  경합인지, 아니면 이 기계의 다른 부하 때문인지 **아직 모른다.**
  추측으로 채우지 않는다(`CLAUDE.md` §1).

★ **한 기계에서만 쟀다.** 1% 가 이 기계 고유인지 일반적인지 모른다.

★ 소크 도중 감독자가 같은 디렉터리에서 수동 실행을 한 번 겹쳐 돌렸다
  (포트·파일 경합 가능). 그 시점이 어느 회차인지 특정하지 못하므로,
  **1차 결과의 실패 2건 중 하나가 그 영향일 가능성을 배제하지 못한다.**
  2차는 겹치지 않게 돌린다.
