허가증 만료를 "추측" 이 아니라 "장치" 로 만들 수 있는가 — 실측
측정일 2026-09-09 · 기계 x600 의 WSL2 (Ubuntu, systemd 259, root)
방법   E:\gputeer-work\deadline\dl2.cmd · dl3.cmd (x600 의 C: 미사용)

════════════════════════════════════════════════════════════════════
§1  왜 쟀나
════════════════════════════════════════════════════════════════════
독립 검수(2026-09-09)가 만료 기반 예약 회수를 기각했다. 세 이유 중
가장 근본적인 것이 이것이다:

  `reservation_release.rs:85` — "fence 일치는 **프로세스 종료의 증명이
  아니다** — 둘을 섞어 말하면 안 된다"

즉 허가증이 만료돼도 그 노드에서 돌던 자식 프로세스는 계속 돈다.
`exec.rs:485` 의 `child.wait()` 에 시한이 없고, 아무도 그것을 멈추지 않는다.

쿠버네티스도 같은 자리에서 막혀 있다 — 작업이 끝나도 기록이 삭제될
때까지 자원을 계속 차지한 것으로 센다(kubernetes#96515, 2020년 개설,
아직 열려 있다). 쿠버네티스는 워크로드의 런타임 계약을 소유하지 않아서
"멈췄다" 를 단정할 수 없다.

★ **우리는 소유한다.** 자식을 우리가 띄우고, 이미 죽일 수 있는 그릇
  (Windows Job Object · Linux cgroup)에 넣는다. 그러면 만료를 **추측이
  아니라 우리가 만든 장치**로 바꿀 수 있는가? 그것을 쟀다.

════════════════════════════════════════════════════════════════════
§2  1차 시도가 두 번 멈췄다 — 내 스크립트 결함
════════════════════════════════════════════════════════════════════
손자 프로세스를 무한 루프로 만들었다. 그래서 **시한 없는 대조군의 범위가
영영 끝나지 않았다.** 그것이 파일을 붙들어 2차 업로드도 실패했고 옛
스크립트가 다시 돌았다. 손자에 상한을 주고, 파일 이름을 바꿔 해결했다.

════════════════════════════════════════════════════════════════════
§3  결과 (1) — 운영체제가 강제하는가
════════════════════════════════════════════════════════════════════
`systemd-run --scope -p RuntimeMaxSec=N` 으로 시한을 운영체제에 건다.

  A. 대조군 — 시한 없이 5초 작업
       5초에 정상 종료
       -> 실험 장치 자체가 동작한다

  B. 대조군 — 시한 30초, 작업 5초 (시한이 넉넉)
       5초에 정상 종료
       -> 시한이 그냥 다 죽이는 것이 아니다

  C. 본 실험 — 시한 5초, 작업 60초
       5초에 종료. 손자까지 정리됨

  D. ★★ 핵심 — 띄운 놈을 죽여도 시한이 발동하는가
       3초에 띄운 껍데기를 SIGKILL
       죽인 직후 작업 상태  active     <- 껍데기 죽음이 작업을 죽이지 않는다
       시한(8초) 뒤        inactive
       남은 프로세스        0
       손자                 정리됨

★ **D 가 이 측정의 전부다.** 띄운 프로세스를 강제로 죽였는데도 시한이
  그대로 발동했다. 즉 **강제하는 주체가 에이전트가 아니라 운영체제다.**
  에이전트가 죽든 얼어붙든 무관하다.

════════════════════════════════════════════════════════════════════
§4  결과 (2) — 규범이 요구한 "체크포인트 후 정지" 가 되는가
════════════════════════════════════════════════════════════════════
`state-machines.md:209` 이 요구한다:
    RUNNING | PAUSED | PARTITION_PAUSE | 허가증 만료 | **checkpoint 후 정지**

  A. 시한 4초 · 정지 여유 20초 · 체크포인트 2초
       [작업] 정지 신호 받음 — 체크포인트 쓴다
       [작업] 체크포인트 완료
       체크포인트 파일 **있다**
       -> 규범대로 된다

  B. 시한 4초 · 정지 여유 3초 · 체크포인트 15초 (일부러 넘긴다)
       체크포인트 파일 **없다**. SIGKILL 로 끝남
       -> ★ 여유는 **유한하다.** 이 대조군이 없으면 "여유가 있다" 와
          "여유가 무한하다" 를 구분할 수 없다

  C. ★ 신호를 아예 무시하는 작업 (`trap '' TERM`)
       4+5 = 약 10초에 종료. 남은 프로세스 0
       -> **협조하지 않는 작업도 죽는다.**
          이것이 CUDA 가로채기와 결정적으로 다른 점이다 — 가로채기는
          협조하는 할당 경로만 막지만, 이건 협조 여부와 무관하다

════════════════════════════════════════════════════════════════════
§5  ★★ 못 하는 것 — 이쪽을 정확히 적는다
════════════════════════════════════════════════════════════════════
  D. 비-root 로는 안 된다
       setpriv --reuid=nobody ... systemd-run --scope
       -> Failed to start transient scope unit: Access denied as the
          requested operation requires interactive authentication.

     즉 **에이전트가 root 여야 이 방법을 쓴다.**
     ★ 다만 이 저장소의 Linux K1 키 보관도 이미 root 를 요구한다
       (`credential.secret` 이 0600 root). 새로 생기는 제약이 아니라
       이미 있던 등급 조건과 같다.
     ★ 안 재 본 대안: `systemd-run --user`(사용자 매니저 + lingering),
       polkit 규칙으로 특정 동작만 허용. **둘 다 측정하지 않았다.**

  Windows 에는 등가물이 없다
     `JOB_OBJECT_LIMIT_JOB_TIME` 은 **CPU 시간**이지 벽시계가 아니다
     (Microsoft 문서 확인). Job Object 에 벽시계 시한은 없다.
       에이전트가 **죽으면**    이미 해결돼 있다
                                (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
                                 가 `runtime-windows/src/lib.rs:674` 에
                                 이미 걸려 있다 — 커널이 트리를 정리한다)
       에이전트가 **얼어붙으면** 못 막는다
     안 재 본 대안: 작업 개체 핸들만 쥔 별도 감시 프로세스, Windows
     작업 스케줄러의 실행시간 제한. **둘 다 측정하지 않았다.**

  이 측정이 다루지 않은 것
     · 시계가 뒤로 가거나 절전에서 깨어난 경우
     · 네이티브 리눅스(잰 것은 WSL2 다)
     · GPU 를 실제로 쓰는 워크로드 — VRAM 이 반환되는지는 안 봤다.
       프로세스가 죽으면 드라이버가 회수하는 것이 정상이나 **재지 않았다**
     · 여러 작업이 동시에 시한을 맞는 경우

════════════════════════════════════════════════════════════════════
§6  그래서 무엇이 바뀌나 — 과장하지 않고
════════════════════════════════════════════════════════════════════
독립 검수가 만료 기반 회수를 기각한 이유는 셋이었다. 이 측정이 건드리는
것은 그중 둘이다.

  ① 예약 행을 지우면 증거가 파괴된다
     -> **그대로 남는다.** 이 측정과 무관하다. 증거 저장소가 예약 대신
        `coordinator_reservation_releases`(영구)를 보게 바꿔야 하고,
        그 앞에 시도 기록이 "끝났다" 를 말할 수 있어야 한다

  ② `PartitionPauseEnforcement` 를 강제하는 코드가 없다
     (`reassignment.rs` — "그 전까지 이 경로를 켜면 안 된다")
     -> **이 측정이 그 강제 수단이다.** 에이전트가 자기 허가증 시한을
        운영체제에 걸어 두면, 만료된 노드가 스스로 멈추는 것을 호출부가
        실제로 강제하게 된다. 다만 **Linux + root 에 한한다**

  ③ fence 는 프로세스 종료를 못 막는다
     -> **Linux 에서는 해결된다.** 운영체제가 멈춘다. 협조하지 않는
        작업도 멈춘다(§4-C). Windows 의 얼어붙은 에이전트는 그대로 남는다

★ 즉 **되살아난 것이 아니라, 셋 중 둘이 조건부로 닫혔다.** ①이 남아
  있는 한 만료로 예약을 지우면 안 된다. `CLAUDE.md` §4 —
  한 조건 통과를 다른 조건 통과로 세지 않는다.
