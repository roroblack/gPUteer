## 제안 조각

제목:

`2026-08-20_coordinator_lease_revoke_영속화_최소_조각_v1`

기준선은 DoD-22 revoke와 DoD-24 재접속 조각이다.

### 1. 스키마

`revoked` bool보다 다음 필드를 권장한다.

```sql
revoked_at_unix_ms BLOB NULL
```

의미는 다음과 같다.

- `NULL`: revoke되지 않음
- 8바이트 timestamp: revoke됨
- revoke 해제 API는 만들지 않음

새 테이블 정의에는 이 컬럼을 포함한다.

기존 DB를 열 때는 다음 보정 절차를 둔다.

```text
CREATE TABLE IF NOT EXISTS ...
PRAGMA table_info(coordinator_leases)
revoked_at_unix_ms 컬럼이 없으면:
    ALTER TABLE coordinator_leases
    ADD COLUMN revoked_at_unix_ms BLOB
```

기존 행은 자동으로 `NULL`이 되므로 active Lease로 해석된다. migration은 `open()` 과정에서, 기존 SQLite `busy_timeout`과 같은 fail-closed 정책으로 수행한다.

`StoredLease`에는 다음을 추가한다.

```rust
pub revoked_at_unix_ms: Option<u64>
```

`SELECT_LEASE_SQL`, `RawLeaseRow`, `row_to_raw()`, INSERT 경로도 함께 확장한다.

### 2. revoke 저장 API

`CoordinatorLeaseStore`에 다음 성격의 메서드를 추가한다.

```rust
pub fn mark_revoked(
    &mut self,
    lease_id: &str,
    revoked_at_unix_ms: u64,
) -> Result<StoredLease, LeaseStoreError>
```

동작은 다음과 같다.

1. `BEGIN IMMEDIATE`
2. `lease_id` 조회
3. 없으면 `NotFound`
4. 이미 revoked면 기존 timestamp를 유지하고 성공
5. 아니면 `revoked_at_unix_ms` UPDATE
6. commit 성공 후 revoked 레코드 반환

이미 revoked인 경우에도 성공시키는 idempotent 동작이 적절하다.

### 3. `send_revoke_notice()` 순서

현재 두 호출 지점:

- ACK 직후 `revoke_after_round == 0`
- renew 회차 완료 후 `revoke_after_round == round + 1`

두 곳 모두 다음 형태로 바꾼다.

```text
send_revoke_notice(
    config,
    grant,
    lease_store,
    signing_key,
    stream
)
```

함수 내부 순서는 반드시 다음이어야 한다.

```text
1. Grant의 실제 lease_id로 mark_revoked() 실행
2. SQLite commit 성공
3. RevokeLeaseNotice 생성·서명
4. TCP 전송
```

wire 전송과 SQLite commit을 하나의 원자적 트랜잭션으로 묶을 수는 없다. 따라서 네트워크 전송 전에 DB commit을 완료하는 것이 최선의 fail-closed 순서다.

- DB commit 실패: notice를 보내지 않고 Coordinator 오류 종료
- DB commit 성공 후 전송 실패: Lease는 계속 revoked 상태
- 전송 실패 때문에 DB revoke를 되돌리지는 않음

notice의 `lease_id` override가 있는 테스트에서도 저장소에는 override 값이 아니라 Grant의 실제 `lease_id`를 기록해야 한다.

`lease_store == None`인 기존 레거시 경로는 그대로 둔다. 이 경로는 원래 재시작 영속성을 약속하지 않았으므로 revoke 영속성도 보장하지 않는다고 문서화한다.

### 4. `get_or_issue()` 거부

기존 레코드 처리 부분에 다음 검사를 추가한다.

```text
existing 조회
identity conflict 확인
existing.revoked_at_unix_ms.is_some() 이면
    LeaseStoreError::Revoked 반환
commit 후 저장 레코드 반환
```

새 오류 유형은 다음 정도면 충분하다.

```rust
LeaseStoreError::Revoked {
    revoked_at_unix_ms: u64,
}
```

그러면 [`issue_lease()`](C:\Users\playdata2\Documents\test_workspace\gPUteer\gputeer\crates\coordinator\src\lib.rs:801)의 기존 오류 전파를 통해 Coordinator는 다음처럼 종료한다.

```text
lease store 최초 발급 실패: lease가 revoke 됨 ...
```

새 Grant는 생성·서명·전송되지 않는다.

추가로 안전성을 위해 `renew_existing_within_duration()`에서도 revoked 레코드를 거부하는 것이 좋다. 그렇지 않으면 notice 전송이 끊긴 기존 Agent가 renew를 재시도할 때 Coordinator가 revoked Lease를 다시 갱신할 수 있다. 이 경우 새 서명된 정책 outcome을 추가하지 않고 기존 raw error 방식으로 연결을 종료한다.

`RenewLeaseResult`에는 현재 revoked 전용 outcome이 없으므로 proto 변경이나 새 signed denial은 이 조각에서 하지 않는다.

## Agent 변경 여부

Agent의 기존 `revoked` 로직은 그대로 둔다.

새 프로세스 쌍의 경우:

```text
새 Coordinator
  -> get_or_issue()에서 Revoked 오류
  -> Grant 미전송, 연결 종료

새 Agent
  -> Grant 읽기 실패
  -> 기존 "Grant 프레임 읽기/검증 실패"로 종료
```

Agent가 “이 Lease는 이미 revoke됐다”는 별도 메시지를 알 필요가 없다. Coordinator가 Grant 발급 자체를 거부하는 것이 이 단계의 fail-closed 정책이다.

따라서 이번 조각에는 다음이 없다.

- Agent의 `revoked` 영속화
- `fence-db` 스키마 변경
- 새 proto 메시지
- 새 `RenewOutcome`
- signed revoke-denial response
