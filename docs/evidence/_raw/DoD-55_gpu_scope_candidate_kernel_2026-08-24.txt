=== 이 조각을 선택한 배경 ===

Grant/Lease scope는 NVML UUID provenance와 확정 자원값이 없다는 이유로 반복해서
차단돼 있었다. 실물 GPU 호스트에서 RTX 4070 SUPER의 NVML UUID, PCI,
compute capability, VRAM 등을 실측한 뒤 다시 판정했다. 그 결과 실제 GPU 값 자체가
없다는 차단만 해소됐고, 관측을 authoritative truth로 승격할 서명·membership·durable
binding 차단은 그대로였다. 따라서 full ResourceScope나 Grant/Lease를 만들지 않고,
명시 입력에서 ScopeCandidate만 계산하는 순수 kernel을 떼어냈다.

=== 구현 경계 ===

- crates/scheduler/src/scope.rs:5 부근에 관측·요구·자원 입력 타입과
  ProvenanceGate를 추가했다.
- crates/scheduler/src/scope.rs:77에 ScopeCandidate를 추가했다.
- crates/scheduler/src/scope.rs:109에 typed ScopeError를 추가했다.
- crates/scheduler/src/scope.rs:130의 gpu_scope_candidate()는 입력을 읽고 검증·정렬한 뒤
  BTreeMap/BTreeSet 기반 canonical 결과만 만든다. I/O, clock, environment variable,
  randomness, crypto, DB/network, global state에 접근하지 않는다.
- crates/scheduler/src/lib.rs:23의 module/export 추가가 기존 production 파일 변경의 전부다.
- ResourceScope, Grant/Lease, 저장·서명·상태 전이 API는 만들지 않았다.

=== 결정성과 입력 순서 독립성 ===

production은 GPU ID를 먼저 canonical 검사하고, 적격 GPU를
(available_vram_bytes, gpu_id) 전체 튜플 오름차순으로 정렬해 필요한 개수만 고른다.
동일 VRAM 동점도 gpu_id로 풀린다. 선택 뒤 결과 ID는 다시 오름차순으로 정렬한다.

crates/scheduler/tests/gpu_scope_candidate.rs:68의 재귀 permutations()는 remaining의
각 index를 제거해 재귀 호출하고 빈 remaining에서 결과를 추가한다. line 117의 테스트는
동점 GPU를 포함한 4개 입력의 실제 4! = 24개 순열을 모두 만들고, 각 순열에서
ScopeCandidate 전체를 assert_eq!로 비교한다. allowlist와 writable-prefix 순서도 별도
테스트로 전체 결과 동등성을 확인한다.

=== fail-closed와 입증하지 않는 값을 만들지 않는 경계 ===

- ProvenanceGate::Verified는 caller가 공급한 입력일 뿐이다. kernel은 서명, signer,
  membership 또는 canonical observation을 스스로 검증하지 않는다.
  Unverified는 즉시 ScopeError::UnverifiedProvenance다.
- PARTITIONED는 GPU가 지원한다고 주장하는 mode 입력과 무관하게 항상
  ScopeError::PartitionedAllocationUnproven이다. NVML [N/A]를 false, unsupported,
  healthy 같은 긍정 값으로 바꾸지 않는다.
- cuda_runtime_version 요구는 타입에 보존한다. 호환 규범이 없으므로 exact match나
  driver mapping을 만들지 않고 ScopeError::CudaRuntimeCompatibilityUnresolved로 닫는다.
- AvailableVramObservation::DerivedFromTotalAndReserved는 선택 계산에 쓰지 않고
  ScopeError::NonAuthoritativeAvailableVram으로 거부한다.
- model, driver, compute capability는 해당 constraint가 있을 때만 요구한다.
  irrelevant fact의 부재 때문에 후보를 과잉 배제하지 않는다.

근거는 CLAUDE.md:96의 "값을 모르면 비워 둔다. 추정으로 채우면 그 오류가 조용히
스케줄링 결정까지 간다" 원칙과 proto/common.proto의 GpuRequest VRAM/count 및
ResourceScope 자원 필드다.

=== 자체 재검토에서 수정한 결함 ===

초안의 JobGpuRequirements가 proto의 cuda_runtime_version 요구를 표현하지 않아 caller
adapter가 해당 요구를 조용히 버릴 수 있음을 발견했다. 필드를 보존하고, 임의 호환 규칙
대신 CudaRuntimeCompatibilityUnresolved typed error와 negative test를 추가했다.

또한 model/driver/compute를 모든 GPU에 무조건 요구하던 과잉 배제를 피하도록 각 constraint가
실제로 있을 때만 해당 fact를 요구하게 했다. health=false 또는 앞선 compatibility gate에서
제외된 GPU의 뒤쪽 irrelevant fact도 요구하지 않는다.

=== 범위 밖과 잔여 위험 ===

- ProvenanceGate::Verified는 caller 입력일 뿐 kernel이 서명·membership을 검증하지 않는다.
- CUDA runtime compatibility는 아직 판정할 수 없다.
- shared mode 입력은 실제 MPS/동일-owner enforcement를 입증하지 않는다.
- wire ResourceScope, Grant/Lease, 저장·서명·전이는 구현하지 않았다.
- MIG partitioned allocation은 입증할 수 없다.
- 실물 NVML 실측은 하드웨어 값 부재만 해소했다. authoritative provenance 차단은 그대로다.
