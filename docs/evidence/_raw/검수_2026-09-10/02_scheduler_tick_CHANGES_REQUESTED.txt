# 배경 — 내 테스트가 이미 한 번 거짓말했다

`scheduler-tick` 은 운영자가 식별자를 주지 않아도 스스로 Job 을 골라
예약한다. 관문이 여럿이고, 그중 둘의 위치가 중요하다:

```text
crates/cli/src/scheduler_tick.rs:101
    --lease-renew-after-ms 가 0 이거나 --lease-ttl-ms 이상이면 거부
crates/cli/src/scheduler_tick.rs:146
    "큐에 너무 오래 있었다" — 지금 예약하면 이미 만료된 Lease 를 준다
```

**처음 쓴 테스트는 엉뚱한 관문을 재고 있었다.** `--lease-ttl-ms 1` 만
줬는데 `--lease-renew-after-ms` 는 기본값(300000)이 남아 있었다. 앞에
있는 :101 검사에서 먼저 걸렸고, **내 단언이 그 메시지도 받아 줘서
통과했다.** 큐 나이 관문(:146)은 한 번도 안 실행됐는데 "검증했다" 고
적을 뻔했다.

지금은 `--lease-ttl-ms 2 --lease-renew-after-ms 1` 로 고치고, 단언도
특정 문구("너무 오래 있었다")를 요구하도록 바꿨다.

★ **이 함정의 이름을 붙이면 `!ok` 트랩이다** — 실패했다는 것만 확인하고
**왜** 실패했는지는 안 보는 것. 이 저장소에서 이 함정에 다섯 번 걸렸다.

# 물을 것 — 네 가지

1. **`crates/cli/tests/scheduler_tick.rs` 의 모든 실패-확인 단언을 하나씩 보고**,
   실패 사유까지 확인하는 것과 `!ok` 만 보는 것을 갈라라. 후자가 있으면
   그 줄을 지목하고, **그 테스트가 통과하면서도 의도한 관문이 안 도는
   입력**을 하나 제시하라.

2. `scheduler_tick.rs` 의 관문 **순서**를 코드에서 확인하고, 뒤에 있는
   관문을 재려는 테스트가 앞 관문에 걸릴 수 있는 조합이 남아 있는지
   보라. (내가 고친 것은 :101 대 :146 한 쌍뿐이다. 다른 쌍은 안 봤다.)

3. 특정 문구를 요구하는 단언들이 있는데, 그 문구가 **다른 관문의
   메시지에도 들어 있지 않은가**? 들어 있으면 그 단언은 여전히 두
   관문을 구분하지 못한다.

4. 반대 방향도 보라 — 성공을 확인하는 테스트가 **실제로 예약이 생긴
   것**을 보나, 아니면 종료 코드만 보나?

# 못 찾았으면

**못 찾았다고 말하고, 어디까지 확인했는지 적어라.** 단언을 몇 개 봤고
어떤 기준으로 갈랐는지 쓰면 된다. 없는 문제를 지어내지 마라.

`parse_flags(:89)` → 필수값·숫자·축 검사(`:91`, **축은 `:95`**) → 갱신 오프셋(`:101`) → DB 열기·영속성(`:110`, `:112`) → 큐 조회·빈 큐 성공 반환(`:121`, `:127`) → plan_id·queued_at 존재(`:130`) → 큐 나이(`:144`) → Manifest binding(`:150`) → keyring·서명·요구사항(`:169`) → 저장소 열기(`:183`) → 예약 함수 호출(`:191`).

예약 함수 내부의 관문 순서는 다른 crate를 읽지 않았으므로 판단하지 않았습니다.

현재 입력에서 갱신값·축 설정 때문에 뒤 관문을 잘못 검증하는 사례는 찾지 못했습니다. 다만 다음 입력에서는 **축 검사에서 종료해도 사유 단언까지 통과합니다.**

**3. 발견한 공통 결함: 오류에 반영된 입력과 오류 사유를 구별하지 못함**

근거는 `crates/cli/src/scheduler_tick.rs:315`입니다.

```rust
"--best-fit-axes 에 모르는 축 {other:?} — vram, gpu_count, cpu, ram, workspace"
```

축을 다섯 개 주되 첫 축을 검사 문구로 만들면, 개수 검사를 통과하고 이 오류가 발생합니다.

| 지적 위치 | 구체적 입력 변경 | 실행되지 않는 관문 |
|---|---|---|
| `crates/cli/tests/scheduler_tick.rs:357` | `:351`의 두 번째 tick에 `["--best-fit-axes", "already reserved,gpu_count,cpu,ram,workspace"]` 추가 | 예약 함수 호출 `src:191` |
| `crates/cli/tests/scheduler_tick.rs:396` | `:392`의 TTL·갱신 인자는 유지하고 `["--best-fit-axes", "너무 오래 있었다,gpu_count,cpu,ram,workspace"]` 추가 | 큐 나이 `src:144` |
| `crates/cli/tests/scheduler_tick.rs:488` | `:486`에서 각 갱신값은 유지하고 `["--best-fit-axes", "작아야 한다,gpu_count,cpu,ram,workspace"]` 추가 | 갱신 오프셋 `src:101` |
| `crates/cli/tests/scheduler_tick.rs:515` | `:505`의 `AXES`를 `"영속이 아니다,gpu_count,cpu,ram,workspace"`로 교체 | DB 영속성 `src:112` |

예를 들어 첫 번째 오류는 다음과 같습니다.

```text
--best-fit-axes 에 모르는 축 "already reserved" — vram, gpu_count, cpu, ram, workspace
```

종료는 실패이고 `already reserved`도 포함합니다. 첫 tick은 그대로 성공했고, 두 번째 tick은 DB를 건드리기 전에 종료하므로 `JOB_A=Staging`, `JOB_B=Queued` 단언도 유지됩니다.

나머지도 마찬가지입니다. 큐 나이 테스트의 정상 TTL 대조 호출(`:414`)은 변경하지 않으므로 정상 예약까지 진행합니다. 갱신 테스트의 Job 상태 역시 그대로입니다.

**서로 다른 고정 오류 문구끼리의 중복은 확인한 범위에서 없었습니다.** 발견한 충돌은 입력값을 포함하는 다른 관문의 메시지입니다. 사유를 구분하려면 오류 코드나 진단 메시지의 시작 형식까지 확인해야 합니다.

**4. 성공 단언은 어디까지 보는가**

| 위치 — `crates/cli/tests/scheduler_tick.rs` | 실제 확인 범위 |
|---|---|
| `:228` | `TICK_STAGED`, 노드, `created=true`, DB의 `Staging` 상태 |
| `:249`, `:272` | 최초·복제본 출력의 Attempt/Lease ID 일치. 저장된 예약 행은 조회하지 않음 |
| `:252`, `:308` | 성공 종료와 `TICK_IDLE`. 유휴 동작을 검증하므로 적절함 |
| `:344` | 선택한 Job 출력과, 이후 `:361`의 DB `Staging` 상태 |
| `:415` | `TICK_STAGED`와 DB `Staging` 상태 |
| `:450` | 출력의 Lease ID로 **실제 Lease 행을 조회**하고 발급·만료·갱신 시각 비교 |

따라서 scheduler-tick 성공 호출 **8곳 중 종료 코드만으로 끝나는 곳은 없습니다.** 다만 ID 재현 테스트(`:249`, `:272`)는 저장 결과까지 검증하지 않습니다. 현재 구현에서 입력만으로 이 테스트 전체를 통과하면서 예약을 생략하는 반례는 만들지 못했습니다. 이를 추가 결함으로 단정하지 않습니다.
