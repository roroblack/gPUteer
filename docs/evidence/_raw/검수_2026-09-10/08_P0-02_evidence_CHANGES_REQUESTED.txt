# 물을 것 — 네 가지

1. **"되는 것" 목록이 실제로 재현된 것인가.** 특히 **가둠**(컨테이너
   안에서 호스트 파일을 못 읽는다)이 핵심이다. 이 테스트에는 이력이
   있다 — **첫 판은 컨테이너 밖에서도 통과하는 공허한 테스트였다**
   (`cmd /c exit 42` 의 종료 코드만 봤다). 지금 판이 그 함정을 정말
   벗어났는지, **대조**(밖에서는 읽힌다)가 실제로 있는지 확인하라.

2. **소거한 가설 넷에 각각 대조가 있나.** 문서는 네 가설(상위 경로 권한 ·
   컨테이너 TEMP · capability 주입 · 다른 Python 배포판)을 소거했다고
   적었다. 각각이 **"해 봤는데 안 됐다"** 인지 **"바꿨는데도 같은
   실패였다"** 인지 원문에서 확인하라. 전자는 소거가 아니다.

3. **결론이 측정을 넘어서지 않는가.** 문서 안에
   **package identity 가설**이 나온다. 그것이 어디에서는 "추측이며 확인
   안 했다" 라고 적혀 있는데, **다른 자리에서 결론처럼 쓰이고 있지
   않은가**? 한 문서 안에서 같은 것을 두 가지 무게로 말하면 읽는 사람은
   무거운 쪽으로 기억한다.

4. **`status: INCONCLUSIVE` 가 맞는 판정인가.** 근거는 "S2 를
   EXPERIMENTAL 로 유지" 쪽으로 기운다고 적혀 있다. 그런데도 확정하지
   않은 이유가 **정당한가**, 아니면 판정을 미루는 핑계인가? 반대로,
   지금 자료로 `FAIL-SCOPE` 를 쓸 수 있다고 볼 근거가 있나?

 210: # P0-02 — Windows AppContainer + CUDA
 211: 
 212: ## 한 줄
 213: 
 214: AppContainer 는 만들어지고 가두기까지 하는데, **그 안에서 torch 를
 215: import 할 수 없다** — `ole32.dll` 이 초기화되지 않기 때문이다.
 216: 
 217: ## 왜 이걸 쟀나
 218: 
 219: 2026-09-05 사용자가 방화벽을 실측해 `netsh advfirewall` 의 **경로 단위**
 220: 아웃바운드 차단이 동작함을 확인했다. 그러나 그것으로는 `NetworkPolicy` 를
 221: 강제할 수 없다 — 남의 PC 에서 `python.exe` 를 통째로 막으면 소유자의
 222: 다른 작업까지 끊긴다(`CLAUDE.md` §0.1).
 223: 
 224: AppContainer 는 프로세스마다 **고유 SID** 를 주므로 그 SID 에 규칙을 걸면
 225: 그 Job 하나만 막힌다. 그래서 방화벽 강제의 선행 조건이고, 그것이 이
 226: 스파이크를 지금 한 이유다.
 227: 
 228: ## 어떻게 좁혔나
 229: 
 230: `import _ctypes` 는 여러 DLL 을 한 번에 시도해 **실패 지점을 감춘다.**
 231: 그래서 `LoadLibraryW` 하나만 하고 Win32 오류 코드를 찍는 `dll_probe` 를
 232: 만들어 컨테이너 안에서 DLL 을 하나씩 열었다. 그렇게 하지 않았으면
 233: "`_ctypes` 가 안 된다" 에서 멈췄을 것이다.
 234: 
 235: ## 이 실험이 증명하지 않는 것
 236: 
 237: **"AppContainer 에서 CUDA 가 안 된다" 를 증명하지 않았다.** CUDA 를
 238: 시도조차 못 했다.
 239: 
 240: **"AppContainer 에서 네이티브 코드가 안 돈다" 도 아니다.** C 확장
 241: (`zlib`·`_socket`)은 로드된다. COM 본체(`combase.dll`)도 로드된다.
 242: 막힌 것은 `ole32` 하나다.

   초안 172–175행은 **“확인하지 않았으므로 추측으로만 적는다”**, 196행도 **“package identity 부재 때문일 가능성”**이라고 명시합니다. [5차 88–93행](C:/Users/playdata2/Documents/test_workspace/gPUteer/gputeer/docs/evidence/_raw/P0-02_appcontainer_cuda_5차_원인지목.txt:88) 역시 **“추측이며 확인 안 했다”**입니다. 질문하신 직접적인 ‘가설의 결론 둔갑’은 확인하지 못했습니다.

   그러나 다른 원인 서술은 측정보다 강합니다. 5차 4행은 도구를 다음처럼 설명합니다.

   > “`LoadLibraryW` 하나만 하고 Win32 오류 코드를 찍는다”

   실제 결과는 14–15행의 `ole32.dll`, `_ctypes.pyd`에 대한 **`ok=false error=1114`**입니다. 그런데 초안 32행은 **“`ole32.dll` 하나가 … DllMain에 실패한다”**, 242행은 **“막힌 것은 `ole32` 하나다”**라고 씁니다.

   기록은 `ole32` 로드 시 초기화 실패를 관측했다는 근거입니다. **오류 코드만으로 실패한 초기화 함수의 위치, `_ctypes` 실패와의 인과관계, 다른 장애의 부재까지 확정한 것은 아닙니다.** “시험한 DLL 중 `ole32` 로드에서도 1114가 관측됐으며, `_ctypes` 실패와의 관계는 추가 확인이 필요하다”가 측정에 맞습니다.

   같은 이유로 5차 71행의 **“combase.dll ok=true”**를 78–79행의 **“본체는 되는데 레거시 계층만 안 된다”**로 확장하면 안 됩니다. 로드 성공 기록은 COM 기능 실행의 성공 기록이 아닙니다.

4. **전체 `INCONCLUSIVE`는 정당하지만, 좁은 구성의 실패 판정까지 원인 규명 뒤로 미루는 논리는 부당합니다. 반복 횟수 표현도 바로잡아야 합니다.**
