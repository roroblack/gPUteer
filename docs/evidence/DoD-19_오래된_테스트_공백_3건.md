# DoD-19 · 오래된 테스트 공백 3건 (코덱스 감사 p116)

## 무엇을 입증하려 했는가

`DoD-18`(max_total_duration_seconds 갱신 차단) 완료 후, 코덱스에게
이 저장소 전체를 다시 훑어 이 세션이 오늘 건드리지 않은 오래된
결함·커버리지 공백이 남아있는지 감사(`p116`)를 요청했다. `DoD-17`이
찾은 것과 같은 종류(배선은 있는데 왕복 테스트가 없는 메시지 타입,
손으로 쓴 배열이라 enum 확장을 못 잡는 테스트 등)를 우선 찾도록
지시했다.

## 코덱스가 찾은 3건

1. **`canonical_vectors.rs::domain_tags_are_32_bytes_and_unique`** —
   손으로 쓴 domain 배열이 24종으로 고정돼 있었는데, `DoD-13`(Lease
   갱신 최소 조각)이 `Domain::LeaseRenewResult` 를 추가해 실제
   enum 은 이미 25종이었다. `t1_signing_targets.rs`·
   `t1b_grant_and_control.rs` 는 이미 올바르게 25종을 나열하고
   있었다 — 이 파일 하나만 뒤처져 있었다. **이 세션이 오늘 이미
   두 번(`DoD-02`·`DoD-06`) 발견한 것과 정확히 같은 종류의 결함
   패턴**이다.
2. **`CoordinatorLeaseStore::check_identity_conflict()` 테스트
   커버리지** — 프로덕션 코드는 4개 필드(`job_id`·`attempt_id`·
   `holder_node_id`·`issuing_coordinator_id`)를 순서대로 검사하지만,
   기존 단위 테스트는 `job_id` 충돌 하나만 확인했다.
3. **`RenewLeaseResult` framed ingress 정상 테스트** — `variant`
   만 확인하고 payload 필드값(`outcome`·`detail`·`schema_version`·
   `coordinator_id`·`issued_at_unix_ms`·`request_nonce`)은 검증하지
   않았다. `DoD-17` 이 `RevokeLeaseNotice` 에서 고친 것과 같은
   얕음이다.

## 수정

세 파일 모두 순수 테스트 추가/보강만 했다(프로덕션 코드 미변경):

1. `Domain::LeaseRenewResult` 를 배열에 추가, 기대 개수 24 → 25.
2. `conflicting_attempt_id_is_rejected_without_overwrite`·
   `conflicting_holder_node_id_is_rejected_without_overwrite`·
   `conflicting_issuing_coordinator_id_is_rejected_without_overwrite`
   3개 단위 테스트 신설 — 각각 `sample()` 원본에서 해당 필드
   하나만 바꿔 정확히 그 필드명으로 거부되는지 확인.
3. `Verified::get()` 으로 6개 payload 필드를 원본 `renew_result()`
   값과 대조하는 assert 추가.

## 코덱스 검수 — 1라운드 만에 ACCEPTED

세 변경 각각을 실제 프로덕션 로직(실제 `Domain` enum 25종, 실제
`check_identity_conflict()` 검사 순서, 실제 `renew_result()` 가
채우는 값)과 직접 대조해 정확함을 확인했다. 지적 사항 없음.

### 뮤테이션으로 비공허성을 확인했다 (2건)

1. `check_identity_conflict()` 의 `attempt_id`/`holder_node_id`/
   `issuing_coordinator_id` 검사 3개를 전부 제거 → 신규 테스트 3건이
   정확히 예상대로 실패(각각 `IdentityConflict` 를 기대했으나 `Ok`
   반환됨). 원복 후 재통과.
2. `RenewLeaseResult` 테스트의 `detail` 기대값을 `"WRONG_ON_PURPOSE"`
   로 변경 → 정확히 그 이유로 실패(`assertion left==right failed`).
   원복 후 재통과.

1번(domain 배열 교정)은 손으로 쓴 정적 목록 수정이라 무력화할
프로덕션 로직이 없어 뮤테이션 테스트 대상에서 제외했다 — `DoD-02`·
`DoD-06` 승격 때도 같은 이유로 동일하게 처리했었다.

## 이 실험이 증명하지 "않는" 것

- 1번은 현재 시점의 누락만 고친다 — 미래에 26번째 `Domain` 이
  추가돼도 이 배열은 자동으로 동기화되지 않는다(구조적 한계,
  `t1_signing_targets.rs` 는 이미 이 한계를 알고 명시적 목록 유지
  방식을 쓴다).
- 세 변경 모두 순수 테스트 추가다 — 프로덕션 코드는 범위 밖이다.
- Windows 단일 플랫폼.

## 결정

1. 코덱스 감사(`p116`)가 찾은 3건을 전부 메웠고, 1라운드 검수에서
   추가 지적 없이 `ACCEPTED`.
2. 이 세션에서 감사→발견→수정→검수 사이클로 찾은 오래된 결함/공백이
   이제 총 6건(`DoD-02`·`DoD-06`·`DoD-05`·`DoD-17`·이번 3건)이 됐다.
3. 코덱스가 `TODO_VISION.md` 를 포함해 재검토했지만 "이 개발
   기계만으로 완결 가능한 신규 항목을 찾지 못했다"고 명시했다 —
   이 시점에서 자율 세션이 계속할 수 있는 저위험 작업이 사실상
   소진됐다고 판단한다.
