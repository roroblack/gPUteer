## 문제

컨테이너 런타임(docker · podman)이 **제대로 답하지 않을 때** — `start` 실패 · 무응답, `inspect` 실패, `logs` 실패, `kill` · `rm` 실패 — Agent 는 작업이
돌았는지 · 멈췄는지 · 출력이 온전한지 · 컨테이너가 남았는지를 **모른다.** 지금 코드는 그 모름을 한 가지 오류(문자열 접두사)로 뭉개고, 그 위에서 자동으로
지우거나 성공을 확정해 왔다. 회차마다 한 경로를 고치면 다른 경로가 열렸다(480~495).

이 경로의 뼈대(`container::run` 의 start · 로그 받기 · 남은 컨테이너 정리)는 이 브랜치 **전부터 main 에 있던** 것이다(`7e54a55` 컨테이너 실행 backend ·
재검수 87~91).

### Out — 떼어 내는 설계 과제 (이 문서의 본론 · 별도 작업)

**P0 — 먼저**

- **두 벌 실행 방지(Lease/Attempt 계약).** 종료를 모르는 컨테이너가 이 노드에 남아 있는 동안 Lease 가 끝나면 Coordinator 가 같은 작업을 다른 노드에 준다.
  노드를 막는 것만으로는 못 막는다. "실행 여부 불명" 을 Agent 가 Coordinator 에 알리고 Coordinator 가 재배치하지 않게 하는 계약이 필요하다 —
  지금 상태표는 `STARTING → FAILED (START_FAILED) — workspace 정리` 만 있어 OCI `poststart` 실패(작업이 돈 뒤 start 가 실패로 답함)를 표현하지 못한다
  (`docs/protocol/state-machines.md` §3 · 250행). ★ 이 브랜치는 두 벌 실행 방지를 **주장하지 않는다.**
- **회차 밖의 상시 소유자 화면.** 서비스(agent-loop)는 회차마다 Agent 를 새로 띄워 그 회차가 끝나면 패널도 사라진다(결함 480). 남은 컨테이너 ·
  사건 표식을 회차와 무관하게 보여 주고 멈출 수 있어야 한다. 남은 컨테이너 정리가 패널 기동보다 먼저라 정리 실패로 패널이 안 뜨는 것도 여기서 푼다.
- **런타임을 거치지 않는 정지.** 런타임이 응답하지 않는 동안 어떤 손잡이도 같은 런타임 CLI 를 거친다(§0.1 의 공백). 컨테이너 프로세스를 호스트에서
  직접 끝내는 길(cgroup · PID) — 플랫폼별 등급으로 적는다(Windows Docker Desktop 은 WSL VM 안이라 다르다).
- **사건 저널과 운영자 명령.** 사건 목록 · 로그 재수집 · 정지 확인 · 삭제 · 민감 데이터 긴급 폐기 · 표식 해제 — 감사 기록과 멱등성.

**P1 — 데이터 보존 품질**

- 실행 중 로그를 계속 받아(follow) 고유 임시 파일에 쓰고, 정지 확인 · flush · fsync 뒤 완결 표식을 남긴다(지금은 끝난 뒤 한 번 받는다 — 결함 492).
- 건진 로그는 새 이름(create-new · 세대 번호)과 메타데이터(시도 · 시각 · 런타임 · 수집 결과)로 남긴다(덮어쓰기 금지 — 결함 493).
- 보존 용량 상한과 고수위 차단 — 자동 삭제 대신 새 작업을 일찍 막는다. 민감도별 암호화 · 폐기 규칙.

**P2 — 어댑터와 검증**

- docker · podman 의 start · kill · logs · rm 결과 의미를 어댑터에서 정규화(nonzero · 시한 초과 · 늦은 응답).
- 상태 전이 시험: nonzero · 시한 초과 · kill 실패 · 부분 로그 · 재기동 사이 crash 주입. 시한을 시험에서 줄일 수 있게(지금 120초라 무응답 경로를 못 잰다 — ★ 2026-09-28 start 만 `start_timeout` 칸으로 줄일 수 있게 했다. inspect · logs · rm 은 120초 · kill 확인은 15초 그대로).
- Agent 와 node-doctor 가 같은 판정 구조를 쓰는 회귀 시험 · 실제 docker · podman 실측(CI 리눅스).
