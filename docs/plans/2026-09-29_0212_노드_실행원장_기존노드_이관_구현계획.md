## 이 조각이 하는 것 — 한 줄

노드에 **실행 원장**(시도마다 시작 · 끝을 적는 SQLite 파일)을 두고, 이미 일을 돌린 노드를 그 원장으로 옮기는 **이관 명령**을 만든다. 중앙(Coordinator)과 주고받는
새 메시지는 **이 조각에 없다** — 원장이 로컬에서 "끝을 확인하지 못한 시도" 를 막는 데까지만 한다.

## 왜 이 순서인가

```text
계약 §5     원장은 "started-attempts 에 기록이 있는데 원장이 없으면 새 작업 거부" 를 요구한다 — 한 번이라도 실행한 노드는 기록이 있다(lib.rs:450 write_once ·
            지우는 경로 없음). 이관 없이 원장을 켜면 **모든 기존 노드가 멈춘다**
계약 호환성  "기존 노드 이관은 이 계약보다 먼저 들어와야 한다"
그래서      원장 + 이관을 한 조각으로, 기본은 **꺼짐**(`--run-ledger` 스위치). 켜기 전 절차: 이관 → 켜기
```

## 범위

```text
한다      (1) 원장 파일 `<루트>.run-ledger.sqlite3` — 열기 · 형식 · 세대 · 전수 대조 · fail-closed
          (2) 실행 순서 1~4(계약 §5): 원장 행 ACTIVE → 시작 기록(sentinel) → 기동 → 종료 보고 보관 뒤 CLOSED
          (3) 기동 때 남은 ACTIVE 행 풀기 — 컨테이너 행 네 갈래 중 알림 꺼짐 갈래(LOCAL_BLOCKED + 사건 표식) · 호스트 행은 CLOSED(지금과 같다)
          (4) 기동 관문 — LOCAL_BLOCKED · 풀지 못한 ACTIVE 가 있으면 새 작업 거부
          (5) `container-incidents --clear` 가 루트 잠금을 잡고, LOCAL_BLOCKED 행을 CLOSED 로 바꾼 **뒤** 표식을 지우고 폴더를 sync(계약 §5 · 단계 3 v7 사실 12)
          (6) 이관 명령 `gputeer run-ledger adopt-legacy -- <agent 인자>`
안 한다    AttemptRunNotice · ACK(FrameType 19 · 20) · OPEN · STOP_PENDING · ACKED 상태 · `--send-run-notice` · Coordinator 쪽 전부 — 다음 조각
          D5 호스트 경로 차단(단계 1 목록 15) — 별도 조각. 호스트 행은 정상 수명주기만
          운영 활성화 — 배포 파일(유닛 · agent.ps1)은 이 조각에서 **켜지 않는다**
```

## 원장 형식

```text
파일       <실경로 루트>.run-ledger.sqlite3 · 루트 잠금을 잡은 뒤에만 연다 · PRAGMA journal_mode=WAL 아님(DELETE) · synchronous=FULL · 열 때 integrity_check
meta       format_version(1) · generation(128비트 난수 hex) · created_at_unix_ms
           ★ 세대 짝: `<루트>.started-attempts/.run-ledger-generation` 파일(write_once)에 같은 generation 을 둔다. 원장을 새로 만들면(지웠다 · 잃었다) 짝이 안 맞아 거부
시작 기록 식별  (r1 ⑤) started-attempts 폴더의 파일 중 **시작 기록**은 이름이 64자 소문자 hex 이고, 내용이 정확히 `attempt_id=<id>\n` 이며,
           blake3(<id>) 의 hex 가 이름과 같은 것이다(지금 쓰는 모양 그대로 — lib.rs:432 · :462). `.` 으로 시작하는 이름(세대 짝)은 기록이 아니다.
           ★ 알려진 부산물(r1b ③) — write_once 는 `<대상>.write_once.lock` 과 `<대상>.tmp` 를 만들고, 최종 파일 · 폴더 sync **뒤에** 잠금 파일을 지운다
             (checkpoint/src/atomic.rs:207~300). 그래서 기록이 확정된 뒤 전원이 끊겨도 잠금 파일이 남을 수 있다. 규칙: 루트 잠금 아래에서, 이름이
             `<기록 이름 또는 .run-ledger-generation>.write_once.lock` · `….tmp` 인 파일만 부산물로 인정해 지우고 폴더를 sync 한다. `.tmp` 는 그 대상의
             최종 파일이 **없을 때만** 지운다(있으면 확정된 것 — tmp 는 쓰레기) — 어느 경우든 지운다. 대상 이름이 규칙에 맞지 않는 부산물은 모르는 파일이다
           그 밖의 파일 · 내용이 깨진 기록 · 이름과 해시가 다른 기록 · 폴더 안 하위 폴더 · 링크 → **원장 열기와 이관 모두 거부**(모르면 받지 않는다)
만드는 순서 (r1 ② · r1c ①) 원장이 처음 생기는 두 경로(새 노드 · 이관)가 같은 순서를 쓴다:
           G 를 고르는 규칙(r1d ①) — **이미 적힌 값이 있으면 새로 뽑지 않는다**: 짝이 있으면 짝의 값 · 짝이 없고 adopting 표식이 있으면 표식의 값 ·
             둘 다 없을 때만 새 난수. 적힌 값은 모두 형식(32자 소문자 hex)을 검사하고, 짝과 표식이 둘 다 있는데 값이 다르면 거부(수동 복구)
           (0) **이관이면** `<루트>.run-ledger.adopting` 표식을 write_once 로 쓴다(내용 = 위 규칙의 G · 이미 같은 값이면 그대로)
           (1) 세대 짝이 없으면 G 를 write_once 로 쓴다(fsync · 폴더 sync)
           (2) 원장을 `<루트>.run-ledger.sqlite3.tmp-<G>` 에 끝까지 쓰고(meta generation=G · 행) fsync
           (3) 덮지 않는 게시 — **하드 링크**로 `<루트>.run-ledger.sqlite3` 를 만든다(대상이 이미 있으면 두 플랫폼 모두 실패 · `std::fs::rename` 은 덮으므로
               쓰지 않는다 — r1j ③) → 임시 파일 삭제 → 폴더 sync. 링크 뒤 · 삭제 전에 끊기면 "짝 + 원장 + 옛 임시 파일" 이다 — 다음 실행이 옛 임시 파일을
               지우고 원장을 그대로 쓴다(내용은 같은 파일이다)
           (4) 이관이면 adopting 표식을 지우고 폴더 sync
           ★ **"짝은 있고 원장은 없다" 는 두 가지다** — (가) 원장을 처음 만들다 끊겼다 (나) **쓰던 원장을 잃었다**. (나)를 (가)로 읽고 다시 만들면 ACTIVE 였을
             시도를 legacy CLOSED 로 덮어 계약 §5 의 "원장 유실 → 새 작업 거부" 를 우회한다(r1c ①). 그래서 가른다:
               짝만 · 시작 기록 **없음**                      → 새 노드가 만들다 끊김 — 그 G 로 이어서(잃을 기록이 없다)
               짝만 · 시작 기록 있음 · adopting 표식(같은 G)  → 이관이 끊김 — **이관 명령만** 그 G 로 이어서(Agent 는 "이관이 끝나지 않았다" 로 거부)
               짝만 · 시작 기록 있음 · adopting 표식 없음      → **원장 유실** — Agent · 이관 모두 거부 · 수동 복구(자동으로 다시 만들지 않는다)
           그 밖의 끊긴 자리:  아무것도 없음 → 처음부터 · 짝 + 임시 원장 → 옛 임시 파일을 지우고 위 판단대로 · 짝 + 원장(+ adopting 남음) → 표식만 지우고 완료 ·
                                 짝 + 원장 → 완료(이관은 "이미 있음" 으로 거부) · **원장만 있고 짝 없음** → 순서상 생기지 않는다 — 누가 지웠다 → 거부(수동 복구)
attempts   attempt_id(PK) · row_format_version(1) · origin('agent'|'legacy_adopt'|'legacy_adopt_attested') · job_id · node_id · fence_epoch ·
           executor('container'|'host'|'legacy') · runtime_program · runtime_kind · container_name · container_id(확인한 뒤) · cgroup_path ·
           state('ACTIVE'|'CLOSED'|'LOCAL_BLOCKED') · reason · stopped · logs_complete · container_left ·
           **container_removed**(r1f ② — 컨테이너를 지우고 새 조회로 "없음" 을 확인했으면 1 · 아직이면 0 · 호스트 · legacy 행은 NULL — 열 때 이 세 값 말고는 거부) ·
           created_at_unix_ms · updated_at_unix_ms
           ★ 이 조각에 **없는** 칸(다음 조각 — 알림 · ACK 가 들어올 때 migration 으로 더한다 · r1c ③): 알림 바이트(RUN_UNKNOWN · STOP_CONFIRMED) ·
             다음 sequence · 알림 전송 표시 · OPEN · STOP_PENDING · ACKED 상태. 계약 §5 의 판정 칸(origin · reason · stopped · logs_complete ·
             container_left · 형식 버전)은 **이 조각에 다 있다**
           legacy 행: attempt_id 만 믿을 수 있다(시작 기록에는 `attempt_id=` 한 줄뿐 — lib.rs:462). 나머지 칸은 NULL · executor='legacy' · state='CLOSED'
전이       ACTIVE → CLOSED · ACTIVE → LOCAL_BLOCKED · LOCAL_BLOCKED → CLOSED(해제 명령만). 그 밖은 코드가 거부(시험)
```

## 열기 · fail-closed (계약 §5 "원장 자체")

`--run-ledger true` 일 때, 루트 잠금 · 실경로 정착(settle_checkpoint_root_with · lib.rs:3402) **직후**, 첫 Grant 전에.
★ 켜는 조건 둘(첫 Grant 전 · CLI 와 `run(config)` 직접 호출 모두 — `run()` 안에서 검사한다):
  (a) **고정 루트** — `--checkpoint-root` 를 줬어야 한다(`checkpoint_root_is_default == false`). 기본 루트는 PID · 시각이 들어간 임시 폴더라(lib.rs:4621~)
      재기동마다 새 원장이 생겨 전수 대조 · ACTIVE 풀기가 이전 원장을 못 본다(r1 ③)
  (b) **보고 보관함** — `--report-over-session true`(보관함 있음)여야 한다. 원장의 CLOSED 는 "종료 보고가 디스크에 남았다" 뒤에 쓰는데, 보관함이 없는
      구성(보고 끄기 · 보관함 없는 발신)에는 그 경계가 없다(r1 ④ — lib.rs:4441~). 배포 유닛은 이미 켜 두었다(gputeer-agent@.service:16)
  (c) **수신 확인** — `--require-ack-receipt true` 여야 한다. 시작 기록(sentinel)은 지금 코드에서 그 경로 안에서만 쓰인다(lib.rs — 수신 확인 관문
      다음 · 실행 직전) — 없으면 "sentinel 없음 = 시작 안 함" 판정이 거짓이 된다. 배포 유닛은 이미 켜 두었다
  셋 중 하나라도 아니면 기동 거부(무엇을 줘야 하는지 안내)

| 상황 | 결과 |
|---|---|
| 원장 없음 · started-attempts 비었거나 없음 | 새로 만든다 · 세대 짝 파일을 쓴다 |
| 원장 없음 · started-attempts 에 기록 있음 | **거부** — "이관 명령을 먼저" 안내 |
| 원장 있음 · 세대 짝 파일 없음 · 또는 값이 다름 | 거부 |
| 열지 못함 · integrity_check 실패 · format_version 모름 | 거부 |
| 어느 한 행이라도 row_format_version · origin · executor · state 가 아는 값이 아님(r1d ②) | 거부 — 열 때 **모든 행**을 검사한다(메타만 보지 않는다) |
| started-attempts 의 시도 중 원장에 행이 없는 것 | 거부(논리적 누락 — 계약 b3 ⑦) |

거부는 지금의 기동 거부와 같은 모양(오류로 끝남 · 루프는 다음 회차에 다시 시도)이다.
★ **켜는 것은 되돌릴 수 없는 선택이다**(r1b ① · r1f ①) — 스위치가 꺼져 있어도 루트에 원장 파일 · 세대 짝 · **이관 표식(adopting)** 중 하나라도
  **있으면 기동을 거부**한다. 이관 표식이 있으면 스위치와 무관하게 "이관이 끝나지 않았다 — 이관 명령을 다시 돌린다" 로 거부하고, 그 표식을 지우는 것은
  이관 명령의 복구 경로뿐이다("이 루트는 원장을
  켰다 — `--run-ledger true` 로 띄운다"). 원장 행(LOCAL_BLOCKED)만이 차단 근거인 순간(행 커밋 뒤 · 사건 표식 쓰기 전 전원 차단)이 있어, 스위치를 빼면
  기존 사건 관문이 표식을 못 찾고 남은 컨테이너 정리까지 가기 때문이다. 한 번도 켜지 않은 루트(원장 · 짝 · 이관 표식 모두 없음)만 **지금 동작 그대로**다.
★ **감지 위치**(r1f ③) — 원장 · 짝 · 이관 표식을 보는 것은 잠금 · 실경로 확정 **직후**, 기동 GC(collect_startup_partials — 정착 함수가 콜백 뒤에 돈다 ·
  lib.rs:3402~3418)와 모든 보관함 전송 **앞**이다. 스위치가 꺼진 채 거부할 루트의 부분 데이터를 GC 가 먼저 지우지 않게

## 실행 순서 (계약 §5 "실행 순서")

```text
1 원장 행 ACTIVE(트랜잭션)          실패 → 띄우지 않는다
2 started-attempts sentinel        지금 코드(record_attempt_started_here · lib.rs:450 · :1491). 실패 → 띄우지 않는다 · 원장 행을 CLOSED(reason=not_started)
3 기동(create · start 또는 호스트 spawn)
4 종료 관측 → **컨테이너 처리 결과를 먼저 원장에 적는다**(r1e ① — 계약의 CLOSED 경계에는 정지 · 부재 확인이 들어 있다):
    컨테이너를 지우고 새 조회로 "없음" 을 확인했으면 → 행에 container_removed=1(아직 ACTIVE) 커밋
    컨테이너를 남겼으면(needs_human — 종료를 봤어도 남길 수 있다 · container.rs:1457 · 표식 쓰기가 실패해도 결과는 돌아온다 · :1625) →
      **보고 보관 전에** 행 ACTIVE → LOCAL_BLOCKED 커밋(표식 쓰기의 성공 여부와 무관 — 원장 행이 차단 근거다)
  → 그 뒤 종료 보고를 보관(persist_report_to_outbox · lib.rs:2525 — rename 뒤 sync_dir)이 **성공한 직후 · 전송 전에** 원장 CLOSED 를 커밋(r1b ④)
    — 단 container_removed=1 인 행만. LOCAL_BLOCKED 행은 보관 뒤에도 LOCAL_BLOCKED 로 남는다(해제 명령만 푼다)
  ★ **종료 단계의 원장 커밋 실패는 치명적이다**(r1g ②) — 실패한 **자리**에 따라 남는 것이 다르다(r1h):
    (가) container_removed · LOCAL_BLOCKED 커밋 실패(보고 보관 **전**) → 보고를 보관하지 않고 **루프를 멈춘다**(CONTAINER_INCIDENT_NOT_RECORDED 와 같게 ·
        새 작업 없음). 행은 ACTIVE · 보고 없음 → 다음 기동에서 "sentinel 있음 · 보고 없음" → LOCAL_BLOCKED(안전한 쪽). 사건 표식 쓰기의 실패
        (container.rs:1622~1638 — 지금은 기록하고 결과를 돌려준다)와 겹쳐도 같다
    (나) CLOSED 커밋 실패(보고 보관 **뒤** — 보관 함수는 이름 바꾸기와 폴더 sync 가 끝난 뒤 돌아온다 · lib.rs:2525~2561) → 보고는 이미 디스크에 있다.
        **전송하지 않고** 루프를 멈춘다. 다음 기동에서 "sentinel 있음 · 인정된 보고 있음 · container_removed=1"(호스트 행은 보고만) → CLOSED(보고가 다시 간다)
    ★ "루프를 멈춘다" 의 연결(r1i ①) — 지금 agent-loop 는 자식 출력의 CONTAINER_INCIDENT_NOT_RECORDED 줄만 보고 멈추고(agent_loop.rs:249 · :299 · :311),

      반복을 멈추고 실패로 끝난다. systemd(Restart=on-failure)가 루프를 다시 띄우면 다음 기동은 위 (가)(나) 의 풀기 규칙으로 판정한다 — (가) 는 LOCAL_BLOCKED 로
      막히고, (나) 는 보고가 인정돼 CLOSED 로 풀린다(그때 새 작업을 받는 것은 안전하다 — 보고가 디스크에 있고 부재가 확인됐다)
  — 전송 · ACK 뒤에는 보고 파일이 지워진다(lib.rs:2613~2625). CLOSED 를 전송 뒤로 미루면 "보관 → 전송 → 파일 삭제 → (CLOSED 전 사망)" 에서 보고가
  사라진 ACTIVE 가 불명으로 오판된다
  (보관함이 없는 구성은 위 켜는 조건 (b) 로 원장을 켤 수 없다)
  호스트 행은 container_removed 가 해당 없다 — 보관 직후 CLOSED(지금과 같다 · D5 조각 전)
```

## 기동 때 ACTIVE 행 풀기 (알림 꺼짐 — 계약 b14 ②)

| 행 | sentinel | 보고 보관함에 그 시도의 종료 보고 | 결과 |
|---|---|---|---|
| 컨테이너 | 없음 | — | CLOSED(시작 안 함 — sentinel 쓰기는 write_once 로 전원 차단을 넘는다) |
| 컨테이너 | 있음 | 있음 — 아래 "보고 인정" 을 통과한 것만 · **그리고 행의 container_removed=1** | CLOSED(보고가 다시 간다) |
| 컨테이너 | 있음 | 있음 · container_removed 없음(부재 증거가 원장에 없다) | LOCAL_BLOCKED — 보고가 유효해도 컨테이너가 남았을 수 있다(r1e ①) |
| 컨테이너 | 있음 | 없음 | (1) 원장 트랜잭션 ACTIVE → LOCAL_BLOCKED (2) 그 뒤 사건 표식(write_incident) — 새 작업 거부 |
| 호스트 | 무엇이든 | 무엇이든 | CLOSED(지금과 같다 — D5 조각 전 · "보장하지 않는 것") |

★ 풀기는 지금의 "남은 컨테이너 정리"(lib.rs:656 부근)보다 **먼저** 한다 — 정리가 사람에게 넘길 컨테이너를 지우지 않게(지금 사건 관문과 같은 이유).
★ **모든 보관함 전송보다도 먼저** 한다(r1b ④) — 지금 루트 정착 안에서 소유자 되찾기 표식이 있으면 보관 보고를 먼저 보낸다(lib.rs:632~645 · 전송 뒤
  파일 삭제). 그래서 원장 열기 · 풀기를 정착 함수의 그 전송 **앞**(잠금 · 실경로 직후)에 둔다.
보고 인정    (r1b ②) 보관함 파일이 "있다" 만으로 CLOSED 하지 않는다. 지금 재전송이 쓰는 검증(reopen_outboxed_report · lib.rs:2825~ — 해독 · 이 노드의 것 ·
             서명 · 필드 조합 규칙)을 통과하고, 보고의 attempt_id · node_id · job_id · fence_epoch 가 **원장 행과 같으며**, 종료 보고(terminal)인 것만 인정한다.
             격리된(quarantine) 보고 · 다른 시도 · 서명 실패 · 해독 실패는 "보고 없음" 으로 본다 → LOCAL_BLOCKED

## 해제 — `container-incidents --clear` (계약 §5 · 단계 3 v7)

```text
지금        clear_incidents(container.rs:1531)는 루트 잠금을 잡지 않고, 지운 뒤 폴더 sync 를 하지 않는다
바꾼다      ★ **한 번도 원장을 켜지 않은 루트는 지금 동작 그대로**(잠금 없이 표식만 — r1i ② · 기본 꺼짐의 약속). 아래 (1)~(4) 는 원장을 켠 루트에만:
            (1) 루트 잠금(실패하면 "Agent 가 떠 있다 — 멈춘 뒤" 안내) (2) 원장이 있으면 그 컨테이너 이름의 LOCAL_BLOCKED 행을 CLOSED(트랜잭션 먼저)
            (3) 표식 삭제 (4) sync_dir. 어느 단계에서 끊겨도 같은 명령을 다시 돌리면 풀린다 — CLOSED 행의 남은 표식은 지워도 되는 것으로 본다
원장 없음    **한 번도 원장을 켜지 않은 루트**(원장 · 세대 짝 · 이관 표식 모두 없음)만 지금처럼 표식만 지운다.
            ★ 세대 짝이나 이관 표식이 있는데 원장이 없거나 열리지 않으면 `--clear` · `--clear-all` **모두 거부**(r1g ①) — 원장을 잃은 루트에서 표식만 지우면
              원장의 LOCAL_BLOCKED → CLOSED 없이 차단 근거가 사라진다(계약 §5 의 해제 순서). 수동 복구로 안내
--clear-all  표식이 있는 컨테이너뿐 아니라 **표식 없이 남은 LOCAL_BLOCKED 행**(행 CLOSED 전 · 표식 삭제 뒤 끊긴 경우)도 전부 CLOSED(r1 ⑤)
```

```text
             R32 LOCAL_BLOCKED 커밋 뒤 표식 쓰기 전 끊김 → 스위치를 빼고 재기동해도 거부(정리가 돌지 않음)
부산물        R33 확정된 기록 옆에 남은 .write_once.lock · 최종 없는 .tmp · 최종 있는 .tmp → 정리 뒤 통과 · 규칙에 안 맞는 대상 이름의 부산물 → 거부
플랫폼        Windows(개발 기계) · 리눅스(CI · 비-root)에서 같은 시험. 권한 조건을 같이 적는다(CLAUDE.md §4)
```
