# 제출된 Manifest 운영자 반입 (operator import)

**작성**: 2026-09-01
**상태**: 진행 중

## 왜 이것인가

이 저장소는 부품이 거의 다 있는데 **이어지지 않아** Job 을 실제로 돌릴 수
없다. 끊긴 곳이 넷이고, 그중 **첫째**가 이것이다.

```text
① Job 투입      gputeer submit 이 서명한 Manifest 를 파일로만 낸다.
                durable job store 에 들어가지 않는다.          <- 이 조각
② scheduler     orchestrate 가 완성돼 있는데 production 호출자가 없다.
③ Grant 발급    Coordinator 가 CLI 인자로 받은 ID 로만 Grant 를 만든다.
④ 데몬화        coordinator-stub / agent-stub 은 한 번 돌고 끝난다.
```

`DoD-50` 이 `submit_verified_manifest()` 를 만들면서 "production wire
연결은 범위 밖" 이라고 적어 뒀다. 그 저장소는 **아무도 부르지 않는다.**

## 이름이 왜 "반입(import)" 인가

★ **이건 "제출 접수" 가 아니다.** 독립 설계 조사가 정확히 짚었다:

> 임의 공개키까지 같은 명령에서 받아 "verified/accepted" 라고 부르는 것은
> 정직하지 않다.

명령줄로 공개키를 받으면 **신뢰 경계가 그 명령 한 줄**이 된다. 아무나
자기 키를 붙여 "검증됨" 을 만들 수 있다. 그건 검증이 아니라 서명 확인일
뿐이다.

그래서:

```text
안 한다   제출자가 네트워크로 보내는 것을 받아들이기
안 한다   누가 제출할 자격이 있는지 판정하기(멤버십)
안 한다   명령줄 공개키를 신뢰하기

한다      운영자가 **미리 provision 한 keyring 파일**에 있는 서명자만 받기
한다      그 서명을 검증한 뒤에만 필드를 읽고 durable 저장소에 넣기
한다      모르는 서명자 · 위조 서명 · 만료를 각각 구분해 거부하기
```

신뢰 경계가 **운영자가 소유하는 파일**이다. 그 파일에 누구를 넣을지는
운영자가 결정하고, 이 명령은 그 결정을 실행할 뿐이다. 멤버십 권위는
여전히 없다 — `PersistentKeyring` 은 `revoke()`·`quarantine()` 을 갖지만
그건 **로컬 운영자의 목록**이지 팀 합의가 아니다.

## 무엇을 만드는가

새 CLI 명령 하나.

```text
gputeer import-manifest
    --manifest <서명된 Manifest 파일>       gputeer submit 이 만든 것
    --submitter-keyring <keyring 파일>      운영자가 미리 provision
    --job-db <SQLite 경로>                  durable job store
    --idempotency-key <32자리 hex>          16바이트
```

하는 일:

```text
1  파일을 protobuf 로 decode 한다
2  keyring 을 열어 Ed25519Verifier 를 만든다
3  verify() 로 Verified<JobManifest> 를 만든다   <- 여기서 실패하면 끝
4  Verified::get() 뒤에만 필드를 읽는다
5  AcceptedJobSubmission 을 구성한다
6  submit_verified_manifest() 를 한 번 부른다
```

★ **4번이 이 조각의 핵심 규율이다**(`CLAUDE.md` §0.2). `Verified<M>` 가
타입으로 강제하지만, 그 앞에서 `manifest.job_id` 를 읽어 로그에 찍는
것만으로도 규율이 깨진다.

## 무엇을 거부하는가 (negative test)

```text
모르는 서명자        keyring 에 없는 signer_id -> 거부, DB 무변경
위조 서명            서명 바이트 한 개 변조 -> 거부, DB 무변경
만료된 Manifest      수명 밖 -> 거부, DB 무변경
평문 keyring         opt-in 없으면 거부 — 신뢰 목록 자체가 위조 가능하다
비영속 DB            :memory: 와 빈 경로 둘 다 거부(저장소에 물어본다)
채워진 DB 에 거부    이미 Job 이 든 DB 가 바이트 단위로 안 바뀐다
같은 입력 재실행     같은 결과, 행 1개 (멱등)
```

★ **거부 뒤 DB 가 안 바뀌는지를 함께 확인한다.** "거부했다" 만 보면
거부하면서 흔적을 남기는 구현도 통과한다.

단 **비영속 DB 거부는 예외다** — `:memory:` 와 빈 경로에는 대조할 파일
자체가 없다. 그 테스트는 거부 여부와 사유 문구만 본다. "매번" 이라고
쓰면 안 되는 이유다(독립 검수 3라운드).

## 정직하게 남기는 한계

```text
멤버십 권위 없음      keyring 은 운영자의 로컬 목록이다. 팀 합의가 아니다.
네트워크 제출 없음    파일로만 받는다. wire ingress 는 별도 조각이다.
스케줄링 안 함        저장만 한다. orchestrate 연결은 ② 다.
키 회전·폐기 절차 없음 keyring 이 API 는 갖지만 운영 절차는 미정의다.
revoke 반례 없음      초안 목록에 있었으나 만들지 않았다. 폐기된 서명자는
                      검증 계층에서 `UnknownSigner` 로 합쳐지므로 "모르는
                      서명자" 반례와 구분되는 관측을 못 만든다.
바뀐 입력 재실행 없음  같은 idempotency key 에 다른 Manifest 를 주는 conflict
                      경로는 저장소(`DoD-50`)가 이미 테스트하고, 이 명령이
                      새로 더하는 것이 없어 빼기로 했다.
```

## 규모

production 100~180줄, 테스트 150~250줄 — 독립 설계 조사의 산정이다.
선행 조건(신뢰된 keyring)을 **외부에 명시**했기 때문에 하루 규모다.
그것까지 새로 설계하면 하루를 넘는다(같은 조사 판정).
