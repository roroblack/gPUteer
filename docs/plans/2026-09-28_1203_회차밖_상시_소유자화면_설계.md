## v1 과 무엇이 다른가 — 구조를 바꾼 이유

v1(A: 루프가 패널을 쥐고 **자식의 패널 포트로 HTTP 중계**)은 c1 이 짚은 대로 그 구조에서 결함이 나왔다:
끝난 자식의 포트를 다른 프로그램이 잡으면 가짜 "성공" 을 중계할 수 있다(높음) · 5초 동기 중계와 30초 걸리는 정지가 어긋난다(높음) ·
자식 인자의 포트 옵션과 배포 파일이 충돌한다(높음) · 같은 인자를 두 번 파싱하면 시드 · 루트가 갈릴 수 있다(중간).
v2 는 **자식이 패널을 띄우지 않는다.** 루프 하나가 패널을 쥐고, 자식과는 **이미 있는 표준 입출력 파이프**로만 말한다.

```text
                 v1(A)                              v2(A′)
자식의 패널      루프 모드에서도 띄움(포트 0)          루프 모드에서는 띄우지 않는다
루프 ↔ 자식      127.0.0.1 TCP 로 HTTP 중계           자식 stdin(명령) · stdout(결과 줄) — 자식 수명에 묶인 파이프. 포트 재사용 문제가 없다
토큰            자식 · 루프가 각자 시드에서 파생       루프만 파생(자식 쪽은 패널이 없어 토큰이 필요 없다)
정지            동기 중계(5초)                        비동기 — 접수 번호를 주고 상태를 따로 읽는다
되찾기 표식      자식이 작업 종료 처리 뒤에 씀          루프가 **정지를 넘기기 전에** 영속으로 쓴다
```

## A′ 의 세부

```text
기동       agent-loop 가 첫 회차 **전에** 패널을 연다(못 열면 루프를 시작하지 않는다 — OWNER_PANEL_REFUSED). 포트는 **루프 자신의 인자**
           `agent-loop --owner-panel-port N -- …` 로 받는다. `--` 뒤(자식 인자)에 --owner-panel-port 가 있으면 루프가 거부한다 — 한 곳에서만 정한다.
           배포 파일(agent.ps1 · gputeer-agent@.service)은 그 옵션을 `--` 앞으로 옮긴다(이관 — 이 조각의 범위)
자식       루프가 띄운 자식에는 새 인자 `--owner-control stdio` 를 붙인다 — 그러면 자식은 패널을 bind 하지 않고, 정지 손잡이를 stdin 명령으로 받는다.
           ★ 지금의 "실행이 켜졌으면 패널이 반드시 있어야 한다"(lib.rs:700~733 — 멈출 수 없는 작업을 시작하지 않는다)는 규칙은 **stdio 제어가 연결됐을 때**만
             대신 채워진다 — stdin 이 닫히면(루프가 죽음) 자식은 새 작업을 시작하지 않는다
설정       루프는 자식 인자를 해석하지 않는다(v1 의 O2 철회). 루프가 알아야 하는 것(시드 파일 · 체크포인트 루트 · 컨테이너 런타임)은 **루프 자신의 인자**로
           받는다 — 루프 모드에서는 --checkpoint-root 를 필수로 한다(생략하면 PID · 시각으로 매번 새 루트가 생긴다 — lib.rs:4621). 자식과 값이 다르면
           자식이 첫 줄 `OWNER_CONTROL_HELLO root=<정규화 경로> owner=<라벨>` 로 알리고 루프가 대조해 다르면 그 회차를 멈춘다
정지(지금 시도)  패널 POST /api/stop → 루프가 (1) 되찾기 표식을 영속으로 쓴다(write_once · sync_dir — 이 시도 id) (2) 접수 번호를 돌려준다(202)
           (3) 자식 stdin 에 `STOP <attempt_id> <접수 번호>` (4) 자식이 뒤에서 ContainerStopper::stop → stdout `OWNER_STOP_RESULT <번호> confirmed|failed|unknown <사유>`
           (5) 패널은 GET /api/stop/<번호> 로 상태를 읽는다. 자식이 결과 없이 끝나면 "unknown(자식 종료)" — 성공이라 하지 않는다
           ★ 표식이 먼저라 "정지 성공 뒤 표식 전에 자식이 죽는" 틈이 없다. 정지가 실패해도 표식은 남는다 — 소유자가 되찾기를 원한 것은 사실이다
             (다시 켜기는 지금처럼 owner-resume)
정지(남은 컨테이너)  자식이 없을 때도 루프가 한다 — 라벨로 찾은 컨테이너를 **확인한 ID 로** 멈추고(kill → 새 조회로 멈춤 확인) 결과를 보인다.
           **지우지 않고 · 로그를 거두지 않고 · 사건 표식을 해제하지 않는다**(그것은 지금처럼 사람이 확인한 뒤의 명시적 명령 — O3). 멈춘 사실은 사건 옆에
           기록으로 남긴다
되찾기     되찾기 표식이 있으면 루프는 **회차를 띄우지 않고 기다린다**(지금은 매 간격마다 자식이 떠서 OWNER_RECLAIMED 로 끝난다). owner-resume 로 지우면 다시 띄운다
조회       사건 폴더 · 되찾기 표식 · 남은 컨테이너 목록은 루프의 뒤쪽 작업자 하나가 주기적으로(예 30초) 읽는다 — 요청은 마지막 결과와 시각만.
           ★ 작업자는 하나 · 겹치지 않는다(앞 조회가 시한을 넘기면 다음 주기를 건너뛰고 "조회 지연" 으로 보인다) — 프로세스가 쌓이지 않는다
사건 파일   no-follow 로 열고, 일반 파일만(폴더 · 링크는 "읽지 않음 — 종류 X" 로 보인다), 항목당 4KiB 까지, 깨진 UTF-8 은 대체 문자, 읽기 실패는 그대로 보인다.
           ★ 목록에 보이는 것은 지금처럼 **모든** 항목이다(결함 498 — 모르는 것도 열린 사건)
HTTP 상한  시작줄 · 헤더 줄 · 헤더 전체(8KiB) · 헤더 개수 · 본문(4KiB — 지금 규칙) · 응답 크기 상한 · 읽기 · 쓰기 · 전체 시한(예 5초) · 동시 연결 상한(예 4) —
           Host · 토큰 검사가 먼저이고, 그 전에는 아무것도 하지 않는다
```

## 루프가 죽으면 — 플랫폼별 (c1 ⑦)

## 하지 않는 것

- 런타임을 거치지 않는 정지(단계 4) — R3 의 정지는 런타임을 거친다. 런타임이 멈추면 "모름" 이다
- 남은 컨테이너 삭제 · 로그 수집 · 사건 해제를 패널에서 하는 것(O3 — 지금처럼 명시적 명령)
- Coordinator 에 불명 · 정지 확인을 알리는 것(단계 2 계약) — 그 계약이 구현되면 "정지 확인" 이 그 알림의 출발점이 된다
- 원격 접속 · 여러 노드 한 화면
