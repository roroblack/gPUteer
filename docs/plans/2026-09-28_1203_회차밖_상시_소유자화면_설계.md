## 구조 A′ — 루프가 패널 · 상태 · 루트 잠금을 쥐고, 자식은 전용 제어 파이프로 말한다

### 불변식

```text
I1  루프는 패널 bind 에 성공한 **뒤에만** 자식을 띄운다(못 열면 루프를 시작하지 않는다 — OWNER_PANEL_REFUSED)
I2  루프는 체크포인트 루트의 OS 잠금을 **수명 전체** 쥔다(지금 자식이 쥐던 것 — 실경로 확정 · 기동 GC 도 루프가 잠금 아래에서 한다). 자식은 재잠금하지 않는다
I3  자식이 패널을 생략하는 길은 **내부 진입점 `agent-stub --loop-child`** 하나뿐이다 — 유효한 제어 파이프 두 개와 GO 를 받아야 일을 받는다. 일반 agent-stub(단독 실행)은
    지금처럼 패널이 필수다(§0.1 — 단순 `--no-panel` 은 두지 않는다)
I4  제어 파이프는 비신뢰 워크로드에 **절대 상속되지 않는다**(아래 "파이프 상속 금지")
I5  되찾기 표식 · 회차 시작 · 다시 켜기는 루프 잠금 아래 한 상태기계에서만 바뀐다. 루트 잠금을 루프가 쥐므로 루프 밖의 CLI 는 그 사이에 표식을 지울 수 없다
```

### 루프의 상태기계와 되찾기 (c1c ① ②)

```text
상태        Idle · Starting(자식 띄움 · GO 전) · Running(GO 뒤) · StopPending(정지 접수) · Reclaimed(되찾음 — 회차를 띄우지 않는다)
generation  상태가 바뀔 때마다 1 오른다. 모든 명령 · 접수 번호 · 표식에 싣는다

POST /api/reclaim(멱등)  Idle → 표식 영속 → Reclaimed
                         Starting → 표식 영속 → 자식에 STOP_BEFORE_GO → Reclaimed(자식이 GO 없이 끝남)
                         Running → 표식 영속 → 지금 시도 정지(아래와 같다) → StopPending → 결과 뒤 Reclaimed
                         StopPending · Reclaimed → 그대로(같은 접수 번호 · 200)
POST /api/stop{attempt}  Running 이고 그 attempt 가 지금 것일 때만 — 위 Running 행과 같다(정지 = 되찾기. 지금 동작과 같다 — 정지하면 표식을 쓴다 · lib.rs:1687)
POST /api/resume         Reclaimed → 표식 삭제 → Idle. StopPending 이면 409(결과 뒤에). 표식 삭제 · 상태 변경은 루프 잠금 아래 한 번에
CLI owner-resume         루트 잠금을 잡아 본다 — 루프가 쥐고 있으면(루프가 떠 있다) 잠금 실패로 멈추고 "패널에서 다시 켜기" 를 안내한다. 잡히면(루프 없음)
                         잠금 아래에서 표식을 지운다
회차 시작     루프 잠금 아래에서 상태가 Idle 이고 표식이 없을 때만 Starting. GO 도 잠금 아래에서 상태가 여전히 Starting 일 때만 보낸다
루프 기동     표식이 있으면 곧바로 Reclaimed(회차를 띄우지 않는다 — 지금의 "간격마다 자식이 떠서 OWNER_RECLAIMED" 를 없앤다)
```

### 자식 기동 — GO 전에는 아무것도 하지 않는다

```text
1 루프가 제어 파이프 두 개를 만든다(자식 쪽 끝만 상속 · 루프 쪽 끝은 비상속) · 설정 스냅샷을 쓴다(아래) · 자식을 띄운다
  Windows  CREATE_SUSPENDED → Job Object(KILL_ON_JOB_CLOSE) 편입 → Job 핸들 비상속 확인 → ResumeThread. 편입 전 루프 사망에도 자식은 멈춘 채라 일을 받지 않는다
  리눅스   유닛 cgroup(KillMode=control-group — 예상, 재지 않았다) + 자식이 PR_SET_PDEATHSIG · 시작 직후 getppid() 가 루프가 아니면 끝난다
2 자식이 스냅샷 · 제어 파이프를 확인하고(루트는 이미 루프가 잠금 · 실경로 확정 · GC 함) 사건 관문 · 쓰기 시험 · 남은 컨테이너 정리를 지나면 READY{config_digest}. 거부면 REFUSED
3 루프가 잠금 아래에서 Starting · 표식 없음 · digest 일치면 GO. 아니면 STOP_BEFORE_GO
4 자식은 GO 뒤에만 Coordinator 에 붙는다. 제어 파이프가 닫히면(루프 사망) 새 작업을 시작하지 않는다 — 도는 작업은 그대로 두고 끝난 뒤 다음을 받지 않는다
```

### 파이프 상속 금지 (c1c ⑤)

```text
Windows  자식은 시작 직후 자기 쪽 파이프 핸들의 상속 비트를 끈다(SetHandleInformation · HANDLE_FLAG_INHERIT=0). 워크로드 spawn 은 PROC_THREAD_ATTRIBUTE_HANDLE_LIST 로
         **명시한 핸들만**(표준 입출력 · 로그 파일) 넘긴다
리눅스   자식 쪽 fd 는 O_CLOEXEC 로 연다(또는 시작 직후 FD_CLOEXEC). 워크로드 spawn 전 열린 fd 목록을 보고 제어 fd 가 CLOEXEC 인지 확인 — 아니면 실행하지 않는다
컨테이너  런타임 CLI 로 띄우므로 fd 가 컨테이너 안으로 가지 않는다(런타임 CLI 자체에도 위 규칙이 적용된다 — CLI 프로세스가 파이프를 쥐지 않게)
```

### 정지 결과 — 자식 안에서 한 곳이 판정한다 (c1c ③)

지금 손잡이는 "이미 끝남" 에도 성공을 돌려준다. 그래서 판정을 손잡이가 아니라 **자식의 실행 상태기계**가 한다 — 워크로드 종료 관측과 STOP 수락을 같은 잠금 아래에서 순서 짓는다.

```text
종료 관측이 STOP 수락보다 먼저        → already_exited(STOP 을 손잡이에 넘기지 않는다)
STOP 수락 → 손잡이 → 그 뒤 종료 관측   → Windows: 종료 코드가 EXIT_CODE_OWNER_STOPPED 면 owner_stop_observed · 다른 코드면 already_exited(그 사이 스스로 끝남)
                                      리눅스(cgroup SIGKILL): owner_stop_observed_ambiguous — 요청 뒤 멈춘 것은 맞지만 같은 순간 스스로 SIGKILL · OOM 으로 끝난 것과
                                      가르지 못한다(결함 524 와 같은 한계 — 화면에 그대로 적는다)
                                      컨테이너: 지금 ContainerStopper 의 판정(ALREADY_EXITED · 137 비-OOM) 그대로
STOP 뒤 종료를 관측하지 못함(시한 · 파이프 EOF · 손잡이 오류) → unknown
```

★ 워크로드가 우연히 EXIT_CODE_OWNER_STOPPED 로 끝나면 Windows 에서도 틀릴 수 있다 — 그 코드를 쓰는 작업은 드물지만 0 은 아니다(적는다).

### 지금 시도 정지 — 비동기 · 표식 먼저

```text
(잠금) Running · 지금 attempt 확인 · 같은 attempt 의 정지가 진행 중이면 그 접수 번호(single-flight) → 표식 영속(실패하면 정지 안 넘기고 500) → StopPending · 202 →
STOP → 자식 STOP_ACCEPTED · 판정 → STOP_RESULT → Reclaimed
GET /api/stop/<번호> → accepted · pending · owner_stop_observed · owner_stop_observed_ambiguous · already_exited · unknown
```

접수 번호 · 결과는 **비영속**이다. 루프가 다시 뜨면 모르는 번호는 unknown(재시작 뒤)로 답한다. 표식은 영속이라 재시작 뒤에도 Reclaimed 로 시작한다. 세 사망 지점
(표식 뒤 STOP 전 · STOP 뒤 결과 전 · 결과 뒤 반영 전)은 모두 "Reclaimed · 결과 unknown" 으로 수렴한다.

### 남은 컨테이너 정지 — 자식 없이 루프가

확인한 ID 로 kill → 새 조회로 멈춤 확인(지금 ContainerStopper 판정). 지우지 · 로그를 거두지 · 사건을 해제하지 않는다. target 별 single-flight.

### 설정 — `--` 경계는 그대로, 파싱은 한 번 (c1c ⑥ · O5)

```text
문법      agent-loop [--interval-ms N] [--max-rounds N] [--owner-panel-port N] -- <agent 인자>. `--` 앞은 루프 전용(지금 둘 + 포트), 뒤는 지금 배포와 같다
          `--` 뒤에 --owner-panel-port 가 있으면 루프가 거부한다. 루프 모드에서는 --checkpoint-root 가 필수다(생략하면 PID · 시각으로 매번 새 루트 — lib.rs:4621)
파싱      루프가 `--` 뒤를 parse_config_from_args 에 **정확히 한 번** 넘긴다 → 루트 잠금 · 실경로 · owner 라벨까지 정착
스냅샷    `<실경로 루트>.loop-config.json` — 정착한 설정(시드 자체는 넣지 않는다 — 시드 파일 경로 · 공개키 지문). write_once(generation 마다 새 이름 · 원자) ·
          파일 권한은 설치 폴더 규칙(현재 사용자 · SYSTEM · Administrators / 0600) · 루프 종료 때 지운다. 자식에는 스냅샷 경로만 넘긴다(`--loop-child <파일>`)
digest    스냅샷 바이트의 BLAKE3 — READY 에 싣고 루프가 대조. 자식은 시드 파일을 읽어 지문이 같은지 확인(두 사이에 시드가 바뀌면 거부)
배포      agent.ps1 · 유닛은 `--` 앞에 --owner-panel-port 만 옮긴다(나머지 인자는 그대로 `--` 뒤) — T20
```

### 상한 — 숫자로, 서로 맞게 (c1c ⑦)

```text

            화면에 그렇게 적는다). 루프 재시작 뒤 커서는 없다 — 처음부터
            no-follow · 일반 파일만 내용을 읽는다(링크 · 폴더 · reparse point 는 종류만) · JSON 이스케이프 · 화면은 textContent 로만
정지 큐      전역 동시 2 · 대기 8 · target 별 single-flight · 넘으면 429. 접수 기록 64개 · 수명 1시간(버린 번호는 unknown)
조회 작업자   하나 · 주기 30초 · 겹치지 않음(넘기면 다음 주기를 건너뛰고 "지연")
```

## 루프가 죽으면 — 플랫폼별 운영 계약 (c1c ⑧)

```text
리눅스 systemd    Restart=on-failure · RestartSec=5(gputeer-agent@.service:17~18). 자식은 PDEATHSIG · 유닛 cgroup 으로 끝난다(예상). 컨테이너는 남는다 →
                 다시 뜬 루프의 자식 기동 관문 · 루프의 남은 컨테이너 조회가 본다

                재시도를 다 쓰면 다음 로그온까지 패널이 없다 — 비보장 범위로 적는다. 자식은 Job 으로 끝난다. Docker Desktop 컨테이너는 남는다
```

## 선택지 — 단계 3 범위에서 공정하게 (c1c ⑨)

| | A′ 루프가 패널 | B 별도 상시 서비스(정지 권한을 서비스 하나에) | C Agent 데몬화 |
|---|---|---|---|
| 무엇 | 위 | 서비스가 패널 · 정지 권한 · 되찾기 상태를 쥔다. 루프 · 자식은 서비스에 **보고만**(시작 · 끝 · 손잡이 위치) — 정지는 서비스만 하므로 경쟁 설계는 필수가 아니다 | 회차 루프를 한 프로세스 안에 |
| 서비스 수 | 그대로 | 하나 는다(설치기 둘 · 작업 스케줄러 · 유닛 · 런북 · 업데이트 순서) | 그대로 |
| 지금 시도 정지 | 자식이 자기 손잡이로(제어 파이프) | 서비스가 손잡이를 **다른 프로세스에서** 써야 한다 — Windows Job 핸들 · 리눅스 cgroup 경로를 서비스에 넘기는 IPC · 권한 설계가 는다 | 같은 프로세스 |
| 루프 crash 결합 | 루프가 죽으면 패널도(재시작 정책까지) | 격리 — 루프가 죽어도 패널은 산다 | 프로세스 하나라 같이 죽는다 |
| 회차 상태 누수 | 없음(회차 = 프로세스) | 없음 | `agent_loop.rs` 머리말이 기각한 이유 그대로(연결 번호 · replay · 잠금이 회차를 건넌다) — 제외 |
| 공통 제약(단계 4) | 런타임을 거치지 않는 정지는 양쪽 모두 플랫폼 도우미가 필요 | 같다 | 같다 |

**권고: A′.** B 의 crash 격리는 큰 장점이지만, 지금 시도의 손잡이(Job 핸들 · cgroup)를 다른 프로세스로 넘기는 IPC · 권한 설계가 A′ 의 제어 파이프보다 크다.
Windows 재시작 정책(O4)으로 A′ 의 crash 공백을 줄인다. **B 를 고르면 단계 3 을 다시 설계한다.**

## 하지 않는 것

- 런타임을 거치지 않는 정지(단계 4) — 런타임이 멈추면 컨테이너 정지 결과는 unknown(호스트 작업은 Job · cgroup 이라 런타임과 무관)
- 남은 컨테이너 삭제 · 로그 수집 · 사건 해제를 패널에서 하는 것
- Coordinator 에 불명 · 정지 확인을 알리는 것(단계 2 계약)
- 원격 접속 · 여러 노드 한 화면
