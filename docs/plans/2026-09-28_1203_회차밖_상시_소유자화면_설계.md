```text

2 자식의 기동 순서  루트 잠금 · 실경로 → 되찾기 표시 → 기동 GC(:3401~3417) → 사건 관문 → 쓰기 시험 → 남은 컨테이너 정리 → 패널. 루트 잠금은 run() 전체 동안
3 정지 손잡이      WorkloadStopper(exec.rs:227) — 호스트(Windows Job Object · 리눅스 cgroup)와 컨테이너를 하나로. stop() 은 **이미 끝난 작업에도 성공**한다.
                  Windows 는 전용 종료 코드 EXIT_CODE_OWNER_STOPPED(0xC0000013)로 끝낸다 · 리눅스는 cgroup.kill(SIGKILL) · 컨테이너는 137 비-OOM 을 정지로 본다

                  정상 Drop 때만 cgroup.kill · 지움(runtime-linux:285~304). 자식이 강제로 죽으면 작업 cgroup 과 그 안의 작업이 남는다
5 Windows 작업     CREATE_SUSPENDED → 작업 Job 편입 → 재개(runtime-windows:654~756). 빠져나가는 옵션(BREAKAWAY)은 쓰지 않는다 — 자식이 속한 Job 을 작업도 물려받는다

8 루프            `--` 앞은 --interval-ms · --max-rounds 만, 뒤는 해석 없이 자식에게(agent_loop.rs:251~277). OWNER_RECLAIMED 를 "일 없음" 과 가르지 않는다
```

## 불변식

```text
I1  루프 기동 순서: 인자 파싱 → 루트 잠금 · 실경로 → **패널 bind · 서비스 시작** → 되찾기 확인 → 기동 GC → (그 뒤에만) 자식.
    기동 GC 가 실패 · 지연하면 루프는 끝나지 않고 StartupFault 상태로 패널에 보이며 자식을 띄우지 않는다(c1d ⑧)
I2  루프가 체크포인트 루트의 OS 잠금을 수명 전체 쥔다. 자식은 재잠금하지 않는다
I3  패널 생략은 내부 진입점 `agent-stub --loop-child` 하나뿐 — 아래 "부모 확인" 을 통과해야 GO 를 기다린다. 단독 agent-stub 은 지금처럼 패널이 필수다
I4  제어 파이프는 비신뢰 워크로드에 상속되지 않는다
I5  되찾기 · 회차 시작 · 다시 켜기는 루프 잠금 아래 한 상태기계에서만 바뀐다
I6  **지금 시도의 정지는 디스크 · 큐 · 다른 정지를 기다리지 않는다**(c1d ② ⑤)
I7  **루프가 회차의 작업을 끝낼 수단을 자식과 따로 쥔다** — 자식이 죽어도(c1d ③)
```

## 루프의 상태기계 (c1d ①)

```text
상태   Idle · Starting(자식 띄움 · GO 전) · RoundActive(GO 뒤 · 시도 없음 — Coordinator 인사 · Grant 검증 · ACK 전) ·
       Running(WORKLOAD_STARTED 뒤) · StopPending · Reclaimed · StartupFault
generation  상태가 바뀔 때마다 1 오른다 — 명령 · 접수 번호 · 표식 · 스냅샷에 싣는다
```

| 지금 상태 | 사건 | 다음 상태 · 한 일 |
|---|---|---|
| Idle | 회차 시간 · 표식 없음 | Starting — 스냅샷 · 회차 감독 수단(아래) 준비 → 자식 |
| Starting | READY · digest 일치 · 표식 없음 | RoundActive — GO |
| Starting | REFUSED · EOF · 불일치 | Idle(회차 감독 수단 정리 · 스냅샷 삭제) |
| RoundActive | WORKLOAD_STARTED | Running |
| RoundActive | WORKLOAD_NOT_STARTED(일 없음 · 거부) · EOF | Idle(정리) |
| Running | WORKLOAD_ENDED | Idle(정리 — 결과 줄은 "마지막 회차") |
| Running | EOF(자식 사망 · 결과 없음) | 루프가 회차 감독 수단으로 작업을 끝낸다(아래) → Idle · 결과 unknown · 사건 기록 |
| 모든 상태 | **reclaim**(패널) | 아래 "되찾기" |
| StopPending | STOP_RESULT | Reclaimed(결과 보관) |
| StopPending | WORKLOAD_ENDED(STOP_RESULT 전) | 결과를 자식 판정 규칙으로(아래) — 대개 already_exited · Reclaimed |
| StopPending | EOF | 회차 감독 수단으로 끝냄 → Reclaimed · unknown |
| Reclaimed | resume(패널) | Idle — 표식 삭제 |
| StartupFault | 운영자가 원인 해결 뒤 패널 "다시 시도" | 기동 GC 재시도 → Idle 또는 StartupFault |

### 되찾기 — 어느 상태에서든, 정지가 먼저 (c1d ① ② ⑤)

```text
순서       ① 메모리 상태를 Reclaimed(또는 StopPending)로 **먼저** 바꾼다(루프 잠금 아래 — 이 순간부터 새 회차 · GO 없음)
           ② 지금 시도가 있으면 **곧바로** 정지를 보낸다(우선 경로 — 아래)
           ③ 표식을 영속으로 쓴다. 실패해도 ①② 는 되돌리지 않는다 — 응답 · 상태에 reclaim_durable=false 를 보이고 30초마다 다시 쓴다.
              ★ 표식이 없는 채 루프가 죽으면 다음 루프는 되찾기를 모른다 — 이 한계를 화면에 적는다("되찾기가 디스크에 기록되지 않았다 — 다시 시도 중")
상태별     Idle → Reclaimed · Starting → STOP_BEFORE_GO · Reclaimed · RoundActive → CANCEL_ROUND(아래) · Reclaimed ·
           Running → 우선 정지 · StopPending · StopPending · Reclaimed → 그대로(같은 접수 번호) · StartupFault → Reclaimed(자식이 없다)
CANCEL_ROUND  자식은 Grant 검증 · ACK 보내기 · 작업 띄우기 **직전마다** 취소 깃발을 잠금 아래 확인하고, 서 있으면 멈추고 ROUND_CANCELLED 를 보낸다.
              이미 작업을 띄웠으면(WORKLOAD_STARTED 가 먼저 나감) ROUND_CANCELLED 대신 그 시도의 STOP 규칙으로 간다 — 루프는 WORKLOAD_STARTED 를 받으면 곧바로 STOP 을 보낸다
```

### 우선 정지 경로 (c1d ⑤)

지금 시도의 정지는 **단일 우선 경로**로 제어 파이프에 즉시 쓴다 — 남은 컨테이너 정지 큐(전역 동시 2 · 대기 8)와 섞지 않는다. 같은 시도의 정지가 진행 중이면 같은
접수 번호(single-flight). 큐 포화 · 표식 실패 · 조회 지연 어느 것도 이 경로를 막지 않는다.

### 회차 감독 수단 — 자식이 죽어도 루프가 끝낸다 (c1d ③ · I7)

```text
리눅스   루프가 회차마다 `<cgroup 부모>/gputeer-round-<generation>` 을 만들어 자식에 넘긴다(자식 자신은 그 밖에 둔다 — 내부 프로세스 금지 규칙).
         자식은 작업 cgroup 을 **그 안에** 만든다. 자식이 죽으면 루프가 round cgroup 에 cgroup.kill(하위 전체) → cgroup.procs 가 빌 때까지 확인 → 지운다.
         ★ 지금 부모 경로 검사는 "cgroup 루트 직속(깊이 1)" 만 받는다 — --loop-child 로 받은 round 경로는 깊이 2 를 허용하도록 검사를 넓힌다(루프가 만든 · 루프가 준
           경로만). 부모 경로를 따로 주지 않은 구성(기본 "내 cgroup")은 루프 모드에서 거부한다 — 루프가 감독할 곳이 없다
Windows  루프가 회차마다 round Job(KILL_ON_JOB_CLOSE)을 만들어 자식을 넣는다(CREATE_SUSPENDED → 편입 → 재개). 자식이 띄우는 작업은 그 Job 을 물려받고 작업 Job 에
         중첩 편입된다(Windows 8+ 중첩 Job — **예상, 재지 않았다** · 빠져나가는 옵션을 쓰지 않는 것은 코드로 확인). 자식이 죽으면 루프가
         TerminateJobObject(round Job, EXIT_CODE_OWNER_STOPPED) → 작업까지 끝난다. 루프가 죽으면 KILL_ON_JOB_CLOSE 로 같다
컨테이너  자식이 죽으면 루프가 이 Agent 의 owner 라벨로 다시 조회해 그 시도의 컨테이너를 남은 컨테이너 정지 경로로 멈춘다(결과는 아래 이름으로)
```

### 부모 확인 — `--loop-child` 는 누가 부를 수 있나 (c1d ④)

```text
확인      자식은 시작하자마자 (1) 부모 프로세스가 스냅샷에 적힌 루프 PID 이고 그 생성 시각이 같다(Windows 는 부모 프로세스 핸들을 상속받아 GetProcessTimes ·
          리눅스는 pidfd + /proc/<pid>/stat 의 시작 시각) (2) 자신이 루프의 round Job · round cgroup 안에 있다 (3) 스냅샷 digest 가 스냅샷에 적힌 것과 같다 — 하나라도
          아니면 GO 를 기다리지 않고 끝난다
한계      **같은 사용자 권한으로 도는 악성 호스트 작업(S0 · RESTRICTED)은 이 확인을 흉내 낼 수 있다** — 그 작업은 이미 소유자 계정의 모든 권한을 가졌다(런북 —
          "호스트 작업은 그 계정의 권한 전부를 갖는다"). 이 확인이 막는 것은 실수 · 다른 계정이다. 컨테이너 전용(S3) 노드에서는 작업이 호스트 계정 권한이 없어
          흉내 낼 수 없다(예상 — 컨테이너 탈출이 없다는 전제). §0.4 에 따라 "막는다" 고 쓰지 않는다
```

### 파이프 상속 금지 (c1d ⑬)

```text
Windows  자식은 시작 직후 자기 쪽 파이프 핸들의 상속 비트를 끈다(SetHandleInformation). 작업 spawn 은 PROC_THREAD_ATTRIBUTE_HANDLE_LIST 로 명시한 핸들만 넘긴다
리눅스   루프는 pipe2(O_CLOEXEC)로 만든다. 자식용 fd 만 pre_exec 에서 고정 번호(3 · 4)로 dup2 — dup2 결과는 CLOEXEC 가 꺼져 첫 exec 를 지난다.
         agent-stub 은 시작 즉시 그 두 fd 에 FD_CLOEXEC 를 다시 켠다. 작업 spawn 전 제어 fd 가 CLOEXEC 인지 확인 — 아니면 실행하지 않는다
```

## 정지 결과 — 자식 상태기계가 판정한다 (c1d ⑥)

```text
종료 관측이 STOP 수락보다 먼저                  → already_exited(손잡이를 부르지 않는다)
STOP 수락 → 손잡이 → 종료 관측                   Windows 호스트: 종료 코드가 EXIT_CODE_OWNER_STOPPED → owner_stop_observed · 다른 코드 → already_exited
                                               리눅스 호스트(cgroup SIGKILL) · **컨테이너(137 비-OOM)** → owner_stop_observed_ambiguous — 요청 뒤 멈춘 것은 맞지만
                                               같은 순간 스스로 같은 방식으로 끝난 것과 가르지 못한다(결함 524)
                                               컨테이너 ALREADY_EXITED → already_exited
STOP 뒤 종료를 관측하지 못함 · EOF · 손잡이 오류   → unknown(루프가 회차 감독 수단으로 끝냈다면 detail 에 적는다 — 그래도 원인 판정은 unknown)
```

★ owner_stop_observed(확정)는 **독립된 원인 증거가 있는 경로(Windows 전용 종료 코드)** 에만 쓴다. 작업이 우연히 그 코드로 끝나면 틀릴 수 있다(드물다 — 적는다).
GET /api/stop/<번호> → accepted · pending · owner_stop_observed · owner_stop_observed_ambiguous · already_exited · unknown. 접수 번호는 비영속(재시작 뒤 unknown).

## 남은 컨테이너 정지 — 자식 없이 루프가

확인한 ID 로 kill → 새 조회로 멈춤 확인. 결과 이름은 위와 같다(137 비-OOM 은 ambiguous). 지우지 · 로그를 거두지 · 사건을 해제하지 않는다. target 별 single-flight ·
전역 동시 2 · 대기 8 · 넘으면 429 — **지금 시도의 우선 경로와 따로**.

## 설정 — `--` 경계 그대로 · 한 번 파싱 (c1d ⑦ ⑨)

```text
문법      agent-loop [--interval-ms N] [--max-rounds N] [--owner-panel-port N] -- <agent 인자>. `--` 뒤에 --owner-panel-port 가 있으면 거부.

배포      agent.ps1 · 유닛: `--` 앞에 --owner-panel-port 만 옮긴다(T20)
```
