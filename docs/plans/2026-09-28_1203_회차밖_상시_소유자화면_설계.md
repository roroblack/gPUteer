## 불변식

```text
I1  루프 기동 순서: 인자 파싱 → 루트 잠금 · 실경로 → 패널 bind · 서비스 시작 → 되찾기 확인 → 기동 GC → (그 뒤에만) 자식.
    기동 GC 가 실패 · 지연하면 루프는 끝나지 않고 StartupFault 상태로 패널에 보이며 자식을 띄우지 않는다
I2  루프가 체크포인트 루트의 OS 잠금을 수명 전체 쥔다. 자식은 재잠금하지 않는다
I3  패널 생략은 내부 진입점 `agent-stub --loop-child` 하나뿐 — 아래 "부모 확인" 을 통과해야 한다. 단독 agent-stub 은 지금처럼 패널이 필수다
I4  제어 파이프 · round Job 핸들은 비신뢰 워크로드에 상속되지 않는다
I5  되찾기 · 회차 시작 · **작업 시작 허가** · 다시 켜기는 루프 잠금 아래 한 상태기계에서만 바뀐다(c1e ③)
I6  지금 시도의 정지는 디스크 · 큐 · 다른 정지를 기다리지 않는다 — 자식이 죽은 뒤의 정지도(c1e ④)
I7  루프가 회차의 작업을 끝낼 수단을 자식과 따로 쥔다. ★ **범위: 회차 울타리(리눅스 round cgroup · Windows round Job · 컨테이너)를 벗어나지 않은 작업.**

    확인한다), Windows 는 같은 계정의 다른 경로(작업 스케줄러 · WMI 등)로 Job 밖에 프로세스를 만들 수 있다(예상). 그런 프로세스는 루프가 **보지 못한다** —
    모든 호스트 작업의 정지 결과는 **울타리 기준**이다 — 아래 "정지 결과" 의 범위 표시(§0.4 · c1e ② · c1f ③).
    컨테이너 작업은 호스트 cgroup 에 접근할 수 없어 이 탈출이 없다(예상 — 컨테이너 탈출이 없다는 전제). 탈출 방지(별도 계정 · cgroup namespace)는 이 설계 범위 밖
```

## 루프의 상태기계

```text
상태   Idle · Starting(자식 띄움 · GO 전) · RoundActive(GO 뒤 · 작업 준비 전 — Coordinator 인사 · Grant 검증 · ACK) ·
       Running(시작 허가 뒤) · StopPending · Reclaimed · StartupFault
       ★ "준비됨(Prepared)" 은 루프에 머무는 상태가 아니다 — WORKLOAD_PREPARED 를 받는 순간 잠금 안에서 허가 · 버림을 정한다(아래 시작 관문).
         자식 쪽에서는 PREPARED 를 보낸 뒤 허가를 기다리는 동안이 준비됨이다
```

| 지금 상태 | 사건 | 다음 상태 · 한 일 |
|---|---|---|
| Idle | 회차 시간 · 표식 없음 | Starting — round_id · 스냅샷 · 회차 울타리 준비 → 자식 |
| Starting | READY(digest 일치) · 표식 없음 | RoundActive — GO |
| Starting | REFUSED · EOF · 불일치 | Idle(울타리 정리 · 스냅샷 삭제) |
| RoundActive | WORKLOAD_PREPARED | **루프 잠금 아래** 되찾기 여부를 다시 보고: 아니면 Running 으로 바꾼 **뒤** START_WORKLOAD · 되찾기면 DISCARD_PREPARED → Reclaimed |
| RoundActive | WORKLOAD_NOT_STARTED(일 없음 · 거부) · EOF | Idle(울타리 정리) |
| Running | WORKLOAD_ENDED | Idle(울타리 정리 — 결과 줄은 "마지막 회차") |
| Running | WORKLOAD_NOT_STARTED{exec_failed}(허가 뒤 도우미의 execve 실패 — c1k ③) | 울타리 정리(도우미는 이미 exit) → Idle · 결과 줄 "실행 실패(errno)" · 되찾기 표식은 그대로(없으면 Idle) |
| Running | EOF(자식 사망 · 결과 없음) | 감독 우선 경로로 울타리 안 작업을 끝낸다(아래) → Idle · 결과 unknown · 사건 기록 |
| 모든 상태 | **reclaim**(패널) | 아래 "되찾기" |
| StopPending | STOP_RESULT | Reclaimed(결과 보관) |
| StopPending | WORKLOAD_ENDED(STOP_RESULT 전) | 결과를 자식 판정 규칙으로 — 대개 already_exited · Reclaimed |
| StopPending | WORKLOAD_NOT_STARTED{exec_failed}(되찾기와 실행 실패가 겹침) | 울타리 정리 → Reclaimed · 정지 결과는 already_exited(실행되지 않았다 — 정지 손잡이를 부르지 않는다) |
| StopPending | EOF | 감독 우선 경로로 끝냄 → Reclaimed · unknown |
| Reclaimed | resume(패널) | Idle — 표식 삭제 |
| StartupFault | 운영자가 원인 해결 뒤 패널 "다시 시도" | 기동 GC 재시도 → Idle 또는 StartupFault |

### 시작 관문 — 작업을 띄울지는 루프가 정한다 (c1e ③)

두 프로세스가 같은 잠금으로 "취소 확인 → 띄우기" 를 원자화할 수 없다. 그래서 자식은 작업을 **실행할 수 없는 상태로 준비만** 하고, 실제 시작은 루프의 허가를 받는다.

```text
준비(자식)     Windows   지금 경로 그대로 — CREATE_SUSPENDED · Job 편입 · 손잡이 준비. 재개하지 않는다
              리눅스     pre_exec 안에서 막지 않는다(위 사실 11 — spawn() 이 돌아오지 않아 교착한다 · c1f ①). 대신 **작은 관문 도우미**를 띄운다:
                        spawn 대상은 Agent 자신의 실행 파일(`/proc/self/exe` 를 연 fd 로 — 경로를 다시 풀지 않는다)의 내부 모드 `--gate-exec <관문 fd>` 이고,
                        pre_exec 는 cgroup 편입만 한다 — ★ **비동기 신호 안전 호출만**(c1h ④ — 지금 코드는 pre_exec 안에서 std::fs::write 를 부르고
                        스스로 다중 스레드 교착 위험을 적어 뒀다 · runtime-linux:397~414). 부모가 fork **전에** 목적지 cgroup.procs 를 열어 두고, pre_exec 는
                        그 fd 에 raw write(2) 로 "0"(자기 자신) · prctl · getppid · dup2 · fcntl · close 만 부른다(할당 · 잠금 없음) →
                        도우미가 exec 에 **성공**하면 spawn() 이 돌아온다 →
                        도우미는 **0 · 1 · 2 · 관문 읽기 fd · 결과 쓰기 fd** 말고 모든 fd 를 닫고(close_range — 두 fd 는 예외로 남긴다) → 결과 쓰기 fd 에
                        FD_CLOEXEC 를 켠다(도우미 자신의 exec 는 이미 지났다 — 그래서 결과 fd 는 도우미 exec 까지는 CLOEXEC 없이 넘기고, 도우미 안에서 켠다 · c1k ①)
                        → 관문을 읽는다 → **허가 메시지**(길이 + 진입점 · 인자 · 환경 전체)를
                        받으면 실행한다 · EOF 이거나 깨진 메시지면 exit(127).
                        ★ 실행 파일 찾기(c1h ③ · c1i) — 지금은 Rust `Command::new` 라 `python` 같은 경로 없는 이름을 PATH 에서 찾는다. 도우미의 규칙:
                        · 이름에 `/` 가 없으면 도우미가 **직접** 허가 메시지 환경의 PATH 를 왼쪽부터 훑어 실행 가능한 첫 파일을 고른다(libc 의 execvpe 는
                          **호출자** 환경의 PATH 를 쓰므로 부르지 않는다) → 고른 절대 경로로 execve
                        · 허가 환경에 PATH 가 없으면 지금 `Command::new` 가 쓰는 기본 검색 경로와 같은 값을 쓴다
                        · 실행 형식을 모르는 파일(ENOEXEC — shebang 없는 스크립트 등)의 처리도 지금 `Command::new` 와 같게 한다
                        · "같게" 는 말로 두지 않는다 — **대조 시험**(T4d)이 같은 입력을 지금 경로와 도우미 경로로 각각 돌려 결과(실행된 파일 · 종료 코드 ·
                          오류 종류)가 같은지 본다. 다르면 도우미를 고친다
              ★ 실행 결과 채널(c1j) — 허가를 보냈다고 작업이 시작된 것이 아니다. 도우미의 execve 가 실패할 수 있고, 그 실패와 "작업이 127 로 끝남" 은
                        종료 코드만으로 가를 수 없다. 그래서 Rust 표준 라이브러리의 spawn 이 쓰는 방식을 그대로 쓴다:
                        자식이 **결과 파이프**를 하나 더 만들어 쓰기 끝을 도우미에 넘긴다. 도우미는 그 fd 에 FD_CLOEXEC 를 켜 둔다 →
                        execve 가 **성공**하면 커널이 그 fd 를 닫아 자식은 0바이트 EOF 를 받는다 · **실패**하면 도우미가 errno(4바이트)를 쓰고 exit(127) →
                        ★ EOF 는 "exec 성공" 의 증거가 **아니다**(c1k ②) — 도우미가 exec 전에 죽어도 쓰기 끝이 닫혀 EOF 다. 가르는 규칙:
                          EOF 뒤 도우미 PID 가 **살아 있고** /proc/<pid>/exe 가 Agent 실행 파일이 아니면 → exec 확인(exec_confirmed=true)
                          EOF 뒤 이미 끝났거나 확인하지 못함 → exec 여부 **모름**(exec_confirmed=false) — 그래도 WORKLOAD_STARTED 로 다룬다
                        ★ EOF 가 **오지 않을 수 있다**(c1l) — 파이프는 모든 쓰기 끝이 닫혀야 EOF 다. 그래서:
                          (1) 자식은 spawn() 이 돌아오면 **곧바로 자기 쪽 결과 쓰기 끝을 닫는다**(자식 쪽 사본은 pipe2(O_CLOEXEC) 로 만든 것이고, 도우미에게 넘길
                              사본만 pre_exec 에서 CLOEXEC 없는 번호로 옮긴다 — 관문 파이프와 같은 절차)
                          (2) 그래도 자식이 **동시에** fork 한 다른 프로세스가 exec 전에 멈추면 그 사본이 EOF 를 늦춘다. 그래서 결과 기다림에 **기한**(10초 —
                              예상값 · 설정)을 둔다. 기한 안에 errno 도 EOF 도 없으면 도우미 PID 를 본다: 살아 있고 /proc exe 가 Agent 가 아니면 exec_confirmed=true ·
                              그 밖에는 exec_confirmed=false — 어느 쪽이든 WORKLOAD_STARTED(안전한 방향). 기한 뒤 늦게 errno 가 오면 사건으로 적는다
                              (이미 "시작함" 으로 보냈다 — 결과는 관측한 종료 상태를 따른다)
                          (3) 결과 기다림은 **따로 된 스레드**에서 한다 — 그동안에도 제어 채널의 STOP 을 받아 손잡이(이미 준비된 작업 cgroup)를 쓴다.
                              기다림이 STOP 처리를 막지 않는다
                          (돌았을 수 있는 시도를 "시작 안 함" 으로 적지 않는다 — 두 벌 실행 쪽의 안전한 방향). 그 시도의 결과는 관측한 종료 상태 그대로이고
                          exec_confirmed=false 가 보고에 실린다 — 성공으로 확정하지 않는다
                        "시작 안 함"(WORKLOAD_NOT_STARTED) 은 **errno 를 받았을 때만** — 그것만이 exec 가 일어나지 않았다는 증거다.
                        자식은 EOF(0바이트)일 때 WORKLOAD_STARTED 를 보내고, errno 를 받으면 지금 경로와 같은 실행 실패(SpawnFailed —
                        runtime-linux:419~425)로 WORKLOAD_NOT_STARTED{exec_failed, errno} 를 보낸다. 결과 파이프도 관문 파이프와 같은 fd 규칙(비동기 신호 안전 ·
                        그 밖의 fd 는 close_range)을 따른다
              ★ 사용자 코드 0줄의 조건(c1g ④) — 도우미는 **빈 환경**(env_clear)으로 띄운다: LD_PRELOAD · LD_AUDIT · LD_LIBRARY_PATH 같은 로더 변수가 도우미의
                        main 보다 먼저 코드를 싣지 못하게. 작업의 진짜 환경은 허가 메시지에 실려 execve 때에만 쓰인다 — 무엇을 실행할지도 허가 전에는 도우미가 모른다.
                        ★ 남는 것: 시스템 전역 `/etc/ld.so.preload`(root 만 쓴다)는 빈 환경으로도 막지 못한다 — root 가 심은 것은 이 설계 범위 밖(§0.4)
              관문 파이프  자식(agent-stub)이 pipe2(O_CLOEXEC)로 만든다. 도우미에게 넘기는 읽기 끝만 CLOEXEC 를 끈 번호로 옮긴다(아래 fd 절차와 같다).
                        **쓰기 끝은 CLOEXEC 그대로** — 도우미의 exec 순간 도우미 쪽 사본이 닫힌다. 그 뒤 쓰기 끝을 가진 것은 자식 하나뿐이다(c1f ②).
                        자식이 동시에 다른 것을 spawn 해도 쓰기 끝은 CLOEXEC 라 새지 않는다
                        → 자식이 죽으면 쓰기 끝이 모두 닫혀 도우미의 읽기가 EOF → exit(127)
              회차 자식 자신(c1h ①) — PR_SET_PDEATHSIG 는 fork 로 물려받지 **않는다**. 그래서 루프가 회차 자식(agent-stub --loop-child)을 띄울 때도
                        pre_exec 에서 PR_SET_PDEATHSIG(SIGKILL) → getppid() 가 루프인지 재확인(아니면 exit) 을 따로 건다. 자식은 **제어 채널 EOF** 를 받으면
                        허가 없이 끝난다(준비만 한 작업은 버린다 · 돌던 작업은 정지 손잡이로 끝낸다). 그리고 systemd 가 루프(서비스 주 프로세스)의 죽음을 보면
                        유닛 cgroup P 전체 — round cgroup 포함 — 를 KillMode=control-group(기본값)으로 끝낸다(예상 — systemd 문서의 기본 동작 · T27 로 확인)
              ★ EOF 만 믿지 않는다(c1g ⑤) — 자식이 **동시에** fork 한 다른 프로세스는 exec 전까지 쓰기 끝 사본을 쥔다(CLOEXEC 는 exec 때 닫는다 ·
                        pre_exec 정체는 runtime-linux:397~414 가 스스로 적은 위험). 그래서 도우미는 두 가지를 더 쓴다:
                        (1) pre_exec 에서 PR_SET_PDEATHSIG(SIGKILL) · 곧바로 getppid() 가 자식인지 확인(이미 죽었으면 exit) — 자식이 죽으면 커널이 도우미를 끝낸다
                        (2) 도우미는 작업 cgroup 안에 있다 — 루프의 round cgroup.kill 이 함께 끝낸다. EOF 는 세 수단 중 하나다
              컨테이너   create 까지만(라벨에 round_id) — start 하지 않는다
              → WORKLOAD_PREPARED{round_id, attempt_id, job_id, submitter_device_id, entrypoint, container_name?} 를 보낸다
결정(루프)     잠금 아래: 되찾기가 없으면 상태를 Running 으로 **먼저** 바꾸고 START_WORKLOAD 를 보낸다. 되찾기면 DISCARD_PREPARED.
              ★ 이 순간 이후의 되찾기는 전부 STOP 경로다 — "허가를 보낸 뒤 되찾기" 와 "되찾기 뒤 허가" 가 루프 잠금 하나로 갈린다
시작(자식)     START_WORKLOAD → Windows 재개 · 리눅스 관문에 허가 메시지 → **결과 파이프 EOF 확인 뒤** · 컨테이너 start → WORKLOAD_STARTED
              (리눅스에서 결과 파이프로 errno 가 오면 WORKLOAD_NOT_STARTED{exec_failed} — 실행 실패는 시작이 아니다)
버리기(자식)   DISCARD_PREPARED → Windows TerminateProcess(일시정지된 것) · 리눅스 관문 쓰기 끝을 닫음(EOF → 도우미 exit) · 컨테이너 rm → WORKLOAD_NOT_STARTED(소유자 되찾기)
자식 사망      준비된 것은: Windows 는 round Job 에 있어 루프가 끝낸다 · 리눅스는 관문 쓰기 끝이 닫혀 EOF → 도우미 exit · 컨테이너는 created 로 남아 round_id 라벨로 찾아 지운다
보장의 경계    **허가 전 되찾기** — 작업의 사용자 코드는 한 줄도 돌지 않는다(Windows 일시정지 · 리눅스 도우미 대기 · 컨테이너 created).
              **허가 뒤 되찾기** — START_WORKLOAD 가 이미 나갔으면 자식이 그것을 읽고 작업이 **잠깐 시작한 뒤** STOP 을 받는다. 이 경우 "한 줄도 안 돈다"
              를 보장하지 않는다 — 정지 결과 규칙을 따른다(c1f ④)
Coordinator   ACK 는 지금처럼 실행 전에 간다. 되찾기로 버리면 그 시도는 "시작 안 함(소유자 되찾기)" 로 보고한다 — 보고 방식은 단계 2 계약을 따른다
대가           한 번의 파이프 왕복(밀리초 단위 — 예상)
```

### 되찾기 — 어느 상태에서든, 정지가 먼저

```text
순서       ① 메모리 상태를 Reclaimed(또는 StopPending)로 **먼저** 바꾼다(루프 잠금 아래 — 이 순간부터 새 회차 · GO · START_WORKLOAD 없음)
           ② 지금 시도가 있으면 곧바로 정지를 보낸다(우선 경로)

              ★ 표식이 없는 채 루프가 죽으면 다음 루프는 되찾기를 모른다 — 화면에 적는다("되찾기가 디스크에 기록되지 않았다 — 다시 시도 중")

           Running → 우선 정지 · StopPending · StopPending · Reclaimed → 그대로(같은 접수 번호) · StartupFault → Reclaimed(자식이 없다)
```

### 회차 울타리 — 만들기 · 끝내기 · 치우기 (c1e ① ⑥)

```text
리눅스   **위임 부모 = 루프 서비스 자신의 cgroup**(c1g ①). cgroup 사이를 옮기려면 목적지뿐 아니라 **출발지와 목적지의 공통 조상**의 cgroup.procs 에도 쓸
         권한이 있어야 한다(커널 cgroup v2 문서). 서비스 cgroup(`system.slice/gputeer-agent@<노드>.service`)에서 시작한 Agent 가 `/sys/fs/cgroup/gputeer-<노드>`
         (지금 `--workload-cgroup-parent` 가 받는 루트 직속 형태 — runtime-linux:600~630)로 작업을 옮기면 공통 조상이 루트라 비-root 는 거부된다.
         그래서 루프 모드는: 유닛에 `Delegate=yes` → systemd 가 서비스 cgroup 을 Agent 계정에 위임 → 루프는 기동 때 `/proc/self/cgroup` 으로 자기 cgroup P 를
         읽고, P 와 그 cgroup.procs · cgroup.subtree_control 이 자기 계정 것인지 확인(아니면 호스트 모드 거부) → 자신을 `P/loop`(잎)로 옮기고 → P 의
         subtree_control 에 +memory → 회차마다 `P/gputeer-round-<round_id>` 를 만든다. 자식(agent-stub)은 `P/loop` 에서 태어난다(round 밖).
         작업은 `P/loop` → `P/gputeer-round-…/<작업>` 으로 옮겨지고 공통 조상은 P(위임됨)다.
         round 는 프로세스를 직접 담지 않고 작업 cgroup 만 담는다(내부 프로세스 금지 규칙). 자식은 작업 cgroup 을 그 안에 만든다.
         ★ 단독 agent-stub(루프 아님)의 `--workload-cgroup-parent`(루트 직속만) 검사는 그대로 둔다 — 루프 모드만 위 규칙을 쓴다
         ★ 자식이 받는 round 경로의 검사 — "깊이 2 허용" 으로 넓히지 않는다. 받아들이는 것은 정확히:
           canonical(round 경로)의 부모 == 루프가 기동 때 확인한 canonical P(스냅샷에 적힘) · 이름 == `gputeer-round-<round_id>` · round_id 가 INIT 메시지의 것과 같음 ·
           경로는 **제어 채널**(INIT)로만 받는다(argv 아님). 다른 round · 임의 깊이 2 · 심볼릭 링크 교체 → 거부
         끝내기: round 의 cgroup.kill(하위 전체)
         치우기: round 의 `cgroup.events` 가 `populated 0` 이 된 것을 확인 → 알려진 작업 cgroup 을 아래에서부터 rmdir → 마지막에 round rmdir.
         (round 의 cgroup.procs 는 처음부터 비어 있다 — 그것으로 판정하지 않는다.) 확인 실패 · 시한 초과면 지우지 않고 사건
Windows  루프가 회차마다 round Job(KILL_ON_JOB_CLOSE)을 만들어 자식을 넣는다(CREATE_SUSPENDED → 편입 → 재개). **round Job 핸들은 루프만 쥔다 —
         상속되지 않는 핸들이고 자식에게 복제해 주지 않는다**(자식이 쥐면 루프가 죽어도 Job 이 닫히지 않는다). 자식이 띄우는 작업은 round Job 을
         물려받고 작업 Job 에 중첩 편입된다(Windows 8+ 중첩 Job — 문서상 가능 · 재지 않았다 · 지금 코드에 빠져나가는 옵션이 없는 것은 확인).
         자식이 죽으면 TerminateJobObject(round Job, EXIT_CODE_OWNER_STOPPED) · 루프가 죽으면 KILL_ON_JOB_CLOSE
컨테이너  create 때 `gputeer.round=<round_id>` · `gputeer.loop=<loop_instance_id>` 라벨(바뀌지 않는다). 자식 사망 뒤 감독 우선 경로가 이 라벨로 찾는다
```

### 파이프 상속 금지 (c1e ⑤)


## 하지 않는 것

- 런타임을 거치지 않는 컨테이너 정지(단계 4) — 런타임이 멈추면 컨테이너 정지 결과는 unknown
- 같은 계정 호스트 작업의 울타리 탈출을 막는 것(별도 계정 · cgroup namespace — I7)
- 남은 컨테이너 삭제 · 로그 수집 · 사건 해제를 패널에서 하는 것
- Coordinator 에 불명 · 정지 확인을 알리는 것(단계 2 계약)
- 같은 사용자 권한의 악성 호스트 작업을 막는 것(§0.4 — "부모 확인" 한계)
