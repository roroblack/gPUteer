# 운영자 inventory 반입 (operator bootstrap import)

**작성**: 2026-09-02
**상태**: 진행 중

## 왜 이것인가

부품은 거의 다 있는데 **이어지지 않아** Job 을 실제로 돌릴 수 없다.
끊긴 곳이 넷이고 ① 은 끝났다.

```text
① Job 투입      gputeer import-manifest 가 durable job store 에 넣는다.  ✅
② scheduler     orchestrate 가 완성돼 있는데 production 호출자가 없다.
③ Grant 발급    Coordinator 가 CLI 인자로 받은 ID 로만 Grant 를 만든다.
④ 데몬화        coordinator-stub / agent-stub 은 한 번 돌고 끝난다.
```

② 를 조사했더니 하루를 넘었다 — production inventory ingress · authoritative
device→member projection · `SUBMITTED→QUEUED` 호출자가 전부 없어 610~990줄이다.
그중 **첫째만** 떼어낸 것이 이 조각이다.

★ **빈 inventory 로는 아무 노드도 못 고른다.** scheduler 커널이 아무리
완성돼 있어도 후보 목록이 비어 있으면 고를 것이 없다. 이 조각이 그
목록을 처음으로 채운다.

## ★ 이름이 왜 "반입" 이고, 왜 "검증" 이 아닌가

독립 설계 조사가 확인했다 — **서명된 inventory 문서가 이 저장소에 없다.**

```text
AgentRegistry · AgentInventory   proto 아님. coordinator crate 의 Rust 구조체
서명 domain 목록                 inventory/bootstrap domain 없음
NodeHeartbeat                    서명 대상이지만 짧은 수명 자기보고다.
                                 inventory 전체나 등록 승인을 서명하지 않는다
ApproveDevice.owner_signature    있기는 하다. 그러나 이것을 검증해
                                 authoritative membership 을 만드는 경로가 없다
```

① 은 "제출자 서명 + 운영자 keyring" 이라는 대응물이 있었다. 여기엔 없다.

**그래서 신뢰 경계가 암호가 아니다** — 이 명령을 실행할 권한과 그 파일의
OS 권한이다. 이 명령이 정직하게 주장할 수 있는 것은 이것뿐이다:

> 운영자가 준 서명 없는 bootstrap 문서를 지원 스키마로 해석하고,
> 필드 정합성·충돌·revision·영속성을 검사한 뒤 원자적으로 반입했다.

증명하지 **못하는** 것:

```text
못 한다   이 Agent 가 실제로 그 키를 가졌는지
못 한다   보고된 GPU 가 실재하는지
못 한다   그 노드가 지금 살아 있는지
못 한다   owner membership 이 유효한지
```

★ 출력과 문서에서 **"verified"·"검증됨" 이라는 말을 쓰지 않는다.**
  더 강한 주장을 하려면 `InventoryBootstrap` proto + canonical + `Signable`
  + operator keyring 정책까지 필요하고 그건 하루를 넘는다(조사 판정:
  production 750~1,050줄).

## ★ 두 API 를 이어 붙이면 안 된다

조사가 찾은 가장 무거운 것이다.

```text
register_agent()      입력 검증 -> BEGIN IMMEDIATE -> commit    (자기 transaction)
update_inventory()    입력 검증 -> BEGIN IMMEDIATE -> commit    (별도 transaction)
```

CLI 에서 순서대로 부르면, **등록이 커밋된 뒤** inventory 갱신이 node 불일치·
revision 충돌·I/O 로 실패했을 때 registry 만 남는다 — ① 이 지켜 온
**"거부하면 DB 가 안 바뀐다"** 가 그대로 깨진다.

그래서 저장소에 새 원자 API 를 넣는다:

```rust
import_bootstrap(&mut self, entries: &[AgentBootstrap])
```

**입력만으로 판정할 수 있는 것은 잠그기 전에** 전부 검사한다 — 모양,
두 반쪽의 node_id 일치, 각 반쪽 자체의 유효성. 그 다음 **하나의
`BEGIN IMMEDIATE` 안에서** 항목을 차례로 쓴다.

★ 저장된 행을 봐야 아는 것(identity 충돌·revision 순서)은 잠금 밖으로
  못 옮긴다 — 그건 입력이 아니라 **DB 에 대한 질문**이다. 그래서 그
  검사들은 쓰기와 섞여 항목별로 일어난다. 원자성은 트랜잭션이 지키지
  실행 순서가 지키는 게 아니다(독립 검수 1라운드가 이 서술의 부정확을
  짚었다).

★ 검증이 잠금 **밖**이어야 하는 이유 — 안에 두면 잘못된 입력을 바쁜
  DB 에 주었을 때 `InvalidInput` 대신 `LockTimeout` 이 난다. 입력 오류가
  경합 오류로 보고된다(`CLAUDE.md` §3). 리팩터가 실제로 그 순서를
  뒤집었고 검수가 잡았다.

## 무엇을 만드는가

```text
gputeer import-inventory
    --inventory <파일>       운영자가 만든 strict JSON bootstrap 문서
    --inventory-db <경로>    durable inventory store
```

★ **영속성 판정을 다시 만들지 않는다.** `CoordinatorInventoryStore` 에
  이미 `is_durable()` 이 있고 `:memory:` 와 빈 경로를 둘 다 거부한다 —
  ① 에서 같은 판정을 두 곳에 뒀다가 한쪽만 낡았던 실수를 되풀이하지
  않는다. 저장소에 물어본다.

## 무엇을 거부하는가

저장소가 **이미** 막는 것과 이 명령이 **새로** 막아야 하는 것을 나눈다 —
이미 막는 것을 다시 구현하면 두 판정이 어긋난다(① 의 교훈).

```text
저장소가 이미 막는다
  빈/공백 node_id · device_id · owner_member_id
  32바이트 아닌 key
  빈 gpu_id · 중복 GPU ID · 빈 model 문자열
  낮은 revision · 같은 revision 다른 payload
  다른 node 가 같은 device_id/key 를 주장

이 명령이 새로 막는다
  지원하지 않는 schema_version
  모르는 필드 · 중복 필드
  registry 와 inventory 의 node_id 불일치
  한 파일 안의 중복 node(정확히 같아도 거부 — 모호하다)
  hex 형식 · 실제 Ed25519 공개키로 해석되는지
    ★ 저장소는 임의 32바이트를 허용한다. 여기서 좁힌다
  미래 timestamp
  scheduler 가 요구하는 fact 의 누락/null
    ★ 저장소는 unknown fact(None)를 **의도적으로 허용**한다.
      그건 저장소 결함이 아니라 계약이다. 그러나 이 명령이 "고를 수
      있는 후보를 만든다" 고 말하려면 CLI 계층에서 더 엄격해야 한다
```

★ **명시적 0 과 unknown 을 혼동하지 않는다.** 빈 GPU 배열·빈 workload
  집합·0 인 자원은 "관측된 0" 이고 저장소가 그대로 보존한다. 누락과
  다르다.

★ 거부 사유를 뭉개지 않는다(`CLAUDE.md` §3). 다만 **안정된 오류 코드는
  주지 않는다** — 저장소의 `Display` 문장을 `BOOTSTRAP_REJECTED:` 뒤에
  그대로 붙인다. revision 이 뒤로 갔는지, 같은 revision 에 다른 내용인지,
  DB 가 손상됐는지, 잠금이 안 풀렸는지가 문장으로 구별된다.
  초안은 `LOWER_REVISION` 같은 코드 이름을 나열했는데 **그런 코드는
  구현하지 않았다** — 있는 것처럼 적으면 안 된다(독립 검수 1라운드).

## 이 조각이 실제로 무엇을 만드는가

integration test 로 끝까지 묶는다:

```text
1  CLI 로 완전한 Agent 한 벌을 durable DB 에 반입
2  새 store 로 그 DB 를 다시 연다
3  pool_snapshot(now) 이 그 node 를 revision/GPU/자원/정책과 함께 돌려주는가
4  evaluate_eligibility() 에 완전한 JobRequirements 를 넣어 SingleEligible 인가
```

⇒ **scheduler 커널이 고를 수 있는 노드가 처음으로 생긴다.**

## 정직하게 남기는 한계

```text
서명 없음          신뢰 경계가 파일 권한이다. "verified" 라고 쓰지 않는다
멤버십 권위 없음    device→member authoritative 해석은 이 조각이 안 만든다
지속 갱신 없음      observed_at 은 시간이 지나면 stale 이 되고 scheduler 가
                   거부한다. 계속 갱신하는 producer 가 따로 필요하다
liveness 미연결     node_liveness_store 가 생겼지만 그 값이 inventory 의
                   node_state 를 갱신하는 projection 은 아직 없다
production 미연결   orchestrate 는 여전히 pub(crate) 이고 호출자가 없다
```

★ **장래 함정 하나를 미리 적어 둔다** — staging 예약이 **자기 DB 의**
  `coordinator_agent_inventory` revision 과 GPU child row 를 직접 읽는다
  (`staging_store.rs:378-389`, `789-819`). production 에서는 inventory DB 와
  job/staging DB 를 **같은 SQLite 파일**로 정하든지 이 결합을 재설계해야
  한다. 서로 다른 파일을 쓰면 후보 선택은 되는데 예약 CAS 가 안 붙는다.

## 규모

production 380~520줄, 테스트 450~650줄 — 독립 설계 조사의 산정이다.
서명 체계까지 만들면 하루를 넘는다(같은 조사 판정).
