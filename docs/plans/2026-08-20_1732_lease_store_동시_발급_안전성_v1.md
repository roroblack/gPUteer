# 2026-08-20_1732 · Lease store 동시 발급 안전성 v1

- 기준선: 로드맵 조각 7("다중 Agent selftest") 설계 조사
- 대상 단계: scheduler 도입 전 정직하게 검증 가능한 storage-level 최소 조각
- 스트림: Coordinator 테스트 · 문서

## 설계 조사 결론

로드맵 조각 7 원안의 진짜 "다중 Agent 동시 경쟁"은 현재 아키텍처로
표현할 수 없다. Coordinator `run()`은 `accept_with_deadline()` 뒤
`serve_one_connection()`을 동기 호출하고, 한 handler가 끝난 뒤에야 다음
`accept()`로 진행한다. 따라서 두 handler가 병렬 실행되지 않는다.

또한 Coordinator 설정은 `agent_device_id`와 Agent 검증 키를 각각 하나만
가지며, `connection_attempt`도 Agent별 값이 아니라 Coordinator 전체의
accept 순번이다. 두 번째 독립 Agent는 동시 handler 경쟁에 도달하기 전에
identity/key 계약과 connection-attempt 의미에서 막힌다. 이것을 제대로
지원하려면 병렬 accept/handler, Agent별 identity/key 디렉터리, Agent별
connection-attempt 및 active-session ownership을 함께 설계해야 한다.
구현·검증 예상 비용은 최소 2~4일이며 scheduler 단계에서 다룬다.

## 이번 조각이 좁혀 검증하는 것

이번 조각은 wire-level 다중 Agent를 흉내 내지 않는다. 현재 코드가 실제로
주장하지만 측정하지 않았던 storage-level 위험 하나만 검증한다.
`CoordinatorLeaseStore::get_or_issue()`가 `BEGIN IMMEDIATE`로 SELECT 전에
write lock을 얻어, 같은 `lease_id`의 동시 최초 발급 check-then-insert를
직렬화하고 identity 혼합이나 부분 덮어쓰기를 막는다는 주장이다.

통합 테스트는 임시 파일 DB의 스키마를 먼저 만든 뒤, 매 라운드마다 두
스레드가 각자 같은 파일에 별도 `CoordinatorLeaseStore` 연결을 열고
`Barrier` 직후 같은 lease identity를 동시에 최초 발급한다. 후보는
`holder_node_id`만 다르다. 정확히 한 후보만 성공해야 하며 패자는
`holder_node_id` `IdentityConflict` 또는 안전한 `LockTimeout`이어야 한다.
timeout이면 경합 종료 뒤 순차 재시도가 반드시 identity conflict로 수렴해야
한다. 최소 10회보다 많은 16개 `lease_id` 라운드를 수행하고, 마지막에는
별도 raw SQLite 연결로 모든 identity·epoch·시각 컬럼을 직접 읽어 각 행이
완전한 승자 값인지 확인한다.

## 범위 밖과 명시적 이월

- 한 Coordinator의 병렬 accept/handler 및 scheduler
- 서로 다른 Agent key/identity 디렉터리와 Agent별 `connection_attempt`
- 두 Agent의 실제 wire-level Renew/Resume 동시 실행
- 동일 identity를 복제한 Agent 중 active-session owner 선정
- 다중 Coordinator HA와 범용 durable request ledger
- 테스트가 실제 결함을 찾지 않는 한 Coordinator/Agent 프로덕션 코드 수정

로드맵 조각 7 원안인 "같은 프로세스 안 시나리오·fault injection·다중
Agent 경쟁" 전체는 이번 조각으로 완료 처리하지 않는다. 원안은 다중 Agent
아키텍처를 도입하는 scheduler 단계까지 명시적으로 미룬다. 이번 결과가
입증하는 범위는 파일 기반 SQLite Lease store의 동시 최초 발급 안전성뿐이다.

## 독립 검수 후속 보강 (2026-08-20)

독립 검수에서 최초 후보 두 개가 `holder_node_id` 외 저장 값이 같아, raw
SQLite 최종 행의 `assert_eq!`가 패자 값의 부분 혼입을 구별하지 못한다는
차단 결함이 확인됐다. 후속 구현에서는 후보 A/B에 다음 표식을 사용한다.

- 공통: 같은 `lease_id`·`job_id`·`attempt_id`. 특히 identity 비교에서
  `holder_node_id`보다 앞선 `job_id`·`attempt_id`를 같게 유지한다.
- A/B 구별: `holder_node_id=node-a/node-b`, `fence_epoch=1000/2000 + round`,
  `issuing_coordinator_id=coordinator-a/coordinator-b`,
  `coordinator_term=101/202`, `issued_at_unix_ms`·`renew_after_unix_ms`·
  `expires_at_unix_ms` 각각에 `1000/2000 + round` 오프셋,
  `max_total_duration_seconds=60/61`.
- `revoked_at_unix_ms`는 최초 발급 INSERT가 후보 입력과 무관하게 항상
  `NULL`로 쓰는 lifecycle 상태이므로 두 후보 모두 `None`을 유지한다.

실제 `check_identity_conflict()` 순서가 `job_id -> attempt_id ->
holder_node_id -> issuing_coordinator_id`임을 확인했다. 따라서 coordinator
표식까지 달라도 충돌은 계속 `IdentityConflict { field:
"holder_node_id" }`에서 먼저 확정된다.

최종 검증은 `(winner, loser)`를 함께 보존하고 raw SQLite 행 전체가 winner와
`assert_eq!`인지 검사한 뒤, 위 8개 구별 필드가 loser 값과 각각
`assert_ne!`인지 명시적으로 검사한다. 별도 self-check 테스트는 winner
복제본의 8개 필드를 하나씩 loser 값으로 바꾸고 같은 최종 검증 helper가
각 경우 실제 panic하는지 `catch_unwind`로 확인한다.
