# 2026-08-20_0310_job_시작_마커_최소_조각_v1

- **기준선:** `../gputeer_master_plan_FINAL.md` §16(Agent 실행)·
  §27.2(Job 상태 흐름 `SUBMITTED→PLANNING→QUEUED→STAGING→RUNNING→COMPLETED`),
  `crates/checkpoint`(오늘 `DoD-21` 이 `write_once()` 동시 호출
  계약을 강제했다)
- **대상 단계:** v0.1 — scheduler·다중 Agent 이전 단계에서 착수
  가능한, Job 실행을 향한 **가장 작은 첫 걸음**
- **선행 게이트:** 없음 — 기존 Grant/Lease handshake·checkpoint
  인프라만 재사용한다
- **상태:** **설계 완료(코덱스 `p154`, read-only). 구현 미착수.**
  다음 조각에서 구현할 후보로 등록만 해둔다 — 지금 세션은 코드를
  건드리지 않았다.

★ 이 문서는 코덱스(`agent:codex-cli`, read-only 샌드박스)의 설계
조사 응답(`p154` 프롬프트)을 정리한 것이다.

## 왜 이 조각이 필요한가

`crates/agent` 는 지금 `Grant`/`Lease` 검증 → `AgentGrantAck` 전송
→ Lease 갱신/revoke 처리 → `RESULT ok=true` 출력 후 종료, 여기서
멈춘다(`crates/agent/src/lib.rs:96~418`). `JobManifest.entrypoint`
·`args`·`env`·`grant.plan` 은 이미 proto 에 있지만 **아무 데도
쓰이지 않는다.** 즉 지금 `RESULT ok=true` 는 "Job 을 완료했다" 는
뜻이 아니라 "handshake/stub 이 성공했다" 는 뜻일 뿐이다 — 이
간극을 메우는 가장 작은 첫 걸음을 찾는다.

## 실측 (설계 단계, `p154`)

- `JobManifest`·`ExecutionGrant` 는 이미 `proto/job.proto:41,103`
  에 있고 `crates/protocol/src/signable.rs:40` 에 canonical/signing
  구현도 있다.
- `control.proto` 의 `SubmitJob`/`TransitionJob`/`CreateAttempt`/
  `TransitionAttempt` 는 있지만 실제 Agent 실행 경로에 연결된 wire
  RPC 가 아니다.
- `crates/checkpoint::durability::record_initial_state()`
  (`crates/checkpoint/src/durability.rs:140`)가 `WRITING` 마커를
  이미 write-once 로 기록할 수 있다 — 매니페스트 없는 디렉터리는
  기존 `write_checkpoint()`/`gc_partial()` 규칙상 이미 PARTIAL 로
  취급돼 GC 대상이다.

## 후보 비교

| 후보 | In | Out | 예상 비용 | proto 변경 |
|---|---|---|---|---|
| 1. 로컬 `JOB_STARTED` 신호만 | 유효 Grant/Lease 검증 후 구조화된 stdout/로컬 로그 | 체크포인트·프로세스·Coordinator 보고 없음 | 0.5~1일 | 없음 |
| **2. `WRITING` 시작 마커(추천)** | 유효 Grant/Lease 뒤 checkpoint root 에 attempt 디렉터리 생성 + `record_initial_state()` 로 `WRITING` 마커 기록 + `JOB_STARTED` 출력 | 실제 entrypoint 실행, 데이터 파일, manifest, `LOCAL_WRITTEN` 이후 전이, 복제·COMMITTED 없음 | 1일 | 없음 |
| 3. 서명된 `JobStarted` wire 메시지 | Agent 가 시작 이벤트를 Coordinator 에 전송, Coordinator 가 attempt 상태 갱신 | scheduler·runtime·실제 프로세스 실행 없음 | 2~4일 이상 | 새 메시지·domain tag·frame·negative test 필요 |

**후보 1** 은 코드량이 더 작지만 휘발성 신호라 재시작 후 "Agent 가
실제로 실행 초기화를 시작했는지" 확인할 방법이 없다.

**후보 2(추천)** 는 기존 checkpoint durability 인프라에 처음
연결되면서도 실제 워크로드 실행(프로세스 spawn, GPU 확인 등)은
전혀 건드리지 않는다 — 오늘 조각들과 같은 "핸드셰이크/stub 수준에
머문다"는 정신을 그대로 잇는다.

**후보 3** 은 새 서명 대상 메시지가 필요해 규모가 커진다 — 이번
조각의 범위 밖으로 미룬다.

## 권장 동작 (후보 2)

```text
Grant/Lease 검증 성공
  → 안전한 결정적 start checkpoint_id 생성
     (job_id + attempt_id + grant_id 에서 digest — Job ID 를
      경로에 직접 붙이지 않는다)
  → checkpoint_root/<checkpoint_id> 생성
  → WRITING 마커 기록 (write_once, 오늘 DoD-21 의 동시 호출
    거부 계약을 그대로 상속한다)
  → JOB_STARTED ... state=WRITING 출력
  → AgentGrantAck 전송
  → 기존 renew/revoke stub 경로 유지
```

동일 attempt 재시도 시 같은 `checkpoint_id` 를 쓰면 `write_once()`
의 idempotent 동작(같은 내용이면 `Ok(false)`)을 그대로 활용할 수
있다.

## 완료 기준 (설계 단계 제안)

- [ ] 정상 Grant → 디렉터리와 `WRITING` 마커 생성.
- [ ] 위조·만료·replay·revoked Lease → 마커 미생성, ACK 미전송.
- [ ] 동일 start 재시도 → 내용 불일치 없이 중복 생성 방지(멱등).
- [ ] 마커 생성 실패 → fail-closed(Grant 실패로 처리).
- [ ] 프로세스가 마커 직후 죽어도 `startup_gc` 가 marker-only
      디렉터리를 정리(기존 `gc_partial` 규칙 그대로 — PARTIAL 로
      취급된다).
- [ ] `RESULT ok=true` 를 "Job 완료" 로 해석하지 않도록 문서화
      (이 마커는 체크포인트 자체가 아니다 — 데이터 파일과
      `manifest.json` 이 없어 resume 후보나 `COMMITTED` 근거가
      될 수 없다는 한계를 명시한다).

## 범위

### In
- 유효 Grant/Lease 검증 뒤 checkpoint 디렉터리 생성 + `WRITING`
  마커 기록.
- 결정적이고 충돌 안전한 `checkpoint_id` 생성 규칙.
- `JOB_STARTED` 구조화 로그 출력.
- 정상/거부/재시도/GC 시나리오 selftest + evidence 기록.

### Out
- 실제 entrypoint 프로세스 실행, GPU 확인, runtime 격리.
- 데이터 파일·`manifest.json` 작성, `LOCAL_WRITTEN` 이후 상태 전이.
- Coordinator 에 시작 사실을 보고하는 wire 메시지(후보 3, 별도
  조각).
- scheduler·다중 Agent — `crates/scheduler` 자체가 아직 없다.

## 하루 규모 판단

**하루 규모가 맞다** — 기존 Grant/Lease 경로 재사용, 기존
checkpoint API 재사용, 새 proto·서명 domain·framing 없음, selftest
에 임시 checkpoint root 만 연결하면 되고, 정상·거부·재시작/GC
테스트와 evidence 기록까지 하루 안에 가능하다.

**scheduler 전체나 실제 Job 실행은 이 범위를 넘는다** —
`crates/scheduler` 자체가 없고, 기준선 §13(hard filter·runtime
estimation·survival probability·exploration budget·queue timeout·
placement rationale)과 다중 Agent 배치(ControlStore·동시 Lease/
Attempt 상태·fencing·reconciliation), §16(environment staging·
runtime backend·process tree·GPU 확인·watchdog·egress 강제)이
전부 필요하다. `runtime-windows` primitive 도 아직 실제 Job 실행
호출부에 연결돼 있지 않다.
