★ 표본은 조건마다 2회다. 10초 경계 근처(9~11초 워크로드)는 재지 않았다.

★ **새로 본 것 — Agent 는 Coordinator 가 이미 실패한 뒤에도 `RESULT ok=true` · exit 0 으로 끝났다.**
  ACK 는 보내고 끝(응답을 받지 않는다)이라, 상대가 이미 닫은 연결에 쓴 ACK 가 오류 없이 지나간 것으로
  보인다(쓰기가 성공한 이유 — 커널 버퍼 · RST 도착 시점 — 는 확인하지 않았다). 즉 **Agent 의 성공
  출력은 Coordinator 가 ACK 를 받았다는 증거가 아니다.**

## 2. 규범 · 코드에서 확인한 것

```text
규범    docs/protocol/state-machines.md §3 Attempt
          CREATED  -> STARTING  GRANT_ACCEPTED       Agent 검증 통과 · workspace 생성
          STARTING -> RUNNING   PROCESS_STARTED      프로세스 기동
          RUNNING  -> COMPLETED WORKLOAD_EXITED_OK   exit 0 AND 최종 artifact HASH_VERIFIED · AttemptReport 제출
          STARTING -> FAILED    START_FAILED         환경 준비 또는 기동 실패
        -> Grant 수락(ACK)은 **프로세스 기동 전**의 사건이다. 지금 코드는 ACK 를 종료 뒤에 보내므로
           ACK 가 사실상 "끝났다" 를 뜻한다 — 규범 순서와 어긋난다
proto   AgentGrantAck(control.proto) 에 accepted 하나 — "받아들였다" 이지 "끝났다" 가 아니다
        AttemptOutcome 에 FAILED 가 있다 — 기동 실패 보고에 새 값이 필요 없다
        SessionMode 는 FRESH · RESUME 뿐이다(lease.proto) — "보고만 하러 온 연결" 을 뜻하는 값이 없다
Coordinator  IO_TIMEOUT 10초(lib.rs:66)를 accept 한 스트림 전체에 건다. ACK 뒤의 heartbeat ·
             이웃 신고 · AttemptReport 읽기도 **같은 10초**다 -> ACK 만 앞당기면 실패가 보고 읽기로 옮겨 간다
             연결은 **순차로** 하나씩 처리한다(serve_one_connection 주석)
Agent   IO_TIMEOUT 10초가 agent/lib.rs:37 에 **따로** 있다(RULE.md §3.1 — 시한 상수가 두 곳)
        레거시 lane 의 Lease 기본 수명 60초(coordinator --lease-ttl-ms 기본값) · 기준선 상수는
        LEASE_DURATION_MS 10분 · LEASE_GRACE_MS 60초(constants.rs)
        exec.rs 에서 expires_at · deadline 을 grep 했고 안 나왔다 — 실행 중 Lease 만료를 보지 않는다
        (다른 이름으로 전달되는 시한은 이 검색이 놓칠 수 있다). 갱신은 ACK · 보고 **뒤** 순차 위치다
```

## 3. 선택지

| | 무엇을 바꾸나 | 얻는 것 | 잃는 것 · 남는 것 | proto |
|---|---|---|---|---|
| **C** 시한만 Lease 에 | ACK 위치는 그대로. Coordinator 의 ACK 읽기 시한을 Lease 만료(+grace)까지 늘린다 | 가장 작다. 10초 이상 워크로드가 Lease 안이면 통과 | ACK = "끝났다" 인 채로 남는다(규범 순서와 계속 어긋남). 순차 Coordinator 가 한 Agent 를 최대 Lease 수명만큼 기다린다 — 그동안 다른 연결을 못 받는다. Lease 보다 긴 워크로드는 여전히 실패 | 없음 |
| **A** ACK 를 실행 전으로 + 보고 대기를 Lease 에 | 사전 관문(opt-in · 상한 · 플랫폼) 통과 뒤 · spawn 전에 ACK. Coordinator 는 ACK 를 10초로 받고, **AttemptReport** 읽기 시한만 Lease 만료(+grace)에 묶는다 | ACK 가 규범의 GRANT_ACCEPTED 와 같은 자리에 온다. ACK 는 짧은 시한을 유지해 "Agent 가 응답하지 않는다" 를 빨리 안다 | 순차 Coordinator 가 보고를 최대 Lease 수명만큼 기다리는 성질은 C 와 같다. 사전 관문을 `execute_with_control` 에서 떼어 내야 한다. ACK 뒤 기동 실패는 FAILED 보고로 보내야 한다(지금은 보고 없이 오류 종료). Lease 보다 긴 워크로드는 여전히 실패(실행 중 갱신 없음) | 없음 |
| **E** A + 실행 중 생존 신호 | A 에 더해, 실행 중 Agent 가 NodeHeartbeat 를 주기적으로 보내고 Coordinator 는 "heartbeat 또는 보고" 를 10초 시한으로 계속 읽는다 | 10초 시한이 "침묵 감지" 뜻을 유지한다. 멈춘 Agent 를 Lease 수명이 아니라 10초 안에 안다 | Agent 에 실행과 동시에 쓰는 흐름(스레드)이 필요하다. Coordinator 는 고정 개수(`--expect-heartbeats`)가 아니라 끝을 모르는 읽기 루프가 된다. 실행 중 갱신까지 넣지 않으면 Lease 초과 문제는 남는다 | 없음(NodeHeartbeat 기존) |
| **B** A + 보고는 별도 연결 | ACK 뒤 첫 연결을 닫고, 종료 뒤 Agent 가 새 연결로 보고만 보낸다 | 긴 워크로드가 소켓을 붙잡지 않는다. Coordinator 가 그동안 다른 연결을 받는다. 데몬화(§5 ④)와 방향이 같다 | "보고하러 온 연결" 을 밝힐 수단이 없다 — SessionMode 에 값을 더하거나 새 hello 가 필요하다 -> RULE.md §3.5 · §4.2(계약 변경 제안 · 승인 · 벡터 재생성). 가장 크다 | **변경 필요** |

## 4. 추천 (결정은 사용자)

**A.** 이유 셋 — 규범 순서(GRANT_ACCEPTED -> PROCESS_STARTED)와 맞추는 유일하게 작은 안이고,
proto 를 바꾸지 않으며, 10초 넘는 워크로드의 양성 테스트를 바로 세울 수 있다. B 는 데몬화 때 함께,
E 는 실행 중 Lease 갱신과 함께 보는 것이 맞다고 본다. ★ A 로도 **Lease 보다 긴 워크로드**는 풀리지
않는다 — 레거시 lane 기본 Lease 가 60초라 60초 넘는 작업은 여전히 실패한다. 그 한계는 열린 채로 적는다.
