## 0. 한 줄

A/B/C 중 **B 가 맞다**(쿠버네티스가 GA 로 검증했다). 다만 **B 만으로는
모자라고 셋을 더해야 한다**(B′). 그리고 그 조사 도중, MPS 없이 VRAM 상한을
거는 네 번째 수단이 있음을 확인했다 — `CLAUDE.md` §0.4 의 목록이 불완전하다.

## 1. A/B/C 프레임이 어긋나 있었다

A/B/C 의 출처는 Mesos(오퍼 기반 비관) 대 Omega(공유 상태 낙관) 논쟁이다.
그건 **스케줄러가 여럿일 때**의 문제다. gPUteer 는 Coordinator 가 하나이고,
지금 충돌은 **같은 Coordinator 의 연속된 두 결정 사이**에서 난다.
같은 모양의 문제를 푸는 것은 Omega 가 아니라 **쿠버네티스 스케줄러 캐시**다.

## 2. B 는 맞다 — 쿠버네티스가 GA 로 검증했다

DRA(Dynamic Resource Allocation, K8s 1.34 GA, 2025-09)가 정확히 B 를 한다.

```text
ResourceSlice   재고. **차감하지 않는다**            <- gPUteer 의 PoolSnapshot
ResourceClaim   할당. status 에 **따로** 산다        <- gPUteer 의 예약
```

즉 "스냅샷은 사실 그대로, 예약은 따로" 는 GA 수준에서 검증된 설계다.

## 3. 그러나 쿠버네티스는 B 위에 셋을 더 얹는다 — gPUteer 엔 없다

### (1) 합치는 지점이 한 곳으로 고정돼 있다

B 는 "목록을 따로 준다" 까지만 말하고 **누가 언제 합치는지**를 안 정한다.
쿠버네티스는 캐시가 스냅샷을 만들 때 이미 접어 넣는다 — 모든 필터가
**합쳐진 같은 뷰**를 본다. 소비자마다 알아서 합치면 서로 다르게 합칠 수 있다.

### (2) ★★ 예약에 시한이 있다 — 그리고 gPUteer 엔 없다. 이건 현재 결함이다

쿠버네티스의 가정(assumed) 배치는 전부 deadline 을 갖고 백그라운드 청소기가
회수한다. 문서가 이유를 그대로 적어 뒀다 — **확인이 영영 안 오는 경우**
(크래시·네트워크 단절)를 위해서다.

gPUteer 를 코드로 확인했다:

```sql
CREATE TABLE coordinator_node_reservations (
    node_id TEXT PRIMARY KEY  ...,          -- ★ 노드 단위다. GPU 한 장이 아니다
    job_id TEXT NOT NULL ...,
    attempt_id TEXT NOT NULL UNIQUE ...,
    inventory_revision BLOB NOT NULL,
    reserved_at_unix_ms BLOB NOT NULL       -- ★ expires_at 이 **없다**
);
```
`crates/coordinator/src/staging_store.rs:235`

해제 진입점은 하나뿐이다 — `release_for_verified_terminal_report()`
(`reservation_release.rs:316`). 만료·회수 경로는 없다(grep 확인).
그리고 그 함수는 Agent 의 종료 보고를 요구하는데 **Agent 는 그것을 안 보낸다**
(`CLAUDE.md` §5-4 — "끊긴 곳은 실행이 아니라 보고다").

```text
그래서 지금:  Agent 가 죽으면 그 노드는 **영원히** 예약된 채 남는다.
              예약 단위가 노드라서, GPU 한 장이 아니라 기계 하나가 통째로 빠진다.
```

★ B 를 그대로 하면 이 누수를 "따로 주는 목록" 에 정직하게 담아 계속 넘긴다 —
  **더 잘 보일 뿐 막히지 않는다.** 그래서 B 로는 부족하다.

### (3) 되돌리기가 이름을 갖는다

쿠버네티스는 Reserve/Unreserve 가 짝이다. gPUteer 는 CAS 가 실패하면 그냥 실패다.

## 4. C 가 gPUteer 에서 특히 나쁜 이유

Omega 가 낙관적 제어의 붕괴 조건을 말한다 — 결정 시간이 길수록, 그리고
**기계를 통째로 잡을수록** 충돌이 는다. gPUteer 의 예약이 정확히 후자다
(`node_id` PRIMARY KEY). §0.4 때문에 노드 독점으로 갔는데, 그 선택이
낙관적 재시도를 가장 불리한 조건에 놓는다.

## 5. 제안 — B′ "가정 예약을 접어 넣은 사실 스냅샷"

| | B | **B′** |
|---|---|---|
| 스냅샷 | 사실 그대로 | 사실 그대로 *(유지)* |
| 예약 | 따로 넘김 | 따로 두되 **`pool_snapshot()` 이 한 번만 접어 넣음** |
| 시한 | 없음 | **`expires_at_unix_ms` 추가.** Lease 와 같은 `<=` 경계 |
| 해제 | 종료 증명만 | **둘로** — ① 종료 증명(정상) ② **만료 회수**(비정상) |
| CAS | 주 수단 | **마지막 안전망**으로 남김 |

★ ②가 `DoD-62` 의 금지를 어기지 않는 이유: `DoD-62` 는 "종료 증명 없이 풀면
  중복 실행 위험" 이라 막았다. 그런데 **Lease 가 만료된 뒤**라면 그 Lease 로는
  아무것도 못 한다 — fence epoch 이 이미 그 안전을 준다. 즉 만료 기반 회수는
  금지를 어기는 게 아니라 **금지가 성립하지 않는 구간**을 집어내는 것이다.

## 6. ★★ 별건 — `CLAUDE.md` §0.4 의 목록이 불완전하다

§0.4 는 이렇게 적어 뒀다:

> 소비자 GPU 에는 VRAM quota 강제 수단이 **없다.** MIG 는 데이터센터 전용,
> MPS 는 Linux 전용, cgroup 은 시스템 RAM 만 제한한다.

**네 번째가 있다 — 유저스페이스 CUDA API 가로채기.**

`HAMi-core`(CNCF sandbox)가 `dlsym` 훅으로 CUDA 드라이버 호출을 가로채
`cuMemAlloc_v2`·`cuMemAllocManaged`·`cuMemAllocHost_v2` 앞에서 상한을 검사하고,
넘으면 **표준 CUDA `out of memory`** 를 돌려준다.
설정은 환경변수 `CUDA_DEVICE_MEMORY_LIMIT`(예: `4g`) 하나다.
**MIG·MPS·root·드라이버 변경이 전부 불필요하고, 소비자 GPU 에서 동작한다.**

실측 근거(HAMi 프로젝트 공개 검증, T4 한 장을 파드 둘이 공유, 각 4147MiB):

```text
3GiB 할당       성공
누적 5GiB 할당  out of memory        <- 표시가 아니라 실제로 막혔다
동시에 B 도 3GiB 할당 성공            <- 격리도 성립
```

### 그런데 이건 "강제" 가 아니다 — 이 저장소가 이미 아는 등급이다

| 출처 | 말 |
|---|---|
| HAMi 문서 | "CUDA API 수준 메모리 강제이지 **MIG 같은 하드웨어 보안 경계가 아니다**" |
| HAMi 문서 | "신뢰할 수 없는 멀티테넌트 **보안 설계로 취급하면 안 된다**" |
| GPU-Virt-Bench (arXiv 2512.22125) | "격리는 **근사적**이다" · 메모리 상한 정확도 98~99% · SM 상한 85~93% |
| GPU-Virt-Bench | 세마포어 기반 추적은 "**작정한 우회를 막지 못한다**" |
| GPU-Virt-Bench | 처리량 18.5% 저하 · 커널 실행 지연 3.6배 |
| CVE-2025-23266 | `LD_PRELOAD` 상속이 CVSS 9.0 취약점 벡터였다 (NVIDIAScape) |

즉 **이 저장소가 cgroup·Job Object 에 이미 써 둔 문장이 그대로 적용된다:**

```text
막는다     실수로 메모리를 너무 먹는 작업
못 막는다  빠져나가려고 작정한 코드
```

★ 그래서 §0.4 의 **결론(Exclusive 기본값)은 살아남는다.** 바뀌는 것은
  "수단이 없다" 가 "수단이 있는데 등급이 낮다" 로 정확해지는 것이다.

## 7. 제안 — SHARED 를 "MPS 있으면" 이 아니라 "회계 + 강제 등급" 으로

`proto/common.proto:168` 이 `GPU_ALLOCATION_MODE_SHARED` 의 조건을
"Linux + MPS memory limit 확인 시에만" 이라고 적어 뒀다. 오늘 그 확인이
x600 WSL 에서 **불가능함이 확정**됐고(`WSL_GPU_MPS_실측_2026-09-08.txt`),
remote5090 는 남의 작업이 점유 중이다. 그대로 두면 SHARED 는 영영 못 쓴다.

쿠버네티스가 2025-09 에 다른 답을 냈다 — **DRA Consumable Capacity**
(KEP-5075). 40GiB 중 10GiB 요청 같은 부분 할당을 **스케줄러 회계**로 하고,
할당마다 `ShareID` 를 줘서 드라이버가 개별 제한을 건다.

```text
회계   스케줄러가 한다 — "합이 용량을 안 넘는다" 를 배치 시점에 강제
강제   드라이버가 한다 — 등급은 플랫폼마다 다르다
       ★ 둘이 분리돼 있다
```

gPUteer 에는 이 어휘가 **이미 있다** — `runtime-policy` 의
`Enforceable` / `Suppressible` / `Unenforceable`.

제안하는 재정의:

| 플랫폼 | VRAM 상한 수단 | 등급 |
|---|---|---|
| Linux + MPS | `CUDA_MPS_PINNED_DEVICE_MEM_LIMIT` | 미실측 (remote5090 대기) |
| Linux (MPS 없이) | HAMi-core 식 CUDA 가로채기 | **Suppressible** — 실측 필요 |
| Windows | Job Object (RAM 상한의 간접 효과) | Suppressible (ADR-027 실측) |
| WSL2 | ★ 가로채기는 될 것으로 보인다 — **오늘 CUDA 동작 확인됨** | 미실측 |

즉 SHARED 의 조건을 **"MPS 확인 시에만"** 에서
**"회계는 항상 하고, 강제 등급을 정직하게 표시한다"** 로 바꾼다.
`Unenforceable` 인 플랫폼에서는 SHARED 를 거부하는 게 아니라 **경고와 함께
등급을 붙여 발급**한다 — §0.4 의 "강제할 수 없는 것을 보장으로 선언하지
않는다" 는 **선언하지 말라는 것이지 하지 말라는 것이 아니다.**

★ **이건 proto 규범 변경이라 사용자 결정이다.**

## 8. 오늘 열린 것 — 이게 다 가능해진 이유

WSL2 에 GPU 가 보인다는 것을 오늘 확인했다. 그래서 **HAMi-core 식 가로채기를
x600 에서 실측할 수 있다** — 리눅스 유저스페이스 `.so` 를 `LD_PRELOAD` 하는
방식이고, WSL 의 `libcuda.so.1` 도 평범한 유저스페이스 라이브러리다.
지금까지 이 실험은 "리눅스+GPU 기계가 없다" 로 막혀 있었다.
