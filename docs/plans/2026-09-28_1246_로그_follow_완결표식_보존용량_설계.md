```text
디스크 보호   작업이 stdout · stderr 에 끝없이 쓰면 런타임의 로그 저장소와 우리가 받는 파일(save_logs — container.rs:1788 부근, 상한 없이 File::create 로
             쓴다)이 소유자 디스크를 채운다. 지금 create 인자에 로그 드라이버 · 옵션 지정이 없다(container.rs:506~524) — 런타임 기본값을 따른다
             (docker 는 json-file · podman 은 문서상 기본이 journald — 예상, 설치마다 다르다)
로그 완결     컨테이너별 상한(--log-opt max-size)을 걸면 런타임이 오래된 부분을 버려, 끝난 뒤 `logs` 의 성공이 "전부 받았다" 가 아니게 된다 —
             그래서 지금 Agent 는 상한을 걸지 않는다(런북 497줄). 결과: 디스크 보호가 없다
```

★ 지금 코드(읽어서 확인):
- 정상 경로는 멈춤 확인 뒤 `logs` 를 **한 번** 받고, 그 성공이 완결 판정이다. `save_logs` 는 최종 경로에 바로 쓰고 fsync 하지 않는다 · 실패하면 부분 파일을 지운다.
- 결과 확정은 작업 폴더 바로 아래 **`stdout.log` · `stderr.log` 두 이름만** 읽고(exec.rs:45~47 · lib.rs:3870~), 파일 하나가 **64MiB** 를 넘으면 확정을
  READ_OUTPUTS 로 실패시킨다(lib.rs:3848 `MAX_CAPTURED_OUTPUT_BYTES` · 결함 540). 출력 불완전(`outputs_incomplete`)이면 파일이 있어도 읽지 않는다(결함 495).
- 사건 표식 · 새 작업 차단은 로그 완결이 아니라 **컨테이너가 남았는가**(`needs_human`)로 정해진다. 둘은 독립된 축이다(exec.rs:559~607).
- start 무응답(결함 532)은 logs_complete=false 로 컨테이너와 사건을 남긴다. 그러나 **start 가 실패로 답했지만 실제로 돈 경우**(poststart — 결함 490)와
  **남은 컨테이너**는 멈춤 뒤 한 번 받은 `logs` 가 성공하면 완결로 본다(container.rs:1356~1389 · :322~368) — 이미 회전돼 잘렸어도 모른다.
- 멈춤 확인은 컨테이너가 **없어도** "안 돈다" 로 본다(container.rs:419~442).

## v1 이 틀린 곳 — 따라 읽기(follow)로는 완결을 증명할 수 없다 (c3 ①)

v1 은 "start 뒤 `logs --follow` 로 따라 읽고, 끊김 · 재접속이 없고 EOF 까지 받으면 완결" 이라고 했다. **증명이 되지 않는다:**

```text
시작 틈      start 와 follow 연결 사이에 대량 출력 → 회전으로 앞부분이 사라질 수 있다
따라잡힘     연결이 끊기지 않아도 런타임 회전이 follow 보다 앞서면 중간이 사라진다 — 런타임은 이것을 알려 주지 않는다(바이트 번호 · 회전 통지가 없다)
외부 삭제    컨테이너가 밖에서 지워지면 follow 가 EOF 를 받고, 멈춤 확인은 "없음 = 안 돈다" 로 통과한다 — 다섯 조건이 모두 참인데 잘린 로그
```

그래서 **런타임의 로그 파일을 읽는 경로(follow · 끝난 뒤 한 번)는 어느 것도 "내용이 완결" 을 증명하지 못한다** — 이 설계는 그것을 인정하고 둘을 가른다:

```text
전송 완결(transport)  우리가 연 연결이 오류 없이 EOF 로 끝났다
내용 완결(content)    작업이 쓴 첫 바이트부터 마지막 바이트까지 빠짐없이 받았다 — 이것만 logs_complete=true 가 된다
```

## 제안 — 시작 전에 붙어서 직접 받는다

```text
받는 길      작업을 시작하는 명령 자체를 붙은 채로 한다 — `start --attach`(docker · podman 둘 다 있다). 붙은 연결은 런타임의 로그 파일이 아니라 컨테이너의
             표준 출력 흐름을 넘겨받는다(예상) — 회전과 무관하다. 연결이 작업의 첫 바이트보다 먼저 선다(예상 — 붙은 뒤 시작한다).
             단계 3 의 시작 관문과 맞물린다: 준비(create) → 허가 → `start --attach`
★ 모르는 것   (가) 붙은 연결이 **첫 바이트보다 먼저** 서는가 — docker CLI 소스는 붙은 뒤 시작하는 순서로 보이고, podman 문서는 --attach 지원만 적는다.
             런타임마다 M1 의 통과 조건으로 잰다 — 못 잡는 런타임은 그 런타임에서 logs_complete 를 늘 false 로 둔다(c3b ③)
             (나) 느린 수신자에게 붙은 연결이 **버리는가 · 막는가**(배압)를 재지 않았다(M1). 막는다면 내용 완결을 증명할 수 있다. **버린다면 붙은 연결로도 증명할 수
             없다** — 그때는 런타임 경로로 완결을 얻는 길이 없다고 적고, 작업이 붙인 폴더에 직접 쓰는 방식(아래 C)만 남는다
완결 조건    (1) 붙은 연결이 시작 전에 섰다 (2) stdout · stderr 둘 다 오류 없이 EOF (3) 종료를 관측했다(멈춤 확인 · 종료 코드) (4) 각 흐름이 상한 L 안
             (5) 아래 "완결 표식" 이 디스크에 있다 — 다섯이 다 참일 때만 logs_complete=true
붙은 명령의 종료 상태  `start --attach` 는 **정상으로 시작한 작업이 0 이 아닌 코드로 끝나도** 그 코드를 CLI 종료 상태로 돌려준다(docker CLI 소스 · podman 은
             예상 — M1). 지금 코드는 start 의 CLI 상태가 실패면 시작 실패로 가른다(container.rs:1308 부근) — 붙은 명령에는 그 규칙을 쓰지 않는다(c3b ①):
             시작 여부 · 종료 코드는 **inspect**(State.StartedAt · State.ExitCode · OOMKilled)로 따로 읽는다. 붙은 명령의 종료 상태 · 출력 EOF 는 **전송**
             신호로만 쓴다. inspect 가 "시작한 적 없음" 이면 시작 실패 · 시작했고 끝났으면 그 종료 코드 · 읽지 못하면 지금 규칙(모른다)
전송 오류 판별  (c3c ①) CLI 로 붙으면 CLI 자신의 오류와 작업의 stderr 가 **같은 stderr** 로 나오고, 붙기 오류도 0 이 아닌 상태로 끝난다(docker CLI 소스).
             그래서 CLI 상태만으로는 "전송이 멀쩡했다" 를 가를 수 없는 경우가 있다. 규칙:
               (a) CLI 상태 ≠ inspect 종료 코드 → 전송 문제 → logs_complete=false
               (b) CLI 상태 = inspect 종료 코드 = **0** → 전송 오류가 없었다(전송 오류는 0 으로 끝나지 않는다 — docker CLI 소스 · podman 은 M1) → 다른 조건이 맞으면 완결
               (c) CLI 상태 = inspect 종료 코드 ≠ 0 → **가를 수 없다** → logs_complete=false(받은 것은 unverified 사본)
             ★ 대가: 0 이 아닌 코드로 끝난 작업의 로그는 CLI 경로로는 늘 "확인되지 않은 사본" 이다. 이것을 완결로 받으려면 CLI 가 아니라 런타임 API 의
               붙기(docker Engine API 의 attach — stdout · stderr 를 프레임 머리로 가르는 흐름 · 전송 오류는 소켓 오류로 따로 온다)를 써야 한다 —
               이 설계 범위 밖(다음 조각 후보 · podman 은 API 서비스를 따로 띄워야 한다)
완결이 아닌 경로  start 가 실패로 답함(poststart — 붙지 않은 start 경로) · start 무응답 · 붙은 연결 오류 · EOF 시한 초과 · 남은 컨테이너(Agent 가 죽은 뒤) · 외부 삭제 —
             **한 번 받은 `logs` 가 성공해도 logs_complete=false** 다(내용 완결을 증명할 수 없다). 받은 것은 "확인되지 않은 사본" 으로 따로 둔다
```

### 파일 배치와 완결 표식 — 기존 확정 경로 그대로 (c3 ④ ⑤)

```text
최종 이름    작업 폴더 바로 아래 `stdout.log` · `stderr.log` — 지금 확정 코드가 읽는 두 이름 그대로. ★ **파일 이름은 그대로 두고, 확정 경로
             (lib.rs `collect_workload_artifacts` — :3878 부근)에는 아래 표식 검증을 더한다**(c3b ④ — 확정 코드는 바뀐다)
쓰는 중      `stdout.log.part` · `stderr.log.part` — create-new. 최종 이름이 **이미 있으면 덮지 않고 실패**(결함 493 과 같은 규칙)
완결 순서    (1) 두 .part fsync (2) 이름 바꾸기 — 덮지 않는 이름 바꾸기(리눅스 renameat2 RENAME_NOREPLACE · Windows MoveFileEx 에 REPLACE_EXISTING 없이)
             (3) 폴더 sync (4) **완결 표식 `outputs.complete` 를 마지막에** create-new 로 쓰고 fsync · 폴더 sync —
             내용: 두 파일의 길이 · BLAKE3 · 받은 길(attach) · 시도 id. 체크포인트의 "매니페스트는 마지막에"(§0.3)와 같은 모양
읽을 때      **컨테이너로 받은 출력에만** 확정이 표식을 요구한다(c3c ②) — 실행기가 결과에 "표식 필요" 를 싣고(ExecutionOutcome 에 칸 하나), 확정은 그때만
             표식이 있고 두 파일의 길이 · 해시가 표식과 같을 때 완결로 읽는다. 표식이 없거나 다르면 outputs_incomplete(재기동 뒤에도 같다).
             호스트 작업(Windows · 리눅스 — exec.rs:692 부근)은 OS 가 프로세스 시작부터 두 파일에 직접 쓰므로 지금 확정 규칙 그대로다(표식 없음 · 요구 없음)
확인 안 된 사본  완결이 아닌 경로에서 받은 것은 `stdout.unverified.log` · `stderr.unverified.log` 로 둔다 — 확정이 읽지 않는다 · 사람이 본다
```

### 상한 — 받는 상한과 확정 상한을 맞춘다 (c3 ④)

```text
L            흐름 하나(stdout · stderr 따로)의 받는 상한. 확정 상한 64MiB 와 **같은 값을 기본**으로 둔다(L1) — "완결" 과 "확정 가능" 이 같은 뜻이 되게.
             L 을 64MiB 보다 크게 두면 완결이어도 확정은 READ_OUTPUTS 로 실패한다(확정을 흘려 읽기로 바꾸기 전까지 — 이 설계 범위 밖)
상한에 닿으면  더 쓰지 않되 **연결은 계속 읽어 버린다**(읽기를 멈추면 붙은 연결이 막아 작업이 멈출 수 있다 — 예상). 결과는 L2
```

### 런타임 로그 저장소 — 안전망 · 드라이버를 고정하고 대조한다 (c3 ③)

```text
고정         docker: `--log-driver=json-file --log-opt max-size=<S> --log-opt max-file=1` · podman: `--log-driver=k8s-file --log-opt max-size=<S>`
             (podman 문서의 --log-opt 에는 max-file 이 없다 — 예상, 설치 판마다 확인). journald 는 받지 않는다(디스크가 journald 설정에 달려 우리 예산에 못 넣는다)
대조         create 뒤 inspect 로 실제 드라이버 · 옵션을 읽어 위와 같은지 본다 — 다르거나 읽지 못하면 **시작하지 않는다**(컨테이너를 지우고 거부)
S            런타임 쪽 상한. 붙은 연결이 주 경로이므로 런타임 로그는 남은 컨테이너의 진단용 사본일 뿐이다 — S = L 기본
런북         497줄 "상한을 걸지 않는다" 는 끝난 뒤 받는 방식의 이유였다 — 이 설계로 바꾸면 그 문단을 고친다
```

### 보존 용량 — 재는 대신 예약으로 센다 (c3 ③)

```text
예산 H       노드 설정(L3). 새 작업을 받기 전에(c3b ② — 실제로 생기는 사본을 모두 센다):
             지금 남아 있는 것  = 저장된 로그의 실제 크기 — 작업 폴더(최종 · .part · unverified) · 건진 로그 폴더 · **체크포인트 폴더 안의 로그 사본 전부**
                                (확정됐든 아니든 — 체크포인트 작성은 로그 파일을 먼저 쓰므로(checkpoint/src/writer.rs:154 부근) 뒤 단계가 실패하면 사본이 남는다 · c3c ③)
                                (확정은 두 로그를 체크포인트에도 쓴다 — lib.rs:3335~ finalize_workload_outputs)
                                + 남은 컨테이너 수 × S(런타임 저장소 — 재지 않고 상한으로 센다)
             새 작업의 최악     = 2 × L(받는 파일) + 2 × L(확정 때 체크포인트 사본 — 확정 중에는 둘이 동시에 있다) + S(런타임)
                                + 2 × S(실패 경로에서 런타임에서 받는 unverified 사본)
             지금 + 새 작업 ≤ H 일 때만 받는다. 크기를 세다 실패하면 **받지 않는다**(fail closed)
풀림         소유자가 지우거나 남은 컨테이너가 치워지면 다음 판단에서 풀린다. 자동 삭제는 하지 않는다(일찍 막는다 — 2306 설계 P1)
★ 한계       회전 · 삭제됐지만 열린 파일 같은 런타임 내부 사용량은 S 상한을 믿는다(드라이버 대조를 통과한 경우에만 — 예상)
```

## 경우별 처리 — 로그 축과 컨테이너 축은 따로 (c3 ⑥)

| 경우 | 작업 | 컨테이너 | 사건 · 새 작업 차단 | 종료 보고 | 로그 파일 |
|---|---|---|---|---|---|
| 정상(완결 조건 다섯) | 끝남 | 지운다(지금 규칙) | 없음 | 지금과 같다 | 최종 이름 + 표식 |
| 상한 초과 | L2 에 따른다 | 멈춤 확인 뒤 지운다(더 알 것이 없다 — 런타임 사본도 S 로 잘렸다) | 없음 | outputs_incomplete="LOG_LIMIT_EXCEEDED" | .part 는 unverified 로 이름 바꿈 |
| 붙은 연결 오류 · EOF 시한 초과 | 영향 없음(작업은 계속 · 끝나기를 기다린다) | **남긴다** — 런타임 사본에 더 있을 수 있다(지금의 "로그 못 받음" 과 같다) | 사건 · 차단(지금 needs_human 규칙) | outputs_incomplete | unverified |
| 소유자 정지 중 | 정지는 로그를 기다리지 않는다(단계 3 · 4) | 정지 결과 규칙대로 | 정지 결과 규칙대로 | 정지 규칙 + 로그 축은 위 두 줄 중 하나 | 연결은 EOF 까지(시한) 계속 읽는다 |
| start 실패 응답(poststart) · start 무응답 | 지금 규칙(돌았을 수 있다) | 남긴다 | 사건 · 차단 | outputs_incomplete | unverified(받을 수 있으면) |
| 남은 컨테이너(Agent 가 죽은 뒤) | — | 멈춤 확인 · 사본 저장 뒤 지운다(지금처럼) | 멈춤 확인 실패일 때만 | 이미 없다(보고는 이전 회차의 일) | unverified 사본만 |

★ 외부 삭제(멈춤 확인이 "없음" 으로 통과)는 붙은 연결의 EOF 가 먼저 왔더라도 종료 코드를 관측하지 못했으므로 조건 (3) 이 거짓 → 완결 아님.

