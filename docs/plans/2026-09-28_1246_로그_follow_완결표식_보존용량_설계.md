## 문제 — 두 요구가 부딪친다

```text
디스크 보호   작업이 stdout · stderr 에 끝없이 쓰면 런타임의 로그 저장소(docker json-file · podman k8s-file — 기본 설정에서 크기 제한 없음, 예상)와
             우리가 받는 파일(save_logs — container.rs:1788, 상한 없이 File::create 로 쓴다)이 소유자 디스크를 채운다
로그 완결     컨테이너별 상한(--log-opt max-size)을 걸면 런타임이 오래된 부분을 버려, 끝난 뒤 `logs` 의 성공이 "전부 받았다" 가 아니게 된다 —
             그래서 지금 Agent 는 상한을 걸지 않는다(런북 497줄). 결과: 디스크 보호가 없다
```

지금 방식은 **끝난 뒤(멈춤 확인 뒤) 한 번** `logs` 로 받는다(결함 492 조치 — 멈추기 전에 받던 것을 고쳤다). 이 방식에서는 두 요구를 같이 채울 수 없다.

★ 덧붙여 확인한 것(코드 읽기): `save_logs` 는 최종 경로에 바로 쓰고 fsync 하지 않는다. 실패하면 부분 파일을 지운다(`discard_partial_outputs`).
완결 판정은 `logs` 명령의 성공 여부다.

## 선택지

| | 무엇 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A** 실행 중 follow + 우리 상한 | start 뒤 `logs --follow` 를 띄워 고유 임시 파일(create-new)에 흘려 쓴다 — 우리 상한(바이트)까지. 런타임 쪽에는 우리 상한보다 조금 큰 `max-size` 를 **안전망**으로 건다(우리가 따라가는 동안 런타임이 버리는 앞부분은 이미 받았다). 멈춤 확인 → follow 가 EOF 로 끝남 → fsync → 완결 표식 | 디스크가 두 곳 모두 묶인다. 완결의 뜻이 분명하다(끊김 없이 EOF 까지 · 상한 안) | follow 가 끊기는 경우(데몬 재시작 · 런타임 무응답)가 생긴다 — 끊기면 **완결이 아니다**(다시 붙어 이어 받을 수 있는지는 런타임마다 다르다 — 예상, 재지 않았다). 실행 중 프로세스가 하나 는다 |
| **B** 런타임 상한만 + 끝난 뒤 받기 | `max-size` · `max-file` 을 걸고 지금처럼 끝난 뒤 받는다 | 코드가 작다 | 잘렸는지 알 수 없다 — 받은 크기가 상한 근처면 늘 "완결 아님" 으로 봐야 한다(런타임이 알려 주지 않는다). 긴 작업은 거의 늘 불완전 |
| **C** 작업이 로그를 붙인 폴더에 쓴다 | stdout 은 작게 두고 큰 로그는 체크포인트 출력 폴더에 | 디스크 상한 설계(0810)의 붙인 폴더 제한과 한 곳 | 작업 계약이 바뀐다(이미지 작성자에게 요구) · stdout 폭주는 그대로 |

**권고: A.** 두 요구를 같이 채우는 것은 A 뿐이다. B 는 "완결" 을 거의 늘 거짓으로 만들고, C 는 작업 쪽 협조에 기댄다.

## A 의 세부

```text
시작        start 가 성공한 **뒤** follow 를 띄운다(start 무응답 · 실패 경로에서는 띄우지 않는다 — 지금 규칙 그대로)
쓰기        <작업 폴더>/logs/<시도>.<n>.{stdout,stderr}.part — create-new(덮지 않는다 · 결함 493 과 같은 규칙). 바이트 상한 L(결정 L1)
상한 초과   작업을 멈춘다(LOG_LIMIT_EXCEEDED — 멈춤 확인 → 보고 FAILED · 사유) 또는 더 받지 않고 "잘림" 으로 표시만(결정 L2).
            ★ 어느 쪽이든 "완결" 이 아니다
완결 표식   (1) 멈춤 확인(지금 규칙) (2) follow 가 EOF 로 끝남(시한 안) (3) 끊김 · 재접속 없음 (4) 상한 안 (5) fsync 뒤 이름 바꾸기(.part → .log) · 폴더 sync
            — 다섯이 다 참일 때만 logs_complete=true. 하나라도 아니면 false(지금처럼 "로그 못 받음" 경로 · 출력은 성공으로 확정되지 않는다)
런타임 안전망  --log-opt max-size=<L 보다 조금 큰 값> · max-file=1(docker · podman 둘 다 지원 — 예상, 드라이버별로 확인). 우리가 따라가지 못해 런타임이
            앞부분을 버리면 (3) 이 거짓이 된다(끊김으로 본다 — 버린 것을 알 수 없으므로 follow 시작 뒤 재접속이 있었는지로만 가른다)
            ★ 런북 497줄의 "상한을 걸지 않는다" 는 끝난 뒤 받는 방식의 이유였다 — A 로 바꾸면 그 문단을 고친다
남은 컨테이너  지금처럼 멈춤 확인 뒤 `logs` 한 번(follow 할 대상이 이미 멈췄다) — 이때도 우리 상한 L 을 적용한다(읽기 상한 · 넘으면 "잘림")
보존 용량   건진 로그 폴더(`<루트>.leftover-container-logs/`)와 작업 폴더 logs 의 합이 높은 물높이(결정 L3)를 넘으면 **새 작업을 받지 않는다**
            (자동 삭제 대신 일찍 막는다 — 2306 설계 P1). 소유자가 지우면 풀린다
```

## 시험 (negative test — `RULE.md` §6)

```text
T1 (가짜 런타임) 끝없이 출력하는 작업 — 우리 파일이 L 에서 멈추고, L2 에 따라 작업이 멈추거나 "잘림" · 어느 쪽이든 logs_complete=false
T2 (가짜 런타임) follow 가 중간에 끊김(런타임 재시작 흉내) — logs_complete=false · 출력은 성공으로 확정되지 않는다
T3 (가짜 런타임) 정상 — 멈춤 확인 · EOF · 상한 안 → .log 로 이름이 바뀌고 logs_complete=true · 대조군
T4 (가짜 런타임) start 무응답 — follow 를 띄우지 않는다(결함 532 경로 그대로)
T5 보존 용량 물높이 초과 — 새 작업 거부 · 지우면 풀림
M1 (x600 · docker · podman) max-size · max-file 이 실제로 걸리는지 · follow 가 데몬 재시작에서 어떻게 끝나는지(EOF 인가 오류인가) — gputeer- 컨테이너만
```
