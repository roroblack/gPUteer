## 왜 지금 이 조각인가

`write_once()`(`crates/checkpoint/src/atomic.rs:148-206`)는 같은
`(dir, name)` 으로 동시에 호출되면 안전하지 않다 — 모든 호출자가
같은 tmp 경로(`{name}.tmp`)를 공유한다. `DoD-08` 이 이 결함을
**고정하는 테스트**(`k1c_concurrent_same_name_writers_are_not_actually_safe`)
로만 등록하고 코드는 고치지 않았다. 오늘(`ENV-03`) Linux 에서
같은 테스트를 돌려보니 증상이 재현되지 않았다 — 플랫폼별 `rename`
시맨틱 차이로 증상만 다르게 나타날 뿐 근본 원인(tmp 경로 공유)은
그대로다. 코드를 고치기 전에 "동시 동일-이름 호출을 지원할지"부터
계약으로 정해야 한다는 게 두 evidence 문서의 공통 결론이었다.

## 설계 단계 실측 (코덱스 `p127`)

- `write_once()` 의 in-tree 호출부는 전부 **한 프로세스 안에서
  순차 호출**이다: `writer.rs:100-105`(데이터 파일), `writer.rs:115`
  (매니페스트), `durability.rs:141-170`(상태 마커류). `cli/selftest.rs`·
  `checkpoint/src/bin/ckpt_writer.rs` 도 체크포인트 ID 를 바꿔가며
  순차 호출한다.
- 그러나 `write_once()` 자체는 public 함수라 외부 호출자를 제한하지
  않는다 — "지금 호출부가 순차적"이라는 사실이 "함수가 동시 호출을
  안전하게 막는다"를 뜻하지 않는다.
- **Lease/fencing 은 파일 쓰기 상호 배제를 보장하지 않는다** —
  `fence_epoch` 검사는 Grant/갱신 수신 시점에만 일어나고
  (`crates/agent/src/lib.rs:373-406`), `DurableFenceWatermark` 는
  낮은 epoch 만 거부하며 같은 epoch 재사용은 명시적으로 허용한다
  (`durable_lease_scope.rs:239-244`). `write_checkpoint()` 자체는
  Lease 나 epoch 인자를 받지도 않는다(`writer.rs:89-95`).
  `proto/lease.proto:12-18` 자체가 "SIDE_EFFECTING Job 의 중복
  실행은 fencing 으로 막을 수 없다"고 명시한다.
- 결론: **지금은 A(동시 호출 미지원 + 명시적 거부)가 맞다.** 실제
  호출부가 전부 순차적이고, 상위 계층이 이 보장을 대신 해주지도
  않으므로 "지원 안 함을 명시하고 강제"하는 편이 "진짜 동시 안전
  재설계"보다 지금 단계의 실제 필요에 맞는다.

## 범위

### In

- `write_once()` 에 **프로세스 간 파일 잠금**(advisory lock, 예:
  `fs4` 크레이트로 Unix `flock`/Windows `LockFileEx` 를 추상화)을
  추가한다 — 인메모리 뮤텍스는 다중 프로세스 시나리오를 못 막으므로
  부적합하다.
- 락은 `final_path.exists()` 첫 검사 **이전에** 획득하고,
  `rename()`·`sync_dir()` 가 끝날 때까지 유지한다.
- `try_lock`(즉시 실패)만 쓴다 — 무기한 대기는 장애를 숨긴다.
- 락 실패 시 새 에러 `CheckpointError::WriteInProgress { path }` 를
  반환한다.
- 락 파일(`{name}.write_once.lock`)이 GC 에서 artifact 로 오인되지
  않도록 명시적으로 제외한다(`crates/checkpoint/src/gc.rs` 류의
  기존 `.tmp` 판별 로직과 같은 자리에 추가).
- `k1c_concurrent_same_name_writers_are_not_actually_safe` 를
  **결정론적** 테스트로 재설계한다 — 타이밍에 기대는 대신, writer-A
  가 락을 잡은 채 대기하도록 테스트 훅을 넣고 writer-B 가 즉시
  `WriteInProgress` 로 거부되는지 확인한다.
- 기존 동작(같은 내용 순차 재호출 -> `Ok(false)`, 다른 내용 순차
  재호출 -> `ContentMismatch`)은 그대로 유지한다 — 이번 조각은
  **동시 호출 경로만** 바꾼다.

### Out (명시하지 않으면 범위가 샌다)

- **진짜 동시 쓰기 지원**(선택지 B — 호출마다 고유 tmp 이름 +
  승자 판정 정책)은 하지 않는다. 트리거가 오면(Agent 실행 계층이
  생기고 실제로 `WriteInProgress` 가 정당한 운영 중 관측되는 시점,
  또는 동일 attempt 를 여러 Agent 가 동시에 publish 해야 하는
  요구사항이 제품 계약으로 승인되는 시점) `docs/vision/TODO_VISION.md`
  에 등록한다.
- `write_checkpoint()` 전체(여러 파일·매니페스트·포인터 교체를
  아우르는 상위 함수)를 하나의 락으로 감싸는 것은 **이번 조각의
  범위 밖**이다 — `write_once()` 자체의 계약만 고친다. 코덱스는
  상위 함수 락도 필요할 수 있다고 언급했지만, 지금 호출부가 전부
  순차적이라 시급하지 않고, 범위를 좁게 유지한다는 이 저장소의
  원칙(RULE.md §3.3 YAGNI)과 맞다 — 필요해지면 별도 조각으로 다룬다.
- `LATEST` 포인터 교체(`replace_with_retry`)의 락은 범위 밖이다 —
  그건 이미 다른 함수이고, 이번 조각은 `write_once()` 만 다룬다.
