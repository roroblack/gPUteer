## 왜 이 설계가 필요한가

`docs/evidence/DoD-24_lease_재접속_최소_조각.md`(완전히 새로운
프로세스가 재시작 후 저장된 Lease 를 복원하는 것만 다룸)와
`DoD-25`·`DoD-26`(revoke·만료 영속화)이 전부 "**같은 프로세스가
살아있는 채로 연결만 끊겼을 때 스스로 재접속을 시도하는 것**은
아직 설계된 적이 없다"는 공백을 남겼다. 이번 조사가 그 공백을
7개의 순서 있는 조각으로 분해했다.

## 실측 결론 (설계 단계)

- Agent 의 `run()`(`crates/agent/src/lib.rs:96`)은 연결이 끊기면
  그냥 `Err` 로 끝난다 — 재시도 로직이 전혀 없다.
- Coordinator 의 `run()`(`crates/coordinator/src/lib.rs:173,205`)
  은 `listener.accept()` 를 **딱 한 번**만 부른다 — 같은 프로세스가
  두 번째 TCP 연결을 받을 방법이 없다.
- 반복 갱신 nonce(`BLAKE3("lease-renew" || lease_id || round)`,
  `crates/agent/src/lib.rs:279,579`)가 재접속 시 `round=0` 부터
  다시 시작하면 기존 연결의 첫 갱신과 같은 nonce 가 된다 — 재접속을
  `InMemoryReplayGuard` 가 replay 로 오인해 거부할 수 있다.
- `RenewLeaseRequest` 를 새 연결의 첫 프레임으로 재사용하는 방식
  (대안 B)은 여러 이유로 **권장하지 않는다** — Coordinator 가 항상
  Grant 를 먼저 보내는 server-first 구조와 정면 충돌하고, "요청은
  적용됐는데 결과만 유실된 경우"를 구분할 수 없다.

## 오류 분류

**재시도 가능**: `FramingError::Truncated`, `ConnectionReset`,
`ConnectionAborted`, `BrokenPipe`, `NotConnected`, `connect()` 의
`ConnectionRefused`/`TimedOut`(budget 안에서만).

**치명적(재시도 안 함)**: `FrameTooLarge`, `UnknownFrameType`,
protobuf decode 실패, 서명 검증 실패, 잘못된 identity, epoch 정책
위반, `SUPERSEDED`/`QUARANTINED`/`MAX_DURATION_EXCEEDED`(서명된
정책 결과이지 연결 오류가 아니다), durable SQLite 오류.

**애매한 경우**: `RenewLeaseRequest` 를 보낸 **뒤** `RenewLeaseResult`
를 받기 **전**에 끊기면 결과가 불명확하다 — `DisconnectedBeforeRequest`
/`DisconnectedAfterRequestBeforeResult`/`DisconnectedAfterResult`
셋을 구분해야 한다. 가운데 상태에서는 같은 갱신을 새 nonce 로
무조건 재전송하면 안 된다(Coordinator 가 이미 durable store 를
갱신했을 수 있다).

## 재시도 정책 권장값

```text
max_reconnect_attempts = 8
max_reconnect_duration = 60 seconds
base_delay             = 250 ms
backoff                 = exponential (raw_delay = min(base*2^n, cap))
backoff_cap             = 5 seconds
jitter                  = full jitter (random(0, raw_delay))
per-attempt timeout     = 3 seconds
deadline = min(reconnect_started_at + 60s, lease.expires_at_unix_ms - safety_margin)
```

무한 재시도는 기본값으로 안전하지 않다 — Job 실행 자체가 아직
없어서 "실패 처리 후 다음 Agent 로 넘긴다"는 동작도 없다. 지금은
`ReconnectExhausted` 를 `run()` 의 `Err` 로 표출하고, Job 실행이
생기면 그때 Job 실패/취소/재배정 정책에 연결한다.

## 재접속 첫 메시지 — 최종 추천: 명시적 Resume 프로토콜

```text
Agent -> AgentSessionHello { mode: FRESH | RESUME, session_id, connection_attempt }

mode=FRESH:  Coordinator -> ExecutionGrant / Agent -> AgentGrantAck (기존 그대로)
mode=RESUME: Agent -> ResumeLeaseRequest / Coordinator -> ResumeLeaseResult
```

`ResumeLeaseRequest` 필드: `schema_version · lease_id · job_id ·
attempt_id · node_id · fence_epoch · session_id · connection_attempt
· issued_at_unix_ms · request_nonce(CSPRNG) · node_signature`.

`ResumeLeaseResult` outcome: `RESUMED · REVOKED · EXPIRED ·
SUPERSEDED · UNKNOWN_LEASE · IDENTITY_CONFLICT · UNAVAILABLE`.
`RESUMED` 는 저장된 Lease 를 돌려주되 만료시각을 연장하지 않는다
— Resume 성공 뒤 정상 `RenewLeaseRequest` 를 별도로 수행한다.

Coordinator 판정 의사코드(우선순위 순):

```rust
if stored.lease_id != request.lease_id { return UNKNOWN_LEASE; }
if stored.holder_node_id != request.node_id
    || stored.job_id != request.job_id
    || stored.attempt_id != request.attempt_id { return IDENTITY_CONFLICT; }
if stored.revoked_at_unix_ms.is_some() { return REVOKED; }
if stored.expires_at_unix_ms <= now { return EXPIRED; }
if request.fence_epoch < stored.fence_epoch { return SUPERSEDED; }
if request.fence_epoch > stored.fence_epoch { return EPOCH_AHEAD; }
return RESUMED(stored_lease);
```

`DoD-25`(revoke 영속화)·`DoD-26`(만료 경계 `<=`)의 규칙을 이
Resume 판정에도 그대로 적용해야 한다.

## 응답 유실 처리 — durable request ledger 필요

Resume 만 추가하고 요청 결과 저장소를 안 두면 완전한 failover 가
아니다. 새 테이블(또는 동등 구조) 필요:

```text
lease_requests(
  lease_id, node_id, request_nonce, request_kind, request_digest,
  result_bytes, applied_at_unix_ms,
  PRIMARY KEY (lease_id, node_id, request_nonce)
)
```

규칙: 같은 nonce+같은 digest → 이전 signed result 재전송. 같은
nonce+다른 digest → replay/tampering 거부. 없는 nonce → Lease 갱신과
result 저장을 하나의 durable transaction 으로. **이게 이 설계
전체를 하루 조각보다 크게 만드는 핵심 이유다** — 기존
`InMemoryReplayGuard` 는 duplicate 를 무조건 거부하므로, idempotent
Resume/Renew 경로를 위해 durable ledger 조회를 generic replay 판정
보다 먼저 하거나 전용 `read_idempotent_frame()` 이 필요하다.

## Coordinator 쪽 필수 변경

`accept()` 를 반복하는 루프로 바꿔야 한다:

```rust
loop {
    let (mut stream, peer) = listener.accept()?;
    match serve_one_connection(&mut stream, &mut lease_store, &signing_key, ...) {
        Ok(()) => {}
        Err(SessionError::TransportDisconnected) => { log(peer); continue; }
        Err(SessionError::ProtocolError(e)) => { log(peer, e); continue; }
        Err(StorageError(e)) => return Err(e), // fail closed
    }
}
```

첫 조각에서는 연결을 **순차 처리**해도 된다(accept → 처리 → 종료
→ 다시 accept) — 같은 Agent 가 끊겼다가 재접속하는 시나리오엔
충분하다. 다중 Agent 경쟁까지 포함하려면 thread-per-connection 또는
async runtime, 공유 lease store 접근 직렬화, active session owner
개념이 별도 조각으로 필요하다.

## `coordinator-agent-selftest` 확장

기존 `run_handshake()` 는 매번 새 프로세스 쌍을 하나씩 spawn 해서
한 번의 handshake 만 검증한다 — "같은 Agent 프로세스가 재접속했다"
는 검증할 수 없는 구조다. 별도 `run_reconnect_case()` 헬퍼가
필요하고, `first_connection_agent_pid == resumed_connection_agent_pid`
(Coordinator 도 동일)를 반드시 확인해야 한다.

필요한 test hook — Coordinator: `--drop-connection-after-ack-once`·
`--drop-connection-after-renew-commit-before-result`·
`--pause-before-next-accept-ms`·`--revoke-before-drop`·
`--expire-before-next-accept`·`--max-connections`. Agent:
`--max-reconnect-attempts`·`--max-reconnect-duration-seconds`·
`--retry-base-ms`·`--retry-cap-ms`·`--deterministic-jitter-seed`.

★ **하네스에는 반드시 hard deadline 을 둬야 한다** — `DoD-22`·
`DoD-23` 에서 "한쪽은 끝났는데 다른 쪽은 다음 프레임을 무한히
기다리는" 교착이 이미 두 번 나왔다.

## proto 변경 여부

**필요하다.** 새 메시지: `AgentSessionHello` · `ResumeLeaseRequest`
· `ResumeLeaseResult` · `ResumeOutcome`. 갱신 필요: `FrameType` ·
`IngressMessage` · `read_frame()` dispatch · `Signable` · canonical
`to_fields` · schema fingerprint · canonical schema checker ·
protocol signing vectors · replay/idempotency ingress · selftest
fixture.

`ExecutionGrant` 에 `resume_token` 추가는 **초기 구현에서 보류**한다
— Agent signing key 와 `holder_node_id` 가 이미 기본 인증 주체이고,
token 을 추가하려면 초기 발급·durable local handle·token 보관·
TLS 없는 환경에서의 bearer secret 노출까지 함께 설계해야 한다.

## 정직한 규모 판단

**하루 조각으로 가능한 부분(조각 1+2 의 축소판)**: 같은 Agent
프로세스 + bounded retry + Coordinator 반복 accept + **기존**
Grant/ACK handshake 를 그대로 재수행(Resume proto 없이) + 연결마다
고유 nonce + revoke/expiry 는 기존 store 가 이미 거부. 이건 "자동
재접속 최소 경로"이지 완전한 Resume 프로토콜이 아니다 — proto
변경도 없다.

**여러 날짜가 필요한 부분**: Resume 의미(첫 프레임 구분) + 요청
nonce idempotency + 응답 유실 복구 + 다중 Agent 경쟁 + durable
request ledger + same-process selftest 전부를 포함하면 하루 작업이
아니다.

**권장 순서**: 1) 연결 오류 분류+Agent 상태 머신 → 2) bounded
retry/backoff/jitter+기존 handshake 재접속 → 3) Resume 프로토콜+
schema/canonical 변경 → 4) Coordinator 반복 accept+dispatcher →
5) durable request ledger → 6) Agent Resume 통합 → 7) same-process
selftest+다중 Agent 경쟁 검증.
