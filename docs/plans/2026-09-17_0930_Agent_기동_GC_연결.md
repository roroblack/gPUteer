## 범위

### In
- Agent 기본 lane 의 `run()` 이 **아무것도 시작하기 전에**(소유자 패널 · fence DB · outbox 재전송 · 연결보다 앞) 체크포인트 루트를
  독점하고 `startup_gc()` 를 부른다. 결과를 `CHECKPOINT_STARTUP_GC root=… dirs=… removed=…` 로 찍는다
- 독점은 루트의 **형제** 파일 `<root>.agent-lock` 의 `try_lock` 이다. 이미 잡혀 있으면 `CHECKPOINT_ROOT_BUSY` 로 시작하지 않는다 —
  같은 루트를 쓰는 다른 Agent 가 쓰는 중인 PARTIAL 을 GC 가 지우면 안 된다(`atomic.rs` gc_partial 주석이 적은 경쟁)
- GC 가 실패하면(권한 등) 시작하지 않는다(`CHECKPOINT_STARTUP_GC_FAILED`) — 남의 PC 에 부분 데이터를 남긴 채 새 작업을 받지 않는다
- 음성 테스트: 지난 실행의 PARTIAL 이 기동 뒤 사라진다 · 완결 체크포인트(매니페스트 있음)는 남는다 · 잠금이 잡혀 있으면 거부하고 PARTIAL 을 지우지 않는다

### Out
- `multi_agent` lane — 체크포인트를 쓰지 않는다(`multi_agent.rs` 에 checkpoint 사용 없음). 쓰기 시작하면 같은 관문이 필요하다
- **SENSITIVE 데이터셋 삭제 · 삭제 검증(§0.5)** — GC 는 PARTIAL 체크포인트 정리이지 데이터셋 캐시 정리가 아니다. 이것으로 §0.5 를 닫았다고 적지 않는다
- 잠금 파일을 지우는 것 — 지우면 다른 프로세스가 새 inode 에 잠금을 잡을 수 있다(`atomic.rs` 의 같은 이유). 파일은 남는다
- 실행 중 주기적 GC · 작업 출력 디렉터리(`<root>.workload-run`) 정리 · 리눅스 실행
