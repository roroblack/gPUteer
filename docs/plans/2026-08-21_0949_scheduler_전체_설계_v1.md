- **대상:** Job 제출부터 Agent 선택·예약·Grant 전달·실행·결과 보고·재배정까지의
  scheduler 전체 경로. 마스터 플랜의 v0.1 단순 best-fit과 v0.2
  chance-constrained 정책을 모두 포함한다.
- **선행 게이트:** 첫 조각(순수 hard-filter kernel)은 즉시 착수 가능하다.
  실제 자동 배치는 durable Job/Node 상태, 다중 Agent 세션, 실행 runtime이
  순서대로 필요하다.
- **상태:** **설계 전용 — 구현 미착수.** 이 문서 외 코드는 바꾸지 않았다.
  9개 조각의 순서와 규모를 정한다.

★ 이 문서는 현재 저장소를 read-only로 조사한 결과다. 자동 재접속 로드맵의
조각 7에서 이월된 진짜 다중 Agent 아키텍처도 여기 포함한다.

## 결론

지금 있는 것은 “Coordinator가 CLI에 고정된 한 Agent에게 빈
`ExecutionGrant`를 보내고, Agent가 Lease를 검증한 뒤 `WRITING` 마커를
남기는 안전한 프로세스 경계 stub”이다. **Job queue, Pool snapshot,
placement, reservation, 실제 entrypoint 실행, 완료 manifest, Coordinator
보고는 없다.** 따라서 scheduler는 점수 함수 하나가 아니라 control-state,
다중 Agent, 실행 계층을 잇는 서브시스템이다.

오늘 가능한 가장 작은 첫 조각은 **`crates/scheduler`의 순수 hard-filter
kernel**이다. 합성된 고정 snapshot을 입력받아 적격/탈락 후보와 사유만
결정하고, 복수 후보의 순위나 Coordinator 연결은 하지 않는다. 이것을
“자동 매칭 완료”라고 부르지 않는다.

### 이 조사에서 확정할 해석

V-10의 “신뢰도·하드웨어 티어 반영”은 하나의 점수로 합치지 않는다.

```text
hard filter   identity / node state / risk / tier / isolation / key protection /
              owner opt-in / 자원 / CUDA / durability / deadline
probability   T_est uncertainty + availability_window_fit + survival_rate
soft rank     normalized cost/performance + reliability + locality + fairness + load
```

이 분리가 §8.4, §13.2, §13.4, §14.3~14.4를 동시에 만족시키는 유일한
일관된 해석이다.

## 현재 구현의 정확한 경계

### `crates/coordinator`

- `CoordinatorConfig`가 `agent_device_id`와 공개키를 **한 개만** 받는다.
  Agent registry나 capability/heartbeat store가 없다.
- `run()`은 여러 연결을 다시 받을 수 있으나 `serve_one_connection()`을
  순차 실행한다. Agent별 task, session owner, per-Agent nonce/session state가 없다.
- Job 제출/queue/state store가 없다. `job_id`, `attempt_id`, holder Agent를
  CLI가 미리 정한다. 즉 Coordinator가 후보를 찾은 적이 없다.
- `issue_grant()`의 `ExecutionGrant`는 `manifest`, `manifest_hash`, `plan`,
  `PlacementRationale`를 채우지 않고 protobuf 기본값으로 둔다.
- durable `CoordinatorLeaseStore`는 안전한 Lease identity/epoch/revoke/expiry를
  제공하지만 Job reservation이나 GPU allocation store는 아니다.
- DoD-40이 storage-level 동시 최초 발급은 증명했으나 실제 다중 Agent
  wire 경쟁은 미착수로 이월했다.

### `crates/agent`

- Grant/Lease 서명, replay, durable fence watermark, 갱신/revoke/resume는
  구현돼 있다. scheduler가 사용할 안전한 실행 티켓 토대는 있다.
- 검증 성공 뒤 `record_start_checkpoint()`가 `.durability.writing`만 만든다.
  `manifest.json`과 데이터 파일은 없고 이 디렉터리는 startup GC 대상이다.
- Grant 안의 JobManifest 9~17단계 검증, GPU 존재/health/VRAM 재확인,
  환경 staging, V-06 정책 강제, entrypoint spawn, process tree 감시,
  checkpoint 완성, artifact/result 보고가 없다.
- `RESULT ok=true`는 handshake/Lease 경로 성공이지 Job 완료가 아니다.

### `crates/cli`

- `selftest`, `coordinator-agent-selftest`, 내부 stub 두 개만 있다.
  `nodes`, `job submit/status`, `drain` 제품 CLI가 없다.
- selftest 시나리오 39는 WRITING marker가 생기고 `manifest.json`은 **없음**을
  일부러 확인한다. 실제 Job 성공 시나리오는 없다.
- 모듈 설명의 “coordinator/agent 미착수” 문구 일부는 최신 Lease/reconnect
  구현과 어긋나지만, scheduler/runtime 미착수라는 결론은 정확하다.

### 이미 있는 schema와 빠진 producer

`GpuRequest`, `ResourceRequest`, `JobManifest`, `GrantedExecutionPlan`,
`PlacementRationale`, `RejectedCandidate`, `NodeRecord`는 proto에 있다. 그러나
현재 `NodeRecord`에는 GPU/resource/availability 전체 snapshot이 없고 그 값을
만드는 heartbeat/capability producer도 없다. **schema가 존재한다는 사실을
live scheduler 입력이 존재한다는 뜻으로 읽으면 안 된다.**

## 의존성 순서

```text
1 순수 hard filter
  ├─→ 2 durable Job/Attempt/Queue truth
  └─→ 3 다중 Agent registry + live PoolSnapshot
            ↓
4 v0.1 best-fit + reservation/admission
            ↓
5 선택된 Agent에 실제 Grant dispatch
            ↓
6 Agent runtime 실행 + 결과 보고
            ↓
7 LOST/drain/requeue/failover
            ↓
8 chance-constrained + fairness + exploration (V-10 완성)
            ↓
9 quarantine provenance + rationale/관측 + 다중 Agent E2E
```

조각 2와 3은 인터페이스 확정 뒤 병행할 수 있지만, 4는 둘 다 필요하다.
점수 함수부터 Coordinator에 붙이면 snapshot이 바뀌는 동안 같은 GPU를 두 Job이
동시에 선택하는 TOCTOU가 생긴다. 따라서 **계산과 durable reservation을 분리**하고,
reservation 실패 시 새 snapshot으로 다시 계산한다.

## 주요 위험과 금지된 지름길

- CLI의 고정 `agent_device_id`를 후보 목록처럼 반복해 “다중 Agent”로 부르지 않는다.
- protobuf 기본값을 “요구 없음”과 “관측 안 됨” 양쪽 의미로 쓰지 않는다.
  scheduler domain에서는 unknown을 별도 표현하고 fail-closed한다.
- `place()` 뒤 따로 GPU를 차감하는 비원자적 흐름을 만들지 않는다.
  snapshot version/CAS reservation 실패는 정상 재계산 경로다.
- reliability를 생존확률로 쓰거나 tier/risk와 한 점수로 합치지 않는다.
- `PlacementRationale`가 존재한다는 이유로 그 안의 값이 계산됐다고 간주하지 않는다.
- `AgentGrantAck`나 현재 `RESULT ok=true`를 Job 시작/완료 보고로 재사용하지 않는다.
- V-11을 CLI override 횟수로 구현하지 않는다. 서명된 위험 관측의 provenance가 먼저다.
- P0-07의 단일 GPU 결과를 노드 간 외삽 정확도 증명으로 확대하지 않는다.
