## CPU

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 상한 값 | **노드가 내놓은 코어 수**(Agent 새 설정 `--workload-cpu-cores <N>`, 설치기가 `--cpu-cores` 값을 그대로 넘긴다) | 한 노드에 한 작업이라 노드 상한 = 작업 상한이다. 작업의 `resources.cpu_cores` 로 더 좁히는 것은 **한 노드에 여러 작업이 들어갈 때** 뜻이 생긴다 — 지금은 안 한다(`TODO_VISION` 등록 — 트리거: 노드 배타 예약이 풀릴 때) |
| 거는 방법 | **`--cpus=<N>`**(CFS 할당량 — cgroup v2 `cpu.max`) | 코어를 고를 필요가 없고 docker · podman 공통이다. `--cpuset-cpus` 는 어느 코어인지 골라야 하고(소유자가 쓰는 코어와의 충돌 · NUMA) `cpuset` 컨트롤러 위임이 따로 필요하다 — 지금 안 한다 |
| 작업의 요구가 더 크면 | 실행하지 않는다(`LimitNotApplied` — "작업이 요구한 코어 k 가 이 노드가 내놓은 N 보다 크다") | 스케줄러가 이미 거르지만 Agent 는 Coordinator 가 보낸 값을 그대로 믿지 않는다(§0.2 의 정신). 서명된 Manifest 의 값이다 |
| 설정이 없으면 | 지금처럼 CPU 상한 없이 돈다 — 대신 **시작 줄에 적는다**(`CPU_LIMIT=none`) · node-doctor 가 WARN | 설치기를 거치지 않은 기존 노드를 한 번에 멈추지 않는다. 조용한 강등이 아니라 신호 있는 강등(`RULE.md` §3.2 예외 ②) |

## RAM — RamGiB 와 작업 메모리 상한의 관계

```text
RamGiB(설치 입력)                    노드가 내놓는 메모리. 가입 파일 → 배치 기준
--workload-commit-limit-bytes(Agent)  작업마다 거는 메모리 상한(컨테이너 --memory = --memory-swap, 호스트 경로는 Job Object · cgroup)
resources.ram_bytes(작업)             작업이 요구한 양 — 배치 때 RamGiB 와 비교된다
```

### 결정

- **설치기가 `--workload-commit-limit-bytes = RamGiB × 1GiB` 를 넘긴다**(556 수정). 두 값의 출처가 설치 입력 하나가 된다.
- 한 노드에 한 작업이라 작업 상한 = 노드가 내놓은 양이다. 작업의 `ram_bytes` 로 더 좁히는 것은 CPU 와 같은 이유로 지금 안 한다(같은 `TODO_VISION` 항목).
- 작업의 `ram_bytes` 가 노드 상한보다 크면 실행하지 않는다(CPU 와 같다).
- 런북에 적는다: 이 상한에는 `/tmp` · `/dev/shm` tmpfs 도 든다 · 스왑으로 새지 않게 `--memory-swap` 을 같게 둔다(그것이 실제로 걸렸는지는 위 2 가 대조한다) ·
  GPU 메모리(VRAM)와는 별개다.
- 기존 노드(설치기 전 · 인자를 따로 넣은 노드)는 바꾸지 않는다 — 다시 설치하거나 서비스 설정에 인자를 더한다(런북).

## 디스크 — 운영 방식과 코드 방식 비교

작업이 쓸 수 있는 곳(컨테이너 노드): 붙인 체크포인트 출력 폴더(`<루트>.workload-run/<시도>/checkpoints-out`) · tmpfs(메모리 상한에 든다) · 런타임이 만드는
docker 이미지 `VOLUME`(익명 볼륨 — podman 은 `--image-volume=ignore` 로 막았다) · 런타임 로그 저장소(stdout · stderr — 결함 539 · 551).
루트 파일시스템은 `--read-only` 라 쓰기 층을 거의 쓰지 않는다.

| 방법 | 막는 것 | 못 막는 것 | 조건 · 비용 | 등급 |
|---|---|---|---|---|
| **운영 A** 체크포인트 루트의 **부모 폴더**를 별도 파티션 · 할당량(XFS 프로젝트 할당량 · 루프백 파일시스템 · 전용 디스크) 위에 | 붙인 폴더에 쓰는 것 전부 — 커널이 `ENOSPC` 로 막는다(초과 없음) | 런타임 데이터 폴더(이미지 VOLUME · 로그 · 쓰기 층) — 그것도 제한된 곳에 두지 않는 한. ★ 같은 파일시스템의 **Agent 상태**(사건 표식 · 시작 기록)도 같이 차서 Agent 가 기동을 거부한다(510 반례) | root 설정 · 소유자 수고. 런북이 이미 권한다 | 강제(커널) |
| **운영 B** 런타임 데이터 폴더(docker `data-root` · podman `graphroot`)도 제한된 곳에 | 이미지 VOLUME · 로그 · 쓰기 층 | 소유자의 다른 컨테이너까지 같은 한도에 묶인다(사용자 컨테이너 불가침) | 런타임 재설정 — 이미지 다시 받기 | 강제(커널) |
| `docker --storage-opt size=` | 쓰기 층 | 붙인 폴더 · VOLUME · 로그. 루트가 읽기 전용이라 **거의 소용없다** | overlay2 + XFS pquota 등 특정 저장 드라이버만 | — (권하지 않음) |
| **코드 C** 주기 관측 — 실행 중 `<루트>.workload-run/<시도>` 의 **할당 크기**(겉보기 크기 아님 — 성긴 파일)를 N초마다 재고 작업의 `workspace_bytes`(없으면 노드의 WorkspaceGiB)를 넘으면 정지(멈춤 확인 → 로그 → 보고 FAILED · 사유) | 천천히 차는 경우 · 실수 | 관측 주기 사이에 빠르게 차는 경우(초과량 = 쓰기 속도 × 주기 — 예 1GB/s × 10초 = 10GB) · 붙인 폴더 밖(VOLUME · 로그) · 큰 폴더 순회의 I/O 비용 | Agent 코드 · 시험. 정지가 실패하면 불명 경로(단계 1 제안) | 억제(사후) — `degraded` 신호와 함께 |
| **코드 D** Agent 상태를 작업 쓰기 폴더와 **다른 파일시스템**에 둘 수 있게(예 `--workload-run-root`) | 작업이 디스크를 채워도 Agent 가 사건 표식을 쓰고 기동한다(510 반례의 "노드가 묶임") | 작업 쪽 파일시스템이 차는 것 자체 | Agent 설정 하나 · 경로 계산(`incident_dir_for` 등 형제 경로) 정리 | 가용성 |
| **코드 E** docker 에서 이미지 설정에 `VOLUME` 이 있으면 받지 않는다(`image inspect` 의 `Config.Volumes`) | 제한 밖 익명 볼륨 쓰기 | 로그 저장소 | 이미지 제약(VOLUME 을 쓰는 이미지는 다시 만들어야) | 거부(실행 전) |
| tmpfs 로 출력 폴더(`size=`) | 출력 폴더 크기 | — | 메모리를 먹는다 — 큰 체크포인트에 못 쓴다 | 강제(메모리) |

### 권장 (D-디스크 — 사용자 선택)

**운영 A(강제) + 코드 D(가용성) + 코드 E(구멍 막기)** 를 먼저, **코드 C** 는 그다음(사후 억제라 A 를 대신하지 못한다 — A 가 없는 노드에서의 조기 경보로 쓴다).
운영 B 는 소유자의 다른 컨테이너까지 묶어 권하지 않는다(런북에 선택지로만). 로그 저장소는 컨테이너 런타임 불확실 상태 설계 P1(로그 follow)과 같이 다룬다.
