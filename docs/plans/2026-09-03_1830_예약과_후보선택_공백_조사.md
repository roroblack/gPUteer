# 예약이 후보 선택에 안 보인다 — 결정 전 조사

**2026-09-03. 이 문서는 결정하지 않는다.** 나흘 뒤 독립 검수를 받은 뒤
바로 결정할 수 있도록 **사실만** 모았다.

## 무엇이 막혀 있는가

노드가 **둘**인데 두 번째 `scheduler-tick` 이 막힌다:

```text
TICK_REFUSED: node is already reserved: node=node-tick-a, job=..., attempt=...
```

`evaluate_eligibility` / `rank_best_fit` 은 **inventory 만** 본다. 예약은
다른 테이블에 있고 둘을 잇는 것이 없어, best-fit 이 늘 같은 노드를 골라
예약 관문에서 막힌다 — **비어 있는 노드가 있어도 그렇다.**

안전에는 문제가 없다(예약 관문이 중복을 막는다). 그러나 **루프를 돌리면
큐 맨 앞에서 영영 멈춘다** — 이것이 ④ 데몬화의 실질적 차단 요인이다.

회귀 테스트로 현재 동작을 고정해 뒀다:
`crates/cli/tests/scheduler_tick.rs::a_second_tick_is_blocked_by_the_first_reservation_even_with_a_free_node`
— **메우면 이 테스트가 실패하며 문서도 같이 고치라고 알린다.**

## 조사한 사실 넷

### 1. 예약과 inventory 는 **같은 DB 파일**에 있다

```sql
CREATE TABLE IF NOT EXISTS coordinator_node_reservations (
    node_id TEXT PRIMARY KEY
        REFERENCES coordinator_agent_inventory(node_id),   -- ★ 같은 파일
    job_id TEXT NOT NULL REFERENCES coordinator_jobs(job_id),
    ...
```

`staging_store.rs:235`. 외래 키가 성립하므로 **파일이 나뉘어 있지 않다** —
"두 DB 를 어떻게 잇나" 는 문제가 아니다. Rust 타입만 나뉘어 있다
(`CoordinatorInventoryStore` vs `CoordinatorStagingStore`).

### 2. `scheduler` crate 는 **순수하다**

```rust
pub fn evaluate_eligibility(
    pool: &PoolSnapshot,
    job: &JobRequirements,
    policy: &Policy,
) -> EligibilityReport
```

`filter.rs:7`. I/O·시계·DB·난수가 하나도 없다(`use std::fs`·`rusqlite`·
`SystemTime` 검색 결과 0건). 이 순수성은 우연이 아니라 `DoD-41` 이 세운
것이고 `DoD-54`·`DoD-55` 가 같은 형태를 반복했다 — **바깥에서 해소한
사실만 받는 커널**.

### 3. `CandidateSnapshot` 에는 예약을 담을 자리가 **없다**

`model.rs:94~`. `inventory_revision` 이 있지만 주석이 못박아 뒀다:

> admission CAS token, not a filtering or ranking input

즉 **지금 있는 revision 을 예약 표시로 재사용하면 안 된다** — 이미 다른
뜻을 가진 값이다.

### 4. 예약 실패는 **fence epoch 을 소모하지 않는다**

`staging_store.rs:1790` 의 회귀 테스트가 `rollback must not consume epoch`
로 고정하고 있다. **차순위 재시도가 싸다**는 뜻이다.

## 선택지 셋 — 각각 무엇을 얻고 잃는가

### A. `pool_snapshot()` 이 예약된 노드를 빼고 만든다

얻는 것 — 호출부가 아무것도 안 해도 된다. 한 곳만 고치면 된다.

잃는 것 — **snapshot 의 의미가 바뀐다.** 지금은 "inventory 가 이렇다" 는
사실인데, "지금 비어 있는 것이 이렇다" 는 **제어 상태**가 섞인다. 그러면
`inventory_revision` 이 무엇의 세대인지 애매해지고, `DoD-47` 의 CAS 가
"inventory 가 안 바뀌었다" 를 뜻하는지 "예약도 안 바뀌었다" 를 뜻하는지
불명확해진다. 순수 커널이 받는 입력에 제어 상태가 들어가는 것도 이 저장소
패턴과 어긋난다.

### B. 예약을 **입력으로 받아** hard-filter 가 거른다

얻는 것 — `DoD-54`·`DoD-55` 가 이미 쓴 형태다("바깥에서 해소한 사실만
받는다"). 순수성이 유지되고, 무엇을 근거로 걸렀는지 `EligibilityReport`
에 **이유로 남길 수 있다**(지금 다른 거부 사유들이 그렇듯).

잃는 것 — 새 입력 타입이 필요하고 호출부가 그것을 채워야 한다. 채우는
순간과 예약하는 순간 사이에 시차가 있으므로 **여전히 관문에서 막힐 수
있다** — 이 방법도 경쟁을 없애지는 못하고 흔한 경우를 줄일 뿐이다.
(그 시차는 `DoD-47` 의 CAS 가 이미 다루는 종류다.)

### C. `orchestrate` 가 차순위 후보로 재시도한다

얻는 것 — scheduler 도 snapshot 도 안 건드린다. 사실 4번 덕에 재시도가
싸다(epoch 을 안 태운다).

잃는 것 — **"한 tick = 한 시도" 라는 지금 의미가 깨진다.** 몇 번까지
재시도할지, 실패를 어떻게 보고할지가 전부 새 정책이고 규범이 없다.
`scheduler-tick` 이 "한 번을 정직하게" 하려던 설계와도 어긋난다.

## 결정에 필요한데 아직 없는 것

- ★★ **예약 해제가 오늘 아예 불가능하다 — 이게 더 근본적인 차단
  요인이다.** 추측이 아니라 코드가 그렇게 적어 뒀다:

      reservation_release.rs:37
      "아직 증명 못 함" 이라 **이 API 는 오늘 아무 예약도 풀지 못한다.**

  `DoD-62` 가 일부러 그렇게 만들었다 — 실행 종료 증명 없이 풀면 중복
  실행 위험이 생기므로, 호출부가 `RuntimeStopProof` 를 진술해야 하는데
  오늘 정직한 값이 전부 "아직 증명 못 함" 이다.

  **그래서 후보 선택만 고치면 두 번째 Job 은 돌지만 세 번째부터 다시
  막힌다.** 노드가 한 번 쓰이고 영영 잠긴다.
- **node-exclusive 를 유지할 것인가.** `DoD-47` 이 노드 단위로 잠갔고
  같은 노드의 다른 GPU 도 못 쓴다. GPU 단위로 내려가면 A·B 의 "예약된
  것" 정의 자체가 달라진다.
