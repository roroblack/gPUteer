## 문제 (요약)

체크포인트 파일을 읽는 여섯 곳이 파일을 통째로 메모리에 올린다. 그중 넷은 파일 **전부를 동시에** 올린다. 크기는 작업이 정한다. 게시하는 Agent,
장애 이어받기를 판정하는 Coordinator, 복원하는 다른 노드가 그 크기만큼 메모리를 쓴다(결함 문서의 표 1~6).

## 지키는 계약 (어느 쪽이든 바꾸지 않는다)

```text
write-once        데이터 파일은 내용 주소 이름(<논리 이름>.b3-<BLAKE3>)으로 한 번만 쓴다. 같은 이름이 있으면 **내용을 대조**한다(같으면 멱등, 다르면 거부)
원자적 확정       tmp → fsync(file) → rename → sync_dir. 매니페스트는 데이터 파일 확정 **뒤 마지막에**. 매니페스트 없는 폴더는 PARTIAL(GC 대상) — ADR-026
확정 전 재검증     commit 은 데이터 파일을 **디스크에서 다시 읽어** 해시를 대조한 뒤에만 매니페스트를 쓴다(commit.rs:386~389 의 순서가 계약)
해시              파일 digest = BLAKE3(내용) · 머클 잎 = BLAKE3(0x00 ‖ 내용) · 내부 = BLAKE3(0x01 ‖ 왼 ‖ 오) — protocol `merkle_root`(canonical.rs:403)
경로 방어          원본 · 공유 폴더 읽기는 링크를 따라가지 않는다(read_beneath — openat2 · reparse 거부)
```

## 스트리밍 설계 (별도 조각 — 여기서 구현하지 않는다)

### 핵심 관찰

해시는 둘 다 **조금씩 이어 계산**할 수 있다 — `blake3::Hasher::update` 를 고정 크기 버퍼(예 1MiB)마다 부르면 파일 digest 와 머클 잎을 한 번의 읽기로 같이
얻는다(잎은 `0x00` 을 먼저 넣은 두 번째 Hasher). 머클 내부 노드는 잎 digest(32바이트)만 필요하다. 그러니 **파일 내용을 메모리에 들고 있을 이유가 없다.**

### 바꾸는 것

```text
1  protocol   merkle_root_from_leaves(&[[u8;32]]) 추가 — 지금의 merkle_root 는 잎을 만든 뒤 이것을 부르게 바꾼다(같은 알고리즘 · 벡터 무변경을 시험으로 대조).
              ★ crates/protocol 은 공용 영역이다(RULE.md §4.2) — 함수 추가라 서명 · 스키마는 그대로지만 변경 제안 한 장을 먼저 낸다
              → 냈다: docs/contracts/proposals/2026-09-28_1104_머클루트_잎digest_입구.md(승인 대기)
2  atomic     write_once_streaming(dir, logical, reader, max_bytes) -> (stored_name, digest, leaf, size)
                · 고유 임시 이름(<logical>.<난수>.stream.tmp)에 버퍼로 복사하며 두 Hasher 를 갱신 · 읽은 바이트가 max_bytes 를 넘으면 중단(임시 파일 삭제)
                · fsync(file) → 이제 저장 이름이 정해진다 → **그 이름으로** 락(지금의 write_once 와 같은 이름 · 같은 락 파일)
                · 저장 이름이 이미 있으면: 크기가 다르면 즉시 불일치, 같으면 **스트리밍으로 해시**해 대조(통째 비교 없음) → 같으면 임시 파일 삭제 · 멱등
                · 없으면 rename(임시 → 저장 이름) → sync_dir. Windows 의 rename-over-existing 을 피하는 것은 지금과 같다(락 안에서 없음을 확인한 뒤)
              ★ 임시 이름이 락보다 먼저 생긴다 — 지금의 write_once 는 이름을 알고 시작해서 락이 먼저다. 달라지는 점: 같은 논리 이름을 동시에 둘이 스트리밍하면
                임시 파일이 둘 생긴다(이름이 달라 서로 덮지 않는다). 승자는 락에서 정해진다. gc_partial 은 매니페스트 없는 폴더의 .tmp 를 지우므로 죽은
                임시 파일도 거둔다(.stream.tmp 는 .tmp 로 끝나야 한다 — 등록된 이름과 겹치지 않게 논리 이름 규칙이 '.b3-' 를 예약한 것과 같은 방식으로)
3  commit     stage_reader(logical, reader, max) — 2 를 부르고 StagedFile 에 digest · 잎 · 크기를 적는다.
              verify_staged_files 는 파일마다 **스트리밍으로 다시 해시**해 digest 대조 · 잎을 다시 만든다(재검증 계약 그대로 — 디스크의 바이트를 본다).
              build_manifest 는 잎에서 merkle_root_from_leaves
4  shared     publish_directory 는 원본 파일을 링크 방어 핸들로 열어 stage_reader 에 넘긴다(read_beneath 대신 open_beneath_for_read).
              publish_or_recover 의 원본 대조는 파일마다 스트리밍 digest 를 확정본 매니페스트의 digest 와 대조(내용 비교 없음)
              verify_on_disk 는 파일마다 스트리밍 해시 · 크기 대조, 잎으로 머클 루트 — **내용을 돌려주지 않는다**(검증 결과만)
              restore 는 검증 뒤 파일마다 스트리밍 복사(임시 → fsync → rename). 복사하면서 **다시 해시**한다 — 검증과 복사 사이에 공유 저장소의 파일이
              바뀌는 경우(TOCTOU)를 복사본 기준으로 잡는다
5  durability verify_files 도 스트리밍 해시
```

### 스트리밍 뒤에도 남는 것

```text
디스크      메모리 대신 디스크를 쓴다 — 1TiB 성긴 파일은 복사하면 1TiB 를 쓴다(성긴 복사를 하지 않는다 — 해시가 0 바이트를 다 읽는다). 상한은 여전히 필요하다:
            작업의 workspace_bytes(서명된 요구) 또는 노드의 WorkspaceGiB 로 파일 · 전체 상한을 건다(자원 상한 설계 — 2026-09-28_0810 의 디스크 절과 같이)
시간        1TiB 를 해시하는 시간(수십 분). 게시기의 안정 판정 · 마지막 게시 백오프(약 15초)와 겹친다 — 상한이 이것도 막는다
공유 저장소  NAS 의 쓰기 속도 · 공간. 운영 문제로 남긴다
```

### 시험 (스트리밍 조각의 DoD)

- 버퍼보다 큰 파일(여러 버퍼)의 digest · 머클 루트가 통째 계산과 같다(벡터 대조 포함)
- 스트리밍 중 원본이 커지면(max_bytes 초과) 임시 파일이 남지 않고 거부
- 같은 논리 이름의 동시 스트리밍 둘 — 하나만 확정 · 다른 하나는 멱등 또는 불일치
- 저장 이름이 이미 있고 크기가 다르면 **읽지 않고** 거부(뮤테이션)
- restore 중 공유 파일이 바뀌면 복사본 해시로 거부
- 메모리 — 큰 파일(예 버퍼의 64배)을 처리하는 동안 최대 할당이 버퍼 크기 수준인지(할당 계측 · Windows 커밋 최대값)

## 지금 하는 것 — 임시 방어 (스트리밍 전까지)

### 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 방어 방식 | **크기 상한**(겉보기 크기) | 성긴 파일 감지는 모자라다 — 조밀한 30GB 파일도 같은 결과다. 겉보기 크기 상한은 성긴 파일(1TiB 로 보인다)도 함께 막는다. 성긴 파일 감지는 두지 않는다 |
| 상한 값 | **체크포인트 하나의 전체 1GiB**(`MAX_IN_MEMORY_CHECKPOINT_BYTES`, `crates/checkpoint/src/shared.rs`) | 지금 코드는 전체를 동시에 올리는 곳이 있어(표 2 · 3 · 4) 봉우리가 "전체 + 가장 큰 파일" 이다 — 상한이 1GiB 면 2GiB 안쪽. 신뢰망 노드 · Coordinator 가 이 정도는 견딘다고 **가정**한다(재지 않았다). 이 값을 넘는 정상 체크포인트는 **게시되지 않는다**(명시적 오류) — 스트리밍 조각이 풀 제한이다. 한 곳에 상수로 둔다(RULE.md §3.1) |
| 어디서 거나 | (a) 게시 전 — 원본 파일들의 크기 합을 먼저 보고 넘으면 `StagedCheckpoint::begin` **전에** 거부(공유 저장소에 아무것도 쓰지 않는다) (b) 읽을 때 — 모든 읽기를 "남은 예산만큼만" 읽고 넘으면 거부(보고 난 뒤 파일이 커지는 경우) (c) `verify_on_disk` — 매니페스트의 `total_bytes` 가 상한을 넘으면 읽기 전에 거부 · 파일마다 매니페스트의 `size_bytes` 만큼만 읽고 넘으면 거부 (d) `commit` 의 재검증 — 스테이징한 크기만큼만 (e) `write_once` 의 기존 파일 대조 — 크기가 다르면 읽지 않고 불일치 | 크기 검사만 하고 읽기를 통째로 두면 검사와 읽기 사이에 커진 파일에 뚫린다 — 읽기 자체를 묶는다 |
| 공개 함수 시그니처 | **바꾸지 않는다** — 상한은 안쪽에서 건다. 시험은 상한을 인자로 받는 안쪽 함수로 한다 | Agent · Coordinator 가 같은 함수를 그대로 부르면서 방어를 받는다(표 4 · 5 포함) |
| 넘으면 | 게시: `SHARED_CHECKPOINT_TOO_LARGE`(게시기는 지금처럼 `CHECKPOINT_PUBLISH_FAILED` 를 찍고 다음 훑기에 다시 — 크기만 보므로 싸다. 마지막엔 `CHECKPOINT_PUBLISH_LOST`) · 이어받기 판정: 그 체크포인트를 건너뛴다(지금의 검증 실패와 같은 길 — `failover.rs:305`) · 복원: `RESUME_REFUSED` | 지금 있는 실패 경로를 그대로 탄다 — 새 경로를 만들지 않는다 |
| 로컬 루트(표 7) | `verify_files` 도 매니페스트의 `size_bytes` 만큼만 읽는다 | 같은 도우미로 싸게 막을 수 있다 |

## 완료 기준 (임시 방어)

- [ ] 상한을 넘는 원본은 공유 저장소에 **아무것도 쓰기 전에** 거부된다(시험 · 뮤테이션)
- [ ] 크기 검사 뒤 커진 파일도 읽기에서 거부된다(묶인 읽기 시험 · 뮤테이션)
