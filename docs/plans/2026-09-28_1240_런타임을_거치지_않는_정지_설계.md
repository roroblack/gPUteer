## 문제

지금 소유자 정지는 `ContainerStopper::stop` → 런타임 CLI `kill`(시한 15초 · container.rs:848) → 새 조회로 멈춤 확인(한 번에 15초 · 최대 10번 ·
:893)이다. 런타임(데몬 · podman 잠금)이 멈추면 kill 도 조회도 시한을 넘기고, 소유자는 "멈추지 못했다" 만 본다. 컨테이너는 GPU 를 쥔 채 계속 돈다.

## 무엇을 구분해야 하나 — "GPU 를 비운다" 와 "정지를 증명한다" 는 다르다

```text
로컬 정지(§0.1)   소유자의 GPU · 메모리를 지금 비운다. 증거가 필요 없다 — 소유자 기계에서 소유자가 누른다
정지 증거(단계 1 MUST 3 · 단계 2 §4)
                 Coordinator 에 STOP_CONFIRMED 를 보내려면 "그 시도가 다시 돌 수 없다" 가 필요하다. 특히 불명 조건 (b)(종결되지 않은 기동 요청)는
                 프로세스를 죽여도 풀리지 않는다 — 멈춘 런타임에 쌓인 start 가 **나중에** 적용될 수 있다. 지금 증거는 "컨테이너를 지우고 새 조회가
                 '없음'" 뿐이다(CONTAINER_ABSENT_CONFIRMED · 단계 2 계약 §4)
```

★ 그래서 이 설계의 목표는 **로컬 정지**다. 런타임을 거치지 않고 프로세스를 끝내도 그것만으로 STOP_CONFIRMED 를 만들지 **않는다** — 아래 "결과 타입" 과
"시도 단위 기록" 이 이것을 코드 모양으로 강제한다.

## 불변식

```text
N1  **검사 시점에 무관한 프로세스가 보이면 아무것도 죽이지 않는다.** 대상은 Agent 가 이름을 정해 영속한 전용 위치뿐이고, 죽이기 직전 그 위치의
    직접 구성원까지 본다(아래). ★ 범위: 검사와 쓰기 사이에 **스스로 들어오는** 프로세스는 막지 못한다 — cgroup 사이를 옮기려면 그 트리에 쓸 권한이
    있어야 하므로, 위임 트리(Agent 계정)에서는 같은 계정 프로세스, root 트리에서는 root 만 그럴 수 있다. 스스로 들어온 것은 그 프로세스의 선택이다
N2  로컬 정지는 STOP_CONFIRMED · 예약 해제 · 재배치 · 사건 해제 어느 것도 만들지 않는다 — **뒤늦게 온 런타임 결과가 그것을 뒤집지도 않는다**(c2b ②)
N3  "비었다" 는 하위 트리 전체가 비었다는 커널 표시(cgroup.events populated 0)로만 말한다. 읽기 실패 · 시간 초과 · 지원 안 됨은 "로컬 정지 불명" 이다
N4  숫자 PID 를 저장했다가 나중에 그 숫자로 죽이지 않는다(PID 재사용)
```

## 대상의 신원 — 이름을 먼저 정해 적고, 구성마다 조건을 따로 확인한다 (c2b ①)

```text
순서       (1) 시도 전용 이름 `gputeer-att-<attempt 해시>` 를 정하고 **원장(단계 2 — "cgroup 경로" 칸)에 먼저 영속**한다
              (단계 2 가 승인 전이면 사건 표식 옆 파일 — 같은 형식)
           (2) 그 뒤에야 create 에 `--cgroup-parent` 로 넘긴다 · start
           → "기동했는데 위치를 모르는" 창이 없다 — 이름이 적히기 전에는 컨테이너가 없다. 디렉터리를 누가 언제 만드는지는 구성마다 다르다(아래 표)
```

|---|---|---|---|---|

| rootless podman · cgroupfs 드라이버 | Agent 가 위임 루트 아래 디렉터리로 미리(예상) | 경로(예상) | 미확인(M1) | Agent 계정(예상) · 위임이 없으면 불가 |

## 죽이기 직전 확인 — 경로가 아니라 연 핸들로 (c2b ③)

```text
열기       위임 루트(또는 root 도우미가 아는 루트)를 연 디렉터리 핸들에서 openat2(RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS)로 전용 cgroup 을 **한 번** 연다
           (checkpoint/src/platform.rs 의 기존 방식). `..` · 심볼릭 링크 · 루트 밖 · 루트 자체 → 거부
확인       그 핸들을 기준으로(openat — 경로를 다시 풀지 않는다):
           (a) 전용 cgroup 자신의 `cgroup.procs` 가 **비어 있다** — 전용 부모는 프로세스를 직접 담지 않는다(컨테이너 cgroup 만 담는다)
           (b) 하위 cgroup 이 **정확히 하나**이고 그 이름이 원장의 컨테이너 ID 와 맞는다
           (c) 하위 cgroup 아래의 모든 cgroup.procs 의 PID 가 그 컨테이너 PID 네임스페이스에 속한다(/proc/<pid>/ns/pid 가 컨테이너 init 의 것과 같다 — 예상)
           하나라도 아니면 아무것도 안 하고 LOCAL_STOP_UNKNOWN(대상 확인 실패)
쓰기       같은 핸들 기준 openat 으로 `cgroup.kill` 을 열어 1 을 쓴다 — 확인과 쓰기 사이에 경로가 바뀌어도 연 디렉터리는 그대로다
위임 한계   구성원을 신뢰할 수 없는 위임 환경(같은 계정 프로세스가 마음대로 드나드는 곳)은 N1 의 범위 밖이다 — 그 구성에서는 로컬 정지를 켜지 않거나,
           켜되 화면에 "같은 계정 프로세스가 스스로 들어오면 같이 끝난다" 를 적는다(S4)
원장 권한   원장 · 사건 표식은 Agent 만 쓴다(설치 폴더 권한 규칙) · 워크로드에 붙이지 않는다(컨테이너 마운트는 작업 폴더 · 입력뿐 — 지금 코드 그대로)
```

## 비었다의 판정

`cgroup.kill` 에 1 을 쓴 뒤 시한(아래 예산) 안에 그 전용 cgroup 의 `cgroup.events` 가 `populated 0` 이어야 LOCAL_TREE_EMPTY 다. `cgroup.procs` 는 직접 속한
프로세스만 보여 주므로 그것으로 판정하지 않는다(지금 호스트 쪽 `cgroup_is_provably_empty`(runtime-linux:431~)도 두 값을 다 본다).
읽기 실패 · threaded cgroup 의 EOPNOTSUPP · 시한 초과 → LOCAL_STOP_UNKNOWN.

(lib.rs:1669~1682 의 `TerminalObservation` · `stopped_by_owner`)에 반영한다. 로컬 정지를 이 `Ok` 에 붙이면 종결되지 않은 start 가 남은 채 정상 종결 보고가
나갈 수 있다. 그래서 결과를 나눈다:

|---|---|---|---|---|

지우고 확인한다". ★ 단계 3 설계의 결과 이름 목록에 local_tree_killed 를 더한다(단계 3 문서는 다음 개정에서 맞춘다).

### 시도 단위 기록 — 뒤늦은 137 이 로컬 정지를 덮지 않는다 (c2b ②)

```text
기록       원장에 시도마다 두 표시를 둔다: start_unresolved(start 가 성공으로 답하기 전 — 무응답 · 실패 응답 포함) · local_stop_done(로컬 정지를 한 번이라도 했다)
규칙       둘 중 하나라도 서 있으면, 그 뒤 런타임이 137(또는 어떤 종료)을 보고해도 **종결 보고를 보내지 않고 보류를 풀지 않는다** — 한 시점의 종료 관측은
           불명 조건 (b) 의 증거가 아니다(단계 2 계약 §4 · 단계 1 MUST 3). 이 시도를 닫는 길은 단계 2 §4 의 해제 명령(CONTAINER_ABSENT_CONFIRMED) 하나다
           둘 다 서 있지 않을 때만 RUNTIME_STOP_OBSERVED · ALREADY_EXITED 가 지금 경로(종료 보고)로 간다
두 경로 합치기  런타임 kill 과 로컬 kill 을 둘 다 보냈으면 local_stop_done 이 이미 서 있다 — 런타임이 137 을 먼저 보였어도 화면은 ambiguous 로 보이되
           보고 · 보류는 위 규칙을 따른다
```

## 플랫폼별 — 누가 그 프로세스를 끝낼 수 있나 (M2 한 줄 말고는 전부 예상)

| 구성 | 작업 프로세스 · cgroup 의 주인 | Agent 가 런타임 없이 끝낼 수 있나 | 수단(예상) |
|---|---|---|---|
| **리눅스 · rootless podman**(런북 권장) | 작업 · cgroup 모두 Agent 계정(keep-id · 사용자 위임 — 예상) | **위 네 조건 확인 뒤에만** | 전용 cgroup 의 `cgroup.kill` → `populated 0` |
| **리눅스 · rootful docker** | 리눅스 호스트에서는 작업이 `--user=<Agent uid>:<gid>`(exec.rs:470~ · container.rs:545) — userns-remap 이면 달라진다. init 이 곧 작업이다(`--init` 없음). shim · cgroup 은 root | **cgroup 경로는 아니오**(root 만 쓴다) · pidfd 보조 경로는 조건부(아래) | 아래 "pidfd 보조 경로" |

| **Windows · Docker Desktop(WSL2 백엔드)** | `docker-desktop` 배포판 안 | **지원되고 검증된 컨테이너 단위 경로 없음** | 마지막 수단: 엔진 전체 종료(`wsl --terminate docker-desktop` — 예상, 이름은 판마다 확인). ★ 소유자의 다른 컨테이너도 멈춘다(S1) |
| **Windows · podman machine** | 머신 VM 안(기본 WSL · Hyper-V 도 가능) | **지원되고 검증된 경로 없음 — 조사 전** | provider 별로 따로 조사. 마지막 수단은 머신 종료(S1) |

★ 재시작 정책은 두지 않는다(`create_args` 에 `--restart` 없음). 로컬로 끝낸 컨테이너를 런타임이 스스로 다시 띄우지는 않는다(예상). 쌓인 start 는 다르다.

### pidfd 보조 경로 — 쓸 수 있는 때가 좁다 (c2b ④)

```text
얻는 때     start 가 **성공으로 답한 뒤** inspect 로 PID 를 읽고 pidfd_open — 지금 흐름에서 손잡이는 start 응답(또는 시한) 뒤에 넘어간다(container.rs:1310~1358).
           그래서 start 무응답 · start 실패 응답 · start 와 pidfd 사이 · Agent 재시작 뒤에는 **pidfd 가 없다** — 그때는 이 경로 없음
검증       pidfd 를 얻은 **뒤에** (1) /proc/<pid>/status 의 NSpid 마지막 값이 1(그 PID 네임스페이스의 init) (2) /proc/<pid>/cgroup 이 그 컨테이너의 것
           (3) uid 가 Agent uid — 셋 다일 때만 쥔다. 아니면 버린다
효과       init 에 SIGKILL → init 이 끝나면 커널이 그 네임스페이스의 나머지를 끝낸다(예상 · M4)
적용       리눅스 호스트의 rootful docker(--user) 에서만. Windows 호스트 경로(user=None) · rootless podman(cgroup 경로가 있다)에는 쓰지 않는다
```

## root 도우미 — `wsl -u root` 는 소유자 버튼으로 좁혀지는 경계가 아니다

```text
사실       그 Windows 계정의 **어떤 프로세스든** `wsl -d <배포판> -u root` 로 그 배포판의 root 가 된다(기본 설정 · 암호 없음). Agent 가 이 길을 쓰든
           안 쓰든 이미 있는 능력이다 — 우리가 만드는 것은 아니다. 다만 우리 코드가 그 길을 **정상 경로로** 쓰게 되면, Agent 가 탈취되었을 때 그
           배포판의 root(그 안의 모든 프로세스 · 파일)로 곧장 이어진다는 것을 S2 에 적는다. "소유자 버튼에서만" 은 UI 규칙이지 보안 경계가 아니다
좁히기     배포판 이름은 설치 때 고정 · 허용 목록. 셸 문자열을 넘기지 않는다 — 배포판 안에 설치한 고정 도우미(`gputeer-cgkill <attempt 해시>`)만 부른다.
           도우미는 위 "죽이기 직전 확인" 을 그대로 한다 — 하나라도 맞지 않으면 아무것도 안 한다(N1)
한계       도우미를 root 로 부를 수 있는 사람은 도우미 없이도 root 다 — 도우미는 **실수 · 버그**의 범위를 좁힐 뿐이다
```

## 즉시 — 시간 예산

지금 순서(런타임 kill 15초 → 조회 15초씩)를 기다리면 로컬 정지까지 30초 넘게 걸릴 수 있다(§0.1 "즉시" 와 어긋남). 그래서:

```text
소유자 버튼   런타임 kill 을 보내고 **2초**(목표 — 재지 않았다) 안에 멈춤이 관측되지 않으면, 대상 확인을 통과한 로컬 손잡이를 곧바로 쓴다.
             런타임 쪽 확인 · 정리는 뒤에서 계속한다(비동기 — 단계 3 의 접수 번호로 결과가 바뀐다)
목표 지연     버튼 → 로컬 kill 발사 ≤ 2초 · 발사 → populated 0 확인 ≤ 5초. 넘으면 LOCAL_STOP_UNKNOWN. ★ 목표값이다 — M2 에서 잰 것은 kill → 종료 43ms 한 번
```

단계 3(상시 화면)과의 연결: 지금 시도의 우선 정지 경로가 이 순서를 쓴다. 회차 자식이 죽으면 루프가 원장의 전용 cgroup 을 같은 방식으로 쓸 수 있다.
