## 문제

지금 소유자 정지는 `ContainerStopper::stop` → 런타임 CLI `kill`(시한 15초 · container.rs:848) → 새 조회로 멈춤 확인(한 번에 15초 · 최대 10번 ·
:893)이다. 런타임(데몬 · podman 잠금)이 멈추면 kill 도 조회도 시한을 넘기고, 소유자는 "멈추지 못했다" 만 본다. 컨테이너는 GPU 를 쥔 채 계속 돈다.

## 무엇을 구분해야 하나 — "GPU 를 비운다" 와 "정지를 증명한다" 는 다르다

```text
로컬 정지(§0.1)   소유자의 GPU · 메모리를 지금 비운다. 증거가 필요 없다 — 소유자 기계에서 소유자가 누른다
정지 증거(단계 1 MUST 3 · 단계 2 §4)
                 Coordinator 에 STOP_CONFIRMED 를 보내려면 "그 시도가 다시 돌 수 없다" 가 필요하다. 특히 불명 조건 (b)(종결되지 않은 기동 요청)는
                 프로세스를 죽여도 풀리지 않는다 — 멈춘 런타임에 쌓인 start 가 **나중에** 적용될 수 있다. 지금 증거는 "컨테이너를 지우고 새 조회가
                 '없음'" 뿐이다(CONTAINER_ABSENT_CONFIRMED)
```

★ 그래서 이 설계의 목표는 **로컬 정지**다. 런타임을 거치지 않고 프로세스를 끝내도 그것만으로 STOP_CONFIRMED 를 만들지 **않는다** — 아래 "결과 타입" 이
이것을 코드 모양으로 강제한다.

## 불변식

```text
N1  **무관한 프로세스가 하나라도 대상에 섞일 수 있으면 아무것도 죽이지 않는다.** 대상은 Agent 가 만들고 영속한 전용 위치뿐이다
N2  로컬 정지는 STOP_CONFIRMED · 예약 해제 · 재배치 · 사건 해제 어느 것도 만들지 않는다
N3  "비었다" 는 하위 트리 전체가 비었다는 커널 표시로만 말한다. 읽기 실패 · 시간 초과 · 지원 안 됨은 "로컬 정지 불명" 이다
N4  숫자 PID 를 저장했다가 나중에 그 숫자로 죽이지 않는다(PID 재사용)
```

## 대상의 신원 — 기동 **전에** 전용 위치를 만들고 적는다 (c2 ①)

```text
순서       (1) Agent 가 시도 전용 cgroup `<Agent 위임 루트>/gputeer-att-<attempt 해시>` 를 만든다(비어 있음을 확인)
           (2) 그 경로를 원장(단계 2 — "cgroup 경로" 칸)에 영속한다 · 단계 2 가 승인 전이면 사건 표식 옆 파일(같은 형식)
           (3) 그 뒤에야 create(`--cgroup-parent=<그 경로>`) · start. 컨테이너 cgroup 은 그 아래 **하나만** 생긴다
           → "기동했는데 위치를 안 적은" 창이 없다 — 적기 전에는 컨테이너가 없다
검증       정지 때 경로 문자열을 믿지 않는다. Agent 위임 루트를 연 디렉터리 핸들에서 openat2(RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS)로 내려간다
           (checkpoint/src/platform.rs 의 기존 방식). `..` · 심볼릭 링크 · 루트 밖 · 루트 자체 · 하위 cgroup 이 둘 이상이거나 원장의 컨테이너 ID 와
           이름이 맞지 않으면 → 아무것도 안 하고 "로컬 정지 불명(대상 확인 실패)"
원장 권한   원장 · 사건 표식은 Agent 만 쓴다(설치 폴더 권한 규칙) · 워크로드에 붙이지 않는다(컨테이너 마운트는 작업 폴더 · 입력뿐 — 지금 코드 그대로)
PID 경로    cgroup 을 못 쓰는 구성에서만. start 직후 **pidfd 를 얻어 Agent 가 계속 쥔다**(얻은 뒤에 /proc/<pid>/cgroup 이 그 컨테이너의 것인지 대조 —
           아니면 버린다). Agent 가 다시 뜨면 pidfd 가 없다 → PID 경로 없음(숫자로 다시 열지 않는다 · N4)
예상       `--cgroup-parent` 의 형식은 cgroup 드라이버마다 다르다 — systemd 드라이버는 slice 이름(`gputeer-att-….slice`), cgroupfs 는 경로(예상 · 재지 않았다).
           위임 루트가 없는 구성은 cgroup 경로가 없다
```

## 비었다의 판정 (c2 ②)

`cgroup.kill` 에 1 을 쓴 뒤 시한(아래 예산) 안에 그 cgroup 의 `cgroup.events` 가 `populated 0` 이어야 LOCAL_TREE_EMPTY 다. `cgroup.procs` 는 직접 속한
프로세스만 보여 주므로 쓰지 않는다(하위 cgroup 의 생존을 못 본다 — 지금 호스트 쪽 `cgroup_is_provably_empty`(runtime-linux:431~)도 두 값을 다 본다).
읽기 실패 · threaded cgroup 의 EOPNOTSUPP · 시한 초과 → LOCAL_STOP_UNKNOWN.

## 결과 타입 — 성공 하나로 접지 않는다 (c2 ③)

지금 `ContainerStopper::stop()` 은 `Result<(), String>` 이고(container.rs:845), `Ok` 면 패널이 `owner_stopped` 를 적고(owner_panel.rs:188 부근) 종료 보고에
반영한다(lib.rs:1682 부근). 로컬 정지를 이 `Ok` 에 붙이면 **종결되지 않은 start 가 남은 채 정상 종결 보고**가 나갈 수 있다. 그래서 결과를 나눈다:

| 결과 | 뜻 | 종료 보고 · Coordinator | 사건 · 노드 | 소유자 화면 |
|---|---|---|---|---|
| RUNTIME_STOP_OBSERVED | 런타임이 137 비-OOM 을 보였다(단계 3 의 ambiguous 와 같다) | 지금과 같다 | 지금과 같다 | "멈췄다(원인 구분 불가)" |
| ALREADY_EXITED | 스스로 먼저 끝났다 | 지금과 같다 | 지금과 같다 | "이미 끝나 있었다" |
| **LOCAL_TREE_KILLED** | 우리 cgroup 을 kill 했고 하위 트리가 비었다 · 런타임은 모른다 | **종결 보고를 보내지 않는다** — 시도는 불명(단계 1 RUN_UNKNOWN · 단계 2 보류) | 사건 표식 · 원장 OPEN · 노드 차단 유지 | "GPU 는 비웠다 — 기록된 프로세스 트리만. 런타임이 멈춰 있어 **쌓인 기동 요청으로 다시 뜰 수 있다**. 런타임이 살아나면 지우고 확인한다" |
| CONTAINER_ABSENT_CONFIRMED | 지우고 새 조회가 "없음" | 단계 2 §4 해제 명령만 STOP_CONFIRMED 를 만든다 | 해제 명령으로만 | "완전히 정리됐다" |
| LOCAL_STOP_UNKNOWN · UNKNOWN | 판정 못 함 | 보내지 않는다 | 유지 | "멈췄는지 모른다" + 이유 |

★ LOCAL_TREE_KILLED 뒤에 컨테이너가 다시 뜨면(쌓인 start) 그것은 같은 전용 cgroup 아래 생긴다 — 소유자는 다시 누를 수 있고, 같은 판정을 거친다.

## 플랫폼별 — 누가 그 프로세스를 끝낼 수 있나 (M2 한 줄 말고는 전부 예상)

| 구성 | 작업 프로세스 · cgroup 의 주인 | Agent 가 런타임 없이 끝낼 수 있나 | 수단(예상) |
|---|---|---|---|
| **리눅스 · rootless podman**(런북 권장) | 작업 · cgroup 모두 Agent 계정(keep-id · 사용자 위임) | **예(예상)** | 전용 cgroup 의 `cgroup.kill` → `populated 0`. 위임이 없는 구성은 pidfd 경로 |
| **리눅스 · rootful docker** | 작업 프로세스는 `--user=<Agent uid>:<gid>`(exec.rs:470~ · container.rs:545) — userns-remap 이면 달라진다. init 이 곧 작업이다(`--init` 없음). shim · cgroup 은 root | **구성별 실측 필요** | cgroup 은 root 소유라 못 쓴다(예상). 작업이 Agent uid 이고 컨테이너 PID 네임스페이스의 init 임이 확인되면 **pidfd 로 init 에 SIGKILL** — init 이 끝나면 커널이 그 네임스페이스의 나머지를 끝낸다(예상). 확인 못 하면 "못 멈춘다" |
| **Windows 호스트 · WSL 배포판 안 docker**(x600 구성) | 그 배포판의 root(dockerd) · 작업은 위와 같이 Agent uid | **예일 수 있다** — M2 가 기제를 봤다 | `wsl -d <고정 배포판> -u root` 로 전용 도우미를 실행 → 전용 cgroup 의 `cgroup.kill` 하나만. 아래 "root 도우미" 참조 |
| **Windows · Docker Desktop(WSL2 백엔드)** | `docker-desktop` 배포판 안 | **지원되고 검증된 컨테이너 단위 경로 없음** | 마지막 수단: 엔진 전체 종료(`wsl --terminate docker-desktop` — 예상, 이름은 판마다 확인). ★ 소유자의 다른 컨테이너도 멈춘다(S1) |
| **Windows · podman machine** | 머신 VM 안(기본 WSL · Hyper-V 도 가능) | **지원되고 검증된 경로 없음 — 조사 전** | provider 별로 따로 조사: WSL 이면 위 x600 행과 같은 길이 있을 수 있다 · Hyper-V 면 `podman machine ssh`(그것도 podman) 말고 VM 접근 · cgroup 권한을 봐야 한다. 마지막 수단은 머신 종료(S1) |

★ 재시작 정책은 두지 않는다(`create_args` 에 `--restart` 없음). 로컬로 끝낸 컨테이너를 런타임이 스스로 다시 띄우지는 않는다(예상). 쌓인 start 는
다르다 — 위 "정지 증거".

## root 도우미 — `wsl -u root` 는 소유자 버튼으로 좁혀지는 경계가 아니다 (c2 ⑥)

```text
사실       그 Windows 계정의 **어떤 프로세스든** `wsl -d <배포판> -u root` 로 그 배포판의 root 가 된다(기본 설정 · 암호 없음). Agent 가 이 길을 쓰든
           안 쓰든 이미 있는 능력이다 — 우리가 만드는 것은 아니다. 다만 우리 코드가 그 길을 **정상 경로로** 쓰게 되면, Agent 가 탈취되었을 때 그
           배포판의 root(그 안의 모든 프로세스 · 파일)로 곧장 이어진다는 것을 S2 에 적는다. "소유자 버튼에서만" 은 UI 규칙이지 보안 경계가 아니다
좁히기     배포판 이름은 설치 때 고정 · 허용 목록. 셸 문자열을 넘기지 않는다 — 배포판 안에 설치한 고정 도우미(`gputeer-cgkill <attempt 해시>`)만 부른다.
           도우미는 인자로 받은 해시로 **자기가 아는 위임 루트 아래** 전용 cgroup 을 openat2 로 찾아 `cgroup.kill` 하나만 연다. 원장 경로 · 컨테이너 ID ·
           하위 cgroup 개수가 하나라도 맞지 않으면 아무것도 안 한다(N1)
한계       도우미를 root 로 부를 수 있는 사람은 도우미 없이도 root 다 — 도우미는 **실수 · 버그**의 범위를 좁힐 뿐이다
```

## 즉시 — 시간 예산 (c2 ⑦)

지금 순서(런타임 kill 15초 → 조회 15초씩)를 기다리면 로컬 정지까지 30초 넘게 걸릴 수 있다(§0.1 "즉시" 와 어긋남). 그래서:

```text
소유자 버튼   런타임 kill 을 보내고 **2초**(목표 — 재지 않았다) 안에 멈춤이 관측되지 않으면, 대상 확인을 통과한 로컬 손잡이를 곧바로 쓴다.
             런타임 쪽 확인 · 정리는 뒤에서 계속한다(비동기 — 단계 3 의 접수 번호로 결과가 바뀐다)
목표 지연     버튼 → 로컬 kill 발사 ≤ 2초 · 발사 → populated 0 확인 ≤ 5초. 넘으면 LOCAL_STOP_UNKNOWN. ★ 목표값이다 — M2 에서 잰 것은 kill → 종료 43ms 한 번
판정 합치기   두 경로가 모두 결과를 내면 표의 뜻이 더 약한 쪽을 보이지 않는다 — 런타임이 137 을 보였으면 RUNTIME_STOP_OBSERVED, 아니면 로컬 결과
```

단계 3(상시 화면)과의 연결: 지금 시도의 우선 정지 경로가 이 순서를 쓴다. 회차 자식이 죽으면 루프가 원장의 전용 cgroup 을 같은 방식으로 쓸 수 있다.

## 시험 · 실측 (negative test — `RULE.md` §6)

```text
가짜 런타임 · 가짜 cgroup 트리(단위 시험)
T1  kill 이 시한을 넘기면 로컬 경로로 넘어간다 · 결과는 LOCAL_TREE_KILLED · 종결 보고 없음 · STOP_CONFIRMED · 예약 해제 · 사건 해제 · 재배치 **어느 것도 없음**
T2  로컬 수단이 없는 구성 — "못 멈춘다" · 성공이라 하지 않는다

T4  하위 cgroup 에만 살아 있는 프로세스 — cgroup.procs 는 비어도 populated 1 → LOCAL_TREE_EMPTY 아님

T6  PID 재사용: 저장된 숫자 PID 만 있고 pidfd 없음(Agent 재시작 뒤) → PID 경로 쓰지 않음 · pidfd 를 얻은 뒤 /proc cgroup 불일치 → 버림
T7  기록 창: 전용 cgroup 영속 전 Agent 사망 → 컨테이너가 없다(create 전) · 영속 뒤 create 전 사망 → 빈 전용 cgroup 을 다음 기동이 정리
T8  런타임 회복 뒤 쌓인 start 가 적용됨 → 같은 전용 cgroup 아래 다시 뜸 · 화면에 보임 · 다시 누르면 같은 판정
T9  로컬 kill 과 자연 종료 137 이 겹침 → RUNTIME_STOP_OBSERVED(ambiguous) 또는 LOCAL_TREE_KILLED — 어느 쪽도 STOP_CONFIRMED 아님
T10 반복 정지 · 동시 정지 → 같은 결과 · kill 한 번 이상 무해
T11 root 도우미: 허용 목록 밖 배포판 · 잘못된 해시 · 셸 메타문자 → 거부 · 아무것도 안 함
T12 시간 예산: 런타임이 답하지 않을 때 버튼 → 로컬 kill 발사까지 2초 안(가짜 시계)
실측(x600 · 사용자 허가 범위 — E: 만 · 사용자 컨테이너 불가침)
```
