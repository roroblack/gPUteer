# 허가증이 만료된 노드를 어떻게 멈추는가 — 4층 설계

> 작성 2026-09-09 · 성격 **설계 제안(사용자 방향 지시 반영)** ·
> 근거 2026-09-08~09 실측 4건 + 독립 검수 3건

## 0. 한 줄

**한 층으로 못 푼다.** 층마다 막는 실패가 다르고, 아래로 갈수록 조건이
가혹해진다. 위층이 닿지 않을 때 아래층이 받는다.

```text
1층  손이 안 닿게  노드가 바깥에 직접 손을 뻗지 않는다  모든 OS 동일
2층  대표 PC       같은 망의 이웃이 관측한다          망이 살아 있을 때
3층  각자의 시간   노드가 스스로 멈춘다                OS 마다 등급이 다르다
4층  예약          증거가 왔을 때만 자리를 비운다      마지막 장부
```

★ 사용자가 이 순서를 지시했다(2026-09-09). 아래는 그것이 코드·규범과
  어떻게 맞물리는지 확인한 결과다.

## 1. 왜 한 층으로 안 되나 — 이틀치 조사의 결론

`reservation_release.rs:85` 가 문제의 핵심을 한 줄로 적어 뒀다:

> fence 일치는 **프로세스 종료의 증명이 아니다** — 둘을 섞어 말하면 안 된다

허가증이 만료돼도 그 기계에서 돌던 프로세스는 계속 돈다. 그래서
"만료됐으니 다른 기계에 다시 띄우자" 가 **중복 실행**을 만든다.

쿠버네티스도 같은 자리에서 막혀 있다. 시한 기능(`activeDeadlineSeconds`)이
있지만 **그것을 강제하는 것이 쿠버네티스 자신**이라, 그 프로세스가 죽거나
망이 갈라지면 시한도 같이 사라진다.

★ 그리고 **모든 OS 를 아우르는 표준이 없다**(2026-09-09 조사):

```text
OCI 컨테이너 표준     자원 설정을 linux·windows·solaris·vm 으로 **분기**한다.
                      `timeout` 은 훅에만 붙고 작업 프로세스엔 안 붙는다
쿠버네티스 시한       모든 곳에서 되지만 **사용자 공간**이 강제한다
POSIX RLIMIT_CPU      커널이 강제하지만 POSIX 계열만
systemd RuntimeMaxSec 커널이 강제하지만 리눅스만 · root 필요
Job Object JOB_TIME   커널이 강제하지만 윈도우만 · CPU 시간
```

**여러 OS 에서 되는 것은 전부 사용자 공간이고, 커널이 강제하는 것은
전부 한 OS 전용이다.** 둘 다 만족하는 표준은 없다.

## 2. 1층 — 손이 안 닿게 한다

★★ **2026-09-10 전면 수정.** 여기 원래 "중계(포워드 프록시)로 길목을
   잡는다" 고 적었다. 사용자가 "그거 다 어렵다" 고 지적했고, 맞다.
   길목을 잡으려면 셋 중 하나가 필요한데 전부 비싸다:

```text
대표 PC 가 실제 게이트웨이가 된다   망 구성을 바꿔야 한다 — 사람 손
노드에 방화벽 규칙을 건다            플랫폼마다 다르고, 프로세스 한 건만
                                     막는 것은 P0-02 가 선행이다
작업이 알아서 프록시를 쓰게 한다     협조하는 작업에만 통한다
```

**막을 필요가 없게 만들면 이 셋이 전부 사라진다.** 아래 셋으로 바꾼다.
공통점은 **전부 제출·배치 시점의 판단이지 우리가 운영하는 설비가 아니라는
것**이다. 망 구성도, 상시 프록시도, 방화벽도 필요 없다.

### 1-A. 부작용을 노드가 아니라 우리가 실행한다 (`outbox`)

작업이 "이걸 저기에 써 달라" 는 **요청서를 결과물에 담고**, 우리가 그
결과를 받아들인 뒤에 **우리가 대신 실행**한다.

```text
허가증이 만료된 노드의 결과물 -> 펜스에서 이미 거부된다
                              -> 거기 담긴 요청서는 실행되지 않는다
=> **중복 실행이 "중복 결과물" 이 되고, 그건 이미 걸러내고 있다**
```

노드는 우리 말고 아무 데도 안 나가면 되므로 **관문 자체가 사라진다.**

★ 이건 이미 계획에 있다 — 여러 evidence 가 "durable outbox 없음" 을
  미착수로 반복해 적어 뒀다(`DoD-47`·`48`·`49`). 새 개념이 아니다.
★ 한계: **실행 중 살아 있는 상호작용이 필요한 작업에는 안 맞는다.**
  부작용이 끝에 몰린다.

### 1-B. 열쇠에 짧은 수명을 준다

바깥 API 를 부르려면 보통 자격증명이 필요하다. 그것을 **우리가 짧은
수명으로 발급**하고 계속 갱신하게 한다.

```text
허가증 만료 -> 새 자격증명을 안 준다 -> 몇 분 안에 그 작업은
               바깥에 아무것도 못 한다
★ 막는 주체가 **상대 서비스**다. 만료된 자격증명을 거부하니까.
  우리는 망에 아무것도 짓지 않는다 — 발급 지점 하나면 된다
```

★ **§4 의 "갱신해야 유지된다" 원칙 그대로**다(아래 참조).
★ 한계: 상대가 짧은 수명 자격증명을 받아 줘야 한다. 사용자가 영구
  API 키를 작업에 직접 심으면 아무것도 못 막는다 — 그건 **정책으로**
  요구해야 한다.

### 1-C. 보장 못 하는 곳에는 안 보낸다 (★ 이미 동작한다)

`crates/scheduler/src/filter.rs:331` 이 **이미 이걸 한다** — 격리 등급이
낮은 노드에는 부작용 있는 작업을 안 보낸다:

```text
ThirdPartyJobMustBePureOnRestrictedIsolation
ThirdPartySensitiveDataForbiddenOnRestrictedIsolation
```

같은 방식에 조건을 하나 더 붙이면 된다 — 정지를 보장할 수 있는 노드에만.
**새로 만드는 게 아니라 확장이다.**

### ★ 그리고 이 문제의 급한 정도를 낮춰 잡아야 한다

`proto/common.proto:126` 이 이미 이렇게 적어 뒀다:

> `SIDE_EFFECT_CLASS_SIDE_EFFECTING` — 비멱등 외부 효과. **중복 실행을
> 억제하되 보장하지 못한다.** `acknowledge_duplicate_risk = true` 가 필요하다

즉 **계약이 이미 "보장 못 한다" 고 말하고 제출자의 동의를 받게 돼 있다.**
지금 하려는 것은 깨진 약속을 고치는 게 아니라 **약속보다 잘하려는 것**이다.
좋은 일이지만 급하지 않고, 그러면 **비싼 방법을 쓸 이유가 없다.**

### 이미 있는 재료 (참고 — 위 셋은 이걸 안 써도 된다)
```text
proto/common.proto:301  NetworkPolicy — staging/runtime allow_hosts · mediated_dns
서명 대상 필드 54       변조가 서명 검증에서 거부됨(DoD-04 실측)
proto/lease.proto:243   operation_id = BLAKE3(job_id||attempt_id||seq)
                        "Hub/CAS 는 (fence_epoch, operation_id) 로 중복을 판정"
                        -> **우리 자원에 대해서는 이미 멱등이 보장된다**
```

### 없는 것
```text
durable outbox 가 없다 (계획에만 있다)
방화벽을 실제로 부르는 코드가 없다 — 위 셋을 쓰면 **필요 없어진다**
자격증명 발급 지점이 없다
```

## 3. 2층 — 대표 PC: 망이 갈라져도 이웃은 본다

중계가 안 닿을 때(WAN 단절, 중계 장애) 같은 망의 다른 기계는 여전히
그 노드를 본다. 그 관측을 신고하게 한다.

### ★ 이 층은 이미 구현돼 있다
```text
proto/lease.proto:322       NeighborUnreachableReport
                            (ADR-033 §7 의 "관측 층")
coordinator/src/neighbor_report_store.rs   신고 저장
coordinator/src/node_liveness_store.rs     생존 관측 영속화
scheduler/src/liveness.rs                  판정 커널
DoD-63·64·65                               wire 메시지·저장소·연결 완료
```

### 그런데 이 층은 **결정하지 않는다** — 그게 설계다
`liveness.rs:32-44` 가 스스로 적어 뒀다:

> "연락이 안 된다" 는 "죽었다" 가 아니다. 네트워크가 갈라졌으면 대상
> 노드는 멀쩡히 계속 실행 중이다. 그 상태에서 다른 GPU 에 같은 작업을
> 다시 띄우면 **두 번 돈다.**
>
> 그래서 이 커널에는 `Dead` 라는 값이 없다. 가장 나쁜 판정이
> `Silent`(정해진 시간 안에 소식 없음)이고, 그것은 **사실 진술이지
> 결정이 아니다.**

★ 그리고 같은 파일이 경고한다 — "`Dead` 가 없는 것 자체는 강제 장치가
  아니다. 지금 안전한 이유는 **재배정 소비자가 아직 하나도 없어서**다."

즉 2층의 역할은 **1층이 못 본 것을 보여 주는 것**이지 정지시키는 것이
아니다. 정지는 3층이, 자리 회수는 4층이 한다.

### 대표 PC 가 더 할 수 있는 것
연구실·LAN 처럼 신뢰 등급이 높은 기계가 있으면 그 기계가 **1층의 중계를
대신** 맡을 수 있다. 원리는 1층과 같고 위치만 다르다. 지연이 줄고,
WAN 이 끊겨도 LAN 안에서는 관문이 산다.

## 4. 3층 — 각자의 시간: 노드가 스스로 멈춘다

바깥 어디에도 안 닿을 때 마지막으로 남는 것. **소유자를 위한 층**이다
(§0.1 — 남의 하드웨어를 인질로 잡지 않는다).

### 2026-09-09 실측 — 두 OS 다 감시 프로세스 없이 커널이 강제한다
```text
Linux   systemd-run --scope -p RuntimeMaxSec
        띄운 프로세스를 SIGKILL 해도 시한대로 발동(3초에 죽였는데 8초에 정지)
        정지 여유 안에서 체크포인트를 쓰게 해 준다 — 규범 §209 그대로
        신호를 무시하는 작업도 죽는다
        ★ **root 필요**. 비-root 는 거부됨

Windows JOB_OBJECT_LIMIT_JOB_TIME
        작업 개체 **손잡이를 닫은 뒤에도** 커널이 종료시킨다
        (0xC0000044 = 할당량 초과)
        ★ **권한 불필요**
        ★ 단 **CPU 시간**이라 어림이고, **정지 여유가 없다**(즉시 종료)
```
근거 `docs/evidence/_raw/운영체제_시한_실측_2026-09-09.txt`
     `docs/evidence/_raw/윈도우_커널_시한_실측_2026-09-09.txt`

### 커널 시한과 살아 있는 감시는 서로의 구멍을 덮는다
```text
                              커널 시한        살아 있는 감시
에이전트가 죽는다                 O                 O
에이전트가 얼어붙는다             O(계산 중이면)      X
감시가 얼어붙는다                 O(계산 중이면)      X
작업이 멈춰서 VRAM 만 쥔다        X                 O
```
둘 다 못 잡는 경우 = 감시도 얼고 작업도 계산을 안 한다 = 아무것도 계산하지
않으면서 VRAM 만 붙들고 있는 상태. **가장 덜 해로운 경우다.**

### 아직 안 건다
`runtime-windows/src/lib.rs:674` 가 `JOB_MEMORY | KILL_ON_JOB_CLOSE` 만
건다. `JOB_TIME` 은 안 건다 — **한 줄 자리다.**
Linux 쪽 `systemd-run` 연결도 없다.

## 5. 4층 — 예약: 증거가 왔을 때만 자리를 비운다

여기는 **바꾸지 않는다.** 2026-09-09 독립 검수가 만료 기반 회수를 기각한
이유 중 하나가 그대로 남아 있기 때문이다:

```text
예약 행이 증거 저장소 **둘**의 외래키다
  attempt_report_store.rs:224
  checkpoint_manifest_store.rs:219
지우면 뒤늦게 도착한 정상 종료 보고가 ReservationNotFound 로 버려지고,
그러면 정상 해제 경로가 **영영** 못 돈다. 체크포인트도 같이 버려진다(§0.3)
```

★ 1~3층이 아무리 튼튼해져도 이건 안 풀린다. **다른 문제다.**

### 이 층의 진짜 뿌리 — 시도 기록이 "끝났다" 를 못 말한다
```text
staging_store.rs:607  INSERT ... VALUES (?1, ?2, 'CREATED', ...)
                                          ^^^^^^^^^ 글자로 박혀 있다
fetch_attempt         저장된 값을 무시하고 무조건 Created 를 돌려준다
```
"이 시도는 끝났다" 를 적어 둘 곳이 없어서, **예약 행의 부재**가 그 역할을
대신한다. 그래서 예약을 못 지운다.

규범은 이미 다 있다 — `state-machines.md` §3 에 전이 21줄,
`protocol/src/attempt_state.rs` 에 상태 11개와 `is_terminal()`.
**저장소만 안 쓴다.**

★ 쿠버네티스도 같은 구조를 쓴다 — 배정 기록(`status.allocation`)과 지금
  쓰는 사람(`status.reservedFor`)이 따로고, 후자에서 빠지는 조건이
  "그 작업이 끝났을 때" 다. 그 조건을 말할 수 있으려면 작업 쪽에 종료
  상태가 있어야 한다.
