## 왜 지금 이 조각인가

지금 Coordinator/Agent 는 Grant/ACK 뒤 같은 TCP 연결에서
`RenewLeaseRequest`/`RenewLeaseResult` **1회 왕복만** 처리하고
`run()` 이 끝난다. 여러 번 반복 갱신은 두 계획 문서가 공통으로
다음 후보로 남겼다.

## ★ 핵심 발견 — nonce 재사용으로 두 번째 갱신이 반드시 거부된다

설계 실측에서 가장 중요한 결과다. **지금 구조에 반복문만 감싸면
두 번째 왕복이 100% 실패한다.**

```text
Agent 의 RenewLeaseRequest.nonce =
  derive_nonce("lease-renew", &held_lease.lease_id)
  (crates/agent/src/lib.rs:197-203, :397-402)

lease_id 는 정상 갱신 중 절대 바뀌지 않는다
  (Coordinator 가 항상 config.lease_id 그대로 발급:
   crates/coordinator/src/lib.rs:313-316. Agent 도 lease_id 가
   바뀌면 거부: crates/agent/src/lib.rs:270-272)

-> 매 회차의 요청 nonce 가 전부 동일하다
-> InMemoryReplayGuard 의 키는 (signer_id, domain, nonce)
   (crates/crypto/src/replay.rs:294-300)
-> 두 번째 RenewLeaseRequest 는 read_frame() 내부 검증에서
   Duplicate 로 거부된다(추측이 아니라 코드 경로상 확정,
   crates/crypto/src/framed_ingress.rs:268-284)

RenewLeaseResult 도 같은 문제 — request_nonce 를 그대로 echo 하므로
  (crates/coordinator/src/lib.rs:262-264, :296-300, :339-347)
  요청 nonce 를 안 바꾸면 결과 nonce 도 회차마다 같아 Agent 의
  결과 replay 검사에서도 Duplicate 가 된다.
```

→ **이 조각의 In 범위에 회차별 nonce 분리를 포함한다.**

### nonce 설계

```text
renew_nonce =
    BLAKE3-256(
        "lease-renew" || 0x00 ||
        lease_id       || 0x00 ||
        round_u64_be
    )[0..16]
```

- `round` 는 0(또는 1)부터 시작하되 양 끝(Coordinator/Agent)이 동일하게
  정의한다.
- `issued_at_unix_ms` 는 시간 검증·서명용으로만 쓴다 — nonce 유일성은
  시계에 의존하지 않는다.
- 기존 `derive_nonce(tag, id)` 와 별도로 `derive_renew_nonce(lease_id,
  round)` 를 새로 둔다(기존 함수를 건드리지 않는다 — 다른 호출부
  (grant-ack 등)에 영향 없음).
- `RenewLeaseResult` 에 새 필드를 추가하지 않는다 — 기존
  `request_nonce` echo 가 회차 식별자로 충분하다(서명 대상 메시지
  변경 불필요).

## `DurableFenceWatermark` 재사용성

`DurableFenceWatermark` 는 인스턴스에 값을 캐싱하지 않는다 —
`check_and_advance()` 호출마다 새 `BEGIN IMMEDIATE` 트랜잭션을 연다
(`crates/runtime-policy/src/durable_lease_scope.rs:32-34, :119-163`).
같은 인스턴스를 여러 번 연속 호출해도 문제없다 — 반복 갱신에 추가
변경이 필요 없다. 같은 `job_id` 를 resource key 로 계속 재사용한다.

```text
같은 epoch  -> 통과
낮은 epoch  -> watermark 가 Stale 거부
높은 epoch  -> 기존 명시적 정책 검사에서 거부(변경 없음)
```

## 범위

### In

- 기존 Grant/ACK 뒤 같은 TCP 연결 유지
- 고정된 `N` 회 `RenewLeaseRequest`/`RenewLeaseResult` 왕복
- 매 회차 독립적인 request·result 서명·검증
- 회차별 nonce 생성(`derive_renew_nonce`) 및 result `request_nonce`
  echo 대조
- 매 회차 nested Lease 독립 검증
- 같은 `job_id` 에 대한 epoch 단조성 확인(매 회차)
- same epoch 재사용 허용 · 낮은 epoch 거부(기존 계약 재사용)
- 로컬 127.0.0.1, 결정적 seed, 기존 OS 프로세스 selftest 구조 재사용

### Out (명시하지 않으면 범위가 샌다)

- 갱신 주기 타이머 · 자동 retry/backoff · 별도 재접속(failover)
- `max_total_duration_seconds` 정책 집행
- 실제 Coordinator Lease 재발급 정책(회차별로 다른 epoch 를 언제
  내려보낼지 등)
- 모든 `RenewOutcome` 의 운영 의미 정의 · Lease revoke
- 다중 Agent · scheduler · HA · TLS
- epoch **상승** 정책의 허용 또는 운영 의미(기존 명시적 거부 유지)
- Coordinator 의 영속 Lease 저장소(별도 계획 — `p106` 진행 중)

## selftest 시나리오 설계

기존 `run_handshake()` 는 Coordinator/Agent 를 별도 OS 프로세스로
띄우고 1회 accept/connect 만 한다(`coordinator_agent_selftest.rs:92-96,
122-170`). 시나리오 19부터 이어 붙인다(기존 1~18 유지).

### 19) 같은 연결에서 3회 정상 갱신

```text
Coordinator: --fence-epoch 5 --renewed-fence-epoch 5 --do-renew true --renew-rounds 3
Agent:       --do-renew true --renew-rounds 3 --fence-db <temp>
```

검증: 양쪽 성공 · `RENEW_RESULT ... outcome=RENEWED` 정확히 3회 ·
최종 `RESULT ok=true` 1회 · round 0/1/2 의 request nonce 가 모두
다름 · 각 result nonce 가 해당 요청과 일치 · 같은 epoch 5 에 대해
watermark 검사 3회 통과.

★ 이 시나리오는 nonce 가 기존 방식 그대로면 round 2(또는 그 전)에서
즉시 실패한다 — **성공 자체가 nonce 충돌 해결의 증거**다.

### 20) 같은 연결에서 중간 회차 강등 — 선택적

Coordinator 가 test-only 로 회차별 epoch 배열(`[5, 5, 4]`)을 내려보내
1·2회차는 성공, 3회차에서 Agent 의 `check_and_advance()` 가 `Stale`
로 거부하는지 확인한다. **Coordinator 에 회차별 epoch 배열을
추가하는 것이 범위를 키운다고 판단되면 생략 가능** — 기존
runtime-policy 단위 테스트(same/lower epoch)와 시나리오 19 만으로도
최소 조각은 완결된다. 구현 단계에서 비용 대비 판단한다.
