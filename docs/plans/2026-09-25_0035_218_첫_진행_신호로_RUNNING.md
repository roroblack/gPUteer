# 218 닫기 — Job 은 ACK 가 아니라 **첫 진행 신호**에 RUNNING 이 된다

> **작성** 2026-09-25 00:35 · **성격** 설계 결정 + 실행 계획 · **짝** `docs/reports/debugs/2026-09-24_0349_재검수84_85_결함_10건과_재발급_철회.md`(218 한계로 되돌린 경위)

## 문제(218 · 256)

ACK 를 받는 순간 Job 을 `STAGING -> RUNNING` 으로 올린다(신뢰망 D). 그래서 ACK 뒤 수신 확인이 유실되거나(218) Agent 가 Lease 가 짧아 시작을
거부하면(256), **한 번도 안 돈** 작업이 RUNNING · 체크포인트 없음 상태가 돼 이어받기에서 FAILED 가 된다. "같은 노드 재발급" 으로 풀려다
두 번 실행 경로가 계속 나와 철회했다(재검수 84).

## 결정 — 계약 변경 없이, 규범 표를 따라

규범 Attempt 표: `STARTING -> RUNNING  PROCESS_STARTED  guard: 프로세스 기동 + 첫 progress 수신`. 실행 중 Agent 가 보내는 **첫 Lease 갱신**이
그 첫 progress 다. 그래서:

```text
ACK(검증 · 기록)       시도 CREATED -> STARTING.  Job 은 **STAGING 그대로**   (전: Job 도 RUNNING)
첫 갱신 성공           시도 STARTING -> RUNNING(PROCESS_STARTED) · Job STAGING -> RUNNING(STAGING_COMPLETE)
수신 확인 유실 · 시작 거부  갱신이 오지 않는다 -> Lease 만료 뒤 이어받기가 STAGING_NODE_LOST 로 **큐에 되돌린다**(한 번도 안 돌았으니 처음부터 돌아도 된다)
```

- Agent 는 실행 직후 **곧바로 한 번** 갱신한다(전에는 첫 갱신이 주기 뒤였다) — "시작했다" 를 빨리 알린다
- 풀 방식 Agent(보고 세션 + 수신 확인 요구)는 실행 중 갱신을 켜야만 시작한다 — 갱신 없이 오래 돌면 STAGING 으로 남아 Lease 만료 뒤
  "안 돈 작업" 으로 보여 다시 배치될 수 있다(두 번 실행). 그래서 설정 단계에서 막는다
- 두 번 실행 가능성(남는 것): 실행을 시작했는데 첫 갱신이 Lease 만료 + 유예보다 오래 도달하지 못하면 STAGING 으로 되돌려진다 — 이미 있는
  "살아 있는 옛 노드" 한계(PURE 전제, 런북 §6)와 같은 종류다. Lease TTL(120초)이 첫 갱신(즉시)보다 훨씬 길다
